# 無人值守模式（本專案版）

使用者叫用後，主控照路線一個工作單元接一個往下做，**直到使用者回來（送出新訊息）為止**，不限晚上。可逆的決定自己拍板並記帳，只有「停下條件」才停。使用者回來時交一份能直接照著測的回來報告。

通用流程在第 1～7 節；本專案專屬的指令、腳本與限制集中在第 8 節，流程裡寫「（專案）」的步驟照第 8 節做。

## 1. 開場：把授權範圍寫下來

在帳本（見第 2 節）開頭寫明，派出去的每個 worker／subagent prompt 也照抄：

- 可改：本 repo 的哪些 worktree／分支；可 ff 合併到 main 並 push（main 會自動部署 Demo）。
- **其他 repo 一律不動**：看到別的 repo（例如 plugin marketplace）該修，只寫進回來報告的「刻意沒做」，不 commit、不 push、不發版。
- 範圍：路線上的哪幾個工作單元、做到哪算哪。
- 電源（專案）：使用者離開前確認接電源、別蓋螢幕；人已經走了就記進報告，並預期長測試可能因睡眠逾時（第 6 節）。

## 2. 裁決帳本

帳本放 repo 外的 `.tmp/<YYYYMMDD>-<slug>/plan.md`，每件事一行，附時間：

- `使用者裁決：…`（原話或明確選項）和 `主控裁決（待使用者確認）：… — 理由 — 選錯的代價` 分開寫，絕不把自己的決定寫成使用者說的。
- 審查結果、閘門數字、commit 範圍、部署結果都記進來。context 被壓縮後以帳本與 `git log` 為準。

## 3. 一個工作單元的流程

0. **設計單元：先裁決、再送審。** 初稿一出來，把「代為決定的事」分兩類：
   - **使用者行為類：** 答案反過來，Demo 上的操作步驟、畫面、誰能做什麼會變（上下限、權限、狀態怎麼推進、刪除與取消規則、訊息揭露）。
   - **技術類：** 只有程式內部不同（存哪張表、格式版本、命名、檢查放在管線哪一步），由主控裁決記帳，不問。

   行為類照推薦做、記成主控裁決待確認，列進回來報告的「待決」；使用者回來第一件事用 AskUserQuestion 一次一題問，題目帶具體例子（例如「訂 100 出 102」），讓人不看設計也能答；推翻的先改設計再續審。
   理由：審查核對的是方向；方向翻盤要整段重審（s2e 因此多審 3 輪）。所以行為類一律標明待確認，不混在技術類裡讓人漏看。
1. 派實作（subagent 或 pane worker），prompt 自足並含第 1 節的授權範圍。
2. 審查：先試跨家族；湊不到就同家、用新 context，回報寫「湊不到別家，退回同家審查」。
3. 依審查裁決修正。會改變使用者看得到的行為的建議，採用也可以，但要記成主控裁決待確認。
4. 閘門（專案）：背景跑，等通知。全部 exit 0 才往下。
5. 外洩掃描（專案）：只看筆數，必須全部是 0。
6. 合併：`git merge-base --is-ancestor origin/main HEAD` 成立就 `git push origin HEAD:main`（fast-forward）；不成立先 rebase 到 origin/main 再重跑閘門。不用 merge commit、不 force push。
7. 部署（專案）：背景等，等通知。
8. Demo 實機（專案）：在四種版型檢查這次動到的頁面。
9. 更新帳本與回來報告，清掉這個單元的 worktree，**接著做下一個工作單元**。做完一個就停是錯的：授權是一路推到使用者回來。

長工作（閘門、部署、審查、worker）丟到背景時，先做或派出不衝突的待辦，沒有才等，不輪詢。

## 4. 資源規則

- 同一個 worktree 裡，有人在改檔時不跑閘門；要並行就讓另一方用另一個 worktree。
- 兩件工作共用資源（同一批檔案、schema 遷移、build 產物、瀏覽器、吃 CPU 的測試）就不並行；本專案的具體清單見第 8 節。
- worker 交回、讀完結果檔就關它的 pane，不留著待命。
- 不寫自動回答 worker 提問的程式；worker 卡在提問就記進報告。

## 5. 停下條件（只有這些）

- 不可逆或破壞性操作：force push、刪分支／資料、`reset --hard`。
- 要動授權範圍外的東西：其他 repo、使用者層設定、帳號、付費服務。
- 閘門或部署失敗，查不出原因，或修了兩次還是失敗。
- 設計沒涵蓋、而且會改格式或使用者行為的分岔；兩邊都可逆的話，照建議做並記帳，不停。

停下時把現況、證據、建議寫進回來報告的「待決」，然後去做路線上不依賴它的下一件事；沒有可做的才結束。

## 6. 異常判讀

- 測試大量逾時、執行時間是平常的好幾倍：先查是不是電腦睡了（專案）。是睡眠就照原樣重跑，不改測試。
- 部署失敗：看託管平台 log；是這次合併造成的就 `git revert` 該 commit 並 push，不 reset。

## 7. 回來報告

寫在帳本同一個資料夾的 `return-report.md`，使用者回來時交出，依序：

1. 一句話結論：哪些可以測、哪些還不行。
2. 可測項目：每項附 Demo 路徑、用哪個示範帳號、具體操作步驟與預期結果。
3. 驗證結果分開宣稱：本機閘門數字、外洩掃描、push 的 commit 範圍、部署、Demo 實機；沒跑到的標「未驗證」。
4. 主控裁決待確認：每條附理由與選錯代價。
5. 刻意沒做的事（含其他 repo 的發現）與已知問題。
6. 待決：用 AskUserQuestion 一次一題問。

## 8. 本專案細節

腳本都在本 skill 的 `scripts/`。

- **閘門**：`bash .claude/skills/unattended/scripts/gate.sh <worktree>`，用 run_in_background 跑。依序跑後端三個測試專案（不平行、不跑 sln）、前端 test／typecheck／build，失敗時印出測試名稱。背景指令不要在結尾加 `echo "exit=$?"`，那會讓背景工作永遠回 0；看輸出最後一行判斷。
- **外洩掃描**：`LEAK_DENYLIST=<repo 外的清單檔> bash .claude/skills/unattended/scripts/leak-scan.sh`，三項筆數都要 0。清單檔不進 repo，掃描只印筆數不印字串。
- **部署**：`bash .claude/skills/unattended/scripts/wait-deploy.sh <sha>`。Render 只在 `poc/` 有變更時自動部署；只改文件或 `.claude/` 的 push 不會部署，不必等。
- **Demo 實機**：**只用登入頁的「Demo 帳號（點一下直接登入）」按鈕**，絕不在任何欄位輸入帳號密碼。登入後整頁重新載入再看畫面，不在同一段腳本裡 pushState 換頁（會讀到舊 schema）。用 `scripts/rwd-check.js` 檢查 390／820／1366／1920 四種寬度：`overflow` 必須是 false；`innerOverflow` 列出表格等容器自己的橫捲，逐項判斷是不是刻意的（寬報表可以，一般列表在手機不行）；做完清掉 emulate、導回 about:blank。
- **不並行的工作**：會加 EF migration 的兩件實作（model snapshot 會衝突）；動 `poc/backend/apps/*.app.json` 的工作；全套 WebAPI 測試與另一個吃 CPU 的測試同時跑（DemoData 測試會逾時）。
- **電源與睡眠**：開場 `pmset -g batt` 看是否接電源。逾時時用 `pmset -g log | grep -E "Entering Sleep|DarkWake to FullWake"` 查那段時間的睡眠原因（Clamshell、Idle、電池）。`caffeinate` 擋不住蓋螢幕。
