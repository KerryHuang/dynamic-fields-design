## 1. 目的

### 1.1 使用者要求（2026-11-10 原話整理）

- 情境：業務收到一個新的活動，在系統上建立活動，系統自動產生任務：
  - 任務一「規劃活動內容」，指派給業務一，2026/12/01 完成；
  - 任務二「展廠佈置」，指派給業務二，2027/01/31 完成；
  - 任務三「活動回饋」，指派給業務三，2027/02/15 完成。
- 每個任務下都有任務記錄，像留言板，可以 @人。
- 任務可以自己建立、可以由其他人指派、可以由系統設定的規則產生。
- 「建立」只是一個情境，規則要能設定成動態的（觸發時機可設定）。

### 1.2 市場做法（主控整理，依對主流產品的了解，未另行上網查證）

| 產品 | 任務來源 | 掛在哪裡 | 留言 |
|---|---|---|---|
| Odoo | 手動；「活動計畫」一次產生多筆，到期日依觸發日偏移 | 任何記錄 | Chatter、@人、追蹤者 |
| Salesforce | 手動；Flow 依規則建立 | 任何記錄（相關對象） | Chatter、@提及 |
| Vtiger | 手動；Workflow「建立待辦」，相對到期日 | 客戶、商機等 | 留言、@提及 |
| Jira／Asana／ClickUp | 手動、範本、自動化規則 | 任務本身為主體 | 留言、@人、追蹤者 |

共通點：三種來源；規則做成「範本組」一次產生多筆；到期日用相對日期；負責人可取記錄上的人；任務掛在業務記錄下、另有「我的任務」；留言、@人、通知是平台能力。

## 2. 目標、不做、反目標

**目標**

1. 平台共用的任務：任何應用程式、任何模組的記錄都能掛任務；也能建不掛記錄的個人任務（使用者裁決：平台共用能力）。
2. 三種來源：自己建、指派給別人、任務規則產生。
3. 任務規則可設定觸發時機、條件、產生哪些任務（使用者裁決，§5）。
4. 任務下的留言串，可以 @人（使用者裁決，§4）。
5. 站內通知：鈴鐺、未讀數；只做系統內通知（使用者裁決，§6）。站內通知做成平台共用，之後簽核（`2026-11-10-approval-workflow-design.md` §12）直接沿用。
6. 「我的任務」頁。
7. Demo：CRM 加「行銷活動」模組與使用者情境的規則，補一位業務三（使用者裁決，§10）。

**不做（第一版）**

子任務、任務相依、優先度、重複任務、工時、看板與甘特圖；Email 與推播通知；留言編輯；指派給群組由人認領、規則指派給固定的人或建立者（使用者只選了「記錄上的人員欄位」，§5.3）；任務的自訂欄位。

**反目標（做了也算失敗）**

- 透過 @人 看到原本沒權限看的業務記錄（使用者裁決，§7）。
- 規則重複派工：同一筆記錄、同一條規則產生兩次。
- 規則同步蓋掉人手動調整過的到期日或負責人。
- 任務功能讓沒開任何應用程式的人看到業務資料。

## 3. 資料模型（核心資料表，不是動態模組）

任務是平台能力，放在核心資料表，不用動態模組實作（主控判斷：動態模組不能掛在「任何模組」底下，也不能有跨模組的權限規則）。

**`Task`**

| 欄位 | 說明 |
|---|---|
| `Id` | |
| `Title` | 必填，200 字以內 |
| `Description` | 選填，純文字 |
| `AssigneeUserId` | 選填；空的是「未指派」 |
| `DueDate` | 選填，日期（不含時間） |
| `Status` | `Todo`（待辦）、`InProgress`（進行中）、`Done`（完成）、`Cancelled`（取消） |
| `ModuleId`、`RecordId` | 選填，兩者同時有或同時空；空的是個人任務 |
| `RecordTitleSnapshot` | 建立時與記錄標題變動時更新，記錄刪除後給原本看得到記錄的人顯示（§7） |
| `RuleId`、`RuleTaskCode` | 規則產生的才有 |
| `DueOverridden`、`AssigneeOverridden` | 人手動改過就設為 true，規則同步不再動它（§5.5） |
| `CreatedBy`、`CreatedTime`、`ModifiedBy`、`ModifiedTime`、`CompletedTime` | |
| `LastDueSoonNotified`、`LastOverdueNotified` | 通知去重（§6.2） |

**`TaskComment`**：`Id`、`TaskId`、`AuthorUserId`（規則或系統寫的為空）、`Body`、`CreatedTime`、`Withdrawn`（作者撤回後顯示「已撤回」，不顯示原文）。留言可帶附件，存在 `TaskCommentAttachment`（`Id`、`CommentId`、`FileName`、`ContentType`、`Size`、`StorageKey`、`CreatedTime`），檔案沿用既有附件儲存（`IAttachmentStore`）。系統事件（建立、改負責人、改到期日、改狀態）也寫成留言串裡的系統記錄，讓任務歷程與留言在同一條時間軸（主控判斷）。

**`TaskParticipant`**：`TaskId`、`UserId`、`Reason`（`Creator`、`Assignee`、`Mentioned`）。決定誰能看任務（§7）與誰收新留言通知（§6.1）。改負責人時舊負責人保留為參與者（主控判斷：他可能還在留言串裡）。

**`TaskRule`**（含 `AppId`）、**`TaskRuleTask`**：§5。**`TaskRuleRun`**：`RuleId`、`RecordId`、`Occurrence`（第幾次觸發，從 1 起），三者唯一；寫入它就代表「這筆記錄第 N 次觸發這條規則」。`Task` 另有 `RuleOccurrence` 與 `(RuleId, RecordId, RuleOccurrence, RuleTaskCode)` 唯一索引（§5.2），另加 `CancelledByRule` 旗標，區分規則自動取消與人手動取消。

**`Notification`**（平台共用，簽核沿用）：`Id`、`UserId`、`Kind`、`TitleSnapshot`、`Link`（站內路徑）、`ReadTime`、`CreatedTime`。只帶標題快照與連結，不帶欄位值（同簽核 §12）。

需要的 migration 一個（`TaskManagement`），只走 EF migration。

## 4. 任務與留言

### 4.1 建立

- 在記錄詳細頁的「任務」區塊新增：預設負責人是自己，可改成任何啟用中的使用者。
- 在「我的任務」頁新增：不掛記錄，負責人預設自己。
- 指派給別人：新負責人收到「指派給你」通知。

### 4.2 留言與 @人

- 留言是純文字；輸入 `@` 跳出使用者清單（全部啟用中的使用者，依名稱篩選）。選定後在內文存成 `@{userId}` 標記，顯示時換成名稱；停用的使用者顯示名稱加「（已停用）」。
- 被 @ 的人加入參與者（`Mentioned`），收到「有人在任務中提到你」通知。
- 作者可撤回自己的留言；不能編輯（主控判斷：避免改寫已被人讀過的內容）。系統管理員也可撤回任何留言。
- **留言附件**（使用者裁決 2026-11-10：設計案來回修改時，客戶標註過的圖、修改說明要跟留言放在一起）：一則留言最多 5 個檔案（主控判斷）；檔名、副檔名白名單、單檔大小上限沿用附件欄位的規則（`AttachmentRules`）與環境設定（停用上傳的環境同樣不能附檔）。可以只有附件、沒有文字。撤回留言時附件一併不再顯示、不能下載；任務被刪除（模組永久清除）時檔案一起刪除。

### 4.3 狀態

- 任何狀態之間都能直接切換，不做狀態機（主控判斷）。切到 `Done` 記 `CompletedTime`，切離 `Done` 清掉。
- 不能刪除規則產生的任務，只能取消（主控判斷：刪了規則不會補，`TaskRuleRun` 已存在）；自己建的任務建立者與系統管理員可以刪除。

## 5. 任務規則

### 5.1 一條規則的內容

規則掛在一個模組上，由有設計器權限（全站一個 `DYN00000`，共用主檔另需系統管理員）的人在設計器「任務規則」分頁設定（主控判斷：沿用連動事件的權限）。規則記錄它屬於哪個應用程式（`TaskRule.AppId`，手動建的為空），應用程式關閉時它的規則一起停用，包括掛在共用主檔上的（主控判斷，builder check 5）。內容：

1. **觸發方式**（使用者裁決：四種都支援）：
   - `onCreate`：記錄建立時。
   - `onUpdateMatch`：記錄從「不符合條件」變成「符合條件」時；建立時就符合也算一次（主控判斷，builder check 2：避免規則上線後，舊記錄一被改到無關欄位就大量補派工）。
   - `onFieldBecomes`：某個欄位從別的值變成指定值的那一刻；建立時就是指定值也算一次。
   - `manual`：記錄詳細頁出現「套用任務範本」按鈕，由人決定時機。
2. **觸發次數**（使用者裁決 2026-11-10）：`once`（預設，每筆記錄只觸發一次）或 `everyTime`（每次符合都觸發，見 §5.2）。`onCreate` 只有一次，不能選 `everyTime`。
3. **條件**（選填）：整條規則的篩選，沿用連動事件的條件格式與條件設定器（例如「類型 = 展覽」）。`onUpdateMatch` 的條件必填。
4. **產生的任務**（一條規則一到多筆）：
   - `code`（規則內唯一）、標題、說明；
   - 負責人：記錄上的一個 `User` 型別欄位（使用者裁決：只支援人員欄位）；
   - 到期日：一個 `Date` 或 `DateTime` 欄位加偏移天數（正數往後、負數往前，例如 −30），或不設（使用者裁決：依記錄日期推算，建立後可改）；
   - 個別任務的條件（選填）：例如只有展覽才產生「展場佈置」。

### 5.2 只產生一次，或每次符合都產生

**`once`（預設）**：同一筆記錄、同一條規則只觸發一次，不論觸發方式（使用者同意的提議）；觸發後，規則裡的**每個任務**也各只產生一次。以 `TaskRuleRun(RuleId, RecordId, Occurrence = 1)` 記規則已觸發，以 `Task(RuleId, RecordId, RuleOccurrence, RuleTaskCode)` 唯一索引保證同一任務不重複，併發下也不會重複。

**`everyTime`**（使用者裁決 2026-11-10：設計案來回修改，每次回到「設計中」都要再派給設計人員）：
- 每次由不符合變成符合（`onUpdateMatch`、`onFieldBecomes` 的邊緣），就是新的一次觸發，`Occurrence` 加 1，產生一批新任務；`manual` 每按一次就是一次，按鈕不變灰。
- **這條規則在這筆記錄上還有未完成（`Todo`、`InProgress`）的任務時，這次不觸發**，留一筆系統記錄在最新那批任務的留言串「條件再次符合，但上一輪任務尚未完成」（主控判斷：避免上一輪沒做完又疊一輪）。
- 個別任務條件的持續判斷、§5.5 的同步，只作用在最新一次觸發的任務；舊批次的任務不再自動變動（主控判斷）。

**個別任務的條件在觸發之後持續判斷**（使用者裁決 2026-11-10）：規則已觸發的記錄每次存檔，重新判斷每個任務的條件：
- 原本不符合、還沒產生的，變成符合就補產生（例如研討會改成展覽，補「展場佈置」）。
- 已產生、狀態是 `Todo` 或 `InProgress` 的，變成不符合就自動取消，留系統記錄「條件不再符合」；之後又變回符合時，把這個任務恢復成 `Todo`，不另建一筆（主控判斷）。
- `Done` 的不動。人手動取消的，不自動恢復（主控判斷）。`onUpdateMatch` 只在由不符合變成符合時觸發；`manual` 套用後按鈕變灰，顯示「已套用」（`everyTime` 例外，§5.2 下段）。

規則產生的任務，建立者記為系統，通知觸發那次操作的人以外的負責人（自己觸發、自己是負責人時不通知自己，主控判斷）。

### 5.3 欄位為空時

- 負責人欄位是空的：任務照樣產生，負責人為空（未指派），在記錄的任務區塊標示「未指派」（主控判斷）。
- 到期日的基準欄位是空的：任務沒有到期日。
- 之後那個欄位補上值，依 §5.5 同步。

### 5.4 執行時機與交易

規則在記錄寫入的同一個交易內執行，跟連動事件同一個位置、在事件之後（主控判斷：事件可能改到規則要看的欄位）。觸發的判斷（變更前後的值）與事件共用同一份寫入日誌。規則本身產生的任務不會再觸發規則（任務不是動態記錄）。匯入、轉換、事件寫入的記錄也會觸發規則，跟使用者在畫面上存檔一樣（主控判斷）。

### 5.5 來源記錄變動時同步（使用者裁決：未完成的跟著變，手動改過的不動）

記錄的到期基準欄位或負責人欄位變了，這筆記錄上由規則產生、狀態是 `Todo` 或 `InProgress` 的任務：

- 到期日沒被人改過（`DueOverridden = false`）的，重算到期日；
- 負責人沒被人改過（`AssigneeOverridden = false`）的，換成新的負責人，新負責人收到「指派給你」通知，舊負責人保留為參與者。

`Done`、`Cancelled` 的任務不動。人改過到期日或負責人之後，那一項不再跟著記錄變。重算用規則**現在**的定義（偏移天數、負責人欄位）；規則停用或刪除後不再同步（主控判斷，builder check 3）。同步看寫入日誌，靜默寫入（彙總重算）也要算進來，不沿用事件階段跳過靜默寫入的過濾（目前基準限 `Date`／`DateTime`，碰不到，先記下）。

### 5.6 規則本身改了、停用、刪了

不回頭改已經產生的任務（主控判斷）。規則可以停用；刪除規則時已產生的任務保留，`RuleId` 留著但標示「規則已刪除」。

### 5.7 記錄刪除

記錄軟刪除時，它的未完成任務改為 `Cancelled`，留系統記錄「相關記錄已刪除」（主控判斷；系統沒有記錄還原）。模組被永久清除（`ModuleRemover`）時，掛在它記錄上的任務、留言、相關通知一起刪除；安全刪除的盤點不把任務列為阻擋（主控判斷，builder check 4）。

記錄所在的模組是 `Closed`（應用程式關閉）時，掛在上面的任務只能看，不能改、不能留言，跟記錄一樣凍結（主控判斷）。

### 5.8 套件格式

應用程式套件加 `taskRules[]`（格式版本 7；簽核用 8，訂單、工令、出貨設計原定的 7、8 順延為 9、10，由主控同步修改該文件，主控判斷，builder check 7）。規則可以掛在套件自己的模組，或它 `requires.masters` 宣告的共用主檔模組，內容同 §5.1，欄位用模組內代號引用；匯出、匯入、開啟、關閉、刪除應用程式時跟著模組走。應用程式關閉時它的規則不再觸發，已產生的任務保留（主控判斷）。

## 6. 站內通知

### 6.1 通知種類

| 種類 | 收件人 |
|---|---|
| 指派給你 | 新負責人（自己指派給自己不通知） |
| 有人在任務中提到你 | 被 @ 的人（自己 @ 自己不通知） |
| 你的任務有新留言 | 負責人與建立者，不含留言者本人；已因同一則留言收到「提到你」的不重複通知（主控判斷） |
| 任務明天到期 | 負責人；任務 `Todo` 或 `InProgress` |
| 任務已逾期 | 負責人；同上 |
| 任務被完成或取消 | 建立者，不是本人操作時（主控判斷） |

### 6.2 到期與逾期提醒

核心沒有背景服務，沿用簽核 §12 的做法：讀通知清單（含未讀數）時，對這位使用者負責、未完成、到期日是明天或已過的任務，補寫提醒並記在 `LastDueSoonNotified`／`LastOverdueNotified`，同一任務同一種提醒最多一天一則。只在登入時看得到，第一版不需要準時推送。

### 6.3 畫面

右上角鈴鐺加未讀數；點開列出最新通知，點一則前往任務並標為已讀；「全部標為已讀」。通知保留 90 天（主控判斷）。

## 7. 權限

- **看得到任務**：看得到那筆記錄的人（記錄讀取權限，含資料範圍），加上這個任務的參與者（建立者、負責人、被 @ 的人）。個人任務只有參與者看得到。系統管理員看得到全部。
- **參與者但看不到記錄時**（使用者裁決：被 @ 的人只看得到這個任務）：看得到任務的標題、說明、留言，可以留言與 @人；相關記錄只顯示「相關記錄（無權限查看）」，不顯示記錄標題與任何欄位值（主控判斷，builder check 6：符合反目標第 4 條）。`RecordTitleSnapshot` 只給看得到記錄的人在記錄刪除後顯示用。
- **規則抄進任務的值**：負責人、到期日是任務自己的屬性，看得到任務的人就看得到，不依來源欄位的欄位權限遮蔽（主控判斷：任務要能協作；風險是能從到期日回推被隱藏的日期欄位，記為已知限制）。
- **在記錄上建任務、留言**：看得到那筆記錄就可以（主控判斷）。
- **改任務**（標題、說明、負責人、到期日、狀態）：建立者、負責人、對那筆記錄有修改權限的人、系統管理員（主控判斷）。
- **留言附件下載**：看得到這個任務的人就能下載，不看記錄權限（與留言內文一致，被 @ 的人也能下載）；看不到任務回 404。
- **@ 的候選人**：全部啟用中的使用者。因為被 @ 的人只拿到任務本身，不會拿到記錄權限。
- **不能透過任務繞道**：任務 API 不回傳記錄的欄位值；規則產生任務時用的負責人、日期只寫進任務本身。

## 12. 測試重點

- 規則：四種觸發各自只產生一次（含併發兩個請求同時符合）；`everyTime`：設計中 → 客戶確認中 → 設計中產生第二批、上一輪未完成時不觸發、`onCreate` 不能選、舊批次不受同步影響；個別任務條件；欄位為空；同步只動未完成且沒手動改過的；匯入、轉換、事件寫入也觸發；應用程式關閉後不觸發。
- 權限：被 @ 的人看得到任務、看不到記錄與欄位值；資料範圍外的記錄的任務看不到；改任務的權限四種身分。
- 留言附件：超過 5 個、不允許的副檔名、超過大小上限各回 400；被 @ 的人能下載、看不到任務的人 404；撤回後下載 404；停用上傳的環境不能附檔。
- 通知：每一種的收件人與「不通知自己」；提醒一天最多一則；未讀數。
- 套件：`taskRules` 匯出入往返、開啟關閉刪除應用程式。
- 畫面：四種寬度、四個語系；@ 選人。

## 14. 主控判斷彙整（可推翻）

1. 任務放核心資料表，不用動態模組（§3）。
2. 任務歷程寫成留言串裡的系統記錄（§3）。
3. 改負責人時舊負責人保留為參與者（§3）。
4. 留言可撤回、不能編輯（§4.2）。
5. 狀態不做狀態機，任意切換（§4.3）。
6. 規則產生的任務不能刪、只能取消（§4.3）。
7. 任務規則用設計器權限設定（§5.1）。
8. 負責人欄位空時任務照樣產生、標示未指派（§5.3）。
9. 規則在事件之後、同一交易內執行；匯入、轉換、事件寫入也觸發（§5.4）。
10. 規則改動不回頭改已產生的任務（§5.6）。
11. 記錄刪除時未完成任務改為取消；模組永久清除時任務一起刪；關閉時任務凍結（§5.7）。
12. 應用程式關閉後規則不觸發、任務保留（§5.8）。
13. 新留言通知負責人與建立者；完成或取消通知建立者（§6.1）。
14. 通知保留 90 天（§6.3）。
15. 看得到記錄就能在上面建任務、留言；改任務四種身分（§7）。
16. 「我的任務」不列簽核待辦，簽核另有頁面（§11）。
17. 任務規則不做成事件效果（§11）。
17a. 條件再度符合時恢復原任務、不另建；人手動取消的不自動恢復（§5.2）。
18. `onUpdateMatch`／`onFieldBecomes` 以「由不符合變成符合」觸發，建立時符合也算（§5.1）。
19. 同步用規則現在的定義，規則停用或刪除後不同步（§5.5）。
20. 規則記錄所屬應用程式，關閉時停用（§5.1）。
21. 看不到記錄的參與者不顯示記錄標題（§7）。
22. 規則抄進任務的負責人、到期日不依欄位權限遮蔽（§7）。
23. 套件格式用 7，s2e 順延（§5.8）。
24. 留言附件一則最多 5 個，規則沿用附件欄位；下載權限跟任務走（§4.2、§7）。
25. `everyTime` 規則在上一輪還有未完成任務時不觸發；持續判斷與同步只作用在最新一批（§5.2）。

## 16. 實作期間的裁決（2026-11-10）

實作計畫與程式碼對不上、或審查發現缺口時，主控依設計原則裁決；只列會影響使用者行為、格式或 Demo 的項目。實作中每段上線時補充。

1. 規則任務的標題與說明是四語系文字，產生任務時依觸發者的語系解析成單一字串存進任務。
2. 規則引用的欄位在刪除應用程式時被清除，規則自動停用；「引用的欄位已刪除」是讀取時即時算出的警告。刪除模組時，掛在上面的規則一併移除。
3. CRM「活動」改名「互動紀錄」、拿掉「已完成」欄位：已開啟過 CRM 的舊資料庫不自動改名、不提供升級腳本，手冊說明由管理員自行調整或重建。
4. 刪除單筆任務時，附件資料一併刪除（實體檔由附件清掃處理），該任務產生的站內通知也一併刪除；通知的來源任務已不存在時，通知清單照常顯示、不出錯。
5. 自己 @ 自己、自己觸發的事件，不通知自己。
6. 應用程式關閉（凍結）期間，掛在上面的任務不發逾期與即將到期提醒；應用程式重新開啟後恢復。
7. 留言附件：錯誤訊息鍵為 `files`，文字錯誤鍵為 `body`；內容超過上限回 413；已撤回的留言不回傳內容、不列附件。Demo 站停用上傳時，附件鈕停用並說明原因。
8. 在清單上取消勾選已完成的任務，一律改回「待辦」，不記住完成前是哪個狀態。
9. 首頁「今天到期」的數字連到任務頁的「今天」篩選（到期日等於今天的未完成任務），點進去的範圍和卡片一致（2026-11-11 補上「今天」篩選）。
10. 通知鈴點一則通知：先標為已讀，再前往通知的站內連結；連結不是站內路徑時只標已讀。清單只列最新 20 則。
