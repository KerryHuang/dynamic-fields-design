# 任務看板、報表、子任務與甘特圖 設計文件

> 2026-11-13｜平台共用能力｜前置：[任務管理](2026-11-10-task-management-design.md)、[政策設定](2026-11-11-policy-settings-design.md)、[報表與儀表板](2026-11-05-reports-design.md)、[報表資料庫端聚合](2026-11-10-report-db-aggregation-design.md)、[PostgreSQL provider](2026-11-12-postgres-provider-design.md)、[簽核流程](2026-11-10-approval-workflow-design.md)（§11 組織骨架）
> 狀態：定稿候選，行為類待確認已由使用者裁決照建議（2026-11-13）。這次只寫設計，不改程式。
> 標記：「（使用者決定）」是使用者 2026-11-13 已拍板的；「（U#，使用者裁決照建議）」原為主控代為決定的行為類事項，使用者 2026-11-13 指示一律照建議；「（主控 T#）」是技術類決定，主控可推翻。全部彙整在 §17。

## 1. 意圖與原因

任務上線後只有兩種看法：記錄頁的「任務」區塊、「我的任務」清單。三個缺口：

- **一眼看不出進度**：清單只能一次看一種篩選，看不出「誰手上卡了多少、哪些今天要交」。看板依狀態、負責人或到期區間分欄，拖一下就改值，是任務工具最常見的工作畫面。
- **主管看不到部屬的工作**：現在只有參與者與看得到記錄的人看得到任務（任務設計 §7）。部門主管要分派、重派部屬的任務，只能請部屬 @ 他。組織骨架（簽核設計 §11）已在核心，可以直接用。
- **沒有統計**：任務不是動態模組，報表設計器選不到它。主管問「誰負載最重」「準時率多少」只能人工數。

子任務與甘特圖是使用者 2026-11-13 追加的範圍：一件工作拆成幾步、依日期排開，是專案型任務的基本需求；任務相依（前置任務）未被選，不做。

## 2. 目標、非目標、反目標

**目標**

1. 任務看板：依狀態、負責人、到期區間分欄，拖卡片換欄即改值；可存自訂看板並分享（使用者決定，§5、§6）。
2. 主管範圍：部門主管可看並重派部屬的任務（使用者決定，§4）。
3. 任務成為報表設計器的資料來源，可下鑽、匯出、放儀表板（使用者決定，§7）。
4. 內建任務統計報表（使用者決定，§8）。
5. 子任務：一層，父任務顯示完成進度（使用者決定，§10）。
6. 甘特圖：任務加開始日，拖拉調整日期，可依父子分組（使用者決定，§11）。
7. 空系統（沒開任何應用程式、沒有部門）也能用：個人任務照樣有看板、報表、子任務、甘特圖。

**非目標**

- 依所屬模組分欄（使用者決定不做）。
- 任務相依、關鍵路徑、資源負載圖（使用者未選）。
- 動態模組記錄的看板（路線階段 5「專案、商機等依狀態分欄」，是另一件事，見 §16）。
- 欄內手動排序（U6，使用者裁決照建議）、在製品上限（WIP limit，💡）。
- 規則產生子任務、規則設定開始日（💡，§10.6、§11.1）。
- 應用程式套件帶任務報表或看板（💡，§8.3）。

**反目標（做了也算失敗）**

- 透過看板、報表、下鑽、匯出、儀表板、分享、子任務、甘特圖，看到無權限的業務記錄內容（沿用任務設計反目標第 1 條與 §7 原則）。
- 主管範圍讓主管看到部屬「掛在無權限記錄上」的記錄標題或欄位值。
- 拖拉改值繞過既有的改任務權限，或繞過規則同步的 `DueOverridden`／`AssigneeOverridden` 語意。
- 報表數字與看板、清單對同一批任務的計數不一致卻沒有說明（基準日差異見 §7.6）。
- 分享看板等於分享資料：被分享者看到的任務比他自己本來看得到的多。

## 3. 限制與既有事實

- 任務放在核心資料表（`Task`），不是動態模組（任務設計 §3）。報表引擎目前只吃動態模組：定義以 `MainModuleKey` 加欄位 Id（`long`）引用，記憶體路徑讀 `Dynamic_Record`，SQL 路徑讀 `Dynamic_RecordIndex`（`ReportRunner.cs`、`ReportQueryBuilder.cs`）。
- 報表分享**只能分享給群組**（`ReportShare(ReportId, GroupId)`、`SetReportSharesHandler`）。使用者決定 4 說「分享給人或部門，沿用報表的分享方式」，兩者不一致，處理見 §6.3 與 §18。
- 組織骨架：一人一個部門（`Dynamic_UserDepartment` 以 `UserId` 為主鍵），部門可有上級，主管可空缺、可不屬於該部門；一個人可以是多個部門的主管（`Department.ManagerUserId` 不唯一）。第一版不做兼任多部門（簽核設計 §11.1）。
- 「本週」的起始日已是政策 A7（出廠星期一）；任務清單的「本週到期」用 `TaskHandlers.WeekEnd(today, weekStart)` 算本週最後一天。「逾期＝到期日早於今天」是定義，維持寫死（政策設計 §4）。
- `TaskAccess.EvaluateManyAsync` 逐筆查記錄 stub（迴圈內發查詢）。看板一次載入上百張卡片，不能沿用這個寫法（§4.4）。
- 報表 SQL 路徑在 PostgreSQL 上要到 pg1 才有；pg0 之後 PostgreSQL 一律走記憶體路徑（PostgreSQL 設計 §5.9）。新查詢都要在兩種資料庫跑過、migration 兩份（PostgreSQL 設計 §1）。
- 量值種類只有 `sum`、`avg`、`min`、`max`、`countMain`、`countChild`、`ratio`；沒有中位數，也沒有「符合條件的筆數」（只有 `ratio` 帶條件）。內建報表需要這兩種（§7.4）。
- 報表設計 §3 目標 4「全新安裝沒有任何報表」與內建報表衝突，見 §8.3 與 §18。

## 4. 主管範圍與任務可見性

### 4.1 誰是部屬（使用者決定 3 的細則）

- 主管 M 的**管轄部門**：M 擔任主管、且啟用中的部門，加上這些部門往下所有層的子部門（遞迴，U1，使用者裁決照建議）。
- 遞迴經過停用的子部門時照樣往下走（停用部門的成員仍屬於它，簽核設計 §11.2）；停用部門本身的主管不因該部門取得範圍（與 `ManagerChain` 把停用部門視同空缺一致，主控 T1）。
- 一人當多個部門的主管：管轄部門取聯集（U1，使用者裁決照建議）。
- **部屬**：所屬部門在管轄部門內的使用者，不含 M 本人。沒有部門的使用者不是任何人的部屬，只有參與者與系統管理員看得到他的個人任務（U2，使用者裁決照建議）。
- 停用的主管不登入，不必處理；停用的部屬照樣算部屬（他留下的任務要能被重派，主控 T2）。
- 異動立即生效：調部門、換主管後，下一個請求就用新組織（`OrgSnapshot` 單次請求載入，不快取）。

### 4.2 部屬的任務

**部屬的任務**＝負責人是部屬的任務，加上「未指派、建立者是部屬」的任務（U3，使用者裁決照建議）。部屬只是建立者或被 @ 的任務不算：那是別人的工作。

主管對部屬的任務可以：

- **看**：標題、說明、狀態、負責人、到期日、留言、子任務（§10）。
- **重派**：改負責人，對象是任何啟用中的使用者（同既有指派），新負責人照常收到「指派給你」（U4，使用者裁決照建議）。
- **留言與 @人**。

主管不因此取得改標題、說明、狀態、到期日的權限；那仍照任務設計 §7 的四種身分（U4，使用者裁決照建議）。主管不因看過或重派而成為參與者（主控 T3：避免主管收到所有部屬任務的留言通知）。

**入口**：任務清單加「部屬的任務」分頁，只在 A32 開啟且這位使用者有部屬時出現；列的是本節定義的任務，篩選（未完成、已逾期、今天、本週到期、全部）與其他分頁相同。這個分頁與看板的「部屬的任務」範圍共用同一個查詢（§4.4），kb1 就上線，不必等看板（U15，使用者裁決照建議 2026-11-13）。

**重派給非部屬**：主管把任務重派給範圍外的人之後，這個任務不再是部屬的任務，主管就看不到它（除非他另有參與者或記錄權限）。這是接受的結果，維持 T3，不讓主管因重派成為參與者（U16，使用者裁決照建議 2026-11-13）。畫面處理見 §5.4。

### 4.3 掛在無權限記錄上的任務

主管看得到任務、但對那筆記錄沒有 Read（或記錄在資料範圍外）時，照任務設計 §7「參與者但看不到記錄」處理：相關記錄顯示「相關記錄（無權限查看）」，不給模組代號、記錄 Id、記錄標題、`RecordTitleSnapshot`。報表、看板卡片、甘特圖、下鑽、匯出一律用同一個判斷（§7.3）。

### 4.4 「看得到任務」的新定義與查詢

看得到任務（取代任務設計 §7 第 1 點，加上第 4 項）：

1. 系統管理員：全部。
2. 參與者（建立者、負責人、被 @ 的人）。
3. 看得到那筆記錄的人（模組 Read 加資料範圍；記錄已軟刪除也照 stub 的擁有者判斷，沿用現行）。
4. **部屬任務的主管**（§4.2），政策 A32 開啟時。
5. **子任務**：看得到父任務就看得到它的子任務（§10.3）。

實作（主控 T4）：

- Application 新增 `TaskVisibility`：在 C# 先算好「這位使用者的可見條件」：是否管理員、自己的 Id、部屬名單、每個可讀模組的資料範圍（`OwnerUserIds`，null 為全部）。模組權限只在 C# 判斷，不進 SQL。
- Persistence 把它轉成**一個** EF LINQ 條件：參與者 `EXISTS`、負責人 `IN` 部屬名單、`(ModuleId = m AND 記錄擁有者 IN 範圍)` 逐模組 `OR`。不寫 raw SQL，SQLite 與 PostgreSQL 同一份；不在迴圈內查記錄 stub。
- 記錄相關資訊（是否可看記錄、記錄標題）用一次批次查詢取得，取代 `EvaluateManyAsync` 逐筆查 stub；單筆的 `EvaluateAsync` 改呼叫同一個批次版本，行為不變。
- 部屬名單放進 `IN` 參數。SQLite 參數上限 32766、PostgreSQL 65535，一般組織遠低於此；超過 2000 人時改成暫存表或分批，列為已知限制（§15）。

### 4.5 政策

| # | 政策 | 出廠 | 範圍 |
|---|---|---|---|
| A32 | 部門主管可看與重派部屬的任務 | 開 | S |
| A33 | 主管範圍含下層部門 | 是 | S |

主管範圍是業務政策（有的公司不讓主管看部屬待辦），依「業務政策不寫死」做成開關；出廠值照使用者決定 3（U1，使用者裁決照建議 的遞迴也由 A33 管）。改了只影響之後的讀取，沒有既有資料要處理。

## 5. 看板

### 5.1 分欄依據（使用者決定 2）

| 分欄 | 欄 | 拖進欄的效果 |
|---|---|---|
| 狀態 | 待辦、進行中、完成、取消 | 改狀態 |
| 負責人 | 每位負責人一欄，加「未指派」 | 改負責人 |
| 到期區間 | 逾期、今天、本週、之後、無到期日 | 改到期日（§5.3） |

「今天」是營運時區的今天（`IBusinessTime.Today`，政策 A17）；「本週」是「今天之後、到本週最後一天」，本週最後一天依 A7 用既有的 `WeekEnd` 算；「之後」是本週最後一天以後。

清單的「本週到期」篩選維持現行，**含今天**（今天到本週最後一天）；所以清單的「本週到期」＝看板的「今天」＋「本週」兩欄，手冊照這個說法註明（U17，使用者裁決照建議 2026-11-13）。看板與清單共用同一個 `WeekEnd` 函式算本週最後一天，邊界不會各算一套（主控 T5）。

### 5.2 狀態欄拖拉

- 任意兩個狀態之間都能拖（任務設計 §4.3 不做狀態機）。拖到「完成」記 `CompletedTime`，拖離「完成」清掉，同清單勾選。
- **拖到「取消」要確認**：「取消這個任務？規則產生的任務取消後不會自動恢復」（U5，使用者裁決照建議）。人手動取消的任務 `CancelledByRule = false`，之後條件再次符合也不自動恢復（任務設計 §5.2），所以要讓人知道。
- 有子任務的父任務拖到「完成」或「取消」時，照 §10.4 的連動確認。

### 5.3 到期區間欄拖拉（U5，使用者裁決照建議）

| 拖到 | 到期日改成 |
|---|---|
| 逾期 | 不允許，欄位顯示禁止放置；要改成過去的日期就開任務詳細改 |
| 今天 | 今天 |
| 本週 | 本週最後一天（A7） |
| 之後 | 跳出日期選擇，預設下週最後一天，只能選本週最後一天之後；按取消就放回原欄 |
| 無到期日 | 清空到期日 |

- **今天就是本週最後一天時**，「本週」欄的區間是空的，拖進去會落在「今天」。這時「本週」欄顯示但不能放置，提示「今天已是本週最後一天」。
- 在同一欄內拖動不改值。
- 到期區間看板只列未完成（`Todo`、`InProgress`）的任務，狀態篩選固定、不能改（U5，使用者裁決照建議）：完成與取消的任務放在「逾期」欄沒有意義。
- 有開始日的任務（§11），新到期日早於開始日時，開始日一併改成新到期日，並在卡片上提示（U12，使用者裁決照建議）。

### 5.4 負責人欄拖拉

- 拖到某人欄＝指派給他；拖到「未指派」＝清空負責人。對象必須是啟用中的使用者；停用者的欄可以拖出，不能拖入。
- 欄的來源：看板設定裡明列的人（§5.7），加上目前篩選結果裡有任務的人（自動附加在後面，可關閉）。範圍是「部屬的任務」時，自動列出所有部屬，即使目前沒有任務，方便主管把任務拖給閒的人（主控 T6）。
- 舊負責人保留為參與者，新負責人收到「指派給你」，與既有指派相同。
- **移動後看不到了**：重派（或任何改值）之後，操作者已看不到這個任務時（最常見是主管重派給非部屬，§4.2），移動 API 回 `visible=false`，卡片從看板消失，畫面提示「已移出你的範圍」並附「復原」。復原＝把負責人改回原負責人，只在提示顯示期間可按（U16，使用者裁決照建議 2026-11-13；實作見主控 T24）。清單與任務詳細的重派也用同一個提示與復原。

### 5.5 規則任務與手動覆寫

拖拉就是「人手動改」，與在任務詳細裡改完全相同：

- 改負責人（含清空）設 `AssigneeOverridden = true`；改到期日（含清空）設 `DueOverridden = true`。之後來源記錄變動，規則同步不再動這一項（任務設計 §5.5）。
- 清空到期日也算覆寫，記錄上的日期之後補上，規則也不會再填回來。拖到「無到期日」時，規則任務的卡片多一行提示「清空後不再隨記錄日期同步」（U5，使用者裁決照建議）。
- 改狀態不涉及覆寫旗標。
- 系統記錄照常寫進留言串（「由看板改負責人」不另立種類，與一般修改同一種系統事件，主控 T7）。

### 5.6 權限與併發

- 能不能拖：狀態、到期區間欄要有改任務的權限（任務設計 §7 四種身分）；負責人欄另外允許部屬任務的主管（§4.2）。沒有權限的卡片不能拖，游標顯示禁止；手機的「移到…」不出現。凍結的任務（應用程式關閉）不能拖。
- 改值走專用的移動 API（§12），由伺服器算「今天」「本週最後一天」，不信任瀏覽器日期（主控 T8）。
- 併發：移動請求帶卡片載入時的 `ModifiedTime`，與目前值不同就回 409，畫面提示「任務已被別人修改」並重新整理那一欄（主控 T8）。
- 拖拉後先樂觀更新畫面，失敗就放回原欄並顯示原因。

### 5.7 自訂看板設定（使用者決定 1）

一個看板存：

- **名稱**（100 字內）。
- **分欄依據**：狀態、負責人、到期區間三選一。
- **範圍**：指派給我、我參與的（建立、負責、被 @）、部屬的任務（§4.2，非主管時這個選項不出現）、全部看得到的（§4.4）。範圍相對於**打開的人**，分享出去後每人看到自己的範圍。
- **篩選**：狀態（到期區間看板固定未完成）、負責人、建立者、來源（個人任務、記錄上的任務、規則產生）、到期日區間、關鍵字（標題）、是否顯示子任務（§10.5）。
- **欄順序與隱藏**：狀態與到期區間的欄可以排序、隱藏；負責人欄是明列的人加上「未指派」的位置，以及「自動附加其他人」開關。
- **欄內排序**：到期日（預設，空的排最後）、建立時間、標題，可選遞增或遞減；「完成」欄固定依完成時間新到舊。

沒有欄內手動排序（U6，使用者裁決照建議）：同一張卡會同時出現在不同人的不同看板上，手動排序要每個看板各存一份順序，而且分享看板的人改順序會互相蓋掉。

### 5.8 預設看板與「我的任務」頁（U7，使用者裁決照建議）

- 看板與清單放在同一頁：「我的任務」頁標題列加「清單／看板」切換（甘特圖上線後加第三個「甘特圖」）。網址帶 `view=board&board=<id>`，重新整理或分享連結都還在同一個檢視。
- 頁面改名「任務」，左側選單同步；首頁卡片連結不變。
- 看板模式上方是看板選擇器：「預設看板」、我的看板、分享給我的看板，以及「另存為新看板」。
- **預設看板**（沒存過任何看板、或選了「預設看板」）：依狀態分欄、範圍「指派給我」、不顯示「取消」欄。預設看板不存在資料表，不能分享；改了設定要「另存為新看板」。
- 上次打開哪個看板記在瀏覽器（依使用者區分，同儀表板做法），換裝置回到預設看板。

### 5.9 卡片內容

- 一定有：標題（兩行截斷）、到期日（逾期標紅，今天標橙）、負責人頭像與姓名（依負責人分欄時省略）、狀態標籤（依狀態分欄時省略）。
- 有才顯示：相關記錄標題，或「相關記錄（無權限查看）」，個人任務不顯示；規則產生的圖示；凍結圖示；子任務進度「2／5」與進度條（§10.5）；子任務卡片上方顯示父任務標題（父任務看不到時不顯示，不會發生，§10.3）；留言數。
- 點卡片開既有的任務詳細對話框；在對話框改完，看板那張卡片就地更新。

### 5.10 每欄數量與分頁

- 每欄先載 50 張，捲到底「載入更多」，每次 50 張；每欄最多載到 500 張，再多顯示「還有 N 筆，請加上篩選或改用清單」（主控 T9）。這是畫面效能的技術上限，不是業務政策，列進可寫死清單（§14）。
- 欄頭顯示該欄總數（不受已載入張數限制）。
- 在製品上限（例如每人進行中最多 5 件）是業務政策，這次不做（💡）；要做時列為政策。

### 6.2 權限（使用者決定 4）

- 建立者才能改設定、改分享、刪除。系統管理員可以刪除任何有分享的看板（同報表「避免離職者留下的共用報表沒人能管」），不能改。

### 6.3 分享對象（使用者決定 4 與既有程式的落差）

使用者要「分享給人或部門，沿用報表的分享方式」，但報表目前只能分享給群組。處理（U8，使用者裁決照建議）：

- 看板的分享對話框沿用報表分享對話框的版面與「只能看、可另存」的規則，對象擴充為使用者、部門、群組三種，分頁切換。
- 分享給部門：只含該部門的直屬成員，不含下層部門（U8）；人調部門後立即跟著變。
- 報表的分享對象這次**不改**，維持群組；第二題照建議：這次不擴充，列進 todo；之後若要改，`ReportShare` 加 `TargetKind`、`TargetId`，與 `Dynamic_TaskViewShare` 同形狀，排在 kr1。
- 刪除群組時清掉看板的群組分享（同 `DeleteGroupAsync` 清報表分享）；部門只有在沒有成員與子部門時能刪，刪除時同樣清掉。

## 7. 報表資料來源：任務

### 7.1 定義格式（主控 T11）

`ReportDefinition` 加選填欄位 `dataset`：省略或 `module` 是現行的模組報表；`tasks` 是任務；`taskEvents` 是任務事件（§7.2）。用 `dataset` 時 `MainModuleKey` 為空、`Child` 必須為空（任務不能合併子模組，也不能被合併）、欄位引用的 `ViaFieldId` 必須為空。舊定義不帶這個欄位，一律當模組報表，`Version` 維持 1，不用 migration。

欄位 Id 用固定的負數代碼（`-1` 起），只在任務資料來源的目錄內有意義，不會與動態欄位的正數 Id 撞號。

### 7.2 兩種「列」

報表每張都要說清楚「每一列代表什麼」（報表設計 §6.1）：

- `tasks`：**一列＝一個任務**。
- `taskEvents`：**一列＝一次建立或一次完成**。每個任務產生「建立」一列（日期＝建立時間）；狀態是完成的任務另有「完成」一列（日期＝完成時間）。只用既有欄位：重開後再完成的任務只留最後一次完成（`CompletedTime` 只存最後一次），列為已知限制。

### 7.3 欄位清單

`tasks` 的欄位：

| 代碼 | 欄位 | 型別 |
|---|---|---|
| -1 | 標題 | 文字 |
| -2 | 狀態 | 選項（四個狀態） |
| -3 | 負責人 | 使用者（空的是「未指派」） |
| -4 | 負責人部門 | 部門 |
| -5 | 建立者 | 使用者（規則產生的是「系統」） |
| -6 | 到期日 | 日期 |
| -7 | 建立時間 | 日期時間 |
| -8 | 完成時間 | 日期時間 |
| -9 | 來源 | 選項（個人任務、記錄上建立、規則產生） |
| -10 | 所屬模組 | 選項（模組名稱） |
| -11 | 任務規則 | 選項（規則名稱） |
| -12 | 是否逾期 | 是否 |
| -13 | 完成狀況 | 選項（準時完成、逾期完成、無到期日完成、未完成） |
| -14 | 完成天數 | 整數 |
| -15 | 延遲天數 | 整數 |
| -16 | 層級 | 選項（獨立任務、父任務、子任務；st1 起） |
| -17 | 開始日 | 日期（gt1 起） |

衍生欄位的算法，都只讀既有欄位（使用者決定 6）：

- **是否逾期**：未完成且到期日早於**報表基準日**（§7.6）。
- **完成狀況**：完成且有到期日時，完成日（營運時區）不晚於到期日是「準時完成」，晚於是「逾期完成」；完成但沒有到期日是「無到期日完成」；其餘是「未完成」。取消的任務也是「未完成」，內建報表另以狀態排除取消（§8.1）。
- **完成天數**：完成日減建立日（營運時區的日曆天），當天完成是 0；未完成為空。
- **延遲天數**：完成任務是完成日減到期日、未完成任務是基準日減到期日，取不小於 0；沒有到期日為空。
- **負責人部門**：負責人**目前**的部門，不是任務當時的部門（組織沒有部門歷史，簽核設計 §11.1），列為已知限制。

`taskEvents` 的欄位：事件種類（建立、完成）、事件日期（日期時間），加上 `tasks` 的 -2、-3、-4、-5、-9、-10、-11、-16。

標題可以放在明細欄與條件，不能分組（同長文字的處理，主控 T12：分組沒有意義、只會產生近乎唯一的分組）。說明（`Description`）、留言、附件、記錄標題都**不提供**，報表永遠拿不到記錄內容。

### 7.4 新的量值種類（一般報表也可用，主控 T13）

- **`countIf`（符合條件的筆數）**：帶條件的筆數，就是 `ratio` 的分子。負載報表的「待辦件數」「逾期件數」、趨勢報表的「建立件數」「完成件數」都要它。
- **`median`（中位數）**：只限數字型別，空值不計入，偶數筆取中間兩筆的平均，用 decimal。

兩者加在 `ReportCalculator`，對模組報表一樣可用。SQL 路徑：`countIf` 用 `SUM(CASE WHEN 條件 THEN 1 ELSE 0 END)`，與 `ratio` 的分子同一個謂詞產生器；`median` 第一版退回記憶體路徑，原因 `measureNotSupported:median`。有合併子模組時，`median` 對主模組欄位照現行去重規則（每筆主記錄在每個分組只算一次）。

**帶條件的數值量值**（主控 T23，kr1 的通用量值能力）：`sum`、`avg`、`median` 都可帶選填的 `Condition`，只拿符合條件的列計算；不符合的列當空值，不計入筆數。沒帶條件時與現行完全相同。

- 例：內建報表 2 的「平均延遲天數」＝`avg(延遲天數)` 帶條件「完成狀況＝逾期完成」，準時完成的 0 天不會把平均拉低。
- SQL 路徑：`SUM(CASE WHEN 條件 THEN x END)`、`AVG(CASE WHEN 條件 THEN x END)`；實作照聚合設計 §9 的精確整數加總，分子與筆數各自加，C# 用 decimal 相除。條件用同一個謂詞產生器；`median` 帶條件照樣退回記憶體路徑。
- 條件用到的欄位進 `AllRefs`，隱藏欄位用在量值條件時整張擋下，與 `ratio` 的條件相同（報表設計 §7）。
- 設計器的量值設定多一個「只算符合條件的」選填區塊，沿用 `ratio` 的條件設定器。

### 7.5 權限過濾放在哪一層（主控 T14）

- **列的範圍**：載入任務時就套 §4.4 的可見條件（Persistence 的 LINQ 條件），看不到的任務根本不進報表，不是載入後再丟。
- **記錄相關的格子**：所屬模組、任務規則兩個欄位，在觀看者看不到那筆記錄時（§4.3），格子狀態是 `restricted`，顯示「（無權限）」並自成一組，沿用報表既有的 restricted 處理（報表設計 §6.6）。依模組判斷不夠：主管可能讀得到模組、但記錄在他的資料範圍外。
- **條件用到記錄相關欄位**：「所屬模組＝請假單」的條件只對 `ok` 的格子成立，`restricted` 一律不符合（同 `Matches` 對 `restricted` 的處理）。所以不能用條件推出看不到的記錄屬於哪個模組。
- 任務欄位沒有欄位權限，不套 `CanSee`；任務設計 §7 已裁決負責人、到期日是任務自己的屬性。
- **下鑽**：一律列任務（標題、狀態、負責人、到期日、完成時間、相關記錄），相關記錄用 §4.3 的顯示；點一列開任務詳細，伺服器再驗一次可見性。筆數上限沿用 A24。
- **匯出**：任務資料來源沒有模組的 PrintExport 可查，看得到報表的人就能匯出看得到的任務（U9，使用者裁決照建議）；匯出內容與畫面相同，`restricted` 格子匯出「（無權限）」。
- **分享、儀表板、指派版**：沿用報表既有規則，數字一律照觀看者計算。

### 7.6 基準日

任務報表沿用報表的基準日（`BasisDateAsync`）：一般環境是今天；Demo 站用資料產生日。看板與清單永遠用今天。所以在 Demo 站，報表的「逾期件數」可能與看板「逾期」欄不同；報表頁照現行標示「資料基準日 yyyy-MM-dd」，手冊註明（主控 T15）。

### 7.7 與 SQL 聚合路徑、記憶體路徑的關係（主控 T16）

- 任務資料來源**只走記憶體路徑**。SQL 路徑建在 `Dynamic_RecordIndex` 上，任務不在那張表；任務量通常比業務記錄少一到兩個數量級，記憶體路徑足夠。回傳的 `engine` 是 `memory`，`fallbackReasons` 寫 `datasetMemoryOnly`。
- 載入用 EF LINQ（可見條件，加上主要日期欄位的區間與狀態條件先在資料庫縮小；只用「證明精確」的條件縮小，記憶體路徑照舊重套全部條件，同聚合設計 §3 總原則）。上限沿用 `Reports:MaxLoadRows` 與 `MaxRows`，超過回「資料太多，請縮小條件」。
- 結果組裝（分組、去重、標籤、排序、卡片選項）走同一份 `ReportCalculator` 與 `ReportRunner.Output`，只是「載入與組格子」換成任務專用的實作。做法：把 `RunAsync` 的步驟 1 至 5 抽成「資料來源」介面（模組來源＝現行程式原封不動、任務來源＝新程式），步驟 6 以後共用。
- `Reports:Engine=SqlOnly` 時，任務報表不丟例外、照樣走記憶體路徑（`SqlOnly` 是證明模組報表覆蓋用的，任務來源本來就不在範圍內）。
- **PostgreSQL**：記憶體路徑只用 EF LINQ，pg0 起就能在 PostgreSQL 跑；pg1 只改模組報表的 SQL 路徑，與任務來源無關。新測試放進雙跑集。日後若要任務報表走 SQL，另開一段，方言運算式一律放 `ISqlDialect`。

## 8. 內建統計報表

### 8.1 四份報表（使用者決定 6）

都依期間、部門篩選，可下鑽到任務清單，只用既有欄位。

**1. 各負責人負載**（`tasks`）

- 列：狀態是待辦或進行中的任務。
- 分組：負責人（含「未指派」）。
- 量值：待辦件數、進行中件數、逾期件數（都是 `countIf`）、合計（`countMain`）。
- 期間：作用在到期日，預設不限（看全部未完成）。
- 呈現：長條圖，三個件數並列，依合計由大到小。

**2. 準時完成率與逾期**（`tasks`）

- 列：狀態是完成、而且有到期日的任務。
- 分組：負責人。
- 量值：完成件數、準時件數、逾期完成件數、準時率（`ratio`，條件「完成狀況＝準時完成」）、平均延遲天數（`avg` 帶條件「完成狀況＝逾期完成」，只算逾期完成的，§7.4）。
- 期間：作用在完成時間，預設本月。
- 另一組「目前逾期」放在負載報表，不重複放；這份只看已完成的。

**3. 完成天數**（`tasks`）

- 列：狀態是完成的任務。
- 量值：件數、平均完成天數、中位完成天數（`median`）。
- 期間：作用在完成時間，預設近 3 個月。
- 「依人、依規則」拆成兩份定義：3a 依負責人分組、3b 依任務規則分組（個人與手動建立的任務在「（無）」一組），所以實際是五份（U10，使用者裁決照建議）。一份報表有兩個分組會變成交叉表，「依規則」的平均會被拆散到每個人，不好讀。

**4. 建立與完成趨勢（每週）**（`taskEvents`）

- 分組：事件日期，依週分桶（ISO 週；區間的起訖依 A7，同既有報表）。
- 量值：建立件數（`countIf` 事件種類＝建立）、完成件數（`countIf` 事件種類＝完成）。
- 期間：作用在事件日期，預設近 12 週。
- 呈現：折線圖，兩條線。

### 8.2 期間與部門篩選（U11，使用者裁決照建議）

- 期間：報表頁上方的暫時區間，沿用卡片與儀表板既有的 `RangeOverride`（作用在主要日期欄位），不存檔。
- 部門：報表頁新增「部門」暫時篩選（樹狀多選，含「包含下層部門」勾選，預設勾），作用在「負責人部門」，只在任務資料來源的報表出現，不存檔；要固定就「另存一份」再加條件。
- 儀表板上的任務卡片只受儀表板既有的日期篩選影響，第一版不加部門篩選（💡）。

### 8.3 如何提供（主控 T17、U10，使用者裁決照建議）

- **隨系統內建**：存成 `Report` 資料列，加 `BuiltInCode`（例如 `task-workload`，唯一），擁有者為空（系統）。啟動時依程式內的定義目錄寫入或更新（以 `BuiltInCode` 對應），所以新版程式改了內建定義會自動更新；已經有的就比對內容，不同才寫。
- 名稱用四語系 i18n 鍵，畫面依語系顯示；資料列的 `Name` 存繁中當備援。
- 所有登入者都看得到（「我的報表」上方多一區「內建報表」），內容一律照各人權限計算。
- **不能改、不能刪、不能分享**（人人本來就看得到）；可以「另存一份」，複製成自己的報表後隨意改（沿用 `CopyReport`）；可以放上儀表板。
- 被儀表板引用照現行規則；內建報表永遠不刪，所以不會有「已不再分享」。
- **不進套件格式**：任務是核心能力，不屬於任何應用程式。應用程式套件帶任務資料來源的報表，列為 💡（要改 `AppReportCodec` 與格式版本）。
- 與報表設計 §3 目標 4「全新安裝沒有任何報表」衝突：內建任務報表會讓全新安裝就有五份報表（§18）。

| 應用程式關閉（模組凍結） | 顯示、不能拖、標凍結 | 照常計入 | 能看、不能重派 |
| 政策 A32 關 | 「部屬的任務」範圍不出現 | 只算自己看得到的 | 無 |
| 沒有部門的使用者 | 只看自己看得到的 | 部門欄為空，「（無部門）」一組 | 不是任何人的部屬 |

負責方：任務、看板、報表資料來源、內建報表、子任務、甘特圖都屬於平台核心；組織骨架屬於核心；沒有任何應用程式負責或擁有它們。模組的 `TasksEnabled` 只管記錄頁區塊、新增與規則（任務設計 §4.4），不管既有任務在看板與報表出不出現。

這也部分解了任務設計 §4.4 的已知限制「模組關閉任務後，看得到記錄但不是參與者的人看不到既有任務」：看板「全部看得到的」範圍與任務報表會列出它們（依 §4.4 第 3 項本來就看得到），記錄頁仍不顯示。

## 10. 子任務（使用者決定：一層）

### 10.1 資料

- `Task` 加 `ParentTaskId`（選填）與索引；加 `CancelledByParent` 旗標（§10.4）。
- 只有一層：父任務本身不能有父任務；已有子任務的任務不能變成別人的子任務。後端強制，回 400。
- 子任務與父任務掛同一筆記錄（`ModuleId`、`RecordId` 從父任務複製，不能另選）；父任務是個人任務，子任務也是個人任務（主控 T18）。
- 每個父任務的子任務數上限是政策 A34（出廠 50，技術上限 200，範圍 S）。改嚴只擋新增（政策設計 §3.5）。

### 10.2 建立與搬移

- 在任務詳細的「子任務」區塊新增：只填標題、負責人（預設父任務的負責人）、到期日（預設空）。
- 有改父任務權限的人可以新增子任務；子任務的建立者是新增的人。
- 不能把既有任務拖進別人底下當子任務（第一版，主控 T18）；子任務也不能脫離父任務，只能刪除或取消。
- 規則產生的任務可以有人手動加的子任務；規則本身不產生子任務（💡）。

### 10.3 可見與權限

- 看得到父任務就看得到全部子任務（§4.4 第 5 項）；子任務本身的參與者另外看得到子任務。只看得到子任務的人，看得到父任務的標題（顯示在子任務上方），點進去照父任務自己的權限判斷，看不到就 404（U13，使用者裁決照建議）。
- 改子任務：子任務自己的四種身分，加上能改父任務的人（主控 T19）。

### 10.4 父子狀態連動（U14，使用者裁決照建議）

| 事件 | 連動 |
|---|---|
| 子任務變成進行中，父任務是待辦 | 父任務自動變成進行中 |
| 最後一個未完成的子任務完成 | 父任務不自動完成；父任務負責人收到「子任務已全部完成」通知，留言串寫系統記錄 |
| 父任務改成完成，還有未完成的子任務 | 確認框三選一：一併完成、一併取消、取消操作 |
| 父任務改成取消 | 未完成的子任務一併取消，設 `CancelledByParent` |
| 父任務從取消恢復 | 因父任務取消的子任務恢復成待辦；人手動取消的不恢復 |
| 已完成的父任務底下，子任務被重開 | 父任務改回進行中，寫系統記錄 |
| 父任務是完成或取消 | 不能新增子任務 |

- 規則自動取消父任務（條件不再符合，任務設計 §5.2）同樣連帶取消子任務；父任務被規則恢復時，因父任務取消的子任務一併恢復。
- 刪除父任務（只有自己建的任務能刪）：確認框寫明子任務數，一併刪除。
- 連動在同一個交易內完成，每個被連動的任務各自寫系統記錄、各自通知（通知收件人照政策 A13）。
- **連動不檢查操作者對父任務的權限**（主控 T25）：子任務的負責人改自己的子任務，即使不能改父任務，父任務照樣依上表連動。連動算系統事件：父任務的 `ModifiedBy` 為 null，留言串寫「因子任務變更」的系統記錄並註明是哪個子任務；父任務取消或恢復帶動的子任務同理寫「因父任務變更」。操作者在父任務上選「一併完成／一併取消」是他自己的操作，要有改父任務的權限，子任務照 T19 不另外檢查。

### 10.5 進度與顯示

- 父任務進度＝完成的子任務數 ÷（子任務數 − 取消的子任務數）；全部取消或沒有子任務時不顯示進度（主控 T20）。
- 清單、看板卡片、甘特圖列都顯示「完成數／總數」與進度條。
- 看板「顯示子任務」預設開：子任務自己是一張卡，照自己的狀態、負責人、到期日分欄，上方顯示父任務標題。關閉時只列父任務與獨立任務。
- 報表：子任務照常各算一筆（它是另一件工作）；要只算頂層，用「層級」欄位篩選。內建報表不篩，負載報表說明列「子任務各算一筆」（U14，使用者裁決照建議 的一部分）。

### 10.6 不做

多層子任務、子任務的子任務進度彙總、規則產生子任務、子任務範本、拖拉改父子關係。

## 11. 甘特圖

### 11.1 資料

- `Task` 加 `StartDate`（選填，日期）。有到期日時，開始日不能晚於到期日（400）。
- 規則產生的任務沒有開始日（規則設定開始日偏移，💡）；規則同步只動到期日，同步後到期日早於開始日時，開始日一併移到新到期日並寫系統記錄（主控 T21）。
- 開始日沒有覆寫旗標：規則不管它。

### 11.2 畫面

- 「任務」頁第三個檢視「甘特圖」。左側是任務列，右側是時間軸；可存成自訂檢視（`Dynamic_TaskView.Kind = gantt`），分享、另存規則同看板（§6）。
- 範圍與篩選同看板（§5.7），沒有分欄依據，改成**分組**：不分組、依父子（預設）、依負責人。
- 依父子分組：父任務一列，子任務縮排在下，可收合。父任務的長條畫自己的日期；另畫一條淡色的「子任務跨度」（最早開始到最晚到期），不自動改父任務日期（U12，使用者裁決照建議）。
- 有開始日與到期日：畫長條。只有到期日：在到期日畫菱形（里程碑）。只有開始日或都沒有：不上時間軸，放在下方「未排程」清單，可拖進時間軸排程（拖進去的那天同時設為開始日與到期日）。
- 時間刻度：日、週、月三種；今天畫一條直線；逾期的長條標紅。
- 不畫相依線（任務相依未被選）。

### 11.3 拖拉

- 拖整條：開始日與到期日一起平移相同天數。
- 拖左緣改開始日、拖右緣改到期日；不能拖到開始日晚於到期日。
- 拖菱形：改到期日。
- 改到期日照 §5.5 設 `DueOverridden`；權限、併發、樂觀更新同 §5.6。
- 拖拉放開時顯示新日期的小提示，按 Esc 取消。

### 11.4 RWD（主控 T22）

時間軸不用整頁橫向捲動（任務設計 §8 第 6 點）：時間軸寬度固定填滿容器，用「上一段／下一段」按鈕平移，刻度切換決定一屏看幾天。

- **桌機 1920、筆電 1366**：完整甘特圖，可拖拉。
- **平板 820**：完整甘特圖，只能看；點長條開日期編輯對話框（觸控拖細長條容易誤觸）。
- **手機 390**：不畫時間軸，改成依週分組的清單，每列顯示日期區間與進度，點開編輯。

## 12. API（主控判斷，實作可調整命名）

路由放在既有的 `api/v3/dynamic` 下。

- `GET /task-views?kind=board|gantt`：我的與分享給我的。`POST /task-views`、`GET/PUT/DELETE /task-views/{id}`、`POST /task-views/{id}/copy`、`PUT /task-views/{id}/shares`、`GET /task-views/share-targets`（使用者、部門、群組的 Id 與名稱）。
- `POST /task-board/columns`：收看板設定（存過的或未存的），回各欄總數與第一頁卡片。`POST /task-board/columns/{column}/page`：載入更多。
- `POST /tasks/{id}/move`：`{ groupBy, toColumn, dueDate?, expectedModifiedTime }`，伺服器依欄算新值（§5.3），回更新後的卡片與 `visible`；`visible=false` 時另回一次性的 `undoToken`（§5.4）。
- `PATCH /tasks/{id}` 既有：主管重派走這裡，只允許改 `assigneeUserId`（§4.2），同樣回 `visible` 與 `undoToken`。
- `POST /tasks/{id}/undo-reassign`：收 `undoToken`，把負責人改回原負責人。
- `GET /tasks?tab=subordinates`：任務清單的「部屬的任務」分頁（§4.2）。
- `POST /tasks/{id}/subtasks`；`PATCH /tasks/{id}` 的狀態連動選項（`cascade: complete|cancel`）。
- `POST /tasks/gantt`：收甘特設定與時間窗，回任務列與日期。
- 報表沿用既有端點；`GET /reports/catalog` 多回兩個系統資料來源與欄位目錄；執行與下鑽多收 `departmentIds`、`includeSubDepartments`（§8.2）。

寫入一律 `ITransactionalRequest`。

## 13. ERP 對照

以下依主控對主流產品的了解整理，未另行上網查證：

- **主流 CRM**：清單檢視可切成看板，依選項欄分欄、拖拉改值；清單檢視可分享給群組與角色。主管看部屬資料靠角色階層，往上逐層繼承，對應 §4 的遞迴範圍與 A33。
- **開源 ERP**：專案任務有看板（依階段）、清單、甘特圖；待辦活動依逾期、今天、計畫中分組，對應到期區間看板。子任務一層，父任務顯示子任務數。部門與主管在人資應用程式底下。
- **專案管理工具**：看板、清單、時間軸是同一批任務的不同檢視，存成可分享的檢視；部分工具把欄內手動排序存在看板層級，部分工具的子任務不出現在專案看板上。
- **傳統 ERP**：任務多半附在單據的工作流程裡，統計靠報表模組，看板較少；主管範圍依組織單位。

Formwright 的取捨：

- 看板、清單、甘特圖做成同一頁的三個檢視，存成 `TaskView`，同專案管理工具。
- 主管範圍依核心組織骨架，同 CRM 的角色階層，但不依應用程式。
- 不做欄內手動排序（U6）：Formwright 的看板是任意篩選的檢視，不是固定的專案看板，手動順序沒有單一的歸屬。
- 子任務會出現在看板上（可關）：多數使用者情境是「拆給不同人做」，子任務才是負責人自己要拖的那張卡。

## 14. 可寫死清單（新增）

**資料完整性**

- 子任務只有一層；子任務與父任務掛同一筆記錄。
- 開始日不能晚於到期日。
- 到期區間看板只列未完成的任務（U5 確認後列入）。
- 內建報表不能改、不能刪、不能分享。
- 「逾期」「今天」「本週」的邊界定義（逾期定義原本就寫死；本週起始日仍由 A7 決定）。

**安全**

- 任務報表不提供說明、留言、附件、記錄標題欄位。
- 看不到記錄時，所屬模組、任務規則格子一律 `restricted`，條件對它恆不符合。
- 分享看板不授予任務權限；主管不因看過、重派而成為參與者。
- 移動 API 由伺服器算日期，不收瀏覽器的「今天」。

**技術限制**

- 看板每欄每頁 50 張、每欄最多載入 500 張。
- 看板名稱 100 字；明列的負責人欄最多 50 人；分享對象每個看板最多 200 個。
- 甘特圖一次最多 500 列（超過提示加篩選）；時間窗最多 366 天。
- 部屬名單超過 2000 人時查詢方式要改（§4.4，列為已知限制，不是使用者可調的值）。
- 任務資料來源只走記憶體路徑；`median` 在 SQL 路徑退回記憶體路徑。
- 內建報表的 `BuiltInCode` 格式同代碼格式（B7）。
- 任務報表的欄位 Id 固定為負數代碼。

**新政策（不寫死）**：A32 主管範圍開關、A33 含下層部門、A34 每個父任務的子任務數上限。看板的在製品上限若之後要做，也列為政策。

## 15. 已知限制

- 「負責人部門」用目前的部門，人調部門後歷史任務也算到新部門。
- `taskEvents` 的「完成」只有最後一次完成。
- Demo 站報表的基準日與看板的今天不同（§7.6）。
- 部屬超過 2000 人時，可見條件的 `IN` 參數要改成暫存表或分批（§4.4）。
- 任務報表資料量大（超過 `MaxLoadRows`）時被拒，沒有 SQL 路徑。
- 甘特圖不畫相依，父任務日期不自動跟子任務。

## 17. 決定彙整

### 17.1 使用者已決定（2026-11-13）

1. 看板拖卡換欄即改值；可存自訂看板（分欄依據、篩選、欄順序）。
2. 分欄維度：狀態、負責人（含未指派）、到期區間；不做依模組分欄。
3. 部門主管可看並重派部屬的任務；記錄無權限時只顯示任務。
4. 自訂看板可分享給人或部門，沿用報表的分享方式；建立者才能改，被分享者可另存；每人只看到自己有權看的任務。
5. 任務納入報表資料來源，可下鑽、匯出、放儀表板，不能看到無權限資料。
6. 內建四份統計報表，可依期間、部門篩選、下鑽，只用既有欄位。
7. 排在簽核流程圖設計器之後。
8. 子任務與甘特圖都要，子任務先做；子任務一層、父任務顯示進度；甘特圖加開始日、可拖拉、可依父子分組；不做任務相依。

- **U1** 主管範圍往下遞迴到所有下層部門（A33 出廠「是」）；兼任多個部門的主管取聯集。

- **U14** 父子狀態連動照 §10.4 的表；報表裡子任務各算一筆。
- **U15** 任務清單加「部屬的任務」分頁，A32 開且有部屬才出現，kb1 上線（使用者裁決照建議 2026-11-13）。
- **U16** 主管重派給非部屬後看不到該任務是接受的結果；畫面提示「已移出你的範圍」，提示期間可復原（使用者裁決照建議 2026-11-13）。
- **U17** 清單「本週到期」維持含今天，等於看板的「今天」＋「本週」，手冊註明（使用者裁決照建議 2026-11-13）。

### 17.3 技術類（主控決定，可推翻）

- **T1** 停用部門的主管不因該部門取得範圍，遞迴照樣經過停用部門。
- **T2** 停用的部屬仍算部屬。
- **T3** 主管不因看過或重派成為參與者。
- **T4** 可見性在 C# 算條件、Persistence 轉成單一 LINQ 條件，取代逐筆查 stub。
- **T5** 清單「本週到期」＝看板的「今天」＋「本週」；兩者共用 `WeekEnd` 算本週最後一天。
- **T6** 範圍是部屬時自動列出全部部屬欄。
- **T7** 看板改值寫一般的系統事件，不另立種類。
- **T8** 專用移動 API、伺服器算日期、以 `ModifiedTime` 擋併發。
- **T9** 每欄 50 張一頁、最多 500 張。
- **T10** 看板與甘特檢視共用 `Dynamic_TaskView`；分享表三種對象；引用失效不讓看板壞掉。
- **T11** 報表定義加選填 `dataset`，欄位用負數代碼，`Version` 不變。
- **T12** 任務標題不能分組。
- **T13** 新量值 `countIf`、`median` 對所有報表可用；`median` 在 SQL 路徑退回。
- **T14** 權限在載入時過濾，記錄相關格子 `restricted`。
- **T15** 任務報表用報表基準日，看板用今天。
- **T16** 任務資料來源只走記憶體路徑，`SqlOnly` 不丟例外；新查詢全用 EF LINQ，與 pg1 無關。
- **T17** 內建報表存資料列加 `BuiltInCode`，啟動時依程式目錄同步。
- **T18** 子任務繼承父任務的記錄；不能搬移父子關係。
- **T19** 能改父任務的人能改子任務。
- **T20** 進度分母不含取消的子任務。
- **T21** 規則同步讓到期日早於開始日時，開始日跟著移。
- **T22** 甘特圖用分段平移代替橫向捲動；平板只看加點擊編輯；手機用清單。
- **T23** `sum`、`avg`、`median` 可帶選填條件，SQL 路徑用 `CASE WHEN`，`median` 退回記憶體路徑；列為 kr1 的通用量值能力。
- **T24** 移動與重派回 `visible`；看不到時由伺服器發一次性 `undoToken`，只能把負責人改回原負責人（原負責人存在伺服器，不信任前端帶來的值），token 用過或逾時即失效。
- **T25** 子任務連動父任務不檢查操作者對父任務的權限；連動是系統事件，`ModifiedBy` 為 null，留言串寫「因子任務變更」。

## 18. 與既有程式或設計的矛盾

1. **分享對象**：使用者決定 4 說「分享給人或部門，沿用報表的分享方式」，但報表只能分享給群組（`ReportShare.GroupId`）。本設計讓看板支援三種對象、報表暫不改（U8）。
2. **全新安裝沒有報表**：報表設計 §3 目標 4 寫「全新安裝沒有任何報表」，內建任務報表會打破它（U10）。
3. **量值種類**：內建報表要的中位數、條件筆數，現有量值沒有，要新增 `median`、`countIf`，`sum`、`avg`、`median` 也要能帶條件（T13、T23）。
4. **報表引擎綁動態模組**：任務不是動態模組，要把 `RunAsync` 的載入與授權抽成資料來源介面（§7.7），是報表引擎的結構改動。
5. **任務可見性**：任務設計 §7 的「看得到任務」要加主管與子任務兩項；`TaskAccess` 逐筆查 stub 的寫法不適合看板，要改成批次（T4）。
6. **路線階段 5 的「看板」**：路線與功能清單的看板指動態模組記錄的看板，不是任務看板；本設計提前做任務看板，不改那一項的位置。
7. **組織不做兼任**：簽核設計 §11.1 第一版不做兼任多部門，所以「兼任」在本設計只指「一人當多個部門的主管」（U1），不處理一人屬多部門。
8. **任務設計 §8 第 3 點**：「我的任務」頁改名「任務」並加檢視切換（U7）。

## 19. 測試重點

- **主管範圍**：遞迴多層、經過停用部門、停用部門自己的主管、一人管多部門、沒有部門的人、主管本人不算部屬、A32 關閉、A33 關閉；「部屬的任務」分頁的出現條件（A32 關、沒有部屬時不出現），分頁與看板同範圍時筆數相同；重派成功、改狀態被拒；重派給非部屬回 `visible=false`，提示期間復原成功，token 用過或逾時後復原被拒，復原只能改回原負責人；掛在無權限記錄上的部屬任務只顯示「相關記錄（無權限查看）」，API 回應不含模組代號、記錄 Id、標題。
- **可見性查詢**：同一組任務用新舊兩種判斷（`EvaluateManyAsync` 與批次條件）結果相同；SQLite 與 PostgreSQL 雙跑；一次載入 500 張卡片時查詢次數固定，不隨卡片數成長。
- **看板拖拉**：清單「本週到期」筆數＝看板「今天」＋「本週」兩欄總數（A7 的七種起始日各跑一次）；三種分欄每一欄的值；本週最後一天依 A7 的七種起始日；今天是本週最後一天；拖到逾期被拒；之後的日期選擇取消會放回；規則任務的兩個覆寫旗標；清空到期日後規則不再同步；凍結任務不能拖；`ModifiedTime` 不符回 409；拖到停用者被拒。
- **自訂看板與分享**：建立者改、被分享者改被拒、另存、分享給人、部門（直屬，不含子部門）、群組；被分享者看到的任務不多於自己的可見範圍（同一看板兩個身分不同結果）；刪除群組、部門時清分享；引用停用使用者不壞。
- **報表**：固定資料集的預期值表（四份內建報表每個數字手算）；`countIf`、`median`（奇數、偶數、空值）；`sum`、`avg`、`median` 帶條件與不帶條件（不帶條件時與現行結果相同）；內建報表 2 手算例：同一負責人 3 件逾期完成、延遲 2、4、6 天，另 2 件準時完成，平均延遲天數是 4（不帶條件會算成 2.4），準時率 40%；帶條件的 `sum`、`avg` 在 SQL 路徑與記憶體路徑結果相同；隱藏欄位用在量值條件時整張擋下；完成狀況四種與跨午夜；`taskEvents` 一個任務兩列；權限矩陣（參與者、看得到記錄、主管、管理員、什麼都不是）；`restricted` 格子在分組、條件、下鑽、匯出各位置；條件「所屬模組＝X」不能推出看不到的記錄；`SqlOnly` 模式下任務報表照走記憶體路徑；PostgreSQL 雙跑。
- **內建報表**：啟動同步（新增、定義變更、不變不寫）、不能改刪分享、另存、放上儀表板。
- **子任務**：一層限制、A34 上限與改嚴只擋新增、§10.4 每一條連動（含規則取消與恢復）、子任務負責人不能改父任務時連動照樣發生，父任務 `ModifiedBy` 為 null，留言串有「因子任務變更」、刪除父任務、可見性繼承、只看得到子任務的人點父任務 404。
- **甘特圖**：開始日不晚於到期日、拖整條與兩緣、里程碑、未排程拖入、規則同步推開始日、四種寬度的行為。
- **畫面**：四種寬度（390、820、1366、1920）沒有整頁或表格內的橫向捲動；四個語系；手機用「移到…」完成三種分欄的改值。

## 20. 建議切段

每段可獨立合併、Demo 不壞。排在簽核流程圖設計器之後（使用者決定 7）；順序是看板、報表、子任務、甘特圖（子任務先於甘特圖，使用者決定 8）。

| 段 | 內容 | Demo 上看得到 |
|---|---|---|
| kb1 | 可見性批次查詢（T4）、主管範圍、A32／A33、主管重派與復原（T24）、清單「部屬的任務」分頁、手冊「本週到期」說明 | 走查：業務主管從「部屬的任務」分頁進任務詳細，重派業務一的任務 |
| kb2 | `TaskViews` migration、檢視與分享 API、看板欄查詢與移動 API | 無畫面變化 |
| kb3 | 任務頁「清單／看板」切換、預設看板、三種分欄、拖拉與「移到…」、自訂看板、分享對話框、四種寬度 | 看板 |
| kr1 | 報表資料來源介面、`tasks` 與 `taskEvents`、`countIf`、`median`、`sum`／`avg`／`median` 帶條件（T23）、權限與 `restricted`、下鑽、匯出（若 U8 擴充報表分享也在這段） | 用 API 可跑任務報表 |
| kr2 | 設計器選系統資料來源、欄位目錄、報表頁部門暫時篩選、下鑽列任務 | 自組任務報表 |

## 21. 留給實作者

- 拖拉與甘特圖套件的選擇：授權免費、可商用、維護中，觸控可用；寫進計畫。甘特圖也可以不用套件，用 CSS grid 自畫。
- `ConfigJson` 的欄位命名與 `version` 升級方式。
- 報表資料來源介面的確切形狀（只要模組來源的行為與測試完全不變）。
- 看板欄查詢是一次回全部欄，還是每欄各一個請求。
- 可見條件在 PostgreSQL 的執行計畫（`OR` 很多時要不要改 `UNION`），以雙跑與計畫輸出決定。
- 內建報表的四語系名稱與說明文案、圖表配色。
- 手機「移到…」是底部選單還是對話框。
