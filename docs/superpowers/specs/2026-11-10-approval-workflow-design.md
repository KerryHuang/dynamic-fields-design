## 1. 目的與範圍

### 1.1 使用者要求

使用者 2026-11-08 的要求：

- 「以市場上的簽核的設計流程，可以由用戶自行定義簽核流程的方式」。
- 以 ERP 系統為設計基準，功能要設計清楚。
- 直接提一版設計，不再逐項提問；主控代為決定的地方要標出來。
- 組織骨架（部門樹、部門主管、使用者所屬部門）放在核心，HRM 往上加；組織寫成獨立一章，排程上先做組織、再做簽核。

### 1.2 對路線文件的變更

這份設計**推翻**路線文件的兩處，路線文件已同步修改：

| 位置 | 原本 | 改成 |
|---|---|---|
| 這版不做・平台類 | 含「多層簽核」 | 拿掉多層簽核 |
| 核心能力表 | 單層簽核（階段 4） | 可自訂簽核流程、組織架構（階段 4） |
| 階段 4 | 單層簽核 | 組織架構、可自訂簽核流程 |

理由：單層簽核（一張單一個人點同意）在市場上已經不是「簽核」的基本盤。小企業最常見的需求是「金額大於某門檻要多一關」「請假超過三天要上兩層主管」，這兩個都是條件式多關。先做單層、之後再擴成多層，資料結構要改兩次；一次把「條件式依序多關」做對，比較省。並行分支仍延到第二版（§16）。

職務分離（同一人不能同時建單與核准以外的其他控管）仍不做，只做「發起人不能簽核自己送出的單」這一條（§10.3）。

### 1.3 範圍

做：

- 組織骨架（核心）：部門樹、部門主管、使用者所屬部門（§11）。
- 簽核流程定義：掛在狀態機的轉移上，條件式選流程、條件式依序關卡（§4 到 §6）。
- 簽核動作：同意、退回、撤回、轉交、後加簽、代理人；全部寫進歷程（§7）。
- 簽核期間的記錄鎖定與可編輯欄位（§9）、簽核人的臨時讀取權（§10）。
- 站內通知的簽核事件與逾期提醒（§12）。
- 設計器、執行期與簽核中心的畫面（§13）。
- 套件格式延伸：內建應用程式可宣告預設簽核流程（§14）。

不做（第一版）：視覺化並行分支（§16 有預留）、逾時自動同意或自動退回、抄送、簽核意見附件、電子簽章、Email／推播通知、對外 API 的簽核回呼。

### 1.4 鐵則（沿用）

- **ERP 邏輯不寫死**：核心程式碼不出現請假、報支、採購這些名詞；流程完全由使用者在設計器定義，內建應用程式只提供預設流程範本（§14.3）。
- 所有簽核行為**由後端驗證**，前端只縮小選項。
- 權限**不 fail-open**：解析不到簽核人、流程定義失效、權限資料缺漏，一律落在「不放行」的一邊。
- **不做執行期 DDL**：新資料表只走 EF migration。
- **空系統是合法起點**：沒開任何應用程式時，組織與簽核照樣可用；平台任何功能不依賴特定應用程式。
- 能力檢驗：同一個能力至少兩個不相干的應用程式用得上。簽核用在請假（HRM）、費用報支（會計／HRM）、採購單（進銷存）三個情境（§17）。

## 2. 市場對照

### 2.1 三家怎麼做

**Odoo Approvals。** 以「簽核類型」（approval category）為單位，每個類型設定簽核人清單、最少核准數、是否需要員工的主管；簽核請求是一張獨立的單，不直接掛在業務單據上。採購單要金額門檻，靠採購模組自己的「兩段式核准」設定，或用自動化規則（automated actions）依內容改路由。主管來自 HR 的員工主檔（`hr.employee.parent_id`）。

**SAP S/4HANA Flexible Workflow。** 以業務物件的情境（scenario）為單位，可定義多個流程，各有**啟動條件**（例如金額 ≥ 門檻），依序比對取第一個符合的；流程由**依序步驟**組成，每步可再設步驟條件（不符合就略過），簽核人可直接指定，或用規則決定（團隊與職責、BAdI 擴充）。進行中的實例綁定啟動時的流程版本。

**釘釘、飛書審批。** 視覺化流程設計器，節點有：條件分支、並行分支、會簽（全部同意）、或簽（一人同意即可）、依序簽；簽核人來源有指定成員、角色、發起人自選、直屬主管、連續多級主管、表單上的成員欄位；動作有同意、退回（給發起人或指定節點）、撤回、轉交、加簽（前加簽、後加簽）、代理；找不到主管時可設「自動通過」「轉給管理員」。

### 2.2 Formwright 的取捨

| 項目 | 取自 | Formwright 第一版 |
|---|---|---|
| 多個流程、啟動條件、優先序 | SAP | 做 |
| 依序關卡、關卡條件（不符跳過） | SAP | 做 |
| 簽核人來源：指定、群組、主管、往上 N 層、表單欄位、發起人自選 | 釘釘／飛書 | 做 |
| 會簽、或簽 | 釘釘／飛書 | 做 |
| 最少核准數（N 中選 K） | Odoo | 不做 |
| 退回、撤回、轉交、代理 | 三家共通 | 做 |
| 加簽 | 釘釘／飛書 | 只做後加簽 |
| 並行分支、視覺化流程圖 | 釘釘／飛書 | 第二版 |
| 獨立的簽核請求單 | Odoo | 不做，掛在單據轉移上 |
| 規則外掛決定簽核人 | SAP BAdI | 不做，留擴充點 |
| 逾時自動處理 | 釘釘／飛書 | 只做逾期提醒 |

取捨的理由：

1. **掛在單據的狀態轉移上，不做獨立的簽核單（主控判斷）。** Odoo 的獨立簽核單在「請一筆錢」這類情境很方便，但核准後要人工去改原單據狀態，兩邊會不一致。Formwright 的單據都有狀態機（單據能力設計 §3），轉移本來就是「誰能把這張單推進到下一步」的唯一閘門；把簽核放在這道閘門上，核准等於轉移生效，事件、分錄、檢查照舊跑（§8），不會有兩套狀態要對帳。要做 Odoo 那種「一般簽核單」，就建一個只有標題、說明、金額的模組，掛狀態機與簽核流程即可，不需要另一套機制。
2. **條件式依序關卡（SAP 的形狀）當第一版，並行分支延後。** 50 人以下的公司，九成的流程是一條直線加幾個門檻；並行（例如法務與財務同時審）可以先用「會簽一關、兩個群組各出一人」近似（§16.1）。依序結構好驗證、好顯示、好在手機上編輯；並行要處理匯流、部分退回、圖形編輯，成本高一個量級。
3. **簽核人來源照釘釘／飛書的清單。** 這是使用者最熟悉的分類，而且每一種都對應到核心已有或本次補上的資料：使用者、群組（已有）、部門主管（§11 新增）、使用者欄位（`FieldType.User`，已有）。
4. **只做後加簽（主控判斷）。** 前加簽（「先給某人看過再回到我」）會讓目前關卡暫停、插入的人處理完再回來，任務狀態要多一種「暫停」；後加簽只是「我同意，之後再加一關」，就是在目前關卡後面插一關，資料結構不用變。
5. **不做最少核准數。** 會簽與或簽涵蓋大多數情境；「三人中兩人同意」在小企業少見，需要時列第二版（關卡 `mode` 預留為字串，可擴成 `{ "atLeast": 2 }`）。

## 3. ERP 對照

| ERP 情境 | 典型流程 | Formwright 表達方式 |
|---|---|---|
| 請假 | 直屬主管；超過 3 天再上一層 | 一個流程兩關，第二關條件「天數 > 3」，來源「往上第 2 層主管」 |
| 加班、出差申請 | 直屬主管 | 一個流程一關 |
| 費用報支 | 直屬主管 → 財務；金額大再加總經理 | 一個流程三關，財務關可改「核定金額」，第三關條件金額門檻 |
| 請購 | 部門主管 → 採購 | 兩關，第二關來源群組 |
| 採購單 | 依金額分級：小額免簽、中額採購主管、大額再加總經理 | 兩個流程依優先序比對；都不符合則直接轉移 |
| 報價折扣 | 折扣超過權限才需主管 | 流程啟動條件「折扣率 > 10%」 |
| 付款申請 | 會計 → 主管 → 出納 | 三關依序 |
| 合約審閱 | 業務主管與法務都要看 | 第一版：一關會簽（兩個群組）；第二版：並行分支 |
| 新進人員帳號、IT 申請 | 申請人自選審核人 | 來源「發起人自選」，候選限定群組 |
| 單據作廢 | 已核准的單要作廢須主管同意 | 把「已核准 → 取消」這條轉移設為需簽核 |

ERP 對照的觀察：

- 主流 ERP 都把「依金額分級」「依天數加關」當成基本盤，所以**啟動條件與關卡條件都要在第一版**。
- 「主管」幾乎出現在每一個人事與費用流程裡；沒有組織骨架，這些流程只能退化成「指定群組」，每換一個部門就要多一個群組。這是 §11 組織骨架要先做的原因。
- 「簽核中可改部分欄位」在費用報支（財務改核定金額、會計科目）與請購（採購填建議廠商）是常見需求，所以第一版就做可編輯欄位（§9.2）。
- 「作廢也要簽」說明簽核不只能掛在「草稿 → 核准」，任何一條轉移都要能掛（§5.1）。

## 4. 概念模型

### 4.1 名詞

| 名詞 | 意思 |
|---|---|
| 簽核流程（flow） | 使用者在設計器定義的流程：掛在哪個目標狀態、啟動條件、優先序、關卡 |
| 流程版本（flow version） | 流程定義的一個不可變快照；實例綁定版本 |
| 關卡（stage） | 流程裡的一步：條件、簽核人來源、模式、可編輯欄位 |
| 簽核實例（instance） | 某筆記錄的一次送簽；從送出到核准、退回、撤回或終止 |
| 關卡實例（stage run） | 實例中某一關實際的執行，含被跳過、被退回重來 |
| 任務（task） | 指派給某一位使用者的待辦；會簽一關有多個任務。畫面上稱「待簽核」，以免與任務管理的「任務」混淆（見 `2026-11-10-task-management-design.md` §11） |
| 簽核歷程（action log） | 每一個動作的不可修改紀錄：誰、何時、做了什麼、意見 |
| 代理設定（delegate） | 使用者在某段期間把新進任務交給另一人 |
| 可編輯狀態 | 起始狀態，以及設計者在狀態機上明確標記「可編輯」的狀態（§9.3） |
| 簽核鎖定狀態 | 需簽核轉移的目標狀態，以及從那裡沿一般轉移、不經過可編輯狀態就走得到的後續狀態（§9.3） |
| 流程快照（flow set snapshot） | 送出時目標狀態上所有流程的完整定義（關卡、條件、簽核人來源）與優先序、啟停狀態，存在實例上（§4.4） |
| 席位（seat） | 會簽關卡中要湊滿的一票；備援頂替的來源佔一個席位（§6.5） |

關係：一個目標狀態有零到多個流程，套用到所有進入它的需簽核轉移（§5.2）；一個流程有多個版本；一筆記錄同時最多一個進行中的實例；一個實例有多個關卡實例；一個關卡實例有一到多個任務；所有動作寫進歷程。

### 4.2 與狀態機的關係（主控判斷）

**簽核掛在單據狀態機的轉移上，不另做一套平行的狀態。**

- 狀態機的轉移（`WorkflowTransition`，現有 `From`、`To`、`GroupIds`）加一個選用設定 `approval`，標記「這條轉移需要簽核」。
- 使用者「送出簽核」時建立實例；記錄的狀態欄位**維持在 `from`**，直到全部關卡通過，系統才把狀態改成 `to`（真正執行轉移，事件、分錄、檢查照舊，§8）。
- 退回給發起人時，實例結束，記錄轉到流程設定的退回狀態（可以就是 `from`，即不動）。
- 「簽核中」不是狀態機的一個選項，而是「這筆記錄有進行中的實例」這個事實；畫面上用徽章顯示（§13.3）。

為什麼不要求設計者建「簽核中」狀態：那樣狀態機會被迫為每個需簽核的轉移多一個中間狀態，而且「中間狀態 → 核准」這條轉移就變成誰都能點，等於把簽核繞過去。現有 CRM 與 MES 報價單用「待核 → 已核准（限 manager 群組）」手工模擬單層簽核，這個做法仍然合法，本設計不強迫遷移（§20.1 第 11 項）。

### 4.3 資料結構草案

全部是新資料表，走一次 EF migration `ApprovalWorkflow`；組織骨架另一次 migration `Organization`（§11.3）。

**`Dynamic_ApprovalFlow`（流程，可改）**

| 欄位 | 說明 |
|---|---|
| `Id`、`Key` | `Key` 全站唯一，2 到 40 字，慣例以應用程式 id 當前綴 |
| `NameI18n` | 多語系名稱 |
| `ModuleId`、`ToOptionId` | 掛在哪個目標狀態；套用到所有進入它的需簽核轉移；被實例用過後不能改（§5.2） |
| `Priority` | 同一目標狀態內的比對順序，小的先比 |
| `Active` | 停用的流程不參與新送出的比對；進行中實例看自己的流程快照（§5.5） |
| `CurrentVersionId` | 目前生效的版本 |
| 稽核欄位 | 同 `AuditableEntity` |

唯一索引 `(ModuleId, ToOptionId, Priority)`。

流程掛在**目標狀態**而不是單一轉移（第二輪審查必修 9，主控裁決，待使用者確認；掛法是修訂時選的實作方式）：進入同一狀態的所有需簽核轉移，流程集合因此在結構上就相同，不靠設計者逐條掛齊（§5.2）。

**`DefinitionJson`**

```json
{
  "shape": "sequence",
  "when": { "all": [ { "field": 21, "op": "gte", "value": 10000 } ] },
  "rejectTo": 11,
  "fallbackApprovers": { "source": "group", "groupIds": [7] },
  "stages": [
    { "code": "mgr", "name": { "zh-TW": "直屬主管" },
      "when": null,
      "approvers": { "source": "manager", "level": 1 },
      "mode": "any",
      "editableFields": [],
      "dueHours": 24,
      "onEmpty": "fallback" },
    { "code": "fin", "name": { "zh-TW": "財務" },
      "when": null,
      "approvers": { "source": "group", "groupIds": [5] },
      "mode": "any",
      "editableFields": [31, 32],
      "dueHours": 48,
      "onEmpty": "fallback" },
    { "code": "ceo", "name": { "zh-TW": "總經理" },
      "when": { "all": [ { "field": 21, "op": "gt", "value": 50000 } ] },
      "approvers": { "source": "users", "userIds": ["u-ceo"] },
      "mode": "any", "editableFields": [], "dueHours": null, "onEmpty": "fallback" }
  ]
}
```

| 屬性 | 說明 |
|---|---|
| `shape` | 第一版只能是 `sequence`；第二版加 `graph`（§16.2） |
| `when` | 流程啟動條件，核心既有的規則條件語法（`ConditionParser`／`ConditionEvaluator`）；null 代表一律符合 |
| `rejectTo` | 退回給發起人時記錄轉到的狀態選項 Id；null 代表留在 `from` |
| `fallbackApprovers` | 關卡找不到人時的備援簽核人（§6.5）；省略代表系統管理員 |
| `stages[]` | 至少 1 關，至多 10 關，依序 |
| `stages[].code` | 流程內唯一，`^[a-z][a-z0-9-]{0,39}$` |
| `stages[].when` | 關卡條件，不成立就跳過；null 代表一律進入 |
| `stages[].approvers` | 簽核人來源（§6） |
| `stages[].mode` | `all`（會簽）或 `any`（或簽） |
| `stages[].editableFields` | 這關的簽核人可以改的欄位 Id（§9.2） |
| `stages[].dueHours` | 逾期提醒的時數；null 代表不提醒 |
| `stages[].onEmpty` | 解析不到人：`fallback`（預設）或 `skip` |

**`Dynamic_ApprovalInstance`（實例）**

### 4.4 流程版本（主控判斷）

**設定變動只影響之後送出的單**（第三輪審查必修 3 改寫，取代第二輪的「在下一次同意時生效」，主控裁決，待使用者確認）。新增流程、調整優先序、停用、改版，都不影響進行中的實例。

- **「被用過」的定義**（第四輪核對必修 A，主控裁決，待使用者確認）：一個流程版本被任何實例綁定（實例的 `FlowVersionId`），**或出現在任何實例的流程快照裡**，就算被用過；流程有任何一個版本被用過，流程就算被用過。這個定義套用到四處：建新版本（這一條）、刪除與改目標狀態（下面與 §5.2）、欄位刪除保護（§8.6）。只看綁定會漏掉快照裡沒被選中的高優先序流程：它被原地覆寫或刪除，重新比對讀到的就是新內容或什麼都沒有。
- 儲存流程時，若目前版本**已被用過**，就新增一個版本並把 `CurrentVersionId` 指過去；沒被用過就直接覆寫目前版本（避免設計期間反覆存檔產生一堆版本）。
- 實例建立時記下 `FlowVersionId`，之後的關卡條件、簽核人來源、可編輯欄位一律讀這個版本。
- 實例建立時同時記下**流程快照**（`FlowSetSnapshotJson`）：目標狀態上每個流程的 id、版本 id、優先序、啟停狀態，以及該版本**完整的定義內容**（啟動條件、關卡、關卡條件、簽核人來源、可編輯欄位、退回狀態、備援簽核人；第四輪核對必修 A，主控裁決，待使用者確認）。之後每次同意的重新比對只讀快照裡的內容，不讀流程與版本表的現行定義（§5.5），所以設定變動不會讓進行中的實例改走較寬鬆的流程，也不會改走較嚴格的流程。存內容而不只存 id，是讓快照不依賴版本表的保護規則才成立；保護規則（上一條）仍然保留，避免快照引用的欄位被刪掉後條件無法求值。
- 管理員要讓新定義套用到進行中的單，就終止實例、請發起人重送（§7.8）。
- 被用過的流程不能刪除，也不能改目標狀態，只能停用（`Active = false`）；沒被用過的可以刪除。刪除與停用都要通過 §5.2 的入口檢查。
- **版本凍結的是定義，不是外部資料。** 「直屬主管」在關卡啟動時才依當下的組織解析（§6.2），所以組織異動會影響尚未啟動的關卡；群組成員、使用者欄位同理。這和 SAP、釘釘的行為一致：流程形狀固定，人依當下組織決定。
- 欄位被流程版本引用時，欄位的停用與刪除檢查要涵蓋**所有被進行中實例使用的版本**，不只目前版本（§8.6）。

## 5. 流程的啟動與比對

### 5.1 哪些轉移能掛簽核

- 模組必須有狀態機；轉移必須已定義。沒有狀態機的模組要先在設計器建狀態機，畫面提示這一點。
- 任何一條已定義的轉移都能設為需簽核，包含「已核准 → 取消」這類作廢轉移。
- 明細模組、擴充模組沒有狀態機（單據能力設計 §3.1），因此也沒有簽核。
- 分錄模組不能有狀態機（事件設計 §6.1），因此也沒有簽核。

### 5.2 送出時比對流程

使用者在「需簽核」的轉移上按送出：

1. 先照既有的狀態機規則檢查轉移資格（`WorkflowEnforcer`：轉移已定義、使用者在轉移的群組內或為系統管理員、模組 Edit 權限）。**送出的資格就是原本執行這條轉移的資格**，簽核不新增送出權限。
2. 取掛在這條轉移目標狀態 `to` 上所有啟用中的流程，依 `Priority` 由小到大，用**送出當下的記錄值**對目前版本的 `when` 求值，取第一個符合的。建立實例時把這時的流程集合存成流程快照（§4.4）。
3. 都不符合時，依轉移的 `approval.noMatch`：
   - `block`（預設，主控判斷）：送出失敗，回 400，訊息「沒有符合條件的簽核流程，請聯絡管理員」。
   - `direct`：不需簽核，轉移直接生效（走一般的轉移寫入，事件照跑）。

預設 `block` 的理由：設計者既然把轉移標成需簽核，「沒有流程接得住」通常代表條件沒寫周全，應該讓人看見，而不是默默放行（不 fail-open）。「小額免簽」要明確選 `direct`，設計器在選 `direct` 時顯示說明「條件都不符合的單據會直接轉移，不經任何人同意」。

`direct` **只在「真的沒有任何流程符合」時生效**：流程不會因為設定缺漏（群組對不上、欄位被取消勾選、找不到簽核人）而被當成不存在，這些情況一律改派備援或擋下（§6.5、§14.4），不會掉到 `direct`。

**流程由系統依優先序決定，發起人不能挑流程**（第一輪審查，主控裁決，待使用者確認）。送出端點不收流程鍵；預覽只顯示系統選中的那一個。

**進入同一狀態的轉移，需簽核開關與流程都要一致**（第一輪審查，第二輪審查必修 9 補強，主控裁決，待使用者確認）。狀態 S 只要是任何需簽核轉移的 `to`：

- 所有以 S 為 `to` 的轉移都必須需簽核。
- 所有以 S 為 `to` 的需簽核轉移，掛載的流程集合都相同。流程掛在目標狀態上（§4.3），所以這一條由結構保證：同一組流程套用到每一個入口。
- 需簽核轉移的目標狀態上沒有掛任何流程，轉移不能存。入口含 `noMatch = direct` 時，還要至少有一個**啟用中**的流程，因為全部停用等於整條入口免簽；全部是 `block` 的入口，流程全停用只會讓送出被擋下，不會少簽，所以允許。

**進入鎖定狀態一律要簽**（第三輪審查必修 2，主控裁決，待使用者確認）：

- 凡是從非鎖定狀態進入任何簽核鎖定狀態（§9.3，起點或延伸出來的下游都算）的轉移，都必須需簽核，沒有例外。例如設計者加了一般轉移「草稿 → 部分進貨」，儲存狀態機回 400：部分進貨是鎖定狀態，草稿的單不能不簽就跳進去。
- 起始狀態不能是鎖定狀態；否則新建、匯入、轉換產生的單一出生就在核准後的狀態。

`rejectTo` 指定狀態時，每一個進入 S 的需簽核轉移，其 `from → rejectTo` 都要是已定義、而且不需簽核的轉移（`rejectTo` 等於該 `from` 時視為留在原地，§8.3）；null 則一律留在 `from`。`rejectTo` 是鎖定狀態而 `from` 不是時不能存，否則退回會讓單據不簽就進入鎖定狀態。

**入口或流程變動時，全部約束重新驗證**（第三輪審查必修 4，主控裁決，待使用者確認）。入口集合由狀態機決定，在狀態機加一條入口，就可能讓原本合法的流程失效。所以下列三種儲存，都要對每個目標狀態上的每一個流程、每一個入口，重算這一節的全部約束：

- 儲存狀態機（含新增、刪除轉移，改需簽核開關、`noMatch`、狀態的 `editable` 旗標）。
- 儲存流程。
- 修改流程的目標狀態（只限沒被用過的流程，定義見 §4.4，見下一段）。

重算的約束：入口一致性與流程數量（上面三條）、進入鎖定狀態一律要簽、起始狀態不是鎖定狀態、每個入口的 `from → rejectTo` 規則、可編輯欄位的 `from` 不能是唯讀或鎖定狀態（§9.2）、可編輯欄位的閉包（§9.2）。任何一條不通過就拒絕儲存，回 400 並指出流程、轉移或狀態。套件驗證 V6 做同樣的檢查（§14.4）。

**會讓流程集合變小的操作**（第三輪審查必修 5，主控裁決，待使用者確認）：

- 被用過的流程（被綁定或出現在任何實例的快照裡，§4.4）只能停用，不能刪除，也不能修改目標狀態；要換目標狀態就建新流程。這也讓實例的 `ToOptionId` 與流程的 `ToOptionId` 永遠一致。
- 停用、刪除、改目標狀態都要重算上面的流程數量規則：會讓某個 `direct` 入口的目標狀態沒有任何啟用中的流程，或讓某個需簽核轉移的目標狀態沒有任何流程，就回 400，要先關掉轉移的需簽核或改成 `block`。

理由：「草稿 → 已核准」需簽核、「已退回 → 已核准」不需，第二條入口開了需簽核卻沒掛流程、`direct` 直接放行，或剛建好的流程被刪掉，都等於留了一條不必簽就能進核准狀態的路；§9.3 的簽核鎖定也靠這幾條規則才成立。

**執行時再驗一次，fail closed**（第三輪審查必修 4，主控裁決，待使用者確認）。儲存時的驗證防的是設定錯誤，執行時的驗證防的是驗證漏洞或資料不一致。系統以系統身分走退回或核准轉移之前（§8.2、§8.3），再檢查一次：

- 要走的轉移必須是狀態機上已定義的轉移；退回轉移必須不需簽核。
- 退回的目標不能讓單據跳過簽核進入鎖定狀態：`rejectTo` 是鎖定狀態而 `from` 不是時不執行。
- 驗證不過時，動作回 409、整筆回滾，實例停在原處；回滾後另開一筆交易寫通知給系統管理員（說明實例、轉移與原因），由管理員修正狀態機或終止實例。

**用狀態欄位區分入口**（第三輪審查必修 7，主控裁決，待使用者確認）。同一個目標狀態的所有入口共用同一組流程；要讓不同入口走不同的簽核，就在 `when` 裡引用狀態欄位。送出與重新比對時記錄都還停在 `from`，所以條件判斷得出是從哪個入口進來。例如採購單的已確認有兩個入口：

- 流程 A（優先序 1）：`when 總額 ≥ 100000`，含總經理一關。不分入口，大額單一律先比到它。
- 流程 D（優先序排在 A 之後、B 之前）：`when 狀態 = 變更中 且 總額 < 100000`，只簽一關主管（`purchaseLead`）。從變更中重送的中小額變更單走這一條。
- 流程 B：照金額分級，從草稿進來的中額單照舊。

D 排在 A 之後，所以從變更中送出的單只要總額 ≥ 100000，照樣先符合 A、要總經理簽；D 只放寬中小額，不會蓋過金額分級（第四輪核對必修 B，主控裁決，待使用者確認）。範例刻意不用「原核准總額」這類輔助欄位：那種欄位要由系統在核准時寫入，會碰到 §8.5 的鎖定後盾，放在可編輯狀態又能被發起人一起改。

狀態欄位因此可以出現在條件裡，但不納入鎖定欄位，也不納入可編輯欄位的閉包（§9.2、§9.3）：狀態本來就由狀態機、送出端點（§5.3）與這一節的規則控制。

### 5.3 一般存檔不能繞過

狀態變更仍可以走 `PUT /records/{id}`（單據能力設計 §3.2），但**目標轉移是需簽核的轉移時，一律回 400**（鍵為狀態欄位，訊息「這個狀態需要送出簽核」），連系統管理員也一樣。唯一入口是送出端點（§15）。`noMatch = direct` 也走送出端點，由後端判斷要建立實例還是直接轉移；這樣前端只有一種按鈕，判斷全在後端。

匯入、單據轉換產生的新單從起始狀態開始，不涉及轉移；匯入的列若狀態欄位不是起始狀態，既有規則已回 400。

**事件不能推動需簽核的轉移。** 事件的 `update` 效果若 `set` 狀態欄位的常數值，使目標記錄走到需簽核的轉移：

- 定義時：儲存事件、或把轉移設為需簽核時，交叉檢查，命中就回 400，指出事件鍵與轉移。
- 執行時（後盾）：事件效果寫入的記錄若發生需簽核的轉移，整筆回滾 409。後盾辨認「這是簽核完成的轉移」靠寫入日誌上的實例標記（§8.5），不靠系統身分：最後一關同意與事件效果都用系統身分，只看身分分不出來。

### 5.4 送出前預覽

送出對話框先呼叫預覽端點（§15），後端以和送出相同的邏輯試算（不寫入）：會用哪個流程、每一關目前會不會跳過、目前解析到誰、哪一關需要發起人自選。預覽只是顯示；送出時後端重新計算。

預覽的資訊揭露：關卡條件可能引用發起人看不到的欄位（欄位隱藏權限），「第三關會不會跳過」本身就洩漏了該欄位的範圍。處理（主控判斷）：預覽只回傳「關卡名稱、目前解析到的簽核人」，**不回傳跳過的理由與條件內容**；條件引用的欄位若對發起人隱藏，該關在預覽中標示為「依條件決定」，不說會不會跳過。這和核心既有的規則推論風險（核心設計風險 24）同性質，列在 §18。

### 5.5 每次同意都重新比對流程（第一輪審查，主控裁決，待使用者確認）

送出後記錄雖然鎖住，值仍可能變：其他模組的子記錄讓彙總變大（§8.5）、公式引用的參照記錄被改、條件用了「今天」。為了不讓單據因此少簽一關：

1. **每一次同意**（含同意並加簽、含最後一關）在同一個交易內，寫入可編輯欄位之後、推進關卡之前，用當下的記錄值重新算出這張單「應走的路線」。重新比對只因**資料**變動而有不同結果，設定變動不會影響它。
2. **選流程只看快照**（第三輪審查必修 3，取代第二輪必修 6 的寫法，主控裁決，待使用者確認）：
   - 候選流程是實例的流程快照（§4.4）裡、送出時啟用中的流程，依快照記下的優先序，用快照裡存的**定義內容**求 `when`，取第一個符合的；不回頭讀流程與版本表的現行定義（第四輪核對必修 A）。
   - 送出後新增的流程、調整的優先序、停用、改版、原地覆寫，一律不看；流程現在是否啟用也不看。
   - 例如總額 150000 走流程 A、停在第 1 關，設計者新增優先序 0 的流程 Z（`when 總額 ≥ 1000`，一關），或把流程 B 上移到 A 前面：快照裡沒有 Z、B 仍排在 A 後面，第 1 關同意時照流程 A 推進，總經理那一關還在。
3. **比對完整路線**（第二輪審查必修 5，主控裁決，待使用者確認）：路線包括流程 id、版本、會生效的關卡集合、各關卡的簽核人來源，不只比 `FlowId`。實務上：
   - 流程或版本不同，就是路線不同。
   - 流程與版本相同時，用當下的值重算**目前關卡之前**每一個 `SkipReason = condition` 的關卡條件；任何一關從「不成立」變成「成立」，就是路線不同。前面已同意的關卡條件變成不成立，不算不同（多簽不算少簽）。目前關卡之後的關卡輪到時才求值（§7.2），不必在這裡比。
   - 路線相同：照常推進。
4. 路線不同：**這次同意不計入**，交易照樣提交以下變更：
   - 舊實例結束為 `rerouted`，所有 `open` 任務關閉，歷程記一筆 `reroute`，說明「單據內容已變，改用流程「{新流程}」重新簽核」。
   - 依新路線建立新實例（`RestartedFromInstanceId` 指向舊實例，發起人不變），從第一關開始，照 §6 解析簽核人。新實例沿用舊實例的流程快照，不重新取目前的流程集合；否則重來就成了讓新設定生效的後門。
   - 通知發起人與舊實例中已經同意過的人（§12）。
   - 回應 200，本文 `outcome: "rerouted"`，畫面提示「你的同意未計入，流程已重新開始」。這裡不用 4xx：4xx 會讓管線整筆回滾，重來的實例就建不起來。
5. **快照裡都沒有流程符合時 fail closed**（第二輪審查必修 6，第三輪審查必修 3 改寫，主控裁決，待使用者確認）：轉移仍需簽核，進行中的實例**不套** `noMatch = direct`。舊實例結束為 `rerouted`，新實例的 `RouteKind = fallback`，只有一關，由舊流程綁定版本的 `fallbackApprovers` 或簽（解析規則同 §6.5，仍為空就 409）。新實例沿用舊實例的流程快照。備援簽核人同意時同樣在快照裡重新比對：有流程符合就改走那個流程；仍然沒有就核准並執行轉移。`direct` 只在送出時判斷。
6. 新流程含發起人自選關卡（發起人不在場，無法自選）：舊實例結束為 `rerouted`，**不自動建新實例**，記錄解除簽核中的唯讀、停在 `from`，通知發起人重新送出。`from` 本身是簽核鎖定狀態時（例如作廢簽核），鎖定照 §9.3 繼續。
7. 簽核中只有可編輯欄位能被人改，而可編輯欄位不得直接或間接影響任何條件（§9.2），所以實務上會觸發重來的只有靜默更新與時間條件；每次靜默更新都留歷程（§8.5），簽核人看得到金額為什麼變了。

送出、退回、撤回、轉交不重新比對：送出本來就是比對；退回、撤回、轉交不會讓單據往核准前進。

## 6. 簽核人解析

### 6.1 來源

| `source` | 參數 | 解析結果 |
|---|---|---|
| `users` | `userIds` | 指定的使用者 |
| `group` | `groupIds` | 這些群組的全部成員 |
| `manager` | `level`（1 到 5） | 發起人往上第 `level` 層主管 |
| `userField` | `fieldId`、`candidateGroupIds` | 記錄上使用者欄位（`FieldType.User`）的值，限候選群組 |
| `initiatorPick` | `candidateGroupIds`、`min`、`max` | 發起人送出時自選；可限定候選群組 |

共同規則：

- 只取**啟用中**的使用者（`AppUser.IsActive`）；停用的帳號不會收到任務。
- 每關解析結果至多 20 人。`users` 指定超過 20 人，儲存流程時回 400；群組成員數要到執行時才知道，關卡啟動時超過 20 人就讓該動作回 409 並指出關卡，整筆回滾（不截斷名單，截斷會讓會簽少了人）。20 人對 50 人以下的公司已經很寬；會簽一個 20 人的群組沒有實務意義。
- 解析結果去重。
- `userField` 的欄位必須是本模組表頭的使用者欄位；值為空就是「找不到人」。
- `userField` 等於讓發起人在送出前自己填簽核人，所以**必須設定 `candidateGroupIds`**（第二輪審查建議 4，主控裁決，待使用者確認），沒設定時儲存流程回 400。送出時，欄位填的人不在候選群組、或填的是發起人自己，送出回 400（鍵為該欄位）。關卡啟動時再驗一次（群組成員可能已異動），不符就當成這個來源找不到人（§6.5）。
- `initiatorPick`：`min` 至少 1、`max` 至多 20；選的人必須是候選群組成員（沒有限定候選群組時，任何啟用中的使用者都可選）。後端驗證，不信任前端名單。自選的結果存在實例裡，關卡啟動時直接用；退回上一關再回來時沿用，不再問一次。

### 6.2 主管的解析

依 §11 的組織骨架：

1. 取發起人的所屬部門 D（第一版一人一個部門，§11.2）。發起人沒有部門就視為「找不到人」。
2. **第 1 層主管**：D 的主管；若 D 的主管就是發起人本人，或 D 沒有主管，就往 D 的上級部門找，直到找到一位「不是發起人」的主管，或到樹根為止。
3. **第 N 層主管**：從第 N−1 層主管所在的那個部門往上找，規則同第 2 步（跳過主管空缺、跳過發起人本人）。
4. 到樹根仍找不到，就是「找不到人」。

這是釘釘、飛書的「主管空缺自動往上」行為。「部門主管就是發起人」是最常見的特例（課長請假要給經理簽），所以內建在規則裡，不需要設定。

「連續多級主管（直到第 N 層）」不單獨做成一種來源：設計者建 N 個關卡，各自 `level` 1 到 N 即可；同一個人因為主管空缺被解析到兩次時，見 §6.4。

### 6.3 解析時機（主控判斷）

**關卡啟動時才解析，不在送出時一次解析全部。**

- 送出時只做兩件事：比對流程、啟動第一個不被跳過的關卡；預覽（§5.4）是試算。
- 每關啟動時，依當下的記錄值求關卡條件、依當下的組織與群組解析簽核人。

理由：簽核可能跨好幾天，期間主管異動、有人離職停用；送出時就把十關的人都定死，會把任務派給已經不在的人。代價是發起人在預覽看到的人可能與最後實際簽的人不同；畫面上註明「實際簽核人依當時的組織決定」。

例外：`initiatorPick` 在送出時就選定（發起人只在送出時在場）。

### 6.4 解析到發起人（主控判斷）

**發起人不能簽核自己送出的單。** 解析結果含發起人時：

| 來源 | 處理 |
|---|---|
| `manager` | 解析規則本身已跳過發起人（§6.2） |
| `group`、`users` | 從名單移除發起人；剩下的人照常派任務 |
| `userField` | 送出時填自己回 400（§6.1） |
| `initiatorPick` | 候選清單不含發起人，送出時選自己回 400 |

某個來源移除發起人後變空，就當成這個來源「找不到人」處理（§6.5）。系統管理員也一樣，不因為是管理員就能核准自己的單。

**同一人連續出現在兩關（主控判斷：不自動略過）。** 例如第一關直屬主管與第二關「主管群組」都含同一人，他要簽兩次。理由：每一次同意都要留下明確紀錄；自動略過會讓「這關到底誰簽的」變得模糊。列 §20.1 第 5 項。

### 6.5 找不到人：逐一處理每個來源（第二輪審查必修 1 改寫，主控裁決，待使用者確認）

一關的簽核人由一到多個**來源單位**組成，關卡啟動時各自解析：

| 來源 | 來源單位 |
|---|---|
| `group` | 每一個群組 |
| `users` | 每一位使用者 |
| `manager`、`userField` | 整個來源算一個 |
| `initiatorPick` | 每一位被選的人 |

某個單位解析為空（沒有部門、主管全空、群組沒有成員、群組在開啟套件時被略過、使用者被停用、使用者欄位空或不在候選群組、或只剩發起人），就由**備援簽核人頂替這個單位**，不能因為名單裡還有別人就略過它：

- 會簽（`all`）：每位解析到的人各是一個席位；每個被頂替的單位另佔一個**備援席位**，由流程的 `fallbackApprovers`（省略時為所有啟用中的系統管理員）各建一個任務，同席位任一人同意即滿足。會簽要的票數不因頂替而減少。例如來源 `group [board, purchaseLead]` 的 `board` 找不到人，這關要 `purchaseLead` 的成員與一位備援簽核人都同意。
- 或簽（`any`）：被頂替的單位把備援簽核人加進候選名單，仍然是任一人同意就完成。
- 任務 `Reason = fallback`，歷程記一筆「來源 {群組或欄位} 找不到簽核人，依設定改派備援簽核人」。
- 備援名單移除發起人，也移除這關已經有任務的人（會簽一人一票，§7.7）；仍然為空（例如唯一的系統管理員就是發起人）時，**送出或推進的那個請求失敗，回 409**，訊息說明哪一關、哪個來源找不到簽核人，整筆回滾。

關卡的 `onEmpty`：

- `fallback`（預設，主控判斷）：照上面頂替。
- `skip`：**只有整關所有來源單位都解析為空時**才跳過，`SkipReason = empty`，歷程記一筆。部分單位為空一律頂替，不看 `onEmpty`。設計者要明確選才會跳過。
- 來源帶有對不上的單位（§14.4 的 `UnmatchedGroups`、`CandidatesUnmatched`）時不算「解析為空」：一律交給備援、沒有備援就 409，不跳關；驗證器也拒絕這類關卡設 `skip`。`initiatorPick` 的候選群組對不上時，依 `min` 產生同樣數量的空單位，會簽仍要湊滿原本的票數（a2b2 審查 M1、M2）。

預設 `fallback` 而不是 `skip`：跳過等於少一道核准，屬於放寬，不能是預設。

推進中的失敗（例如第一關同意後，第二關找不到人且備援也為空）會讓「同意」這個動作回 409、什麼都不留；簽核人看到錯誤訊息，由管理員補組織或備援名單後再按一次。這比「同意成功但流程卡住」好處理。

## 7. 簽核動作

### 7.1 動作總表

| 動作 | 誰 | 何時 | 結果 |
|---|---|---|---|
| 送出 | 有轉移資格的人 | 記錄沒有進行中的實例 | 建實例、啟動第一關 |
| 同意 | 目前關卡的任務負責人 | 任務 `open` | 任務完成；關卡滿足就推進 |
| 退回發起人 | 目前關卡的任務負責人 | 任務 `open` | 實例 `rejected`，記錄轉到 `rejectTo` |
| 退回上一關 | 目前關卡的任務負責人 | 任務 `open`，且前面有已同意的關卡 | 目前關卡關閉，上一關重新啟動 |
| 撤回 | 發起人 | 目前關卡還沒有任何人動作 | 實例 `withdrawn`，狀態不動 |
| 轉交 | 目前關卡的任務負責人 | 任務 `open` | 任務改由另一人負責 |
| 後加簽 | 目前關卡的任務負責人 | 任務 `open` | 視同同意，並在目前關卡後插入一關 |
| 終止 | 簽核管理員 | 實例 `pending` | 實例 `cancelled`，狀態不動 |
| 改派 | 簽核管理員 | 任務 `open` | 同轉交，歷程記管理員 |

每個動作都寫一筆歷程，附意見。意見在退回時**必填**，其他動作選填。

### 7.2 同意與關卡推進

- **或簽（`any`）**：任一任務同意，關卡完成；同關其他 `open` 任務改為 `closed`（歷程不另記，畫面顯示「已由他人處理」）。
- **會簽（`all`）**：全部席位都滿足，關卡才完成；備援席位的其他任務在有人同意後改為 `closed`（§6.5）。任一人退回，整關以退回處理。
- 推進前先重新比對流程（§5.5），流程變了就重來，不推進。
- 關卡完成後，依序找下一關：用當下的記錄值求 `when`，不成立就寫一筆 `skip`（`SkipReason = condition`）繼續找；成立就解析簽核人、建任務。
- 沒有下一關：實例 `approved`，系統執行轉移（§8.2）。

### 7.3 退回

- **退回發起人**：實例結束為 `rejected`；記錄由系統轉到流程版本的 `rejectTo`。`rejectTo` 為 null 或等於 `from` 時狀態不動；不等於 `from` 時，`from → rejectTo` 必須是已定義的轉移（定義時驗證，§5.2），由系統以轉移方式執行，所以該轉移上的事件照常觸發。發起人修改後可以再次送出，那是一個**新的實例**，從第一關開始（「從退回的關卡繼續」列第二版，§20.1 第 6 項）。
- **退回上一關**：目前關卡標 `returned`，其餘任務關閉；回到**最近一個已同意的關卡**，以新的關卡實例重新啟動（重新解析簽核人）。第一個實際執行的關卡沒有上一關，只能退回發起人。被跳過的關卡不算「上一關」。

### 7.4 撤回

發起人在**目前關卡還沒有任何同意或退回**時可撤回（會簽關卡只要有一人同意就不能撤回）。實例結束為 `withdrawn`，記錄狀態不動、解除鎖定。已經通過的前面關卡不影響撤回資格；撤回的判斷只看目前關卡，對應使用者說的「在下一關動作前」。

### 7.5 轉交

- 任務負責人把自己的任務交給另一位啟用中的使用者，意見選填。
- 原任務改為 `transferred`，新建一個任務給對象（`Reason = transferred`、`OriginalUserId` 保留最初的人）。
- 對象不能是發起人、不能是這關已經有任務的人（避免會簽關卡一人兩票）。
- 轉交後原負責人，以及新任務 `OriginalUserId` 上的人，都失去這筆任務帶來的臨時讀取權與同意權；任務以新的受託人為準（第二輪審查建議 1，主控裁決，待使用者確認；§10.1）。

### 7.6 後加簽（主控判斷：只做後加簽）

- 任務負責人選一到五位使用者，以及新關卡的模式（會簽或或簽），按「同意並加簽」。
- 效果：本任務視為**同意**（照 §7.2 判斷目前關卡是否完成）；目前關卡完成後，**先**進入加簽關卡（`StageCode = null`、`AddedByUserId` = 加簽的人），加簽關卡完成後才回到定義的下一關。
- 會簽關卡中有人加簽、其他人還沒簽：加簽關卡排在目前關卡完成之後；同一關多人各自加簽，依加簽時間依序排。
- 加簽關卡的人同樣不能是發起人；加簽關卡沒有可編輯欄位、不設逾期時數。
- 加簽關卡內的人也可以再加簽；一個實例的加簽關卡總數至多 5 個，超過回 400。

### 7.7 代理人

- 使用者在個人設定填代理人與起訖日期（`Dynamic_ApprovalDelegate`）。
- 期間內**新建**給他的任務改派給代理人：`AssigneeUserId` = 代理人、`OriginalUserId` = 本人、`Reason = delegated`；歷程的 `OnBehalfOfUserId` 記本人。
- 期間開始前已經存在的任務不搬（主控判斷：避免設定代理的瞬間大量改派；要搬的請本人逐一轉交）。
- 本人在期間內仍可以自己處理被代理的任務（休假中臨時回來簽也合法）；誰先處理誰算。本人與代理人同時對這筆記錄有臨時讀取權（§10.1）。
- **會簽一人一票**（第一輪審查，主控裁決，待使用者確認）：同一關裡，實際簽核的人必須都不同；同一人不論以本人或代理身分，在同一關只算一票。代理會造成重複時（代理人本身就是這關的簽核人，或同一關兩位簽核人代理給同一人），該任務**不代理**，維持由原簽核人處理，歷程記一筆說明。動作時再檢查一次：使用者在同一關已經以任何身分同意過，就不能再處理同關的另一個任務（409）。
- **不串代理**：A 代理給 B、B 又代理給 C，A 的任務只會到 B。避免循環與「沒人知道最後到了誰手上」。
- 代理人是發起人時不代理，任務留給本人。
- 代理人的臨時讀取權規則同簽核人（§10.1）。

### 7.8 簽核管理員（主控判斷：使用既有的 Approve 動作軸）

核心的七個動作軸中，`Approve`（`CanApprove`）目前「保留，先不使用」（核心設計 §10）。本設計把它定義為**該模組的簽核管理權**：

- 查看該模組全部實例與歷程（仍受資料範圍限制）。
- 終止進行中的實例、改派任務。
- **不包含**代替別人同意；管理員要簽，必須是任務負責人（改派給自己也會留下歷程）。

系統管理員自動擁有所有模組的 Approve 軸（`PermissionResolver.ForSystemAdmin` 已是全部動作），但同樣受「發起人不能簽自己的單」限制。

## 8. 與狀態機、事件、分錄、檢查的互動

### 8.1 每個動作是一個交易

每個簽核動作（送出、同意、退回、撤回、轉交、加簽、終止、改派）是一個寫入請求，實作 `ITransactionalRequest` 與 `IRecordWriteRequest`，走既有的 MediatR 管線（事件設計 §2）：`Transaction`（`WriteGate` 排隊、`BEGIN IMMEDIATE`）→ `Idempotency` → handler → `RecordEffects` → 提交或回滾。所以：

- 動作支援 `Idempotency-Key`（前端一律帶），重送只生效一次。
- 動作與它造成的所有寫入（記錄轉移、可編輯欄位、事件效果、分錄、通知）同一個交易，任何一步失敗整筆回滾，實例與任務的狀態也一起回到動作前。

### 8.2 最後一關同意：轉移在同一個交易內執行

最後一關同意時，在同一個交易內依序：

1. 若這次同意帶了可編輯欄位的值（§9.2），先寫入這些值。
2. 重新比對流程（§5.5）；流程變了就改走重來，不執行以下步驟。
3. 寫歷程、任務、關卡實例、實例狀態（`approved`）。
4. **以系統身分把狀態欄位從 `from` 改成 `to`**：走既有的記錄更新流程（內部請求，狀態欄位列入 `SystemKeys`；步驟 1 與這一步的寫入在日誌上標記實例 id，供 §8.5 的後盾辨認），所以步驟 1 到 10（事件設計 §2 表）全部照跑：狀態機檢查轉移已定義（但不檢查群組，資格在送出時已檢查過）、唯讀狀態、`Process`、彙總、**事件（`transition` 觸發）**、**分錄**、**跨記錄驗證**。
5. 寫通知（§12）。

任何一步失敗，整筆回滾，回傳失敗原因給按同意的人。最常見的是**跨記錄驗證失敗**：請假單在等待期間假別餘額被別張單用掉，最後一關同意時「已核准天數 ≤ 額度」不成立，同意回 400，訊息是檢查的 `message`；實例仍停在最後一關，簽核人可以改按退回。這是正確的語意：餘額檢查要看核准當下，而不是送出當下。

稽核欄位：轉移造成的記錄 `ModifiedBy` 與事件效果的 `CreatedBy` 是**按下最後一個同意的人**；擁有者規則照事件設計 §4.2（取來源擁有者）。

### 8.3 退回到其他狀態

退回發起人且 `rejectTo ≠ from` 時，同 §8.2 第 4 步，以系統身分執行 `from → rejectTo`；該轉移的事件與檢查照跑。`rejectTo` 這條轉移本身若也被設為需簽核，定義時回 400（退回不能再要求簽核）；這條檢查在儲存狀態機、儲存流程、改流程目標狀態時都要重算（§5.2）。

執行前再驗一次（第三輪審查必修 4，主控裁決，待使用者確認）：`from → rejectTo` 未定義、需簽核，或 `rejectTo` 是鎖定狀態而 `from` 不是，就不執行轉移，退回回 409、實例停在原處，並通知系統管理員（§5.2）。§8.2 第 4 步的核准轉移同樣先確認 `from → to` 仍是已定義的轉移。

### 8.4 併發

- **一筆記錄一個進行中實例**：部分唯一索引（§4.3）。兩人同時送出，第二個違反唯一索引，回 409「這張單已在簽核中」。
- **或簽的兩人同時同意**：動作請求帶實例的 `rowVersion`；handler 在交易一開始就把實例的 `RowVersion` 換新值（`WHERE RowVersion = 舊值`），做法同單據轉換（單據能力設計 §4.4）。後到的那個回 409「這一關已由他人處理」，畫面重新讀取。
- **送出時鎖住記錄**：送出會換記錄的 `RowVersion`，正在編輯該記錄的人存檔會收到 409（舊畫面上的修改不能在送簽後偷偷生效）。
- 正確性來自 SQLite 交易一開始就持有寫入鎖，同事件設計 §7；換資料庫時由實例的 `RowVersion` 條件更新與部分唯一索引保證，不依賴 `WriteGate`。

### 8.5 簽核期間與簽核鎖定的其他寫入

下表列出**所有寫入路徑**（第二輪審查必修 8，主控裁決，待使用者確認）。「鎖定」指記錄在簽核鎖定狀態（§9.3），只鎖鎖定欄位，附件全鎖。

| 寫入路徑 | 簽核中的記錄 | 鎖定狀態的記錄 |
|---|---|---|
| 一般寫入：`PUT` 表頭 | 409，含系統管理員 | 鎖定欄位 400 |
| 一般寫入：明細列增刪改 | 409 | 閉包含本單明細的彙總時 400 |
| 刪除 | 409 | 照既有規則 |
| 其他狀態轉移 | 409「請先撤回」 | 照狀態機；離開見 §9.3 |
| 簽核人帶可編輯欄位的同意 | 允許，限本實例的記錄（§9.2） | 不適用 |
| 匯入（更新既有列） | 409 | 鎖定欄位 400 |
| 單據轉換 | 當來源允許（不改值） | 當來源允許 |
| 事件 `update` 效果 | 整筆回滾 409 | 鎖定欄位整筆回滾 400 |
| 應用程式整合的寫入 | 同事件 | 同事件 |
| 附件上傳 | 409 | 409 |
| 附件刪除、替換 | 409 | 409 |
| 彙總重算（子記錄在別的模組） | 允許，寫 `content-changed` | 允許（§20.2 已知限制） |
| 公式因參照記錄變動而重算 | 同上 | 同上 |
| 定義變更的整批重算 | §8.6 守衛擋，`FrozenRecords` 跳過 | `FrozenRecords` 跳過（§9.3） |
| 參照目標被刪除造成 `SetNull`／`Cascade` | 整筆回滾 409 | 動到鎖定欄位就整筆回滾 400 |

被當作單據轉換的來源時，轉換不改來源的值；要禁止就用轉換的 `sourceStates`。

**靜默更新留歷程**（第一輪審查，主控裁決，待使用者確認）：`RecordEffects` 在請求結束前看寫入日誌，凡是「請求開始前就在簽核中」的記錄被允許的路徑改了值（彙總、公式重算），就替它的進行中實例寫一筆 `content-changed` 歷程（系統身分），列出變動的欄位與前後值（值的可見性照讀者的欄位權限遮蔽）；不另發通知，時間軸上看得到。

**把關位置。** `Process` 增加「簽核中」與「簽核鎖定」判斷，與 `IsWorkflowLocked`、事實鎖並列；`RecordEffects` 的寫入後盾（事件設計 §2 步驟 9）加一類：日誌裡有「請求開始前就在簽核中」的記錄被修改或軟刪除，或簽核鎖定狀態記錄的鎖定欄位被改，就整筆回滾。

**豁免以記錄為單位**（第二輪審查必修 7，主控裁決，待使用者確認）：後盾只放行一種寫入：日誌上標了實例 id 的寫入（§8.2 步驟 1 與 4），而且寫的是那個實例自己的記錄、只動可編輯欄位與狀態欄位。可編輯欄位的豁免另要在執行時確認實例的 `from` 不是簽核鎖定狀態（第三輪審查必修 4，主控裁決，待使用者確認）：從鎖定狀態出發的簽核（例如作廢簽核）不能借豁免改掉核准過的值，定義時的限制（§9.2）漏網時由這裡擋下。辨認靠這個標記，不靠系統身分，也不看「這次請求是不是簽核動作」。同一個請求裡，事件、整合寫到**其他**簽核中或鎖定中的記錄，照常被擋下，整筆回滾：A 單最後一關同意觸發的事件改到簽核中的 B 單，A 的同意就回 409。

**後盾只涵蓋實作 `IRecordWriteRequest` 的請求。** `RecordEffectsBehavior` 只處理這類請求，所以每一條寫入路徑都要實作它，新增路徑時也要列進上表。目前的缺口是附件：

- 上傳（`UploadAttachmentRequest`）目前只實作 `ITransactionalRequest`，上傳資格檢查（`AttachmentUploadGate`）只看唯讀狀態，檢查完直接改寫記錄的值。要改成實作 `IRecordWriteRequest`，經過後盾；資格檢查同時加「有進行中實例」與「簽核鎖定狀態」的判斷，讓控制器在收檔前就能擋。
- 刪除與替換沒有獨立的請求，是以 `PUT` 改寫附件欄位的值，照一般寫入擋；鎖定狀態下附件欄位一律視為鎖定欄位。

### 8.6 定義變更

- 被流程版本引用的欄位（條件、`userField`、可編輯欄位）不能刪除或停用，範圍是**目前版本，加上所有進行中實例綁定的版本與流程快照裡的版本**（「被用過」的定義見 §4.4，第四輪核對必修 A，主控裁決，待使用者確認）；回 409 並指出流程。這與事件、檢查引用欄位的檢查點相同（事件設計 §10.5）。
- **進行中實例會用到的轉移與狀態都受保護**（第一輪審查，主控裁決，待使用者確認）：核准轉移 `from → to`、退回轉移 `from → rejectTo`、撤回與終止要回到的 `from` 狀態，只要有任何進行中實例用到，設計器就拒絕刪除轉移、修改它的起訖狀態、從狀態機移除這些狀態、換狀態欄位或刪除整個狀態機，`approval.required` 也不能關掉；回 409 並列出實例。要改請先等實例結束或終止它。理由：最後一關同意、退回、撤回都要靠這些轉移與狀態完成，少一條實例就卡死或走錯路。
- **進行中實例存在時，不能改會改寫記錄值的定義**（第一輪審查，第二輪審查建議 2 補範圍，主控裁決，待使用者確認）：一項定義變更的**受影響模組集合**中，任何一個模組有進行中實例時，設計器拒絕會改變記錄值的操作——新增、修改、刪除公式與彙總，修改帶值（`Config.Fill`）對應，換標題欄位，改數字欄位的小數位，刪除仍有值的欄位——回 409 並列出進行中的實例。受影響模組集合沿用 `ClosedDataGuard.RejectFormulaRecalcAsync` 的範圍：被修改的模組本身，加上以它為來源的彙總所在的父模組。所以改明細模組或「追加費用」模組的公式，表頭有進行中實例時同樣回 409。理由：前面關卡核過的金額，不能因為設計者改了公式就在背後變成另一個數字。這個守衛在設計器入口判斷，與 `ClosedDataGuard`、`ImmutableDataGuard`（事件設計 §10.3）共用同一組檢查點，**不靠**寫入後盾：定義變更觸發的整批重算本來就不經過記錄寫入管線的後盾。不改記錄值的操作（新增欄位、改標籤、權限、檢視）照常放行。
- **定義變更的整批重算不改已鎖定的記錄**（第二輪審查必修 4，第三輪審查必修 6 補明細，主控裁決，待使用者確認）：沒有進行中實例、定義變更放行時，`FormulaRecalc` 與 `RollupRecalc` 的整批重算跳過「簽核中」與「在簽核鎖定狀態」的記錄，以及表頭是這兩種的明細列，保留舊值（§9.3）。上一條擋簽核中的定義修改，這一條處理已核准的記錄，兩者並存。
- 被引用的群組刪除時（使用者與群組設計已有刪群組流程），若有流程版本引用，回 409 並列出流程；只被已結束的實例用過的版本不擋。
- 部門刪除見 §11.4。
- 應用程式關閉（模組 `Closed`）：記錄唯讀，所有簽核動作回 409；進行中的實例保留，重新開啟後繼續。待我簽核清單照常列出，但標示「應用程式已關閉」且按鈕停用。

## 9. 記錄鎖定與可編輯欄位

### 9.1 鎖定

簽核中的記錄對所有人唯讀（§8.5），包含發起人：要改內容，先撤回。這和釘釘、飛書一致，也避免「簽核人看到的內容與最後核准的內容不同」。

### 9.2 可編輯欄位

關卡的 `editableFields`：這一關的簽核人在按同意（或同意並加簽）時，可以同時修改這些欄位。

- **只能隨動作送出**，不另開「暫存」：同意請求本文帶 `values`，值與動作在同一個交易。
- 只有**目前關卡、任務 `open` 的負責人**能改，且只能改這幾欄；送其他欄位的值一律 400（不是忽略：簽核人以為改了卻沒改，比回錯誤更糟）。
- 這些鍵視為系統填入（略過模組 Edit 權限、欄位唯讀權限、`Config.ReadOnly`），但**仍**走型別 `Normalize`、規則的驗證與必填、下拉可選範圍；欄位對該簽核人隱藏時，不能編輯（回 400）。
- 存流程時只對推得出的簽核人群組檢查（主控裁決）：來源是群組就是那些群組、指定使用者就是他們所屬的群組，流程備援照同樣兩條；可編輯欄位對其中任一組隱藏（含限定可見而沒有可見列）回 400。主管、使用者欄位、發起人自選存檔時推不出人選，不在存檔時擋，靠上一條的執行期 400。
- 修改寫進 `RecordHistory`，`ChangedUserId` 是簽核人；與簽核歷程以 `OperationId` 對得上。

定義時限制（儲存流程、儲存狀態機、改流程目標狀態時都驗證，回 400；§5.2）：

- 只能是本模組表頭、啟用中的欄位；不能是公式、彙總、自動編號、狀態欄位、轉換的追溯欄位、分錄沖銷欄位、`lock` 帶值的目的欄位。
- **不能被同一目標狀態上任何流程的啟動條件、任何關卡條件、任何簽核人來源直接或間接引用**（第一輪審查改寫，主控裁決，待使用者確認）。否則簽核人可以改金額讓後面的高階關卡被跳過、讓流程重選到較鬆的那個，或改掉下一關的簽核人。
  - **直接引用**：條件裡的欄位、`userField` 的欄位。
  - **間接引用**：以上欄位的相依閉包。公式引用的欄位（遞迴到底）；帶值的目的欄位相依於它的參照欄位（改參照就改了目的欄位）；彙總欄位的值來自子記錄，表頭的可編輯欄位改不到它，所以彙總本身不會讓可編輯欄位落入閉包，但它的來源明細在核准後要鎖（§9.3）。
  - 範圍是同一目標狀態上**所有**流程（不只本流程），因為每次同意都會重新比對（§5.5）。
  - 狀態欄位不算進閉包：條件可以引用狀態欄位來區分入口（§5.2），而狀態欄位本來就不能是可編輯欄位。
  - 設計器存檔流程時計算閉包，交集非空就回 400，列出「可編輯欄位 → 經由哪些公式或帶值 → 影響哪個條件」。之後改公式、彙總、帶值或其他流程，使閉包產生交集時，同樣回 400；有進行中實例時，這類定義變更本來就被 §8.6 擋下。
- 流程套用的任何一個 `from` 狀態是狀態機的唯讀狀態，或是簽核鎖定狀態（§9.3，例如作廢簽核的「已確認」）時，不能設可編輯欄位（唯讀與鎖定的語意優先）。之後在狀態機新增入口、使某個 `from` 變成這類狀態時，儲存狀態機同樣回 400（§5.2）；執行時的豁免另有一道檢查（§8.5）。
- 明細列不能編輯（第一版）；要讓簽核人調整明細，請退回發起人。

### 9.3 簽核鎖定：依狀態判斷，不依實例（第一輪審查，第二輪審查必修 2、3、4 改寫，第三輪審查必修 1、2、6、7 改寫，主控裁決，待使用者確認）

單據核准後若還能改金額，大額採購可以先用小額核准、再把金額改大，等於少簽。第一輪的寫法把鎖定綁在「最近一次實例是 `approved`」上，小額 `direct` 不建實例、作廢簽核被撤回或退回都會讓鎖失效；這一輪改成：**鎖定依單據目前的狀態判斷，與有沒有建立實例、最近一次實例的結果無關。**

**可編輯狀態只有兩種**（第三輪審查必修 1）：起始狀態，以及設計者在狀態機上明確標記 `editable` 的狀態（§4.3，例如「已退回」「變更中」）。「是不是某條需簽核轉移的 `from`」不再影響可不可以編輯：能不能改是設計者的意圖，光看圖的結構分不出「往後推進」和「退回重來」。

**簽核鎖定狀態**（第二輪審查必修 2，第三輪審查必修 1、2 改寫）：

- 起點：凡是任何「需簽核」轉移的目標狀態，都是鎖定狀態。
- 延伸：從鎖定狀態沿一般轉移（不需簽核）能走到的後續狀態也是鎖定狀態，例如「已確認 → 部分進貨 → 已進貨」。延伸到可編輯狀態為止：可編輯狀態本身不算、也不再往下走。
- 從鎖定狀態出發的需簽核轉移不會讓出發狀態解鎖。例如設計者加了需簽核的「部分進貨 → 已取消」（進貨一部分後作廢也要主管同意），部分進貨仍是鎖定狀態，已進貨也是。
- 起點同時被標成 `editable` 時，以鎖定為準，設計器存檔回 400，請設計者取消標記。
- 起始狀態不能是鎖定狀態；從非鎖定狀態進入鎖定狀態的轉移一律需簽核（§5.2）。
- 設計器儲存狀態機或流程時計算，在狀態機分頁標出鎖定狀態與可編輯狀態（§13.1）。

記錄在鎖定狀態時就鎖。下列情況照樣鎖定：小額 `noMatch = direct` 直接進入、作廢簽核被撤回或退回、管理員終止、重新比對後需發起人重送（§5.5 第 6 點）。

**鎖定欄位**（第二輪審查必修 3），取下列三類的聯集：

1. 這個模組所有「需簽核」轉移上，所有流程（含停用的流程、各版本）的啟動條件、關卡條件、簽核人來源（`userField`）引用的欄位。不只鎖這次走的那個流程：流程 A 看供應商、流程 B 只看總額，以流程 B 核准後改供應商，本來就該走流程 A。**狀態欄位除外**（第三輪審查必修 7）：條件可以引用狀態欄位來區分入口（§5.2 的流程 D），狀態變更本來就由狀態機、送出端點與 §5.2 的規則控制；把它鎖起來，鎖定狀態的記錄就連解鎖轉移與往後推進都走不了。
2. 第 1 類欄位經公式、彙總、帶值依賴的閉包（同 §9.2，同樣排除狀態欄位）。閉包含彙總、而彙總來源是本單據的明細時，明細列同樣不能增刪改。
3. 簽核人在簽核中可以編輯的欄位：所有流程、各版本的 `editableFields`（例如核定金額）。核准時傳票取的是核定金額，單據上的值不能事後被改成別的數字。

使用者 `PUT`、匯入、事件與整合的寫入、附件都受鎖（逐條見 §8.5），回 400（鍵為欄位，訊息「這個欄位已經過簽核，要修改請先退回可編輯的狀態」）。附件在鎖定狀態一律鎖定。鎖定持續到記錄離開鎖定狀態為止，**不因走到後續一般狀態而解除**。

**定義變更的整批重算**（第二輪審查必修 4，第三輪審查必修 6 補明細）：`FrozenRecords` 目前只含唯讀狀態的記錄、有事件事實的記錄，以及表頭有事實的明細列（`headersWithFacts`）。擴大為再加上：

- 「簽核中的記錄」與「在簽核鎖定狀態的記錄」。
- **明細列跟著表頭一起固定**：明細列的表頭在簽核中或在鎖定狀態，這筆明細列就固定。`FrozenRecords` 對明細模組比照 `headersWithFacts`，載入「簽核中或在鎖定狀態的表頭 id」，用明細列的表頭欄位判斷，不能只看事件事實。整批重算是以被修改的模組（明細模組）自己的 `FrozenRecords` 跑，只固定表頭的話，明細的小計照樣被改寫。

`FormulaRecalc`、`RollupRecalc` 都套用；設計器存檔公式或彙總時，列出因此保留舊值的記錄數。否則核准後把「總額」公式改成含稅，整批重算會讓已核准的金額跨過大額門檻，卻沒有人重簽、也沒有歷程。明細沒固定還有連帶問題：明細小計被改成新值後，使用者改表頭備註存檔時，表頭會依明細重算彙總，總額跟著變，鎖定後盾隨即回滾，這張單的任何欄位都再也存不了。

**解鎖**：只能走一條已定義的轉移回到可編輯狀態（例如「已確認 → 草稿」）；回去後要進鎖定狀態就必須再送簽，因為從非鎖定狀態進入任何鎖定狀態（起點或下游）的轉移全部需簽核，而起始狀態不能是鎖定狀態（§5.2）。這延續第一輪的寫法，SAP 的對照見下段。

- 不在鎖定欄位內的欄位（備註、交期）照狀態機原本的規則可改；鎖定狀態若本來就是唯讀狀態，維持全單唯讀。設計器另外提示：核准之後的狀態，建議設成唯讀狀態。
- 已知限制：彙總的來源是**其他獨立模組**（例如付款加總到採購單）時，核准後子記錄的增減會即時改到彙總，鎖不住；設計器在條件引用這類彙總時顯示警告，列在 §20.2 已知限制。定義變更造成的重算則被 `FrozenRecords` 擋住，不在此限。

對照 SAP：採購單與請購單的核准策略（release strategy）把影響策略的欄位視為「核准相關」，核准後改這些欄位（例如金額增加超過容差）會**自動重設核准**，單據回到待核准。Formwright 改成**直接鎖定**、要改就明確轉回可編輯狀態：效果同樣是「改了關鍵欄位就要重簽」，但不需要容差設定，也不會出現「使用者存了一次檔，單據就悄悄變回未核准、下游已轉的單據怎麼辦」的情況；轉回可編輯狀態的轉移上的事件與檢查（例如已轉量）照常把關。

## 10. 權限

### 10.1 簽核人的臨時讀取權（主控判斷）

簽核人不一定有模組的讀取權（財務人員不一定能看全公司的請假單）。規則：

- 使用者是某筆記錄上 **`open` 任務的可動作者**時，對**這一筆記錄**取得唯讀權：表頭、明細、附件、列印預覽。可動作者是任務的 `AssigneeUserId`，代理任務（`Reason = delegated`）再加上原簽核人 `OriginalUserId`（本人仍可處理，§7.7；第一輪審查修正，主控裁決，待使用者確認）。**只有 `Reason = delegated` 才加原簽核人**（第二輪審查建議 1，主控裁決，待使用者確認）：轉交、加簽、備援的任務只有 `AssigneeUserId`；轉交出去的人在轉交後就失去讀取權與同意權，即使新任務的 `OriginalUserId` 還是他。同意等動作的資格判斷用同一個定義。
- 欄位可見性：以該使用者自己的群組欄位例外（限制優先）計算；**另外對這一筆記錄給 `Pricing` 軸**，看得到金額欄位。理由：審核費用與採購單卻看不到金額，簽核沒有意義；金額是簽核內容本身。
- 欄位可見性在檢視端（可編輯欄位清單、歷程遮蔽）與同意端共用同一個來源：臨時讀取看得到的欄位（含 Pricing 金額），若在這一關的可編輯欄位內，同意時就能改；不在可編輯清單的欄位仍回 400（§20.4 第 20 項）。
- 不放寬其他任何東西：不能讀同模組其他記錄、不能在清單頁看到這筆（清單照原本的資料範圍）、不能匯出、不能看反向關聯分頁、參照欄位只顯示標題（既有的 `TitleVisibleTo` 規則）。
- 任務離開 `open`（同意、退回、轉交、關閉）後，所有可動作者的讀取權一起收回。之後在「我已處理」清單只看得到 `TitleSnapshot` 與自己的歷程，點進去照一般權限判斷（沒有權限就 404）。

實作：記錄讀取的權限判定（`DynamicAccessGuard` 判 Read）加一條放行：「這位使用者是這筆記錄某個 `open` 任務的可動作者」，只對單筆讀取端點與附件下載生效。判定查 `Dynamic_ApprovalTask`：`AssigneeUserId = 我 AND Status = 'open'`，或 `OriginalUserId = 我 AND Reason = 'delegated' AND Status = 'open'`（索引見 §4.3）；查詢失敗或資料缺漏時不放行。

### 10.2 誰能看簽核歷程

- 發起人：自己送出的實例，永久可看（含已失去模組權限之後，只看歷程與標題快照）。
- 任務負責人：自己處理過的關卡。
- 對記錄有 Read 的人：該記錄的全部實例與歷程（記錄詳情頁的「簽核」區塊）。
- 簽核管理員（Approve 軸）：見 §7.8。
- 意見內容與歷程不受欄位權限影響；意見是簽核人寫給相關人看的。

### 10.3 職務分離

只做一條：**發起人不能簽核自己送出的單**（§6.4），後端強制，系統管理員也不例外。其他職務分離（建單者不能是核准者、同一人不能同意兩關、限制金額授權額度）仍在「這版不做」。

### 10.4 設計器權限

流程定義端點需要設計器（`DYN00000`）Edit，與其他設計器端點相同。組織維護需要系統管理員（§11.5）。

## 11. 組織骨架（核心能力）

### 11.1 定位（使用者裁決）

**組織骨架放在核心，HRM 往上加。** 核心只放三件事：部門樹、部門主管、使用者所屬部門。性質和現有的使用者與群組相同：屬於平台、空系統也能用、不依賴任何應用程式。HRM 的員工主檔參照它，再加職稱、到職日、聘雇類別等人事欄位。

對照市場：

- **Odoo**：部門（`hr.department`，含 `parent_id`、`manager_id`）與員工（`hr.employee`，含 `parent_id` 主管、`department_id`、`user_id`）都屬於 HR 應用程式；Approvals 的「需要員工的主管」要先裝 HR。
- **SAP**：組織管理（Organizational Management）是 HCM 的一部分，有組織單位、職位、職位持有人與彼此的關係；Flexible Workflow 決定簽核人時依這個組織結構。

Formwright **刻意改放核心**：鐵則要求應用程式可以獨立開關、空系統是合法起點（路線鐵則 5）。若主管放在 HRM，沒開 HRM 的客戶（只用進銷存）就沒有「直屬主管」，採購單簽核只能用群組；開了 HRM 又關掉，所有用主管的流程同時失效。放在核心，簽核與「依部門的資料範圍」（路線階段 4）都只依賴核心。代價是核心多三張表與一個管理頁，HRM 要和核心的組織對應（§11.6）。

第一版不做：職位（position）與職位持有人、矩陣式組織、兼任多部門、虛線主管、部門歷史（某天某人屬於哪個部門）。

### 11.2 模型

**`Dynamic_UserDepartment`**

| 欄位 | 說明 |
|---|---|
| `UserId` | 主鍵：一人一個部門（主控判斷，第一版不做兼任） |
| `DepartmentId` | |

規則：

- 允許多個樹根（小公司常見「總經理室」與「董事會」並列）；主管解析到樹根為止（§6.2）。
- 深度至多 10 層；`ParentId` 不能形成環（儲存時沿父鏈檢查）。
- 部門主管**不必**屬於該部門（總經理可以兼任業務部主管而所屬部門是總經理室）。
- 停用的部門不能再指派使用者；已在其中的使用者保留，主管解析時停用部門視同空缺、繼續往上。
- 停用的使用者若是某部門主管，解析時視同空缺。

### 11.3 Migration

`Organization` migration 新增兩張表，既有資料不受影響（沒有部門的使用者照常使用系統，只是「主管」來源解析不到人）。

### 11.4 刪除與異動

- 部門有子部門或有使用者時不能刪除（409，列出數量）；要刪先搬移。沒有子部門與使用者的部門可刪；被流程引用不會發生（流程不引用具體部門，§6.1）。
- 搬移部門（改 `ParentId`）、換主管、調動使用者：立即生效。進行中的實例中**已建立的任務不重派**，尚未啟動的關卡依新組織解析（§6.3）。主管離職前要把手上任務轉交，畫面在停用使用者時提示「此人有 N 筆待簽任務」，並提供一鍵改派給指定的人（走 §7.8 的改派，歷程記錄）。

### 11.5 管理員在哪裡維護

在**系統管理**選單（和「使用者」「群組」同一區），只有系統管理員看得到，API 由伺服器端檢查 `IsSystemAdmin`，與使用者管理相同（使用者與群組設計 §4）：

- **系統管理 → 組織**：部門樹。桌機左側樹、右側部門詳情（名稱、代號、上級、主管、成員清單）；拖曳或用「移到…」改上級；新增子部門。手機 390 寬：樹改成縮排清單，點部門進全螢幕詳情，搬移用「移到…」選單，不用拖曳。
- **系統管理 → 使用者**：編輯使用者時多一個「部門」下拉（樹狀選單）；清單多一欄部門，可依部門篩選。
- 匯入：使用者清單匯入時可帶部門代號，4a 一併做；既有使用者匯入功能不存在時，第一版只做畫面逐一指定（§20.1 第 9 項）。

### 11.6 HRM 開啟時員工與使用者的對應（主控判斷，HRM 設計時細化）

- HRM 的「員工」是一個動態模組（由 HRM 套件定義），不是核心實體。員工有一個使用者欄位（`FieldType.User`）「登入帳號」，**選填**：現場人員可以有員工資料而沒有帳號。
- 一個帳號最多對應一位員工：用跨記錄驗證 `count ≤ 1`、以「登入帳號」分組。現有檢查的分組欄位不含使用者型別（事件設計 §5.1 的 `groupBy` 型別限制），HRM 實作時要把 `user` 加進允許型別（`RecordIndex` 對使用者欄位已有 `RefKey` 索引，`DynamicQueryBuilder` 已支援），這是一個小的通用擴充。
- **部門與主管以核心為準**：簽核與資料範圍只讀核心的使用者所屬部門與部門主管，員工主檔不另存主管。員工的「部門」欄位參照核心部門（與 ERP 資料模型草稿 §2.6「所屬部門參照核心組織」一致；需要核心把部門開放為參照目標）：有登入帳號的員工，這欄由系統依帳號的核心部門帶入並唯讀，以核心為準；沒有帳號的員工手填，只供顯示與報表分組，不參與簽核。開 HRM 不會另建一份部門。
- HRM 開啟時**不**自動為每個使用者建員工；開啟頁面提示「可從使用者清單匯入員工」，走既有匯入。這符合「應用程式不改核心資料」的原則。
- HRM 關閉：組織照舊存在，所有用主管的流程照常運作。

### 11.7 Demo 資料怎麼產生組織

Demo 資料（`DemoService`）在建立使用者之後、建立記錄之前產生組織，資料虛構：

| 部門（代號） | 上級 | 主管 | 成員 |
|---|---|---|---|
| 總經理室（`exec`） | 無 | `manager01` | `manager01` |
| 業務部（`sales`） | `exec` | `sales02` | `sales01`、`sales02` |
| 採購部（`purchasing`） | `exec` | 空缺 | `buyer01` |
| 營運部（`ops`） | `exec` | `ops01` | `ops01`、`keeper01` |
| 生產部（`production`） | `ops` | `planner01` | `planner01`、`floor01`、`floor02`、`maint01`、`qa01` |

設計用意：業務部主管是本部門成員（測「主管是發起人往上找」）；採購部主管空缺（測「空缺往上到總經理」）；生產部有兩層（測「往上第 2 層」）。實際對照以實作時 `IDemoPeople` 的帳號為準，這張表是建議。Demo 的簽核流程與實例隨各應用程式的 Demo 情境產生（例如進銷存加幾張「簽核中」「已退回」的採購單），不另造假資料假裝功能存在。

### 11.8 也支援「依部門的資料範圍」

路線階段 4 的「依部門的資料範圍」會在 `DataScope` 加 `Department`（本部門）與 `DepartmentTree`（本部門含下級）。這份設計不實作，但要先記下一個已知問題：`PermissionResolver` 目前用 `readScopes.Max()` 合併多群組的範圍，前提是 `Own < Group < All` 是全序；`Department` 與 `Group` 彼此不可比較，屆時要改成「可見擁有者集合的聯集」，不能只在列舉中插一個值。

## 12. 通知

站內通知已隨任務管理先做（`2026-11-10-task-management-design.md` §6），簽核沿用它的 `Notification` 資料表、鈴鐺與讀取時補提醒的做法，下表的事件加為新的通知種類；4b 只剩接上簽核事件。簽核發出的通知：

| 事件 | 收件人 |
|---|---|
| 待簽 | 新任務的負責人（含代理、轉交、加簽、備援） |
| 被退回 | 發起人；退回上一關時另通知上一關的新任務負責人 |
| 已核准 | 發起人 |
| 已撤回、已終止 | 目前關卡 `open` 任務的負責人；終止另通知發起人 |
| 內容變更、流程重來 | 發起人與舊實例中已同意過的人（§5.5） |
| 轉交給你、加簽給你 | 同待簽，文案不同 |
| 逾期提醒 | 逾期任務的負責人 |

- 通知在動作的同一個交易內寫入（動作失敗就沒有通知）。唯一例外是執行時驗證失敗（§5.2）：動作回 409、整筆回滾後，另開一筆交易寫通知給系統管理員。通知只帶記錄標題快照與連結，不帶欄位值。
- **逾期提醒（主控判斷：查詢時產生，不跑背景排程）。** 核心目前沒有背景服務（`IHostedService`）；站內通知只有登入時看得到，所以不需要準時推送。做法：讀通知清單時，對使用者 `open` 且 `DueTime` 已過、`LastRemindedTime` 為空或超過 24 小時的任務，補寫一則逾期提醒並更新 `LastRemindedTime`（同一個交易）。之後若加 Email 或推播，再補背景排程。
- `DueTime` = 關卡啟動時間 + `dueHours`，以日曆時數計（不扣假日，§20.1 第 10 項）。
- 逾時自動同意、自動退回、自動轉主管：第一版不做。

## 13. 畫面

### 13.1 設計器

**狀態機分頁（既有 `WorkflowTab`）**：轉移清單每列多一個「需簽核」開關；打開後顯示「條件都不符合時：擋下（預設）／直接轉移」與「目標狀態已掛 N 個流程」連結；N 為 0 時不能存（§5.2）。狀態清單每列多一個「可編輯（退回重送）」開關（起始狀態固定打開），並標出簽核鎖定狀態、列出鎖定欄位（§9.3）；存檔時 §5.2 的全部約束不通過，就顯示後端指出的流程、轉移或狀態。

**新增分頁「簽核流程」**（模組編輯頁，沿用 `WorkflowTab`／`ConversionEditorDialog` 的做法，不手寫個別模組頁面）：

- 上方依目標狀態分組（標出套用的入口轉移），列出流程卡片：名稱、啟動條件摘要、關卡數、啟用開關、目前版本、進行中實例數。同一目標狀態內用「上移／下移」調整優先序（桌機另可拖曳）。
- 流程編輯對話框，三段：
  1. **基本**：名稱與鍵、目標狀態（下拉，只列需簽核轉移的目標狀態；流程被實例用過後停用，§5.2）、啟動條件（重用規則的條件編輯器）、退回狀態、備援簽核人。
  2. **關卡**：直向卡片串，卡片之間有「＋」插入關卡；每張卡片：關卡名稱、條件（條件編輯器，空白代表一律進入）、簽核人來源（下拉，依來源顯示參數：使用者多選、群組多選、主管層級 1 到 5、使用者欄位下拉與候選群組、自選的候選群組與人數）、模式（會簽／或簽，單人來源時隱藏）、可編輯欄位（多選，只列符合 §9.2 的欄位）、逾期時數、找不到人時（備援／跳過）。卡片可上移、下移、刪除。
  3. **試算**：選一筆既有記錄（或輸入幾個欄位值）與一位發起人，按「試算」呼叫預覽端點，以時間軸顯示每關會不會跳過、解析到誰、哪一關會用備援。
- 儲存失敗顯示後端的欄位錯誤；被進行中實例使用的流程，儲存時提示「會產生新版本，進行中的 N 張單照舊版本走完」。新增流程、調整優先序、停用時，同樣提示「只影響之後送出的單」（§4.4）。被用過的流程（§4.4）沒有刪除按鈕，只能停用。

**手機 390 寬**：流程卡片單欄；編輯對話框全螢幕，三段改成上方分段標籤；關卡卡片全寬，參數欄位上下堆疊，不橫向捲動；排序只用上移／下移按鈕。

### 13.2 送出簽核

- 記錄詳情頁的狀態區：目標是需簽核的轉移時，按鈕文字為「送出簽核：已核准」而不是直接轉移。
- 送出對話框：流程名稱、關卡時間軸（預覽結果）、自選簽核人欄位（有 `initiatorPick` 時）、意見、送出。手機上全螢幕，送出鈕固定在底部。
- `noMatch = direct` 而條件都不符合時，對話框顯示「這張單不需簽核，會直接轉為已核准」。

### 13.3 記錄詳情頁的簽核區塊

- 標題列旁徽章：「簽核中（第 2 關／財務）」「已退回」等；沒有實例時不顯示。
- 同意回應 `outcome = rerouted` 時，顯示「單據內容已變，流程改為「{新流程}」重新開始，你的同意未計入」，並重新讀取時間軸；舊實例收合在「先前的簽核」下。
- 簽核鎖定狀態下的鎖定欄位與附件，表單顯示鎖頭與說明「已經過簽核，要修改請先退回可編輯的狀態」。
- 「簽核」區塊：時間軸列出每個關卡實例（已同意、跳過、退回、進行中），每關列出任務負責人、代理與轉交關係、動作時間、意見。
- 動作列（只顯示使用者有資格的動作；後端仍重新檢查）：任務負責人有「同意」「退回」「轉交」「同意並加簽」；可編輯欄位在表單中解鎖並標示「這一關可修改」；發起人有「撤回」（不能撤回時停用並說明原因）；簽核管理員有「終止」「改派」。
- 手機：動作列固定在畫面底部，最多顯示兩個主要按鈕（同意、退回），其餘收進「更多」；時間軸單欄。

### 13.4 簽核中心

新頁面「簽核」（主選單一項，所有登入者可見）：

- 分頁：待我簽核（附逾期標示）、我已處理、我送出的；簽核管理員多一個「全部」（依模組篩選）。
- 每列：記錄標題快照、模組、目前關卡、發起人、送出時間、逾期。點列進記錄詳情頁（依 §10.1 的臨時讀取權）。
- 可依模組、狀態、時間篩選；不做批次同意（主控判斷：每張單都應該被打開看過，批次同意第二版再評估）。
- 手機：卡片清單，篩選收進抽屜。
- 模組清單頁另加系統篩選「簽核中」（以實例表子查詢，不做成欄位），隨 4e 做（§20.1 第 7 項）。

「代理人」區塊：代理人（使用者選單，排除自己）、起訖日期、清除。期間內在簽核中心頂端顯示「你的簽核目前由某某代理」。

## 14. 套件格式與匯出匯入

### 14.1 格式版本

套件格式提高到 **8**（`CurrentFormatVersion = 8`，`MinFormatVersion` 仍為 2；原寫 6，但 6 已由共用主檔、7 由任務管理使用，2026-11-10 改號，文中其他「格式 6」一律讀作 8）。理由同事件設計 §12：舊讀取器靜默略過簽核設定，客戶會以為單據有簽核卻沒有，必須提高版本。格式 7 以下出現 `approvalFlows` 或轉移上有 `approval`，整份拒絕。

### 14.2 形狀

轉移加 `approval`：

```json
"transitions": [
  { "from": "draft", "to": "confirmed", "groups": ["buyer", "manager"],
    "approval": { "required": true, "noMatch": "direct" } }
]
```

狀態加選用的 `editable`（§4.3、§9.3）：

```json
"states": [ { "option": "returned", "readOnly": false, "editable": true } ]
```

頂層新增 `approvalFlows[]`：

```json
"approvalFlows": [ {
  "code": "inv-po-large", "name": { "zh-TW": "採購單（大額）" }, "active": true,
  "module": "po", "to": "confirmed", "priority": 1,
  "when": { "all": [ { "field": "po.total", "op": "gte", "value": 100000 } ] },
  "rejectTo": "draft",
  "fallbackApprovers": { "source": "group", "groups": ["manager"] },
  "stages": [
    { "code": "buyer-lead", "name": { "zh-TW": "採購主管" },
      "approvers": { "source": "manager", "level": 1 }, "mode": "any",
      "editableFields": [], "dueHours": 24, "onEmpty": "fallback" },
    { "code": "gm", "name": { "zh-TW": "總經理" },
      "approvers": { "source": "group", "groups": ["manager"] }, "mode": "any",
      "editableFields": [], "dueHours": 48, "onEmpty": "fallback" }
  ]
} ]
```

引用規則沿用套件規格：模組用模組代號、欄位用限定欄位名、狀態用選項代號、群組用 `groups[].code`。

**套件不收具體的人與部門**：`users` 來源、`initiatorPick` 以外指定具體使用者的設定、具體部門，一律不能進套件（帳號與部門屬於這個資料庫，換一個資料庫會指到別人）。這和報表條件不收具體使用者的既有規則一致（`AppReportCodec.ConcreteUserMessage`）。套件只能用 `group`、`manager`、`userField`、`initiatorPick`（後兩者的候選限群組，`userField` 必帶候選群組，§6.1）。

### 14.3 內建應用程式的預設流程範本

內建套件只提供**範本**，開啟後屬於客戶，客戶可改可刪（路線「升級合併」決定）：

| 應用程式 | 預設流程 | 時機 |
|---|---|---|
| 進銷存 | 採購單 `draft → confirmed`：一萬以上採購主管、十萬以上加總經理、以下直接轉移 | 簽核做完時隨套件更新 |
| HRM | 請假：直屬主管，超過 3 天加第 2 層主管 | HRM 套件（階段 4） |
| HRM 或會計 | 費用報支：直屬主管 → 財務（可改核定金額）→ 金額大加總經理 | 費用報支所在的套件 |

金額門檻、天數是範本預設值，寫在流程條件裡，客戶自己改；核心沒有任何門檻常數。

既有的 CRM 與 MES 報價單「待核 → 已核准」不改（§4.2、§20.1 第 11 項）。

### 14.4 匯出、匯入與開啟

- **匯出**（`AppExporter`）：匯出流程的**目前版本**，不匯出歷史版本、實例、任務、歷程、代理設定（都是資料，不是定義）。流程含 `users` 來源時匯出失敗，指出流程與關卡（同報表）。
- **匯入與開啟**（`AppFlowInstaller`）：安裝順序 狀態機 → 分錄 → 事件 → 檢查 → **簽核流程**（流程需要狀態機的轉移，事件交叉檢查需要事件已在）。開啟時流程建成版本 1。
- **流程一律保留，不因設定對不上而略過**（第一輪審查修正，主控裁決，待使用者確認）。原本「對不上就整個流程略過」會讓大額流程消失，`noMatch = direct` 的轉移就變成大額也免簽。
  - 被流程引用的欄位（條件、`userField`、可編輯欄位）在開啟頁面**不能取消勾選**，旁邊標示「簽核流程需要」；要不要這個欄位，開啟後再到設計器改流程。
  - 簽核人來源引用的群組在開啟時被管理員選擇「略過」（第二輪審查必修 1 改寫，主控裁決，待使用者確認）：**不從名單移除**，而是在定義裡記成「對不上的來源單位」，執行時解析為空，依 §6.5 由備援簽核人頂替這個單位。會簽關卡因此仍要湊滿原本的票數：`group [board, purchaseLead]` 略過 `board`，這關要 `purchaseLead` 成員與一位備援簽核人都同意，不會只剩一票。`userField`、`initiatorPick` 的候選群組被略過，同樣視為該來源對不上，由備援頂替。套件裡關卡的 `onEmpty` 是 `skip` 時，開啟時改成 `fallback`（略過群組不能變成少簽）。
  - `fallbackApprovers` 的群組被略過：備援改為系統管理員（§6.5 的省略值）。
  - 開啟結果頁**逐一列出每個被頂替的來源**：哪個流程、哪一關、原本的群組、現在由誰頂替，並連到設計器。
  - 結果：開啟後目標狀態上的流程數量與套件相同，`direct` 只在真的沒有流程符合時生效（§5.2）。
- 驗證層（`AppPackageValidator`）加 V6：結構（`shape` 只收 `sequence`、來源列舉、`mode` 列舉、上限）、引用（模組、欄位、狀態、群組都在套件內；流程的目標狀態至少有一條需簽核轉移；`rejectTo` 轉移存在；可編輯欄位符合 §9.2；`userField` 帶候選群組；事件不推動需簽核轉移，§5.3）、狀態一致性（第二輪審查建議 3，主控裁決，待使用者確認：進入同一狀態的轉移需簽核開關一致；需簽核轉移的目標狀態至少掛一個流程，入口含 `direct` 時至少一個啟用中，§5.2）、鎖定一致性（第三輪審查必修 2、4，主控裁決，待使用者確認：從非鎖定狀態進入鎖定狀態的轉移都需簽核；起始狀態不是鎖定狀態；每個入口的 `from → rejectTo` 已定義、不需簽核、不會讓非鎖定的 `from` 退進鎖定狀態；可編輯欄位的 `from` 不是唯讀或鎖定狀態，§5.2、§9.2）。`AppFlowInstaller` 安裝狀態機時若不經過設計器的儲存驗證，就靠 V6 把關，所以這些規則一定要在 V6 裡。
- 跨應用程式：流程只能掛在同一份套件的模組上，條件與欄位只能引用同一份套件的欄位（同事件，理由同套件規格 §7.4）。
- `apps/app.schema.json` 加 `approvalFlows` 與轉移的 `approval`。

## 15. API

| 用途 | 端點 |
|---|---|
| 流程定義（設計器） | `GET/POST /approval-flows?module=`、`GET/PUT/DELETE /approval-flows/{key}` |
| 流程試算（設計器） | `POST /approval-flows/{key}/preview` |
| 轉移的需簽核設定 | 既有 `PUT /modules/{key}/workflow`，轉移加 `approval` |
| 記錄的簽核狀態與歷程 | `GET /records/{id}/approval` |
| 送出前預覽 | `POST /records/{id}/approval/preview` |
| 送出 | `POST /records/{id}/approval/submit` |
| 同意、退回、轉交、後加簽 | `POST /approval-tasks/{id}/{approve,reject,transfer,add-sign}` |
| 撤回、終止 | `POST /approval-instances/{id}/{withdraw,cancel}` |
| 改派 | `POST /approval-tasks/{id}/reassign` |
| 簽核中心 | `GET /approval-tasks?box=todo,done,submitted,all` |
| 代理設定 | `GET/PUT/DELETE /me/approval-delegate` |
| 組織 | `GET/POST /departments`、`PUT/DELETE /departments/{id}`；使用者部門走既有使用者管理端點 |

- 動作請求本文：`{ rowVersion, comment, values?, to?, userIds?, mode? }`，依動作取用；送出另帶 `{ to, picks, recordRowVersion }`，不收流程鍵（流程由系統決定）。同意的成功回應帶 `outcome`：`advanced`、`approved` 或 `rerouted`（§5.5）。
- `GET /records/{id}` 回應加 `approval: { status, stage, canSubmit } | null`；schema 的 `workflow.transitions` 每條加 `approval: true|false`，ETag 納入。
- 所有動作支援 `Idempotency-Key`。
- 錯誤語意：資格不符 403；任務不存在 404；schema 的臨時讀取（`?recordId=`）記錄不存在、屬於別的模組、或沒有臨時讀取權，一律回原本的 403（§20.4 第 19 項）；狀態不允許（已處理、已撤回、簽核中、找不到簽核人）409；輸入錯誤（意見缺漏、可編輯欄位以外的值、自選人不在候選）400；檢查或事件失敗依事件設計 §9。

## 16. 第二版預留

### 16.1 為什麼第一版不做並行分支

- **使用情境少**：50 人以下的公司，常見的並行只有「法務與財務同時看合約」。第一版可以用一關**會簽**、來源為兩個群組近似（兩個群組各至少一人同意的語意不完全相同：會簽是名單上每個人都要同意；若兩個群組各只有一人，就等價）。
- **成本高**：並行要定義匯流（全部分支完成才往下）、分支內各自的條件、某分支退回時其他分支怎麼辦、「退回上一關」的上一關是哪一關；設計器要有圖形編輯，手機上很難操作。
- **驗證難**：依序結構的「目前在哪一關」只有一個答案；並行時有多個，撤回、加簽、通知的語意都要重寫。

### 16.2 資料結構怎麼預留

- `DefinitionJson.shape`：第一版只收 `sequence`；第二版加 `graph`，`stages` 改成 `nodes`（每個節點有 `id`、`kind`：`stage`／`parallel`／`join`）與 `edges`。`sequence` 可以無損轉成 `graph`（一條鏈），所以舊版本不需遷移。
- `Dynamic_ApprovalInstance.CurrentStageRunId`：第二版改為「同時可以有多個 `active` 的關卡實例」。為此**第一版就不在資料庫層限制一個實例只有一個 `active` 關卡**，而是由程式保證；查詢「目前關卡」一律查 `StageRun WHERE Status = 'active'`，`CurrentStageRunId` 只是快取。
- `StageRun` 預留可為空的 `NodeId`、`BranchKey` 欄位（第一版不寫入），避免第二版再 migration 已有大量資料的表。
- `mode` 是字串，第二版可加 `{ "atLeast": n }`（N 中選 K）。
- 前加簽：任務 `Status` 預留 `waiting`（第一版不使用）。

### 16.3 其他第二版候選

抄送、退回後從退回的關卡繼續、逾時自動處理、批次同意、意見附件、依「單據上的部門欄位」找該部門主管、簽核人規則擴充點（同事件的 `IEffectHandler` 模式）、Email 與推播通知、相鄰關卡同一人自動略過。

## 17. 測試與驗收

### 17.1 原則

- 每項先寫失敗測試再實作；被測程式碼沒有業務名詞（沿用事件設計 §14.5 的詞表掃描，加入請假、報支、簽核情境的詞）。
- 三個情境的模組、欄位、流程都在**測試資料內自己定義**，跑在 WebAPI 整合測試的 `TestApp`（檔案型 SQLite）。
- 下面三份劇本寫成可直接轉成整合測試的步驟；每一步的「預期」就是斷言。

共同組織（測試內建立）：

| 部門 | 上級 | 主管 | 成員 |
|---|---|---|---|
| 總部 | 無 | `gm` | `gm` |
| 業務部 | 總部 | `mgrA` | `mgrA`、`emp1`、`emp2` |
| 業務一課 | 業務部 | `lead1` | `lead1`、`emp3` |
| 採購部 | 總部 | 空缺 | `buyer1`、`buyer2` |
| 財務部 | 總部 | `fin2` | `fin1`、`fin2` |

群組：`finance`（`fin1`、`fin2`，對費用模組**沒有** Read）、`purchaseLead`（`buyer2`）、`board`（`gm`）。

### 17.2 劇本一：請假（條件加關、主管解析、檢查、代理）

定義：模組「假別餘額」（員工、額度天數）；模組「請假單」（天數、假別餘額參照、狀態 草稿／已核准／已退回）；轉移 草稿 → 已核准 需簽核、`noMatch = block`；跨記錄驗證「同一假別餘額已核准天數 ≤ 額度」；事件「核准時把假別餘額的最後核准日設成今天」。流程「請假」：`when` 空；第 1 關 `manager level 1`；第 2 關 `when 天數 > 3`、`manager level 2`；`rejectTo = 已退回`（草稿 → 已退回 是已定義轉移）。

1. `emp3` 建 2 天請假單並送出 → 201；實例 `pending`；第 1 關任務給 `lead1`；記錄狀態仍是草稿；`lead1` 收到待簽通知。
2. `emp3` 以 `PUT` 改天數 → 409「簽核中，不可修改」。`emp3` 以 `PUT` 直接把狀態改成已核准 → 400「這個狀態需要送出簽核」。
3. `lead1` 同意 → 第 2 關條件不成立，歷程有一筆 `skip`；實例 `approved`；記錄狀態已核准；假別餘額的最後核准日是今天（事件在同一交易）；`emp3` 收到已核准通知。
4. `emp3` 建 5 天請假單送出 → 第 1 關 `lead1`；`lead1` 同意 → 第 2 關任務給 `mgrA`（業務一課的上級業務部的主管）。
5. `lead1` 自己建 2 天請假單送出 → 第 1 關任務給 `mgrA`，不是 `lead1`（主管是發起人，往上找）。
6. 額度 10 天、已核准 8 天；`emp3` 送出 3 天 → 第 1 關 `lead1` 同意 → 400，訊息是檢查的 `message`；實例仍 `pending` 在第 1 關，任務仍 `open`，記錄仍是草稿，沒有事件事實。`lead1` 改按退回（意見必填，不填 → 400）→ 實例 `rejected`、記錄轉到已退回。
7. `emp3` 送出後、`lead1` 動作前撤回 → 實例 `withdrawn`、記錄草稿、可再編輯；`lead1` 的任務 `closed` 且收到「已撤回」通知。
8. `lead1` 設代理人 `emp2`（今天到明天）；`emp3` 送出 → 任務負責人 `emp2`、`OriginalUserId = lead1`；`emp2` 沒有請假單 Read 也能 `GET` 這筆（200），但 `GET` 清單看不到它、`GET` 另一筆請假單 404；`emp2` 同意後再 `GET` 這筆 → 404。
9. 把 `lead1` 停用；`emp3` 送出 → 第 1 關依空缺往上，任務給 `mgrA`。
10. 修改流程（第 2 關改 `level 1`）→ 產生版本 2；步驟 4 那張還在第 2 關的實例仍依版本 1 走完。

### 17.3 劇本二：費用報支（可編輯欄位、退回上一關、轉交、加簽、臨時讀取權）

定義：模組「費用報支」（申請金額、核定金額、科目、明細「費用列」與申請金額彙總）；轉移 草稿 → 已核准 需簽核；事件「核准時新增一張傳票（分錄模組），金額取核定金額」。流程：第 1 關 `manager level 1`；第 2 關 `group finance`、或簽、可編輯欄位 核定金額與科目；第 3 關 `when 申請金額 > 20000`、`group board`；`rejectTo = 草稿`。另一個負面案例：把第 3 關條件改成引用「核定金額」→ 儲存流程 400（可編輯欄位不能被條件引用，§9.2）。

1. `emp1` 送出申請金額 30000 → 第 1 關 `mgrA`。
2. `mgrA` 同意並加簽 `emp2`（或簽）→ 插入加簽關卡，任務給 `emp2`；`emp2` 同意 → 進第 2 關，`fin1`、`fin2` 各一個任務。
3. `fin1`、`fin2` 都沒有費用模組的 Read：兩人 `GET` 這筆 → 200，金額欄位可見（臨時給 Pricing）；同模組另一筆 → 404；匯出端點 → 403。
4. `fin1` 同意時帶 `values` 改「申請金額」→ 400（不在可編輯欄位），什麼都沒寫入。
5. `fin1` 退回上一關，不填意見 → 400；填意見「請附收據」→ 第 2 關 `returned`，回到加簽關卡（最近一個已同意的關卡），新任務給 `emp2`；`fin2` 的任務 `closed`；`fin1` 再 `GET` 這筆 → 404（臨時讀取權已收回）。
6. `emp2` 再同意 → 第 2 關重新啟動；`fin1`、`fin2` 同時送同意（`Task.WhenAll`），`fin1` 帶 `values` 核定金額 18000 → 一個 200、一個 409「這一關已由他人處理」；成功者的 `values` 寫進記錄與 `RecordHistory`。
7. 第 3 關（申請金額 30000 > 20000）任務給 `gm`；`gm` 轉交給 `fin1`（不是發起人、這關沒有任務）→ `gm` 的任務 `transferred`，`fin1` 有新任務（`OriginalUserId = gm`、`Reason = transferred`）；`gm` 再 `GET` 這筆 → 404，`gm` 對 `fin1` 的任務按同意 → 403。轉交給 `emp1`（發起人）→ 400。
8. `fin1` 同意 → 實例 `approved`，記錄已核准，傳票一張、金額 = 核定金額，傳票的 `CreatedBy = fin1`。
9. 同一把 `Idempotency-Key` 重送第 8 步的同意 → 回放成功結果，傳票仍只有一張。
10. `fin1` 自己送一張報支：第 1 關給 `fin2`（財務部主管）；第 2 關群組 `finance` 移除 `fin1`，任務只給 `fin2`。
11. 停用 `fin2` 後 `fin1` 再送一張：第 1 關主管空缺往上給 `gm`；第 2 關群組移除發起人後為空 → 改派備援（系統管理員），歷程有 `fallback` 說明。

### 17.4 劇本三：採購單金額門檻（多流程優先序、直接轉移、會簽、作廢簽核）

定義：模組「採購單」（總額、狀態 草稿／已確認／已取消）；轉移 草稿 → 已確認 需簽核、`noMatch = direct`；已確認 → 已取消 需簽核、`noMatch = block`。流程 A（優先序 1）：`when 總額 ≥ 100000`；第 1 關 `manager level 1`；第 2 關 `group [board, purchaseLead]`、會簽。流程 B（優先序 2）：`when 總額 ≥ 10000`；第 1 關 `group purchaseLead`。流程 C（掛在目標狀態已取消，即作廢轉移）：第 1 關 `group board`。

1. `buyer1` 建總額 5000 送出 → 沒有流程符合、`direct` → 200，記錄直接變已確認，沒有實例；`PUT` 直接改狀態仍是 400（入口一致）。已確認是簽核鎖定狀態：`PUT` 把總額的來源明細改成 500000 → 400（沒有實例也鎖定，§9.3）。
2. 總額 50000 送出 → 用流程 B，任務給 `buyer2`。
3. 總額 150000 送出 → 用流程 A（優先序先比）；第 1 關 `manager level 1`：採購部主管空缺 → 往上到總部 `gm`。`gm` 同意 → 第 2 關會簽 `gm`、`buyer2` 兩個任務（`gm` 連續出現兩關，不自動略過）。`gm` 同意 → 關卡未完成，`buyer1` 此時撤回 → 409（目前關卡已有人動作）；`buyer2` 同意 → 實例 `approved`、記錄已確認。
4. `buyer2` 送出總額 50000 → 流程 B 第 1 關群組只有 `buyer2` 自己 → 移除後為空 → 備援 → 任務給系統管理員。
5. 已確認的採購單，`buyer1` 送出作廢 → 流程 C，任務給 `gm`；`gm` 退回 → `rejectTo = 已確認`（狀態不動），實例 `rejected`；`PUT` 改總額的來源明細 → 400（鎖定依狀態，不看最近一次實例）。
6. 把流程 A 停用；送出總額 150000 → 用流程 B。
7. 把流程 C 停用後送作廢 → 400「沒有符合條件的簽核流程」（作廢轉移是 `block`）。
8. 簽核中的採購單被當作轉換來源（轉進貨單）→ 依轉換的 `sourceStates`（只允許已確認）回 400；已核准後可轉。
9. 兩人同時送出同一張草稿 → 一個 201、一個 409「這張單已在簽核中」。
10. 關閉進銷存應用程式 → 待簽任務仍列在簽核中心但按鈕停用，同意 → 409；重新開啟後可繼續。
11. 匯出進銷存套件 → 格式 6，含流程 A、B、C；把流程 A 的來源改成 `users` 後匯出 → 失敗並指出流程與關卡；匯入到空資料庫並開啟 → 三個流程版本 1、轉移需簽核設定保留。

- 整合：簽核中的記錄被事件 `update`、`SetNull`、`Cascade` 改動 → 整筆回滾 409；彙總更新允許；被進行中實例引用的欄位、轉移、群組不能刪；組織的環與深度、有成員的部門不能刪。

### 17.7 劇本四：CRM 設計案（使用者 2026-11-10 情境）

業務主管接了客戶、指派給業務；業務收到產品需求，和產品設計部門來回；設計上傳圖，業務給客戶確認，客戶要調整就再改，三方確認後交業務主管確認結案。

- **模組**（內建 CRM，新增 `crm-design-case`「設計案」）：客戶（往來對象）、負責業務（人員，業務主管填）、設計負責人（人員）、需求說明、狀態；明細「設計圖」：版本、圖檔（附件）、上傳人、客戶意見。
- **狀態機**：需求確認 → 設計中 → 客戶確認中 →（客戶要修改，回到設計中）→ 待主管確認 → 結案；另有取消。「待主管確認」與「結案」是簽核鎖定狀態。
- **任務規則**（任務管理設計 §5.2 `everyTime`）：狀態變成「設計中」→ 任務給設計負責人「依需求繪製／修改設計圖」；狀態變成「客戶確認中」→ 任務給負責業務「將設計圖交客戶確認」。來回幾輪就產生幾批。
- **溝通**：任務留言加附件與 @（任務管理設計 §4.2）；客戶不登入系統，客戶的回饋由業務記在 CRM「互動紀錄」或貼在留言。
- **簽核**：轉移「客戶確認中 → 待主管確認」需簽核，流程一關、簽核人是記錄上負責業務的部門主管（§6.2 直屬主管）；同意後轉到待主管確認，再由主管轉結案；退回回到設計中（可編輯狀態）。
- **驗收**：Demo 一筆設計案跑兩輪（第一輪客戶要求修改）、第二輪送簽、業務主管同意、結案；留言附件下載、通知、四種版型。

## 19. 主控判斷彙整

標「審查」的是第一輪審查後新增或改寫的項目，標「二審」「三審」的是第二輪、第三輪審查後新增或改寫的項目，都屬於主控裁決，待使用者確認。

1. 簽核掛在狀態機的轉移上；記錄停在 `from` 直到全部通過，不另做「簽核中」狀態（§4.2）。
2. 流程掛在目標狀態上，套用到所有進入它的需簽核轉移；一個目標狀態可有多個流程，由系統依優先序取第一個符合的，發起人不能挑；都不符合時預設擋下，可設為直接轉移，直接轉移只在送出時、真的沒有流程符合時生效（§4.3、§5.2，審查改寫、二審改寫）。
3. 需簽核的轉移只能走送出端點，`PUT` 一律 400；事件不能推動需簽核的轉移（§5.3）。
4. 進入同一狀態的轉移，需簽核開關與流程集合都一致；需簽核卻沒有流程的目標狀態不能存；從非鎖定狀態進入鎖定狀態一律要簽，起始狀態不能是鎖定狀態；儲存狀態機、流程、改目標狀態時重驗全部約束，執行時再驗一次、不過就停在原處並通知管理員；用過（被綁定或出現在快照裡）的流程不能刪、不能改目標狀態；V6 同樣檢查（§5.2、§8.3、§14.4，審查、二審補強、三審補強）。
5. 預覽不揭露跳過理由與條件內容（§5.4）。
6. 每次同意都在同一交易內重新比對完整路線（流程、版本、前面被條件跳過的關卡）；只在送出時的流程快照裡、依快照的優先序與定義內容比對，設定變動不影響進行中的實例；路線變了，這次同意不計入，實例從第一關重來；快照裡沒有流程符合時改由備援簽核人簽一關（§5.5、§4.4，審查、二審、三審改寫）。
7. 簽核人在關卡啟動時才解析，發起人自選例外（§6.3）。
8. 主管解析內建「主管空缺或是本人就往上找」（§6.2）。
9. 發起人不能簽自己的單，系統管理員也一樣；解析到發起人就移除，移除後為空走找不到人（§6.4）。
10. 同一人連續出現在兩關不自動略過（§6.4）。
11. 找不到人逐一處理每個來源單位：對不上的單位由備援簽核人頂替，會簽票數不減；備援省略時是系統管理員；跳過要明確設定，且只在整關都為空時才跳過（§6.5，二審改寫）。
12. 只做後加簽，加簽視同同意，加簽關卡至多 5 個（§7.6）。
13. 撤回只在目前關卡還沒有任何人動作時（§7.4）。
14. 代理只影響期間內新建的任務，不串代理，本人仍可處理（§7.7）。
15. 會簽一人一票：代理會造成同一人在同一關兩票時不代理（§7.7，審查）。
16. 既有的 Approve 動作軸定義為該模組的簽核管理權（§7.8）。
17. 每個動作一個交易，最後一關同意時在同一交易內執行轉移與事件、分錄、檢查；檢查失敗則同意失敗（§8.2）。
18. 簽核中的記錄對所有人唯讀；§8.5 列出所有寫入路徑（含附件），寫入後盾只涵蓋實作 `IRecordWriteRequest` 的請求，附件上傳要改實作它；豁免以記錄為單位、靠實例標記辨認；允許的靜默更新寫進簽核歷程（§8.5，審查補充、二審改寫）。
19. 受影響模組集合（本模組加彙總父模組）中有進行中實例時，設計器拒絕改寫記錄值的定義變更，也拒絕刪改實例會用到的轉移與狀態；整批重算跳過簽核中與鎖定狀態的記錄（§8.6，審查、二審補充）。
20. 可編輯欄位只能隨同意送出，不能被同一目標狀態上任何流程的條件或簽核人來源直接或間接引用，閉包含公式與帶值（§9.2，審查改寫）。
21. 簽核鎖定依狀態判斷、不依實例：需簽核轉移的目標狀態及其後續狀態都鎖定，可編輯狀態只有起始狀態與設計者標記的狀態；鎖定欄位是全模組所有流程與版本的條件閉包加可編輯欄位（狀態欄位除外，條件可引用它來區分入口），附件全鎖；明細列跟著表頭一起固定；要改得先轉回可編輯狀態、再送簽；對照 SAP 的自動重設核准，改用鎖定（§9.3，審查、二審、三審改寫）。
22. 臨時唯讀與 Pricing 發給任務上所有可動作的人：負責人，代理任務再加原簽核人（只限 `Reason = delegated`）；轉交後原負責人失去讀取與同意權；任務結束一起收回（§10.1，審查改寫、二審補充）。
23. 流程版本：被用過（被綁定或出現在任何實例的快照裡）才產生新版本；版本凍結定義，不凍結組織；送出時把流程集合的完整定義存成快照，新增、調整優先序、停用、改版只影響之後送出的單（§4.4，二審、三審、四輪改寫）。
24. 組織第一版一人一個部門、允許多個樹根、主管不必屬於該部門（§11.2）。
25. 簽核只讀核心組織；HRM 員工的部門欄位參照核心部門，有帳號時以核心為準並唯讀（§11.6，對齊 ERP 資料模型草稿）。
26. 逾期提醒在讀通知時產生，不跑背景排程（§12）。
27. 不做批次同意（§13.4）。
28. 套件格式升到 6；套件不收具體使用者與部門；開啟時流程一律保留，略過的群組記成對不上的來源、由備援頂替並逐一列出，被流程引用的欄位不能取消勾選（§14，審查改寫、二審改寫）。
29. `userField` 來源必須限定候選群組；送出時填的人不在候選群組或是發起人自己，就拒絕送出（§6.1，二審）。

9. 使用者匯入帶部門：4a 一併做；沒有現成匯入就只做畫面逐一指定（§11.5）。
10. 逾期以日曆時數計，工作日曆隨 HRM 出勤一起做。
11. 既有報價單的「待核」狀態暫不改成簽核流程，等套件更新入口決定後一起處理。
12. 簽核意見附件留第二版，先用單據本身的附件欄位。

### 20.2 已知限制

1. **核准後，來自其他獨立模組的彙總鎖不住**（§9.3）：例如付款加總到採購單。設計器在條件引用這類彙總時警告；需要時第二版加「核准後變動通知簽核人」。定義變更的整批重算不在此限，已由 `FrozenRecords` 跳過。
2. **簽核中由獨立模組彙總造成的變動**不會阻擋，只會留歷程並在下一次同意時重新比對完整路線（§5.5）；若路線沒有改變，已同意的前面關卡不會重簽。
3. **鎖定狀態的記錄不隨定義變更重算**（§9.3）：改公式或彙總後，已核准單據保留舊值，與新單的算法不同。設計器存檔時列出保留舊值的記錄數；要套新算法，就把單據轉回可編輯狀態再送簽。
4. **鎖定欄位取全模組所有流程與版本的聯集**（§9.3）：停用很久的舊流程引用的欄位也會被鎖。這是刻意的保守選擇；欄位太多時，設計者可刪除沒被用過的流程（§4.4）來縮小範圍。
5. **預覽的推論管道**（§5.4）：同核心設計風險 24 的性質，只遮蔽不消除。記錄預覽顯示的流程名稱本身也透露流程層條件的結果：條件引用發起人看不到的欄位時，選中哪個流程就等於透露了該欄位的範圍，性質同核心風險 24。

### 20.3 待決

1. **重來時的發起人自選**：重新比對後的新流程含發起人自選關卡時，目前設計是結束實例、請發起人重送（§5.5 第 6 點）。建議維持；替代做法是沿用舊實例的自選結果，但舊選擇不一定符合新流程的候選群組。
2. **重新比對的回應語意**：目前是 200 加 `outcome = rerouted`（因為 4xx 會回滾）。建議維持；若前端偏好錯誤碼，可改成 200 之外再加回應標頭，不建議改成 409。

### 20.4 實作期間的裁決（2026-11-10）

實作計畫與程式碼對不上、或審查發現缺口時，主控依設計原則裁決；只列會影響使用者行為、格式或 Demo 的項目，純技術選擇不列。實作中每段上線時補充。

1. 沒有模組讀取權的人讀其他記錄維持既有的 403，不因簽核改變全站單筆讀取行為。
2. 簽核中內容變更只寫歷程、不發通知；流程因重新比對而重來時才通知（以 §8.5 為準，§12 表格的對應列視為筆誤）。
3. 流程可掛在任何非起始狀態；目標狀態下拉會標示哪些已有需簽核的入口。
4. CRM 設計案（§17.7）的簽核人用「發起人的第 1 層主管」，送簽轉移限業務群組，所以由負責業務送出、他的主管簽核；依欄位找主管留第二版。
5. Demo 組織：總經理室 → 營運部（生產部、採購部）、業務部；業務主管為業務部主管；產品設計部（上級總經理室、主管 designer01）隨 CRM 設計案一起建立。資料一律虛構。
6. 進銷存採購單的「已取消」狀態標為可編輯，行為不變；採購單預設流程照 §14.3 提供。
7. Demo 站預設停用上傳：設計案的 Demo 由產生器在伺服器端寫入虛構的設計圖與留言附件，訪客可看、可下載、不能上傳；自架環境可以上傳。
8. 使用者管理表格在手機寬度改為卡片模式，不在表格內橫向捲動。
9. 流程代碼 `order` 為保留字（與排序端點衝突），驗證器拒絕。
10. 整合流程重新啟用事件時，也要通過定義的交叉檢查；不通過就維持停用。
11. 備援簽核人可選「指定使用者」「群組」「主管」；「表單上的人員欄位」與「發起人自選」不能當備援。設計器選項與套件格式 8 的驗證照此一致。
12. 沒有進行中的實例時，改公式或帶值造成鎖定欄位閉包交集，依 §9.2 回 400。
13. 簽核人可編輯的欄位，不得是對該簽核人隱藏的欄位：設計器存流程時拒絕（400），執行期同意時帶了隱藏欄位的值也回 400（a2b2）。
14. 事件或系統動作把記錄推進到需簽核的轉移時，回 409 `TransitionBlocked`，不會繞過簽核。
15. 整合流程重新啟用時，若交叉檢查不通過，整合維持 Blocked，所有項目一併停用。
16. 流程條件無法判斷時一律擋下（409），不退回「直接通過」；空條件群組視為沒有條件、成立。
17. 後盾會檢查同一請求內的連鎖轉移；簽核完成後，同一請求裡的事件再推同一筆記錄的狀態也會被擋。退回上一關時通知發起人。
18. 會簽、退回、備援的防少簽規則（a2b2）：同一關已同意的人不能再處理另一個任務；或簽時備援名單全是候選人要報錯；解析出零個席位時擋下；會簽晚到者看到的文案說明自己的席位狀態。
19. schema 的臨時讀取（`GET modules/{key}/schema?recordId=`）：記錄不存在、屬於別的模組、或沒有臨時讀取權，一律回原本的 403，不洩漏記錄是否存在（主控裁決 2026-11-12，取代設計 §15 原本的 404）。
20. 同意端與臨時讀取共用同一個欄位隱藏來源：沒有模組讀取權、靠臨時讀取的簽核人，可修改這一關可編輯清單內的金額欄位；清單外的欄位仍 400（主控裁決 2026-11-12，U-A）。
21. 簽核檢視的 `titleSnapshot` 依標題欄位可見性遮蔽：只有發起人、在該實例有任務的人、簽核管理者，或標題對他可見的讀者看得到，其餘回空字串（主控裁決 2026-11-12，U-B）。

## 21. 審查處置

總原則（主控裁決）：設定缺漏或資料變動都不能讓單據少簽任何一關；有疑慮就擋下或重簽。第二輪補上的核心觀念：鎖定依單據目前的狀態判斷，不依簽核實例。第三輪補上的核心觀念：設定變動只影響之後送出的單，入口一變動就重驗。三輪全部採納，屬主控裁決，待使用者確認。
