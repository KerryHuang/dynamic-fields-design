# 模組、欄位、區塊的安全刪除

狀態：階段 0 設計（對應 `2026-11-06-erp-roadmap-design.md` 的「安全刪除」）。核心設計 `2026-11-03-dynamic-modules-design.md` 寫了「新增、排序、停用、清除」，但後端沒有刪除 API；這份文件補上。

## 使用者裁決（不重問）

- 只有**未啟用、無資料、未被引用**才可刪，其餘一律用停用。
- 記錄刪除是軟刪除（`Record.DeleteFlag`）。**只剩軟刪除記錄視為無資料**：刪除模組時連同軟刪除記錄、索引與歷程一起永久清除，事前明確警告並告知清除筆數。
- 有未軟刪除的記錄就不可刪，也不提供一鍵清空全站。

## 我的設計決定

### 「未啟用」「無資料」的定義

| 對象 | 未啟用 | 無資料 |
|---|---|---|
| 模組 | `Module.Status` 不是 `Active`（草稿或停用） | 該模組沒有 `DeleteFlag = false` 的記錄 |
| 欄位 | `Field.Status = Inactive` | 該模組沒有未軟刪除記錄在此欄位有**非空值**；公式與彙總欄位是衍生值，不算資料 |
| 區塊 | 區塊內每個欄位都未啟用 | 區塊內每個欄位都無資料 |

- 空值：JSON 值為 `null`、空字串（含只有空白）、空陣列，或鍵不存在。數字 `0` 與布林 `false` 是有值。
- 自動編號欄位算資料：編號已發給記錄，不能當衍生值丟掉。
- 判斷「欄位有無資料」讀 `Record.ValuesJson`，不讀索引表：不是每種欄位都有索引，`ValuesJson` 才是唯一真相。

### 「被引用」的盤點

下列任何一項指向目標，就算被引用，列出來源後擋下。**停用中的來源也算**（停用的公式、規則、欄位重新啟用時會壞掉，所以不能放行）。

| 引用來源 | 位置 | 擋的對象 |
|---|---|---|
| 參照欄位（含明細關係） | 任何模組的 `Field.Config.RefTarget`（Kind = module） | 被指向的模組 |
| 彙總欄位 | `Config.Rollup` 的來源參照欄位、被彙總欄位、條件裡的欄位 | 該欄位所在的明細模組與這些欄位 |
| 公式欄位 | 公式運算式引用的欄位（`FormulaGraph.RefsOf`） | 被引用的欄位 |
| 預設帶表頭值 | `Config.ParentDefaultFieldId` | 表頭模組的該欄位 |
| 記錄標題 | `Module.TitleFieldId` | 該欄位 |
| 規則 | 條件裡的欄位（含 `fieldRef`）、`field:<id>` 與 `block:<id>` 目標（`RuleReferences`） | 被引用的欄位、區塊 |
| 檢視 | `ListView.Columns`、`Filter`、`Sort` 裡的欄位 | 被引用的欄位 |
| 報表 | `Report.DefinitionJson`：主模組、子模組、連結欄位、欄、分組、量值、篩選、日期欄位、經參照欄位帶出的欄位（`ViaFieldId`） | 被引用的模組與欄位 |

自身模組的內部引用（本模組的欄位互相指向、本模組的檢視與規則）在**刪除整個模組**時不算被引用，因為會一起消失；刪除單一欄位或區塊時，其他欄位、規則、檢視引用它仍然擋下。

不會被擋、但會一起清除的設定：模組的檢視、規則、選項、欄位權限、選項範圍、資料範圍、群組與個人的程式權限、權限目錄項目（`Dynamic_Program`）、自動編號流水號。這些是模組自己的組態，不是別人的依賴。

### 欄位與區塊的資料清理

欄位被刪除時：

1. 刪除該欄位的 `RecordIndex` 列與 `RecordHistory` 列（歷程對欄位有外鍵，不清會刪不掉）。
2. 從模組全部記錄的 `ValuesJson` 拿掉 `f_<id>` 鍵（包含軟刪除記錄，以及衍生欄位在未刪除記錄上的值）。被改寫的未刪除記錄換新 `RowVersion`，編輯中的人存檔會收到 409。
3. 刪除 `FieldPermission`、`FieldOptionScope`、`NumberSequence` 列，再刪欄位本身（選項隨欄位級聯刪除）。

區塊被刪除時，先對區塊內每個欄位做上述檢查與清理，最後刪區塊。**模組至少保留一個區塊**（設計器假設有預設區塊），最後一個區塊不能刪。

### 預先告知與確認

刪除會永久清除軟刪除資料，所以分兩步：

1. `GET .../delete-check`：回傳是否可刪、擋下的原因與來源清單、將被清除的筆數。
2. `DELETE ...?purged=<筆數>`：呼叫端必須帶上它看到的「軟刪除記錄筆數」。後端在交易內重算，筆數不符（使用者看完警告後又有人刪了記錄）回 409 並附最新的檢查結果，要求重新確認。沒帶 `purged` 回 400。

這樣警告與實際行為綁在一起，不會有「畫面說清 3 筆、實際清了 300 筆」。

## 後端 API

路由前綴 `/api/v3/dynamic`；權限用設計器代碼 `DYN00000` 的 **Delete 動作軸**（路線的「權限不 fail-open」）。沒有 Delete 權限回 403，連 `delete-check` 也不給（它會洩漏定義結構）。

| 方法與路徑 | 說明 |
|---|---|
| `GET /modules/{key}/delete-check` | 模組刪除檢查 |
| `DELETE /modules/{key}?purged=n` | 刪除模組 |
| `GET /fields/{id}/delete-check` | 欄位刪除檢查 |
| `DELETE /fields/{id}?purged=n` | 刪除欄位 |
| `GET /blocks/{id}/delete-check` | 區塊刪除檢查 |
| `DELETE /blocks/{id}?purged=n` | 刪除區塊 |

回應（檢查與 409 共用）：

```json
{
  "canDelete": false,
  "blockers": [
    { "kind": "referenceField", "moduleKey": "order", "id": 12, "name": "客戶", "count": null }
  ],
  "purge": { "records": 3, "indexRows": 9, "historyRows": 8 }
}
```

`kind` 的值：`moduleActive`、`liveRecords`（`count` = 筆數）、`fieldActive`、`fieldData`（`count` = 有值的記錄數）、`titleField`、`lastBlock`、`referenceField`、`rollup`、`formula`、`parentDefault`、`rule`、`view`、`report`。`moduleKey` 是來源所在的模組（報表為主模組），`name` 是來源的顯示名稱（欄位標籤、規則訊息、檢視名稱、報表名稱）。

- 找不到目標回 404。
- 被擋回 409，內容同上；這是裁決的「擋下時列出被誰引用」。
- 成功回 200。

### 交易與併發

- 刪除命令是 `ITransactionalRequest`：檢查、清除、刪除定義全在 `TransactionBehavior` 開的同一個交易內，任何一步丟例外就整個回滾。
- 清除後再驗一次事後條件（模組已無任何記錄列）；不成立就丟例外回滾。這是針對 SQLite 以外的資料庫（讀已提交）的保險，與路線風險 3 的做法一致。
- SQLite 下併發寫入由資料庫鎖序列化；落敗的請求拿到忙碌錯誤並回滾，不會留半套。

## 設計器畫面

- 模組設計器頁首：模組未啟用時，操作選單多一項「刪除模組」。
- 欄位列與區塊標題：已停用的欄位、區塊旁多一個刪除圖示；啟用中的欄位要先停用（沿用既有流程）。
- 點刪除先呼叫 `delete-check`：
  - 被擋：對話框列出原因與來源清單（模組、類型、名稱），只有「關閉」。
  - 可刪：對話框用警告色標明「永久刪除」，顯示將清除的軟刪除記錄、索引、歷程筆數；要輸入模組代碼（欄位與區塊則是勾選確認）才能按確認。
- 沒有設計器 Delete 權限的使用者（`/me` 的 `designer.delete` 為 false）看不到任何刪除入口；就算繞過畫面直接呼叫，後端仍回 403（fail-closed）。
- 顏色一律用語意 token，文案進四語系。

## 測試

後端（SQLite、真實 migration）：

1. 有未軟刪除記錄 → 模組、欄位被擋。
2. 只剩軟刪除記錄 → 可刪，且記錄、索引、歷程、權限列、流水號、選項真的清乾淨。
3. 被引用 → 被擋並列出來源（參照欄位、彙總、公式、規則、檢視、報表各一例）。
4. 啟用中的模組、欄位 → 被擋。
5. 沒有 Delete 權限 → 403，含 `delete-check`。
6. 失敗不留半套：在資料庫放觸發器讓最後一步失敗，確認前面的清除全部回滾；併發刪除與啟用，結束後不留孤兒列。
7. `purged` 筆數不符 → 409。

前端：刪除對話框元件的單元測試（被擋清單、可刪確認）；顏色掃描測試照常通過。

## 不在範圍

- 不做垃圾桶或還原；永久清除就是永久。
- 不做批次刪除與「一鍵清空」。
- 不刪使用者、群組、報表（它們各有自己的刪除路徑）。
- 不處理指向「既有實體」（`entity` 類參照）的刪除，它們不是動態模組。
