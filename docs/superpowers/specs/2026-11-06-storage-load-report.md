# 儲存層負載測試與數值精度報告

狀態：階段 0 實測報告（對應 `2026-11-06-erp-roadmap-design.md` 的「儲存負載測試」）。測試工具在 `poc/backend/tools/LoadTest`，重跑方式見 §9。

## 1. 結論

1. **SQLite 撐得住「每年數十萬筆、累積十年、20 人同時用」的寫入，也撐得住大多數查詢，但撐不住報表。**
   - 寫入：單一行程每秒可寫入 230 至 340 次（新增與修改混合；只新增是 331），現實需求（一年 30 萬筆，以 250 個工作日、每天 8 小時計，約每分鐘 2.5 筆）差三個數量級。
   - 列表與篩選：單一模組到約 90 萬筆時，所有量測的列表操作在 20 人同時使用下 p95 都在 410 ms 以內，達標。
   - 300 萬筆（十年）時，有三類操作超過門檻：命中大量筆數的篩選（如狀態＝草稿）、熱門科目加日期篩選、整表排序與關鍵字搜尋。
   - **報表是最大的缺口，與資料庫無關**：報表執行器會把來源模組的記錄全部載入記憶體再篩選，來源超過 20 萬筆直接回「筆數過多」，縮小條件也沒用；19 萬筆時單人要 1.8 秒，20 人同時用要 8 至 22 秒，還會拖慢所有人。實測安全範圍是約 5 萬筆（單人 0.4 秒）。
2. **PostgreSQL 現在不必換，也沒有加進專案。** 該評估的時機與理由見 §7。報表要先改成在資料庫內聚合，這件事換了資料庫也一樣要做。
3. **已修一個小問題：數值精度。** 金額與整數的索引欄是 double，超過 15 位有效數字會讓不同金額被當成同一個值；已把寫入驗證收在安全範圍內（§6）。其餘效能問題都不是小修，列在 §8，沒有動。
4. **本機測試與實機分開宣稱：** 本報告全部數字是本機行程內的量測（不含 HTTP），不是部署環境的實測。

## 2. 環境與方法

| 項目 | 內容 |
|---|---|
| 機器 | Apple M5、10 核心、32 GB、內建 SSD（macOS） |
| 執行環境 | .NET 8 runtime（SDK 9.0.317）、SQLite 3.41.2（Microsoft.Data.Sqlite 內附） |
| 資料庫設定 | 與 WebAPI 相同：EF Core migration 建立，`journal_mode = wal`（已實測確認）、`synchronous = FULL`、頁面 4096、快取 2 MB |
| 資料規模 | 科目 300 筆、客戶 2 萬筆、分錄 302 萬筆（十年，每年 30 萬）；資料庫 2.9 GB，索引表 2,012 萬列、歷程表 302 萬列 |
| 分錄欄位 | 摘要、日期、科目（參照）、客戶（參照，70% 有值）、借方、貸方、狀態（95% 已過帳）、自動編號 |
| 資料分布 | 科目偏斜（最熱的科目約佔 15%），金額偏小額，日期依序遞增（記錄 Id 與日期同向） |

方法：

- 工具在同一個行程內直接送 MediatR 請求，服務組態與 WebAPI 相同（每個請求一個 DbContext 與連線），所以數字不含 HTTP 與序列化，是伺服器處理時間的下限，真實請求每次再加幾毫秒。
- 大量資料用批次寫入灌（302 萬筆約 90 秒），索引投影用正式的 `RecordIndexer`；`selfcheck` 指令對同一份值各走一次 `CreateRecordHandler` 與批次路徑，比對記錄、索引、歷程三張表的列完全一致（已用突變驗證它會失敗）。
- 四種階段：單人逐項各 20 次（第一次暖機不計）；**有思考時間**（20 人，每人每 1 至 3 秒做一件事，約 80% 讀、20% 寫，這是門檻的依據）；**不停手**（20 人無思考時間，量容量上限）；**只寫**（20 人不停寫，量鎖等待）。
- 每項調整都從同一份乾淨的資料庫複製重跑，一次只改一個變數。

量測的雜訊：這台機器同時有別的工作階段在跑測試（負載曾達 30 以上）。對策是每次執行前等 1 分鐘平均負載低於 4 才開始，起始負載記在各次的記錄檔。單人階段重跑差異約 ±3%，有思考時間階段的 p50 約 ±15%，p95 與 p99 樣本少、更不穩；下表引用的比較都是差距明顯大於這個雜訊的。

## 3. 「可接受」的定義

依據是 Nielsen 的回應時間三個界線：0.1 秒覺得即時、1 秒內思路不中斷、10 秒是注意力的極限。ERP 的使用者是每隔幾秒操作一次的作業員，列表與篩選是最常重複的動作，所以要壓在 1 秒內留餘裕；整表排序與關鍵字搜尋使用者看得到載入中的提示，容許久一點。

| 類別 | p95 | p99 | 理由 |
|---|---|---|---|
| 一般互動：開列表、篩選、翻頁、換檢視 | ≤ 500 ms | ≤ 1.5 s | 留一半的餘裕給網路與畫面，整體仍在 1 秒內 |
| 整表操作：不篩選的欄位排序、關鍵字搜尋 | ≤ 3 s | ≤ 6 s | 使用者主動觸發、有載入提示 |
| 新增、修改 | ≤ 300 ms | ≤ 1 s | 存檔後要立刻看到結果；另外**不得有資料庫鎖錯誤** |
| 報表 | ≤ 5 s | ≤ 10 s | 另外**不得因來源筆數被拒**（這是功能性要求） |

量測條件：20 人、有思考時間階段，是現實使用強度（每秒約 9 個請求、約 1.7 次寫入，已高於實際）。不停手階段只用來看容量上限，不拿來對門檻。

不停手（20 人無思考時間）時整體只剩約 10.7 個請求每秒，p95 落在 0.8 至 11 秒，預設列表的 p50 由 57 ms 升到 372 ms：這是 10 核心 CPU 被重查詢吃滿的容量上限，不代表現實使用。

單位 ms，20 人有思考時間階段的 p95（括號內是單人 p50）。

| 操作 | 19 萬筆 | 30 萬筆（1 年） | 90 萬筆（3 年） | 302 萬筆（10 年） |
|---|---|---|---|---|
| 開預設列表 | 415（7） | 22（9） | 41（19） | 109（57） |
| 日期區間一個月 | 467（66） | 86（101） | 87（110） | 119（103） |
| 科目＋一季日期 | 685（32） | 140（46） | 317（101） | 1341（180） |
| 狀態＝草稿 | 795（24） | 74（36） | 160（103） | 919（343） |
| 關鍵字搜尋 | 378（56） | 127（89） | 386（269） | 2463（930） |

- 整表操作（排序、關鍵字、計數）與資料量成正比：每增加 10 倍，單人時間增加約 10 倍。日期區間這類由索引直接定位的篩選，只與命中筆數有關，十年資料與三十萬筆一樣快。
- 19 萬筆那一欄的 p95 特別高，不是列表本身慢，而是這個規模下報表**沒被拒**，20 人同時跑報表把 CPU 與記憶體吃光，所有操作一起變慢（新增的 p95 也到 765 ms）。30 萬筆起報表被上限擋掉，其他操作立刻恢復正常。換句話說，20 萬筆的載入上限現在是在保護伺服器。

### 4.3 寫入併發與鎖等待

- WAL 已開，讀不擋寫、寫不擋讀；寫入彼此仍序列化。
- 單人新增 3 ms；20 人同時有思考時間時，新增 p99 約 310 ms、沒有任何鎖錯誤。
- **極端壓力（20 人不停手只寫，每秒 300 多筆，是現實的上千倍）出現尾端延遲與鎖錯誤：**

| 設定（只寫階段 60 秒） | 新增 p95 / p99 / 最大 | 修改 p95 / p99 / 最大 | 鎖錯誤 |
|---|---|---|---|
| 現況 | 6 ms / 913 ms / 8.9 s | 914 ms / 2.4 s / 6.5 s | 0 |

  只跑新增（40 秒）時最大等待 28 秒，13,688 次裡有 2 次回 `SQLite Error 5: database is locked`。Microsoft.Data.Sqlite 預設的命令逾時是 30 秒，等不到鎖就丟例外；API 沒有專門處理這個例外，會變成 500。
- 這是寫入者之間搶鎖的不公平：等待的連線輪流重試，運氣差的等很久。現實的寫入強度下不會碰到，但它說明 SQLite 的單一寫入者沒有排隊保證。

### 4.4 報表

- 報表執行器先把來源模組全部未刪除的記錄載入（`ListForReportAsync`，上限 `MaxLoadRows` 20 萬），再在記憶體算儲存格與條件；日期區間與條件都是載入後才套用，所以來源筆數決定成本，不是命中筆數。
- 實測：5 萬筆單人 0.4 秒、20 人同時 p95 0.8 秒；19 萬筆單人 1.8 秒、20 人同時 p50 8 秒；30 萬筆以上直接被拒。
- 同時，被拒的報表仍然要先讀 20 萬筆再丟掉，每次約 0.6 秒的無效 CPU。

## 5. 已評估的調整

一次只改一個變數，都從同一份乾淨資料庫重跑。**沒有任何一項套進程式碼**，原因見各項。

| 調整 | 結果 | 決定 |
|---|---|---|
| `ANALYZE`（讓規劃器有統計） | 查詢變化在 ±15% 內；客戶報表由 66 ms 變 220 ms（變慢 3 倍）；統計是整個索引的平均，看不出單一科目的偏斜 | 不採用，有退步風險 |
| `mmap_size` 開 4 GB（實際上限約 2 GB） | 索引型查詢單人快 30% 至 45%（日期一個月 103→70、狀態 343→217），有思考時間的 p95 也降（狀態 919→372）；沒有退步 | 不採用：效益取決於映射到資料庫的多大比例（只開 256 MB 無效果），且是否預設吃記憶體是部署決策，建議當作大型部署的設定項 |
| `synchronous = NORMAL` | 寫入壓力下無差異（新增 p99 913→908） | 不採用，沒有好處 |
| 關閉自動 checkpoint（`wal_autocheckpoint=0`） | 新增 p99 由 913 ms 降到 12 ms；修改的尾端與最大值不變 | 不採用：WAL 會無限成長，需要另外的定期 checkpoint 才安全，不是小改動 |
| `busy_timeout = 30000`（改由 SQLite 等鎖） | 新增 p99 由 913 降到 7 ms、修改 p95 由 914 降到 7 ms，**但**最大等待升到 25 至 29 秒、鎖錯誤由 2 次增至 3 至 12 次 | 不採用：多數人變快、少數人更慘，且報錯變多；治本要在應用層排隊 |

## 6. 數值精度

**問題：** 記錄值（`Record.ValuesJson`）、公式、彙總、報表都用 `decimal`；篩選與排序用的索引欄 `RecordIndex.NumberValue` 是 `double`。

**量測**（`NumericPrecisionTests`，隨機取 20 萬筆、有效數字 1 至 15 位、小數 0 至 6 位的 decimal）：

- 進索引再轉回來，**完全一致**；排序與相異性都保留（兩個不同金額不會變成同一個索引值）。
- 所有索引值都是從 JSON 文字經同一個 `GetDouble()` 轉換（記錄值、篩選值、公式結果都一樣），所以等於、大於、小於的比較兩邊永遠自洽。`(double)decimal` 強制轉型與 JSON 解析在這個範圍內也完全相同（50 萬筆 0 筆不同），沒有「公式結果差一個 ulp」的問題。
- 超過 15 位有效數字就失真：`12345678901234567.89` 與 `…567.88` 變成同一個索引值，篩選的「等於」兩筆都命中；整數超過 2^53（9,007,199,254,740,991）末位被吃掉。修改前寫入驗證只限制小數位數，這些值都收得進來。

**規則（已寫進程式與測試）：**

1. 記錄值是唯一真相，以 decimal 精確存放；小數位數不得超過欄位的 `Scale`（預設 2）。
2. 小數類欄位（金額、小數、百分比）的有效數字最多 **15 位**；整數的絕對值最多 **2^53 − 1**。超過就在寫入時拒絕，訊息為「有效數字最多 15 位」或「必須是整數」。既有資料不動，下次寫入該欄位才檢查。
3. 計算結果的捨入是「四捨五入，0.5 進位離零」（`MidpointRounding.AwayFromZero`），捨入到欄位的 `Scale`：公式（預設 2 位，`ROUND` 函數用指定位數）與彙總都如此。每一列先捨入、再加總，彙總不做二次捨入。
4. 報表的加總是對已捨入的記錄值做 decimal 精確加總；平均與比率用 decimal 除法保留到 28 位，**不在計算中捨入**，只在前端顯示時捨入（`report-format.ts`，顯示最多 4 位小數、比率 1 位）。
5. 前端拿到數字是 JS 的 double，所以合計超過 15 位有效數字時前端顯示會失去小數；這與規則 2 同一個界線。

**為什麼這樣收：** 金額 15 位有效數字（小數兩位就是到 10 兆）足夠實際使用；而放寬索引到 decimal 需要改欄位型別（schema 變更），不是小改動。這次只做驗證，不改 schema。

**已知取捨：** 若某個欄位真的需要超過 15 位（如小數 6 位的匯率乘大數量），要改成文字儲存或另建索引欄，屬於 schema 變更，列為建議，不在本次範圍。

## 7. PostgreSQL 建議

**現在不換，專案也沒有加 PostgreSQL。** 本次沒有量過 PostgreSQL，以下「能改善」都是該引擎的已知能力，不是本報告的實測。

不必現在換的理由：寫入容量差現實三個數量級；單一模組 90 萬筆以內所有列表操作達標；最大的缺口（報表整表載入、整表排序）是應用程式的做法，換資料庫不會自己好。

建議在下列任一情況成立時評估：

1. **需要多個後端行程或高可用。** SQLite 是單一檔案，不能讓多個伺服器共用，這是硬限制。
2. **單一模組超過約 100 萬筆，而且使用者會用命中大量筆數或熱門值的條件篩選。** 本報告在 302 萬筆時，科目＋日期與狀態篩選就是因為規劃器不知道單一值的分布（`ANALYZE` 只有整個索引的平均）而未達；PostgreSQL 有單一欄位值的統計，且可平行查詢。
3. **要在資料庫內做大量聚合報表。**

在換資料庫之前，下面這些改善對兩種資料庫都有用，順序見 §8：報表改成在資料庫內聚合；整表排序改成從索引起走；關鍵字搜尋改用全文索引（SQLite 有 FTS5）。

## 8. 找到但沒修的問題（建議順序）

1. **報表整表載入（最優先）。** 把篩選、分組、加總下推到 `Dynamic_RecordIndex` 的 SQL 聚合，成本才會跟命中筆數而不是來源筆數成正比。這需要決定報表能支援的欄位類型（有索引的欄位才能下推），是產品方向，需要使用者定奪。在那之前，20 萬筆上限應該維持。
2. **熱門值與大範圍篩選。** 查詢建構器把每個條件寫成 `r.Id IN (SELECT RecordId …)` 非相關子查詢，先建完整的清單再與其他條件相交。設計文件把它當不變式（防 NOT IN 的語意錯誤），改寫成相關子查詢可以讓日期先縮小範圍再查科目，但要重驗所有運算子，不是小改。
3. **整表排序與關鍵字。** 排序用 `CASE WHEN … IS NULL` 的運算式，擋住用索引排序，變成對全部記錄做暫存排序；關鍵字是 `Title LIKE '%…%'` 全表掃描。兩者都與筆數成正比（302 萬筆約 1 秒）。
4. **鎖等待不公平。** 極端寫入壓力下最大等待可達 28 秒，鎖錯誤會變成 500。應用層用單一寫入佇列（先進先出）可以治本；現實強度不會碰到，所以排在後面。同時 API 應該把資料庫忙碌錯誤轉成 503 而不是 500。
5. **WAL 自動 checkpoint 在寫入壓力下造成約 1 秒的新增停頓。** 現實強度看不到（有思考時間階段新增 p99 約 310 ms）。
6. **修改記錄的吞吐明顯低於新增**（每秒約 120 對 330，p95 約 0.8 秒）：沒有診斷出原因，只確認與 checkpoint、`synchronous`、`busy_timeout` 無關。需要時再用單項計時找。
7. **效能設定項：** `mmap_size` 對大型資料庫有 30% 至 45% 的效益（§5），建議當作設定項而不是預設值。

## 9. 重跑方式

見 `poc/backend/tools/LoadTest/README.md`。本報告的主要執行：

```bash
cd poc/backend
dotnet build tools/LoadTest -c Release
T=tools/LoadTest/bin/Release/net8.0/LoadTest.dll
dotnet $T selfcheck
dotnet $T seed --db /path/full.db --years 10 --per-year 300000 --accounts 300 --customers 20000
cp /path/full.db /path/run.db && cp /path/full.db.seed.json /path/run.db.seed.json
dotnet $T run --db /path/run.db --users 20 --duration 60 --solo-runs 20 --out /path/result.json
```

資料規模對照用 `--years 1 --per-year 190000`（19 萬）、`--years 1 --per-year 300000`、`--years 3 --per-year 300000`、`--years 1 --per-year 50000`。調整實驗用環境變數 `LT_PRAGMAS`，例如 `LT_PRAGMAS="mmap_size=4294967296"`。
