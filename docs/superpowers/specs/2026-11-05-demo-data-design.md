# Demo 資料 設計文件

> 2026-11-05｜上位文件：[動態模組與自訂欄位 設計文件](2026-11-03-dynamic-modules-design.md)
> 標「（我的判斷）」的是我代為決定、可以改的；其餘是使用者已拍板的決策。

## 1. 意圖

Demo 站（Render 免費方案）每次休眠或重新部署後資料都會清空，打開只看到空的系統，看不出這套系統能做什麼。要有一批「像真的」的業務資料：打開就能逐一示範系統每一項能力，切換不同身分就看得出權限與資料範圍的差別。

產品化之後，這批資料也是新客戶試用、業務展示、教育訓練的起點。

## 3. 目標、非目標、反目標

**目標**

1. 四個情境合起來涵蓋上位文件 §3 的每一項能力（對照表見 §5），每項至少有一個「打開就看得到」的實例。
2. 記錄數量足以展示列表的分頁、篩選、排序：每個主要模組 30–80 筆（我的判斷）。
3. 記錄分屬不同使用者與群組，切換身分時資料範圍（全部、本人、同群組）與金額遮罩的差別一眼可見。
4. 日期以「今天」為基準往前後展開（近 3 個月到未來 1 個月），任何時候打開都有「本週到期」「逾期」這類資料。
5. 有變更歷程可看：部分記錄在產生後再由其他使用者修改過（狀態推進、改數量）。
6. 附一份 Demo 腳本（`docs/demo.md`）：每個情境用哪個身分、看哪個畫面、示範哪項能力。

**非目標**

- 從檔案匯入任意資料（既有的 CSV 匯入已涵蓋）。
- 清除或重設資料的按鈕（Render 重啟就會清空；本機刪 `poc.db`）。
- 使用者與群組管理畫面（下一個子專案）；這次需要的額外使用者與群組放在種子資料（§4.5）。

**反目標（做了算失敗）**

- 繞過驗證直接寫資料表：Demo 記錄必須走和使用者操作相同的指令，否則自動編號、公式、彙總、索引、歷程會和真實操作不一致，Demo 示範的就不是真正的行為。
- 每次產生的資料不同：同一天產生兩次，內容要一樣（固定亂數種子），Demo 腳本才寫得出「打開第 3 筆」。
- 產生到一半失敗留下殘缺資料。
- 在已經有使用者自建資料的庫裡覆蓋或刪除任何東西。

## 4. 四個情境

每個情境 = 一個內建範本（建模組結構）＋一段記錄產生規則＋範本帶不了的權限設定。新範本放在 `poc/backend/templates/`，和「訂單」一樣也能被「從範本建立」使用。

### 4.1 訂單（既有範本 `order`）

- 結構沿用訂單範本：表頭＋明細、明細逐列編輯、未稅合計／稅額／含稅合計彙總、明細帶表頭交期。
- 記錄：約 40 張訂單，每張 1–6 列明細；業務一、業務二各自建立（資料範圍「本人」），業務主管看全部。
- 狀態分布：草稿、確認、出貨、結案都有；部分訂單逾期未結。
- 權限示範：現場人員沒有金額權限，看不到單價與合計。

### 4.2 故障報修（新範本 `repair`）

- 欄位：報修單號（自動編號，`REP-{yyyyMM}-{0000}`）、模具（參照既有實體「模具」）、申請人（使用者）、報修日期（預設今天）、故障類別（下拉）、狀態（下拉、帶顏色：待處理、處理中、待驗收、結案）、故障說明（多行文字）、處理說明（多行文字）、處理人（使用者）、完成日期、停機時數（小數）。
- 規則：狀態為「結案」時處理說明、完成日期必填；結案後整張唯讀；故障類別為「其他」時才顯示「其他說明」；完成日期不能早於報修日期（跨欄位驗證）。
- 記錄：約 50 筆，現場人員提報、保養人員處理；狀態推進留下變更歷程。
- 共用清單檢視：「未結案報修」「近 30 天結案」（篩選沒有「目前使用者」與「本月」，裁決 3）。
- 報修單加「關聯報修單」（參照自己的模組），示範反向關聯清單。

### 4.3 模具保養＋客戶擴充（新範本 `mold-care`）

- 擴充既有實體：「模具」加上次保養日、保養週期（天）、累計射出數；「客戶」加信用等級（下拉）、付款條件、業務窗口（使用者）。
- 保養紀錄模組：參照模具、保養類別（多選：清潔、更換零件、校正…）、保養人員、保養日期、保養週期（天）、費用（金額）、下次保養日（公式：保養日期＋保養週期；公式不能跨模組引用模具上的週期，所以保養紀錄自帶週期，裁決 4）。
- 參照刪除行為：保養紀錄被刪除時處理方式示範 Restrict／SetNull／Cascade 至少各一處（例如保養紀錄的「更換零件」子模組 Cascade）。（我的判斷：具體放哪由實作決定，只要三種都看得到）
- 記錄：每支模具數筆保養紀錄。反向關聯只支援指向動態模組的參照，模具是既有實體，所以反向關聯改在保養紀錄的「更換零件」、訂單的「品質異常」、報修單的「關聯報修單」示範（裁決 2）。

### 4.4 品質異常（新範本 `quality`）

- 欄位：異常單號（自動編號）、狀態（開立、處置中、結案；結案後唯讀，裁決 5）、訂單（參照「訂單」模組，一般參照；所以單獨「從範本建立」品質異常時，庫裡要先有 `order` 模組，裁決 6）、異常類型（下拉）、不良原因（下拉，依異常類型連動）、處置方式（多選）、不良率（百分比）、責任單位、嚴重度（下拉；「重大」只有品保群組能選）。
- 訂單模組加一個彙總欄位「品質異常筆數」（一般參照的計數彙總）。（我的判斷：彙總欄位由 Demo 產生器在套用兩個範本後加到訂單上，不改訂單範本本身）
- 欄位權限示範：「責任單位」對業務群組唯讀；「不良率」對現場人員隱藏。
- 共用清單檢視：「未結案的重大異常」（多條件篩選＋排序）。
- 記錄：約 30 筆，引用 §4.1 的部分訂單。

### 4.5 使用者與群組

現有 5 位使用者、4 個群組不夠演四個情境。放進既有種子資料（`SeedData`，不存在才加），不由 Demo 產生器補：使用者清單在程序啟動時只載入一次，事後補的人會被擋在外面，而且沒有新增使用者的指令（裁決 1）。名單：保養人員 `maint01`（群組「保養」）、品保 `qa01`（群組「品保」）、第二位現場人員 `floor02`。（我的判斷：名單可以改）

## 5. 能力對照

| 上位文件 §3 能力 | 在哪個情境看得到 |
|---|---|
| 模組管理、區塊、多欄排版 | 全部 |
| 20 種欄位型別 | 四個情境合起來每種至少一個；檢查表以 `FieldType` 列舉的 20 個值為準，驗收時以測試斷言全部出現 |
| 選項顏色、群組限定選項、下拉連動 | 故障報修狀態、品質異常嚴重度／不良原因 |
| 條件顯示、條件必填、條件唯讀、跨欄位驗證 | 故障報修 |
| 參照：動態模組、既有實體、反向關聯、刪除處理 | 品質異常→訂單、故障報修／保養→模具、模具保養 |
| 擴充既有實體 | 模具保養＋客戶擴充 |
| 列表、篩選、排序、共用檢視 | 故障報修、品質異常 |
| 動作權限、欄位權限、資料範圍、金額遮罩 | 訂單、品質異常 |
| 稽核與變更歷程 | 故障報修、訂單 |
| 匯出匯入 | 任一模組（記錄量足夠） |
| 範本 | 四個新範本本身 |
| 表頭明細、彙總 | 訂單、品質異常筆數 |

## 6. 行為

- **產生方式**：先依範本建模組（走既有「從範本建立」），再補範本帶不了的權限與跨範本欄位，最後以各記錄的建立者身分逐筆走既有的記錄新增、修改指令。
- **以誰的身分**（我的判斷）：產生器以每筆記錄的建立者（或修改者）身分送指令，權限檢查照常進行；所以要先套好權限再產生記錄。結構與權限以 `admin` 身分建立。實作上在 Application 層提供一個能在指定範圍內切換 `ICurrentUser` 的機制，不經過 HTTP；要在同一個 DI scope 內切換（不同 scope 是不同 DbContext，做不到單一交易，裁決 7）。
- **模擬時間**（我的判斷）：每筆記錄有一個模擬日期；建立與修改的稽核時間、變更歷程時間、自動編號的期別（`yyyyMM`）都跟著模擬日期，不是全部「剛剛」。實作上讓產生器在指定範圍內覆寫 `IBusinessTime`，和切換身分用同一套範圍機制。
- **整批、單一交易**（我的判斷）：四個情境有依賴（品質異常參照訂單、在訂單上加彙總），所以整批一起產生、同一個交易；任何一步失敗整批回滾，畫面顯示失敗原因。
- **冪等與衝突**（我的判斷）：產生前檢查四個情境用到的模組代碼，以及「模具」「客戶」是否已有擴充模組；任何一個已存在就整批不產生，列出衝突的項目（例如「模組代碼 order 已存在」），不覆寫、不補資料。檢查在交易內做，兩個同時觸發時後到的會看到已存在。
- **權限放哪**（我的判斷）：群組層的動作權限與資料範圍寫在範本裡（範本格式已支援）；欄位隱藏／唯讀、群組限定選項範本不支援（上位文件 §15 第 47 條），由產生器套用範本後用既有的權限指令補上。所以單獨「從範本建立」這三個新範本時，不會有那些欄位層權限，這和訂單範本一致。
- **既有實體的資料量**（我的判斷）：模擬的模具增加到 12 支、客戶增加到 8 家，放在既有的種子資料（`SeedData` 的 add-if-missing），不是 Demo 產生器；它們模擬的是外部系統的資料，不屬於 Demo 情境。
- **確定性**：固定亂數種子；日期依「今天」平移，所以不同天產生的日期不同，但相對關係一樣。
- **啟動自動產生**：設定 `Demo:SeedOnStartup`（環境變數 `Demo__SeedOnStartup=true`），在 migration 與種子資料之後、站台開始接受請求之後於背景執行，不擋健康檢查；`render.yaml` 開啟。失敗只記 log，不阻止站台啟動。（我的判斷）
- **手動產生**：「系統管理」選單加「Demo 資料」頁，顯示狀態（未產生／已產生／產生中／衝突項目），一個「產生 Demo 資料」按鈕。產生中再按回 409。需要設計器的新增與修改權限（和「從範本建立」相同）。
- **耗時**：四個情境合計數百筆記錄、上千次指令；Render 免費方案 CPU 很弱，目標是 60 秒內完成（我的判斷），超過就改成背景執行並在頁面顯示進度。

## 7. 限制

- 沿用上位文件的分層：產生器在 Application 層，透過 MediatR 送既有指令，不直接碰 DbContext。
- 範本格式不改版本（formatVersion 1）；四個新範本必須通過既有的範本驗證。
- 繁中為主要語系；範本名稱、欄位名稱同時提供 en-US（比照訂單範本），th、vi 可以留空。

## 8. 留給實作者

- §5「20 種欄位型別」的缺口要補在哪個情境。

## 9. 實作裁決（寫計畫時）

計畫 `docs/superpowers/plans/2026-11-05-demo-data.md` 發現原設計有做不到的地方，裁決如下（都採計畫的建議，已回寫到上文）：

1. 額外使用者與群組放種子資料，不由產生器補。
2. 模具是既有實體，沒有反向關聯；改在更換零件、訂單的品質異常、關聯報修單示範。
3. 共用檢視沒有「目前使用者」「本月」條件；改成「未結案報修」「近 30 天結案」。
4. 公式不能跨模組；保養紀錄自帶保養週期。
5. 品質異常加狀態欄位與結案後唯讀，讓「未結案的重大異常」檢視成立。
6. 品質異常範本參照 `order`，單獨套用前庫裡要有訂單模組，寫進手冊。
7. 身分切換在同一個 DI scope 內，維持單一交易。
8. 手動產生需要設計器新增＋修改權限，與「從範本建立」相同（第 8 階段最終修正後已是如此）。
