### 開發順序（使用者 2026-11-10 確認）

1. **任務管理與簽核**（含 CRM 設計案情境）。簽核後端一條線；任務畫面與規則平行。工作段見下表。
2. **多語系**（穿插進行）：模組選單分區多語系化；全面盤點後修補高、中兩級；之後做翻譯匯出／匯入（Excel，只含設計資料，介面固定文字不開放覆寫）。進度：m1 選單分區、i1 前端寫死文字已上線；i2a 後端語系機制與高頻訊息進行中，i2b 記錄寫入與簽核訊息、i3 名稱欄位多語未開始。
3. **共用主檔收尾**：s2d-1g（Demo 公司跨應用程式共用等）、s2d-1h、s2d-2（品項共用、移除模擬實體）。
4. **訂單到出貨整合**：s2e-a 追溯與履約核心 → s2e-b 應用程式間整合 → s2f 訂單變更單。
5. **會計**：s3b 期間鎖定、分組小計、損益表列結構、Top N → s3c 會計應用程式。
6. **HRM**：依部門的資料範圍，以及員工、請假、出勤、費用報支。
7. **階段 5 其餘**：看板與日曆、專案與工時、客服與 IT 工單、應用程式開啟頁面、刪除應用程式、手動群組對應、備份還原。

## 目的

使用者裁決：Formwright 要長成一套簡單版 ERP，把 CRM、MES、HRM、會計等系統串成一套，讓客戶像 Odoo 一樣選擇開哪些系統；但核心不變，模組要能全自主定義。

ERP 有兩個作用：它是產品目標，也是核心的壓力測試。做不出來的地方，就是核心缺的能力。

差異化定位是我的判斷：**每個應用程式都能被客戶自己打開來改，不必找開發商。**

## 已定決定

這些是使用者的裁決：

- 目標客戶是 **50 人以下的小型企業**。
- 只做**簡單版 ERP**。
- **宣告式優先。** 很多情境在目前核心上有難度，所以留一個接口讓外掛客製不足的地方；外掛先不考慮，這份路線只規畫正常流程下做得出來的版本。
- **合規只提供資料與報表，不申報。** 費率與級距由客戶設定，正確性由客戶和會計師確認。
- 第一個應用程式是 **CRM 與銷售**。
- 資料庫**先留 SQLite**，目前不加 PostgreSQL：階段 0 壓測的數字夠用；階段 3 開頭做完報表的資料庫端聚合並重新壓測後，再看數字決定要不要加。
- 應用程式共七個：CRM 與銷售、MES 模具廠、進銷存、會計、HRM、專案與工時、客服與 IT 工單。
- **儀表板排在 CRM 之前。** 計畫已寫好，首頁也靠它長出內容。

## 鐵則

1. **ERP 邏輯不寫死。** 應用程式只能由核心的定義組成：模組、欄位、規則、流程、報表、權限。少了什麼，就做成通用能力。
2. **檢驗方式：** 同一個能力至少要有兩個不相干的應用程式用得上。
3. **沿用核心既有反目標：** 不做執行期 DDL、權限不 fail-open、不替個別模組手寫頁面、驗證不只做在前端。
4. **每階段都要能展示：** 每階段以一條跑得通的業務流程收尾，部署到 Demo 站。Demo 不用假資料假裝功能存在。
5. **空系統永遠是合法起點（使用者確認）：** 全新安裝不開任何應用程式時，只有管理員，由使用者自己新增模組，和現在的用法相同。應用程式不是必裝，平台任何功能都不能依賴特定應用程式存在。
6. **以 ERP 慣例設計（使用者 2026-11-08 指示）：** 主檔全系統一份（往來對象、聯絡人、品項為共用主檔；組織骨架在核心）；每張單據有擁有的應用程式，並寫明各開關組合下誰負責、收掉什麼、啟動哪些整合；每份應用程式或功能設計都要有「ERP 對照」一節，以 [ERP 資料模型](2026-11-10-erp-data-model-design.md) 為準，衝突時先改那份文件。簽核另見 [簽核流程設計](2026-11-10-approval-workflow-design.md)。

## 貫穿流程

潛在客戶 → 商機 → 報價 → 訂單 → 工令 → 製程 → 報工 → 出貨 → 銷項發票 → 收款 → 傳票 → 損益表

## 這版不做

- **計算類：** 計薪公式、折舊攤提、缺料計算（MRP）、自動排程。
- **平台類：** 外掛與腳本執行環境（只在事件設計中留接口）、多公司、職務分離、對外 API 與 Webhook、全站搜尋。
- **資料類：** 多幣別、單位換算、版本與有效日期。
- **同畫面三層明細：** 明細維持一層（做法見「核心要補的能力」的多層明細），不做同一個畫面編輯三層。
- **升級合併：** 應用程式開啟後就屬於客戶，之後由客戶自己改，新版不自動合併（這是我的判斷，能省下最難的一塊）。
- **套件更新入口（延後）：** 目前沒有把新版內建應用程式套到客戶已開啟的應用程式上的入口。**第一個客戶正式上線前必須重新決定**；不決定，內建應用程式之後的修正就送不到客戶手上。
- **法規類：** 申報檔、電子發票串接、內建法定費率。
- **呈現類：** 甘特圖。
- **定位：** 不追 Odoo 的模組數量，也不做多租戶。

## 風險

1. **儲存撐不撐得住：** JSON 值加索引表沒有壓測過。目標客戶小，風險降低不少，但還是要驗。我的初步門檻：同時上線 20 人、分錄每年數十萬筆、累積十年資料時，常用查詢延遲仍可接受。
2. **數值正確性：** `RecordIndex.NumberValue` 是 `double`，公式用 `decimal`；金額的查詢比較與計算可能不一致。階段 0 要驗證並定下進位規則。
3. **超轉與重複過帳：** 兩人同時轉單可能超轉，所以剩餘量檢查要和單據轉換一起做。重送請求可能重複扣庫存，所以事件要有操作識別與冪等約束。
4. **改定義影響舊單：** 現在允許改公式後重算，歷程的參照名稱也讀目前值。已過帳的單據要固定數值，不隨定義改變。

- 應用程式封裝格式的設計。

**驗收：** 數字對照門檻寫成報告。

### 儀表板（中）

- 依 `docs/superpowers/plans/2026-11-05-reports-stage2.md` 實作，接到首頁。

**驗收：** 依該計畫的驗收項目；Demo 站首頁看得到儀表板。

### 階段 1：單據流與 CRM（大）

- 帶值、單據轉換（含剩餘量檢查）、多層明細、附件、狀態機、列印範本、應用程式開關。
- 應用程式：**CRM 與銷售**。

**驗收：** 潛在客戶一路轉到訂單，報價單能印出；兩人同時轉同一張單不會超轉；同樣能力用在採購情境也成立；應用程式關閉後，既有引用與資料仍可查閱。

### 階段 2：事件、帳本、進銷存與 MES（大）

- 事件觸發（含操作識別、冪等、循環防護，並留外掛接口）、跨記錄驗證、不可修改分錄。
- 應用程式：**進銷存**、**MES 模具廠**。現有的四個內建範本一併併入 MES，不再各自獨立。

**驗收：** 併發與重送測試下庫存餘額都正確；訂單到報工到出貨跑通。

**完成紀錄（2026-11-08）：** 進銷存、MES 模具廠兩個內建套件與四個範本併入 MES 已做完（設計見 `2026-11-08-inventory-mes-design.md`，實作與設計的出入見該文件 §19）。待決事項（選用依賴、逐列轉換、客戶主檔、兩套訂單並存）留給階段 2 的後續（s2c），三個應用程式暫時彼此獨立。

**階段 2 之後的順序（2026-11-10 更新）：** s2c 整合層（設計見 `2026-11-09-app-integration-design.md`）之後，依 [ERP 資料模型](2026-11-10-erp-data-model-design.md) 的工作單元對應：

1. **s2d 共用主檔：** 往來對象、聯絡人、品項全系統一份；移除模擬實體 `sales.customer`、`design.mold`，模具改為 MES 自有模組。
   - **任務管理（插在 s2d-1f 之後、s2d-1g 之前，使用者 2026-11-10 裁決）：** 平台共用的任務、留言與 @、任務規則、站內通知（設計見 `2026-11-10-task-management-design.md`）。站內通知因此從階段 4 提前，簽核沿用。套件格式用 7，s2e 的格式順延為 9、10。
   - **簽核流程（與任務管理一起做，使用者 2026-11-10 裁決）：** 組織骨架、簽核核心、進階動作、畫面、套件格式 8（設計見 `2026-11-10-approval-workflow-design.md` §18），以 CRM「設計案」情境驗收；依部門的資料範圍仍在階段 4。
2. **s2e 訂單與出貨依 ERP 慣例：** CRM 與 MES 都開時 CRM 訂單是唯一銷售訂單並建立工令；MES 與進銷存都開時完工入庫、出貨只用進銷存出貨單；移除 s2c 的 `stockOut`（設計見 `2026-11-11-order-workorder-shipment-design.md`）。分兩個依序交付的工作單元，每個合併點都驗完整既有行為（含 Demo）：
   - **s2e-a 追溯與履約核心：** 單據追溯到明細列、履約量核心（已完工量、已出貨量）、取消類狀態與追溯守衛、數量 3 位，以及 CRM、MES、進銷存各自單開時的適配；合併後 Demo 行為不得壞。
   - **s2e-b 應用程式間整合：** CRM、MES、進銷存兩兩之間的成對整合，覆蓋收掉重複的選單，跑通完整的訂單到出貨鏈；含補連動、成對卸除，以及訂單狀態依履約量自動轉移（使用者 2026-11-09 裁決）。
3. **s2f 訂單變更單：** 已確認訂單改量並連動下游（工令數量、出貨剩餘量依新量重驗與調整），不必取消重開。使用者 2026-11-09 接受「確認後不能改明細」為 s2e 第一版限制並排入此單元；排在 s2e-b 之後、s3c 之前，與 s3a、s3b 沒有依賴（主控判斷）。
4. **階段 3：** s3a 報表資料庫端聚合（進行中）→ s3b 期間鎖定等核心能力 → s3c 會計。

### 階段 3：會計（中）

- **開頭先做：** 報表在資料庫端聚合（目前是把資料載入記憶體再算），並重新壓測；會計的帳務量大，沒有這一步後面的報表撐不住。
- 期間鎖定、分組小計、損益表列結構、Top N。
- 應用程式：**會計**：科目、銷項與進項發票、收付款、傳票、應收帳齡、損益表、試算表、進銷項彙總。

**驗收：** 從發票到損益表，數字可下鑽回單據；試算表借貸平衡；由會計專業人士看過。

### 階段 4：簽核與 HRM（中）

- 依部門的資料範圍（組織架構、可自訂簽核流程、站內通知已隨任務管理提前做）（設計見 `2026-11-10-approval-workflow-design.md`）、依部門的資料範圍。
- 應用程式：**HRM**：員工、請假與假別餘額、出勤、費用報支。

**驗收：** 請假簽核後扣餘額；費用報支核准後進傳票。

### 階段 5：檢視與收尾（中）

- 看板、日曆。
