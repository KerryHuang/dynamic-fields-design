# 單據能力設計：帶值、狀態機、單據轉換、多層明細

> 2026-11-06｜路線階段 1 的四項通用能力｜前置：[路線](2026-11-06-erp-roadmap-design.md)、[核心設計](2026-11-03-dynamic-modules-design.md)、[應用程式套件](2026-11-06-app-package-design.md)
> 標「（我的判斷）」的是我代為決定、可以改的。

## 1. 範圍與鐵則

四項能力都是**由定義宣告的通用能力**，程式碼裡不出現報價、訂單、請購、採購這些名詞。驗收用兩個不相干的情境，各自只靠測試資料定義：

| 情境 | 單據鏈 | 帶值的例子 | 狀態 |
|---|---|---|---|
| 銷售 | 報價單 → 訂單 | 選客戶，帶出客戶名稱與付款條件；選品項，帶出品名與單價 | 草稿 → 已核准（唯讀）→ 已結案 |
| 採購 | 請購單 → 採購單 | 選廠商，帶出廠商名稱；選料號，帶出品名與單位 | 草稿 → 已核准（唯讀） |

沿用核心的反目標：不做執行期 DDL（新資料表只走 EF migration）、權限不 fail-open、不替個別模組手寫頁面、驗證不只做在前端。

這份文件**不做**：事件觸發與自動轉移（階段 2）、跨記錄驗證、不可修改分錄、多層簽核、附件與列印範本。

## 2. 選參照後帶值

### 2.1 宣告

參照欄位（`reference`，目標為動態模組）的 `Config.Fill`：

```json
{ "mode": "lock", "map": [ { "from": 31, "to": 12 }, { "from": 32, "to": 13 } ] }
```

- `from`：被參照模組的欄位 Id；`to`：本模組的欄位 Id。存檔格式用 Id，和規則、彙總一致；套件格式換成代號（§7）。
- `mode`：
  - `lock`：欄位值由系統填，使用者不能改。
  - `default`：只是建議值，使用者可以改。

### 2.2 語意（已成立的單據固定數值）

帶值是**快照**：選了參照（或參照改成另一筆）的那一刻，把目標記錄的值複製進本筆，之後存成本筆自己的欄位值。目標記錄日後被修改，本筆不會跟著變。這是路線風險 4 的做法，不需要額外機制。

| 時機 | `lock` | `default` |
|---|---|---|
| 新增，有選參照 | 一律以目標的值覆蓋 | 欄位空白才填 |
| 修改，參照改成別筆 | 一律以新目標的值覆蓋 | 欄位空白，或值與修改前相同（使用者沒動它）才填 |
| 修改，參照沒變 | 不動 | 不動 |
| 參照被清空 | 清空這些欄位 | 不動 |

目標的來源欄位值為空時，`lock` 會把本欄清成空；`default` 不填。

### 2.3 驗證與權限

- **後端是權威**：`ReferenceFill` 在 `RecordValueProcessor.Process` 之前算出要填的值，連同鍵一起交給 `Process`；這些鍵不受 `Config.ReadOnly`、欄位唯讀權限限制（系統填，不是使用者寫），但仍走該型別的 `Normalize`（長度、小數位照驗）。使用者送來的 `lock` 欄位值一律不採用。
- `lock` 的目的欄位必須設為 `Config.ReadOnly`（定義時驗證）。這樣沒有走帶值的路徑（直接 API、匯入）也寫不進去。
- **不洩漏**：複製時用使用者對目標模組的有效權限。看不到的來源欄位（欄位隱藏、沒有金額權限）、資料範圍外的記錄，一律不帶（`lock` 欄位視為來源為空）。目標記錄的可見性沿用 `ReferenceValidator` 已查的結果。
- **前端只負責即時顯示**：選了參照就用 `GET /records/{id}` 取回目標值，依 schema 的 `fill` 設定填進表單，`lock` 欄位顯示成唯讀。存檔時後端照上面規則重算，前端的結果不被信任。
- 明細列的參照欄位同樣生效（品項帶品名與單價），因為明細列和表頭走同一個 `Process`。

### 2.4 定義時驗證

- 本欄是參照欄位、目標是動態模組（不能指向既有實體，因為既有實體沒有欄位模型）。
- `from` 屬於目標模組、啟用中、不是 `reference` 以外的不相容型別；`to` 屬於本模組、啟用中，不是公式、彙總、自動編號。
- 型別相容：兩邊型別相同；或來源是自動編號而目的是文字；或來源是公式／彙總而目的是同為數字（整數、小數、金額、百分比）或日期的欄位。`enum`、`multienum` 不能帶（選項 Id 每個模組不同）；`reference` 只能帶到目標相同的參照欄位。
- `to` 不重複，也不是本參照欄位自己。

## 3. 狀態機

### 3.1 宣告

每個模組最多一個狀態機，掛在一個單選下拉（`enum`）欄位上，存成資料表 `Dynamic_Workflow`（一模組一列）：

```json
{ "statusFieldId": 5, "initialOptionId": 11,
  "states": [ { "optionId": 11 }, { "optionId": 12, "readOnly": true } ],
  "transitions": [ { "from": 11, "to": 12, "groupIds": [3] } ] }
```

- `states`：參與狀態機的選項（必須是該欄位啟用中的選項）。`readOnly` 見 §3.3。
- `transitions`：允許的轉移。`groupIds` 是誰能推進：有列群組，使用者屬於其中之一才行；**空陣列代表有該模組 Edit 權限的人都可以**（和 `FieldOptionScope` 的慣例一致：沒有任何列代表不限）。
- 系統管理員可以做任何**已定義**的轉移；沒定義的轉移，任何人都不行。
- 明細模組、擴充模組不能有狀態機（（我的判斷）：狀態屬於單據，明細列跟著表頭）。

### 3.2 後端強制

狀態的變更仍然走 `PUT /records/{id}`（沿用既有的存檔流程，不另開端點），由 `WorkflowEnforcer` 在 `Process` 之後檢查，匯入與新增走同一處（`RecordCreator.ValidateAsync`）：

- **新增**：沒送狀態就帶起始狀態；送了不是起始狀態的值，回 400（欄位錯誤，鍵為狀態欄位）。
- **修改**：狀態沒變就放行；變了則必須有 `from → to` 的定義，且使用者在該轉移的群組內（或系統管理員），否則 400，記錄不變。
- 狀態欄位不是 `readOnly` 之類的特殊欄位，一般欄位權限、規則照舊；狀態機是在其上再加一層閘。

（我的判斷）違反轉移用 400 欄位錯誤，而不是 403：前端本來就會把欄位錯誤顯示在狀態欄位旁，不用另外處理一種錯誤。

### 3.3 唯讀狀態

`readOnly` 的狀態下，記錄**除了狀態欄位以外都不能改**：

- `Process`：處於唯讀狀態的記錄，其他欄位一律視為不可寫（輸入忽略，與規則唯讀同語意）。
- 明細列的新增、修改、刪除都被擋（回 400，`_record` 鍵，訊息同全單唯讀）。
- 記錄不能刪除（`DeleteRecord` 回 409，訊息說明狀態唯讀）。
- 狀態欄位本身仍可轉移，因此「已核准 → 取消」之類的轉移不被鎖住；若不想讓人退回，就不要定義那條轉移。

和既有的 `ReadOnly` 規則（條件成立時全單唯讀）的關係：兩者獨立並存。狀態機的唯讀是**狀態的屬性**，由後端依狀態值強制；規則的唯讀是**條件**。同時存在時，兩者都要放行才能改。範本的「已結案全單唯讀」不需要改，但新定義建議用狀態機的 `readOnly`，因為它同時擋刪除與明細，規則版不擋刪除。

### 3.4 schema 與前端

schema 回傳 `workflow`：狀態欄位的 key、起始狀態、狀態清單（含 `readOnly`）、以及**目前使用者**能做的轉移清單（已依群組過濾，系統管理員為全部）。ETag 納入此段的雜湊，群組異動後自然失效。前端據此：

- 新增表單：狀態欄位固定為起始狀態；
- 編輯表單：狀態下拉只列「目前狀態＋可轉移的目標」；唯讀狀態下其他欄位與明細表格停用；
- 前端不做任何授權決定，只是縮小選項；後端照 §3.2 重新檢查。

### 3.5 定義時驗證

狀態欄位是本模組啟用中的單選 `enum`；每個 `optionId` 是該欄位啟用中的選項；起始狀態在 `states` 內；轉移的 `from`／`to` 在 `states` 內、`from ≠ to`、不重複；`groupIds` 存在；模組非明細、非擴充。停用狀態欄位時，若它掛著狀態機要擋（先移除狀態機）。

## 4. 單據轉換

### 4.1 宣告

資料表 `Dynamic_Conversion`（`Key` 唯一、來源模組、目標模組、啟用旗標、`DefinitionJson`）：

```json
{
  "sourceStates": [12],
  "header": { "sourceFieldId": 80, "copy": [ { "from": 21, "to": 71 } ] },
  "lines": {
    "sourceModuleKey": "…", "targetModuleKey": "…",
    "sourceLineFieldId": 90,
    "quantity": { "from": 41, "to": 91 },
    "copy": [ { "from": 42, "to": 92 } ]
  }
}
```

- `sourceStates`：來源單據目前狀態必須在其中才能轉；空代表不限（需要來源有狀態機才有意義，沒有就不限）。
- `header.sourceFieldId`：**目標表頭**上的參照欄位，指向來源表頭；轉換時由系統填入，這就是可追溯的來源。`header.copy` 是表頭欄位對應。
- `lines`（可省略）：來源明細模組與目標明細模組；`sourceLineFieldId` 是**目標明細列**上指向來源明細列的參照欄位；`quantity.from` 是來源明細的數量欄位、`quantity.to` 是目標明細的數量欄位；`copy` 是明細欄位對應。
- 沒有 `lines` 的轉換是表頭轉換（例如潛在客戶 → 商機）：同一張來源**最多轉一次**。

### 4.2 追溯

追溯就是兩個普通的參照欄位，沒有另外的連結表：

- 目標表頭的 `sourceFieldId` → 來源表頭；來源的明細頁因此自動出現「反向關聯」分頁，列出由它轉出的單據。
- 目標明細列的 `sourceLineFieldId` → 來源明細列。
- 這兩個欄位必須是 `Config.ReadOnly`（定義時驗證），一般存檔改不動；只有轉換流程（帶 `SystemKeys` 的內部請求，見 §4.4）寫得進去。

### 4.3 剩餘量

來源明細列的**已轉量**＝所有未刪除、`sourceLineFieldId` 指向該列的目標明細列的數量總和；**剩餘量**＝來源數量 − 已轉量。算法即時查，不另存計數器，所以目標單據改量、刪除都自動反映。

- 一次轉換每列的數量必須 > 0 且 ≤ 剩餘量，否則 400（鍵 `lines[i].quantity`）。至少要轉一列。
- 取消目標單據**不會**自動釋放數量；要釋放就刪除該單（唯讀狀態的單據不能刪，見 §3.3）。（我的判斷，列入未解項。）
- 目標單據事後改大數量可能超轉：本階段不檢查（列入未解項）。

查詢：`GET /records/{id}/conversions` 回傳此來源可用的轉換，每個含每列的 `quantity`、`converted`、`remaining`，以及已轉出的目標單據清單。

### 4.4 併發：剩餘量檢查和轉換一起做

兩人同時轉同一張來源，不得超轉。做法：**把來源表頭記錄的 `RowVersion` 當互斥鎖**。

1. 轉換的交易一開始就把來源記錄的 `RowVersion` 換新值（`Record.RowVersion` 本來就是 EF 的 concurrency token，更新語句帶 `WHERE RowVersion = 舊值`）。
2. 然後才算剩餘量、建立目標單據，最後提交。
3. 兩個交易同時進來：第二個的更新要嘛等第一個提交後發現 `RowVersion` 已變（0 列受影響 → `DbUpdateConcurrencyException` → 409），要嘛在 SQLite 因寫鎖而得到 `SQLITE_BUSY`；後者在轉換處理器內轉成 409。**不論哪種，都是 409，沒有超轉。**
4. 請求可帶來源的 `rowVersion`，與目前不符直接 409（使用者看到的是舊畫面）。

這個做法不依賴 SQLite 的單一寫入者特性：SQL Server 讀已提交下，第二個更新會等第一個交易的列鎖，放開後條件不成立，同樣失敗。代價：轉換會讓來源記錄的 `RowVersion` 變動，正在編輯來源的人存檔會收到 409（與彙總重算的行為一致，風險 33）。

測試要真的併發：同一個 `TestApp`（檔案型 SQLite）上用 `Task.WhenAll` 同時送出多個轉換請求，斷言「已轉量總和 ≤ 來源數量」，且至少有一個成功、其餘都是 409。

### 4.5 權限與流程

- 使用者要能讀取來源記錄（動作軸 Read、資料範圍）。
- 建立目標單據走既有的 `CreateRecordHandler`：目標模組的 Add 權限、驗證、規則、自動編號、彙總、帶值、狀態機（目標從起始狀態開始）全部照舊。
- 複製來源值時用使用者對來源模組的有效權限：看不到的來源欄位不複製。
- 請求可帶表頭欄位覆寫值（例如改交期）；明細列只能指定來源列與數量。

### 4.6 定義時驗證

來源、目標模組不同、都是啟用中的獨立模組、非明細；`header.sourceFieldId` 是目標表頭的 `reference`（目標是來源模組）且 `Config.ReadOnly`；有 `lines` 時：兩個明細模組分別是來源表頭、目標表頭的明細，`sourceLineFieldId` 是目標明細模組的 `reference`（目標是來源明細模組）且 `Config.ReadOnly`，數量欄位是 `integer`／`decimal` 且兩邊啟用；`copy` 的型別相容規則同 §2.4（`from`／`to` 各屬正確模組、`to` 不重複、不含追溯欄位）；`sourceStates` 需來源有狀態機，且為其 `states` 內的選項。

## 5. 多層明細（查證結論）

**結論：目前核心的明細只有一層**，`FieldRules.CheckDetailAsync` 明確擋掉兩種情況：表頭本身是別的模組的明細（「表頭模組不能是擴充模組或其他模組的明細」）、以及自己有明細的模組再當明細（「這個模組有自己的明細，不能再當明細」）。`DetailWriter` 一次只處理一個層級，彙總也只支援直接子記錄（核心設計 §8）。

**工令 → 製程 → 報工需不需要多層明細？不需要。** 理由是三層裡只有「工令 → 製程」需要在同一張畫面逐列編輯、同一個交易存檔；報工是現場事後陸續登錄的事件，每次一筆、各自存檔，用一般參照（`lookup`）就夠：

- 工令是表頭，製程是它的明細（現有能力）。
- 報工是獨立模組，用一般參照指向製程；製程的明細頁自動有「報工」反向關聯分頁，可以直接新增報工；製程可以用「一般參照彙總」把報工數量加總回來（核心設計 §9、風險 33）。
- 這個組合已有自動測試驗證（`ThreeLevelDocumentTests`）：報工新增、修改、刪除後，製程列上的累計報工量即時更新。

不需要的代價是：報工沒有「隨工令一起編輯」的巢狀表格，也沒有工令層級直接彙總報工的欄位（彙總只有一層，要看工令的累計要從製程那一列再加一層彙總，彙總不支援孫記錄）。這些列為缺口表的「待階段 2 事件」項目：階段 2 的事件觸發可以讓報工回寫工令的累計量。若之後確實需要在一張畫面編輯三層，要改 `DetailWriter`（遞迴準備與寫入）、`RollupRecalc`（連鎖重算）與前端的巢狀表格，工程量大，這次不做。

## 6. 資料與 API

### 6.1 Migration

`DocumentFlow` migration 新增兩張表：`Dynamic_Workflow`、`Dynamic_Conversion`。`Field.Config.Fill` 存在既有的 JSON 設定裡，不需要資料表。既有資料與定義不受影響（新欄位都有預設值或可為 null）。

### 6.2 端點

| 用途 | 端點 |
|---|---|
| 狀態機（設計器） | `GET/PUT/DELETE /modules/{key}/workflow` |
| 轉換定義（設計器） | `GET/POST /conversions`、`GET/PUT/DELETE /conversions/{key}` |
| 此記錄可用的轉換與剩餘量 | `GET /records/{id}/conversions` |
| 執行轉換 | `POST /records/{id}/conversions/{key}/convert` |
| 帶值設定 | 欄位設定 `PUT /fields/{id}` 的 `config.fill` |

設計器端點需要設計器（`DYN00000`）的 Edit 權限，與其他設計端點相同。

## 7. 序列化進應用程式套件

套件預留 `workflows[]`、`conversions[]`，目前只能是空陣列（套件規格 §4.6）。本設計的定義形狀可以直接放進去，只需要把 Id 換成代號（沿用套件規格 §4.7 的限定名稱）。**不修改套件程式**；套件格式要升到 3 才能載入非空陣列（套件規格的決策）。

`workflows[]` 元素：

```json
{
  "module": "quote",
  "statusField": "status",
  "initial": "draft",
  "states": [ { "option": "draft" }, { "option": "approved", "readOnly": true } ],
  "transitions": [ { "from": "draft", "to": "approved", "groups": ["salesLead"] } ]
}
```

`conversions[]` 元素：

```json
{
  "code": "quoteToOrder",
  "name": { "zh-TW": "報價轉訂單" },
  "source": "quote", "target": "order",
  "sourceStates": ["approved"],
  "header": { "sourceField": "order.fromQuote", "copy": [ { "from": "quote.customer", "to": "order.customer" } ] },
  "lines": {
    "sourceModule": "quoteLine", "targetModule": "orderLine",
    "sourceLineField": "orderLine.fromQuoteLine",
    "quantity": { "from": "quoteLine.qty", "to": "orderLine.qty" },
    "copy": [ { "from": "quoteLine.item", "to": "orderLine.item" } ]
  }
}
```

帶值寫在欄位設定裡（`modules[].blocks[].fields[].config.fill`），`map` 的 `from` 用被參照模組的限定欄位名、`to` 用本模組的欄位代號：

```json
"fill": { "mode": "lock", "map": [ { "from": "customer.name", "to": "customerName" } ] }
```

套件的 `config` 現有**未知鍵檢查**（套件規格 §4.8）；加入 `fill` 時要把它列為合法鍵。選項引用用 `選項代號`（`status`、`approved` 這類），群組用 `groups[].code`；轉換的追溯欄位與數量欄位在套件的驗證層要加上與 §4.6 相同的檢查。這些屬於套件作者的工作，這次只保證形狀對得上。

## 8. 驗收

後端：每項能力的單元與整合測試先寫（見實作計畫的提交順序）；銷售與採購兩個情境各一份端到端測試，**測試資料自己定義模組**，被測程式碼沒有任何業務名詞；併發測試見 §4.4。前端：型別檢查、單元測試、建置；有畫面的部分以本機實機走過（設計器設定帶值、狀態機、轉換；執行期選參照帶值、狀態轉移、轉換對話框顯示剩餘量）。

## 9. 未解與風險

1. **取消不釋放數量**：目標單據取消後，已轉量仍計入；要釋放必須刪除該單。之後可在狀態定義加「釋放來源數量」旗標。
2. **目標單據事後改大數量不檢查**：轉成訂單後，使用者可以把訂單明細改大而超過來源。需要時在明細存檔加檢查（同一把鎖）。
3. **轉換會讓來源的 `RowVersion` 變動**：同時編輯來源的人會收到 409。
4. **來源明細列被刪或改量**：來源單據建議用唯讀狀態鎖住（`sourceStates` 只允許唯讀狀態），否則剩餘量可能變成負數；目前即時計算會顯示負的剩餘量，不另外阻擋。
5. **帶值用目標記錄的目前值**：目標是前一刻剛被別人改的值也照帶，沒有版本比對（快照語意本來就是「選的那一刻」）。
6. **狀態轉移的權限判斷不看欄位層權限**：轉移由群組決定，使用者即使對狀態欄位是欄位層唯讀，只要送上來的值有變仍會被當作轉移檢查；欄位層唯讀會先把輸入忽略，所以實際上轉移不會發生，這是預期行為。
7. **轉換定義停用或刪除後**：已轉出的單據保留追溯欄位，不受影響；只是不能再用該定義轉換。
