# 階段 1c 設計：套件單據能力、附件、列印範本、內建 CRM 與銷售

> 2026-11-07｜路線階段 1 的收尾｜前置：[路線](2026-11-06-erp-roadmap-design.md)、[應用程式套件](2026-11-06-app-package-design.md)、[單據能力](2026-11-06-document-flow-design.md)
> 標「（我的判斷）」的是我代為決定、可以改的。這份文件只寫決定與理由，細節以程式與測試為準。

## 1. 範圍與順序

五段，各自 commit，順序不改；做不完就停在段落邊界。

1. 套件支援單據能力（狀態機、轉換、帶值、報表、ExportApp）。
2. 附件欄位。
3. 列印範本。
4. 內建「CRM 與銷售」應用程式。
5. Demo。

鐵則不變：程式裡不寫業務名詞，CRM 只是 `apps/*.app.json` 加上測試；採購情境只放測試專案。

## 2. 第 1 段：套件格式升到 3

### 2.1 版本

`formatVersion` 提高到 3（單據能力設計 §7 的約定）。讀取器接受 2 與 3：

- 版本 2 的檔案照舊：`workflows`、`conversions`、`reports`、`printTemplates` 必須是空陣列，`config` 不認得 `fill`。這維持 v2 讀取器「保留 section 非空就拒絕」的 fail-closed 語意。
- 版本 3 才能帶這幾個 section 與 `fill`。`dashboards`、`events` 仍是保留 section。
- 寫出（ExportApp）一律用 3。

### 2.2 形狀

全部用代號，不出現資料庫 Id。選項用「選項代號」（模組內唯一），欄位用限定名 `<模組代號>.<欄位代號>`。

- `workflows[]`：`{ module, statusField, initial, states[{option, readOnly}], transitions[{from, to, groups[]}] }`，一模組一個。
- `conversions[]`：`{ code, name, active, source, target, sourceStates[], header{sourceField, copy[]}, lines{sourceModule, targetModule, sourceLineField, quantity{from,to}, copy[]} }`。`code` 就是 `Conversion.Key`（全站唯一，慣例以應用程式 id 當前綴）。
- `reports[]`：`{ code, name, shareWith[], definition }`。`definition` 對應 `ReportDefinition`，欄位引用換成限定名，選項值寫 `opt_<選項代號>`。
- 帶值：欄位 `config.fill = { mode, map[{from, to}] }`，`from` 是被參照模組的限定欄位名，`to` 是本模組的欄位代號。

### 2.3 開啟

沿用既有交易：實例化 → 啟用 → 以下新步驟 → 記帳，任一步失敗整批回滾。

- 帶值在實例化的「預設值」步驟寫入（那時所有欄位都已存在）。指向被排除欄位的對應會被丟掉。
- 啟用之後：狀態機（`SaveWorkflowRequest`）、轉換（`CreateConversionRequest`）、報表（`CreateReportRequest`＋`SetReportSharesRequest`），全部走既有指令，既有驗證照跑。
- **轉移的群組沒有對應時，整條轉移不建並警告**（我的判斷）：轉移的空群組代表「有 Edit 權限的人都可以」，如果把略過的群組拿掉就變成放寬，所以寧可少一條轉移。代價：套件開出來後該轉移沒人能做（含管理員），要事後到設計器補。
- 轉換 `code` 與現有轉換重複時，預覽與開啟回錯誤，不自動改名。
- 新增資料表 `Dynamic_AppReport`（`AppId`、`ReportId`、`Code`），用途是匯出重建 `reports[]` 與刪除應用程式時一併刪除。狀態機屬於模組、轉換以「來源與目標模組都是成員」判定，不另建關聯表。

### 2.4 匯出（ExportApp）

`GET apps/{key}/export`：由目前的成員模組重新產生套件，不保留開啟時的原文。

- 模組代號用 `AppModule.Code`；欄位、區塊、選項沿用範本匯出的 `Field.Key`、`b_<id>`、`o_<id>`。
- 參照目標：成員模組用代號；別的應用程式的模組寫成 `{key: 代號, app}` 並補進 `requires.apps`；既有實體補進 `requires.entities`；指向「不屬於任何應用程式的模組」表達不了，該欄位不匯出並記 warning。
- 補上範本匯出缺的欄位層例外與選項範圍（`fieldAccess`、`optionScopes`），群組以 `Key` 當代號輸出到 `groups[]`。
- 狀態機、轉換、報表、帶值照上面形狀輸出；引用到停用或未匯出的欄位時該項不匯出並記 warning。

### 2.5 刪除

`DeleteApp` 同一交易內多刪三樣：應用程式的報表（`AppReport`）、成員模組間的轉換（既有的 `ModuleRemover` 已會刪）、狀態機（隨模組級聯）。盤點時，屬於這個應用程式的報表不算「外部引用」。

### 2.6 驗收

`AppPackageV3Tests`（WebAPI 整合測試）：

1. v3 套件開啟後，狀態機實際擋非法轉移、轉換實際執行、帶值實際帶、報表建出且分享。
2. 匯出再匯入到另一個空資料庫，上述行為都還在。
3. v2 檔案帶 `workflows` 被拒；`fill` 在 v2 被拒；v3 的引用錯誤整份拒絕；開啟中途失敗不留殘餘。
4. 關閉後：轉換不能執行（目標寫入被擋）、狀態機不能推進；重新開啟後恢復。
5. 重複開啟冪等（409）。

## 3. 第 2 段：附件欄位

### 3.1 資料模型

新增欄位型別 `attachment`（第 21 種）。值存在記錄的 JSON 裡，是檔案描述陣列 `[{ id, name, size }]`：`id` 是系統產生的 32 碼十六進位，同時是磁碟上的儲存名；`name` 只用來顯示與建議下載檔名；`size` 是位元組。不另開中繼資料表，所以這一段沒有 migration。附件欄位不可篩選、不可排序、不進索引，也不進報表（`ReportFieldEligibility` 排除）。明細模組不能建附件欄位（建立時回 400），附件只掛在表頭記錄。

### 3.2 檔案怎麼進來

- **一般存檔（`PUT records/{id}`、匯入）只能保留或移除既有的檔案。** `AttachmentHandler.Normalize` 拿送來的 id 對照記錄目前的值，不在裡面就回 400「附件只能透過上傳加入」，名稱與大小以舊值為準。所以沒有任何方式用記錄存檔偽造出一個檔案參照。
- **新檔案只經 `POST records/{recordId}/attachments/{fieldId}`（multipart，欄位名 `file`）。** 只能對已存檔的記錄上傳（新增模式的畫面請使用者先存檔）。上傳走和編輯同一套檢查：模組可寫（Closed 回 409）、Edit 權限與資料範圍、欄位可見且目前可寫（規則唯讀、狀態機唯讀狀態都擋）、RowVersion 與歷程照常更新。
- 檔案先寫磁碟、後寫記錄；記錄寫入失敗就刪掉剛寫的檔案。

### 3.3 安全邊界

| 面向 | 做法 |
|---|---|
| 檔名 | 從不用來組路徑。去掉兩種分隔符前的路徑與控制字元，限制 150 字並保留副檔名；磁碟上只用產生的 id（再分兩層目錄），儲存層自己再驗一次 id 格式 |
| 副檔名 | **白名單**，預設 `pdf png jpg jpeg webp txt csv docx xlsx pptx`（不含 svg、html、壓縮檔與任何可執行、腳本類）；沒有副檔名、只有結尾點的一律拒絕；`a.pdf.exe` 看最後一段 |
| 大小與數量 | `Attachments:MaxBytes`（預設 10 MiB）、`MaxFilesPerField`（預設 20）。串流寫入時逐位元組累計，超過就中止並刪掉寫到一半的檔 |
| 下載 | `GET records/{recordId}/attachments/{fieldId}/{fileId}` 和讀記錄同一套檢查（模組可讀、Read 權限、資料範圍、欄位看得到），而且檔案必須是這筆記錄這個欄位**目前的值**列出的；軟刪除的記錄、被移除的檔案、別筆記錄的檔案 id 一律 404 |
| 回應標頭 | 一律 `application/octet-stream`（不依檔名猜 MIME）、`Content-Disposition: attachment`、`X-Content-Type-Options: nosniff`、`Content-Security-Policy: sandbox; default-src 'none'`、`Cache-Control: private, no-store`。站內不會解譯或執行 HTML／SVG |
| 設定端點 | `GET attachments/settings` 只回上傳開關、原因與上限，不含伺服器路徑 |

### 3.4 生命週期

- **從記錄移除檔案**、**軟刪除記錄**：實體檔案都保留（軟刪除的記錄可能被還原）。
- **永久清除**（刪模組、欄位等）：不同步刪檔，檔案變成沒人參照的孤兒。
- **孤兒清掃**：系統管理員專用 `POST attachments/sweep?graceMinutes=60`。掃出所有記錄（含軟刪除）目前參照的 id，沒被參照且最後寫入時間超過寬限時間的檔案才刪；寬限時間讓「已寫檔、記錄尚未提交」的上傳不被誤刪。清掃不自動排程，營運時由管理員或排程呼叫。
- **Closed 模組**：可以下載，不能上傳（409）。

### 3.5 Demo 與免費主機

- 公開 Demo 站（`Demo:LoginEnabled=true`）**預設關閉上傳**，既有附件仍可下載；可用 `Attachments:UploadEnabled` 明確覆寫。關閉時上傳回 409，並在畫面上顯示原因（`Attachments:DisabledReason`，沒設就用各語系的預設說明）。理由：任何人不用密碼就能登入的站台，不該讓人往磁碟寫檔。
- **Render 免費方案的磁碟在每次重新部署時會被清空**，所以附件不會跨部署保留；Demo 就算開了上傳，檔案也會消失，這是預設關閉的另一個理由。要長期保存附件需要掛持久磁碟（付費），不在這個專案的範圍。
- 儲存根目錄 `Attachments:Root`；沒設時放資料庫檔旁的 `attachments`，記憶體資料庫則用暫存目錄。

### 3.6 匯入、匯出、報表

- **匯入 CSV**：附件欄位的欄會回明確錯誤「附件欄位不支援匯入」（逐列報錯，不 500）。
- **匯出 CSV／xlsx**：儲存格是檔名以 `; ` 連接，不含內容。
- **報表**：附件欄位不在可選欄位裡。
- **套件／範本**：附件欄位的定義可以匯出入（它只是欄位型別）；檔案內容不隨套件走。

### 3.7 驗收

後端 WebAPI 測試涵蓋：往返與回應標頭、路徑穿越檔名、副檔名白名單（含雙副檔名、無副檔名）、大小與數量上限且不留殘檔、偽造 id 被拒與保留／移除正常、下載的權限與別筆記錄的 id、軟刪除、永久清除後清掃（含寬限）、清掃需系統管理員、Closed、上傳關閉的 409 與設定端點、Demo 預設關閉與明確覆寫、明細模組禁建、匯出與匯入與報表不 500。前端有 `AttachmentInput` 元件測試。

## 4. 第 3 段：列印範本

### 4.1 資料模型
`Dynamic_PrintTemplate`（ModuleId、Key、NameI18n、Body、Active），(ModuleId, Key) 唯一，隨模組級聯刪除。一個模組可有多份範本；明細模組沒有自己的範本，由表頭範本的 `{{#each 明細模組鍵}}` 迴圈列印。

### 4.2 語法與引擎
純文字 HTML。`{{f_12}}` 取欄位值，`{{_title}}`、`{{_printedAt}}` 是系統值，`{{#each 明細模組鍵}}…{{/each}}` 對每列重複（不可巢狀，迴圈內 `{{_index}}` 為列號）。引擎只掃描範本一次，替換進去的值不會再被當成占位符。後端算值：先過有效欄位權限（隱藏欄位、無 pricing 的金額欄位印空白），再用既有格式（數字、日期、金額）轉字串，最後 HTML 跳脫。缺範本回 404、欄位被停用或不存在印空白，不丟 500。

### 4.3 安全
- 儲存時 `PrintTemplateSanitizer` 以白名單重建標籤（不是用 regex 刪字）：移除 script／style／iframe 等、所有 `on*` 事件屬性、`javascript:` 等非白名單協定的連結。
- 輸出時所有值再跳脫一次（第二層）。
- 前端預覽用 `sandbox="allow-same-origin allow-modals"` 的 iframe（無 `allow-scripts`）以 `srcdoc` 載入，由瀏覽器列印；不引入 PDF 函式庫。
- 列印前先檢查讀取權限與資料範圍（own／all），與詳情頁一致。

### 4.4 套件
格式 3 的 `printTemplates` 區段（module、code、name、active、body）。body 內欄位以 `<模組代號>.<欄位代號>` 寫，開啟時換成 `f_<id>`、匯出時換回代號；引用被排除的欄位時警告並印空白。格式 2 帶 `printTemplates` 仍拒收。

### 4.5 驗收
Application 單元測試 62（sanitizer、引擎）、WebAPI 測試 29（權限、XSS、缺範本、停用欄位、明細迴圈）、套件往返與刪除清理；前端 PrintTab／i18n spec。

## 5. 第 4 段：內建「CRM 與銷售」

### 5.1 形狀
`poc/backend/apps/crm-sales.app.json`（formatVersion 3，id `crm-sales`），隨 WebAPI 發行，由 `AppCatalog` 啟動時載入驗證。**沒有開啟之前不產生任何模組、選單或資料**；開啟走既有的 `POST apps/packages/crm-sales/open`，從空系統即可。程式碼裡沒有任何 CRM 專用邏輯：所有行為都是套件宣告，換成採購情境（請購 → 採購單）用同一組能力（測試內定義，不出貨）。

### 5.2 模組（鍵一律 `crm-` 開頭）
潛在客戶 `crm-lead`、客戶 `crm-customer`、聯絡人 `crm-contact`、產品 `crm-product`、商機 `crm-opportunity`、互動紀錄 `crm-activity`（原名「活動」）、行銷活動 `crm-campaign`、報價單 `crm-quote` ＋明細 `crm-quote-line`、訂單 `crm-order` ＋明細 `crm-order-line`。群組兩個：「CRM 業務」（`sales`）、「CRM 業務主管」（`manager`）；開啟時由管理員對應（新建、對應既有、略過）。產品對業務唯讀。

**任務管理之後的修改（套件 1.1.0、格式 7）**：「活動」改名「互動紀錄」，拿掉「已完成」欄位，只記已發生的電話、拜訪、郵件、會議，待辦改用任務。新增「行銷活動」：名稱（標題）、類型（展覽、研討會、線上活動）、開始日、結束日、地點、狀態（規劃中、確定舉辦、已結束、取消）、規劃、佈置、回饋三個負責人、說明；業務與業務主管權限同互動紀錄。任務規則 `crm-campaign-tasks`（行銷活動派工）在建立時觸發：規劃活動內容（規劃負責人，開始日 −62 天）、展場佈置（佈置負責人，開始日 −1 天，只限展覽）、活動回饋（回饋負責人，結束日 +12 天）。設計見[任務管理](2026-11-10-task-management-design.md) §10。已開啟過舊版 CRM 的資料庫不會升到 1.1.0（開啟回 409 已開啟），不自動改名或移除欄位，也不會出現行銷活動與派工規則；要用新版請重建資料庫。

**設計案（套件 1.2.0、格式 7）**：新增設計案 `crm-design-case` ＋明細設計圖 `crm-design-drawing`，跑「業務主管建案並指派業務，業務與設計人員依狀態來回派工，設計上傳圖、業務記下客戶意見再交回設計，兩輪後送簽，由送出人的直屬主管同意，最後結案」的故事（簽核設計 §17.7）。
- **表頭**：案號（自動編號 `DC-{yyyyMM}-{000}`）、案名（標題）、客戶（共用主檔往來對象，限客戶或兩者）、負責業務、設計負責人、需求說明、狀態、設計圖檔（附件）。**明細**設計圖：版本、圖檔名稱、上傳人、客戶意見。
- **圖檔放表頭**：平台規定明細模組不能建附件欄位（§3.1），所以圖檔放表頭的附件欄位「設計圖檔」，明細列用「圖檔名稱」對應檔名，靠檔名對版次，不能在明細列直接點下載。使用者已裁決照此做（2026-11-12）。「平台先支援明細附件」記為構想；費用報支的明細附收據也用得上。
- **狀態機**：需求確認 → 設計中 → 客戶確認中 → 待主管確認 → 結案，另可從前三個狀態取消，客戶確認中可退回設計中。結案、取消是唯讀狀態。轉移限制的群組（空陣列表示有編輯權的人都可以）：需求確認 → 設計中是業務、主管；設計中 → 客戶確認中是設計、業務；客戶確認中 → 設計中、→ 待主管確認是業務；待主管確認 → 結案、各取消是主管。取消不從待主管確認出發，免得落進簽核鎖定狀態的後續範圍。
- **群組與權限**：新增群組 `designer`（CRM 產品設計）。設計人員對設計案可讀可改、不能新增與刪除，明細模組跟著表頭；往來對象的貢獻區段給設計人員唯讀（才看得到客戶名稱）。頂層 `fieldAccess` 讓設計人員對客戶、負責業務、設計負責人、需求說明唯讀（寫入被忽略，不是整筆拒絕）。
- **任務規則（三條）**：`crm-design-case-intake`（建立時，一次，「確認需求並交設計」給負責業務，讓主管建案後業務馬上收到指派）、`crm-design-case-draw`（狀態變成設計中，每次，「依需求繪製／修改設計圖」給設計負責人）、`crm-design-case-confirm`（狀態變成客戶確認中，每次，「將設計圖交客戶確認」給負責業務）。每次進入該狀態就派一批，上一批沒完成就不重派（任務設計 §5.2），來回幾輪就派幾批。三條規則的每個任務都帶任務層條件「狀態不是取消、也不是結案」，所以案子取消或結案時，未完成的任務由系統自動取消（留言串記條件不成立）；來回修改時狀態不是取消或結案，「上一輪沒完成就不重派」不受影響。
- **簽核**：套件不含簽核流程，因為簽核流程要等套件格式 8（簽核 a5）才能放進套件。a5 之前，一般安裝的「待主管確認」不需簽核、不鎖定，只有結案與取消唯讀；Demo 由產生器以既有 API 建立流程「設計案主管確認」（掛在待主管確認，一關，簽核人是送出人（業務群組，通常是負責業務本人）的第 1 層直屬主管，來源 `manager`，退回到設計中；送簽轉移開給整個業務群組，所以另一位業務代送時簽核人會是代送者的主管，依欄位找負責業務的主管排第二版，見簽核設計 §20.4 第 4 項），並把「客戶確認中 → 待主管確認」標成需簽核。a5 之後改由套件內建。流程沒有條件欄位也沒有可編輯欄位，所以簽核鎖定的欄位只有附件「設計圖檔」；需求說明與明細在待主管確認不鎖。
- **已知限制**：
  - 主管同意（待主管確認）之後沒有回頭路：不能取消，也不能退回修改，只能結案，要改就另開新案。原因是「待主管確認 → 取消」會讓取消變成鎖定延伸的狀態，其他取消轉移都得改成需簽核；退回修改則要目標狀態可編輯，格式 7 的狀態沒有這個屬性。a5（格式 8）支援後再加「待主管確認 → 設計中」（主管，目標標可編輯）。
  - 設計人員的唯讀欄位（客戶、負責業務、設計負責人、需求說明）以最嚴的群組為準：同一個人同時屬於業務與產品設計群組時，這四欄會被當成唯讀，存檔成功但值不變、沒有錯誤訊息。業務兼設計的人不要加進產品設計群組；開啟時也不要把兩個套件群組對到同一個既有群組。
- **升級限制**：已開啟過舊版 CRM 的資料庫不會升到 1.2.0（開啟回 409 已開啟），不會出現設計案；要用新版請重建資料庫，同 1.1.0。

### 5.3 流程
- 潛在客戶（已確認）→ 客戶、→ 商機：表頭轉換，各只能轉一次，追溯欄位唯讀。
- 商機（提案報價／議價）→ 報價單：表頭轉換（一個商機一張報價單）。
- 報價單（已核准）→ 訂單：含明細的部分轉換，剩餘量即時計算、轉換用來源 `RowVersion` 當互斥鎖，同時轉不會超轉。
- 狀態機：潛在客戶、商機階段、報價單（草稿 → 待核准 → 已核准／已退回，**核准與退回只有業務主管**，已核准唯讀）、訂單（已完成、已取消唯讀，取消僅主管）。
- 帶值：報價單選客戶帶名稱、電話、Email、地址（`lock`）；報價明細選產品帶品名、單位、單價（`default`：建議值，業務可改價）。訂單明細的品名、單價是轉換時複製的快照，不再帶值，所以產品日後改價不影響已成立的單據。
- 列印範本：報價單 `quote-sheet`（客戶資料、明細表、小計／稅額／總計）。
- 報表：商機階段分布（圓環圖）、各業務訂單金額（未稅，長條圖；彙總欄位不能直接進報表，所以對明細金額加總）。`dashboards` 區段在格式 3 仍是保留段落，所以沒有看板卡片，以兩份報表代替。

### 5.4 驗收（`CrmSalesAppTests`）
未開啟時完全看不到；空系統開啟；潛在客戶一路走到分兩次轉訂單；業務不能核准；報價單列印（含 XSS 跳脫）；8 個請求同時轉同一張報價單不超轉；關閉後可讀、參照仍顯示、寫入 409、重開資料仍在；採購情境跑同一組能力。

### 5.5 設計案的 ERP 對照

| ERP 情境 | 典型流程 | Formwright 表達方式 |
|---|---|---|
| 客製設計需求（訂製品、ODM） | 業務接單 → 設計 → 客戶確認 → 主管核可 | 設計案狀態機；客戶確認後的核可是一關簽核，簽核人是送出人的直屬主管 |
| 工程變更申請（ECR／ECO） | 提出 → 評估 → 核准 → 發行，每次改版留版次 | 「設計圖」明細記版次與客戶意見；檔案在表頭附件 |
| 銷售待辦 | 依狀態自動派工 | 任務規則 `onFieldBecomes` 加 `everyTime`，來回幾輪就派幾批 |

主流 ERP 把圖檔掛在版次（文件管理）上。Formwright 第一版明細不能放附件，所以圖檔先放表頭，靠檔名對應版次。

設計案不和既有主檔或單據重複：客戶用共用主檔的往來對象，互動紀錄沿用 CRM 既有模組，不另建「客戶回饋」模組；客戶對某一版的意見記在設計圖明細的「客戶意見」，需要整段討論時用任務留言（可附圖與 @）。

## 6. 第 5 段：Demo 預設開啟 CRM

### 6.1 做法
- `AppOpener`：把開啟應用程式的實作從 `OpenAppHandler` 抽出，回傳代號對照（`TemplateIdMap`），HTTP 路徑行為不變。Demo 產生器在已經是系統管理員的交易內直接呼叫，不走權限 pipeline。
- `DemoStructure` 在補完權限之後開啟 `crm-sales`，群組對應：套件的 `sales` → Demo 既有的 `sales`、`manager` → `sales-manager`。所以 sales01、sales02、manager01 登入就有權限走完整條流程，**沒有新增任何帳號或權限機制**。`DemoContext.Crm` 另存 CRM 的對照（CRM 的模組代碼 order 等與四個範本重名）。
- `CrmScenario`（種子 20261107，與其他情境相同的確定性規則）：8 項產品、10 家客戶與聯絡人、12 筆潛在客戶（4 新線索、3 已聯繫、3 已確認、2 流失；2 筆已轉客戶與商機）、12～13 筆商機（六個階段齊全）、18 筆互動紀錄、10 張報價單（2 草稿、2 待核准、1 已退回、5 已核准）、4 張訂單（1 張報價單分兩次轉、1 張只轉一部分、1 張報價單轉單後訂單取消）。全部走一般的建立、更新、轉換指令，以 sales01、sales02、manager01 的身分執行，所以權限、狀態機、帶值都真的跑過一次。
- 行銷活動（任務管理 t5）：sales01 三天前建「春季工具機展」（展覽，約 88 天後開展、展期三天，三個負責人是 sales01、sales02、sales03），sales02 兩天前建「智慧製造研討會」（約 60 天後，不產生展場佈置）；另有兩則含 @ 的任務留言。為此新增 Demo 帳號 `sales03`（業務三，`sales` 群組）。
- `CRM 儀表板`：引用套件自帶的兩份報表（`dashboards` 區段在格式 3 仍保留，套件放不了），指派給 sales-manager、sales、mis。
- 設計案（簽核 a6）：Demo 另有三筆設計案（結案、第二輪客戶確認中、設計中），流程見 §5.2。新增帳號 `designer01`（設計人員，群組 `design`「產品設計」、部門「產品設計部」，上級總經理室、主管 designer01）；套件的 `designer` 對到 Demo 的 `design`。設計圖與留言附件由產生器在伺服器端寫入虛構的 640×400 圖檔：`ServerUploadScope` 只在產生器的時間軸執行期間略過「環境停用上傳」這一道檢查，權限、副檔名、大小上限照常，HTTP 請求不受影響，所以 Demo 站訪客仍不能上傳。簽核流程（客戶確認中 → 待主管確認，負責業務的直屬主管一關）在 a5 之前由 `DemoApprovals` 用既有 API 建立，a5 讓套件內建後刪除。
- 資料全是虛構：公司與人名自編、電話用 555 號段、Email 一律 `example.com`，沒有任何競品或真實公司名稱。

### 6.2 不變的東西
既有的四個情境、帳號與報表、儀表板不動（只新增）。Demo 映像（`Dockerfile.demo`）是建置時就產生資料，所以執行時啟動時間不受影響，只有建置多花幾秒。

### 6.3 已知限制
- 已經產生過舊版 Demo 資料的資料庫（沒有 CRM），啟動時的「已有 Demo 資料」判斷仍視為已產生，不會補開 CRM；Render 的磁碟每次部署都會重建，不受影響。
- Demo 站預設關閉附件上傳（§3.5），所以只有設計案的附件由產生器在伺服器端寫入（上述 `ServerUploadScope`），其他模組的 Demo 資料不含附件。
