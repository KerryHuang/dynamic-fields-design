# 報表與儀表板 設計文件

> 2026-11-05｜上位文件：[動態模組與自訂欄位 設計文件](2026-11-03-dynamic-modules-design.md)；相關：[使用者與群組管理 設計文件](2026-11-05-users-groups-design.md)、[Demo 資料 設計文件](2026-11-05-demo-data-design.md)
> 標「（我的判斷）」的是我代為決定、可以改的；其餘是使用者已拍板的決策。功能概念參考本機的自助報表專案，但那個專案含公司資訊，**不可複製它的文字、欄位名稱或設定檔**。

## 1. 意圖

資料已經能存進動態模組，但主管要看「這個月接了多少單、哪一區最多、哪些逾期」時，只能匯出 Excel 自己算。報表模組讓主管登入就看到儀表板，一般使用者也能自己組報表，不用寫 SQL、不用找 IT。

這是給客戶的產品功能：模組和欄位是客戶自己定義的，所以資料主題不能人工維護，要從模組自動產生。

## 3. 目標、非目標、反目標

**目標**

1. 主管登入後的首頁就是自己的儀表板，五種卡片：指標、折線、長條、環圈、表格。
2. 一般使用者不靠別人就能組出「各客戶地區的本月接單金額」並放上自己的儀表板、分享給群組。
3. 點卡片上的數字，能看到組成它的明細。
4. 全新安裝沒有任何報表；Demo 四情境各有示範報表與儀表板。

**非目標**

- 排程寄送、列印版型、使用者自寫 SQL 或公式、外部資料來源。
- 多條一對多同時合併；多層一對多（§6.2）。
- 跨幣別換算（§6.5）。
- 多資料庫實作。但不寫 SQLite 專屬語法，引擎放在應用層（§5）。
- 查詢結果快取與預先彙總（§5 留了放大時的方向）。

**反目標**（技術上能跑也算失敗）

- 數字錯了卻看不出來。
- 透過報表、分享、儀表板、篩選條件或下鑽，看到或推測出自己原本無權看的資料。
- 模組被改了（欄位刪除、停用）之後，整張儀表板壞掉，而不是只有那張卡片說明原因。

## 4. 使用者看到什麼

**報表（第一段）**：選單新增「報表」區，「我的報表」列出自己的與分享給我的。設計器五步：

1. **選資料**：選主模組，可選擇合併一個子模組（§6.2）。
2. **選欄位**：主模組欄位、沿參照帶出的欄位、子模組欄位。只列觀看者看得到的（§7）。
3. **設條件**：沿用列表篩選的條件模型，加上相對日期區間（§6.4）。
4. **分組與彙總**：分組欄位、數值與彙總方式。不設分組時是明細報表。
5. **預覽與儲存**：看結果、切換呈現方式、命名、分享。

**儀表板（第二段）**：選單新增「儀表板」，網頁內左側清單分三區「指派給我」「我的」「分享給我」的報表；右側是可拖放、可調大小的卡片。頁面上方的日期篩選只暫時套用、不存檔。手機寬度（小於 600px）時清單收合、卡片單欄排列、不可拖放（我的判斷）。

**首頁**：有可看的儀表板時，`/` 開上次看的那張（記在瀏覽器，依使用者區分，換裝置就開第一張），沒有上次就開第一張。沒有儀表板就顯示一般首頁（歡迎區、最近開過、我的應用、報表與系統管理捷徑），不再自動導向（使用者決定，取代原本「維持導向」的判斷）。儀表板完成後在首頁接上。

報表存預設呈現方式；放上儀表板時複製成卡片，呈現方式與下列選項都屬於卡片（我的判斷）：

- **排序與前幾名**：依某欄排序，只顯示前 N 組。其餘不併成「其他」，標題標示「前 N 名」，總計仍算全部。
- **累計占比**：只限長條圖。依數值由大到小，折線顯示累計占全部分組總和的百分比，不是占前 N 名的。
- **與前 N 期平均比較**：只限指標卡，報表要有主要日期欄位。一期的長度跟著卡片區間走：本月比前 N 個月，近 30 天比前 N 個 30 天。
- **卡片自己的日期區間**：見 §6.4 的優先順序。
- **連結到另一張儀表板**：觀看者看不到目標時，連結不顯示。

## 5. 查詢引擎：在應用層算

**決定（我的判斷）**：讀出觀看者可見的記錄，在 C# 內合併、去重、彙總，不產生 SQL 聚合。理由來自現有程式：

- 欄位值存在 `Record.ValuesJson`。`Dynamic_RecordIndex` 只收可篩選或可排序的欄位；Demo 範本的金額與數量都不在索引內，全專案也沒有 JSON SQL 函式。
- 要走 SQL 就得強制索引所有欄位或寫各資料庫的 JSON 語法，與「日後接主流資料庫」衝突。`ISqlDialect` 目前只有分頁與跳脫。
- `NumberValue` 是 double，有浮點誤差；現有彙總用 decimal，報表要與它一致。
- 按上層去重在記憶體內很直接，在 SQL 內要視窗函式或子查詢，各資料庫成本高。

**代價與上限**：每張卡片都要讀 JSON。單次查詢合併後超過 `Reports:MaxRows`（預設 50,000 列）就停止，回明確訊息請使用者縮小條件，不回部分結果（我的判斷）。超過上限的正確性比速度重要。之後若要放大，方向是先用索引縮小記錄、加結果快取，不改定義格式。

**效能驗收**：1 萬筆主記錄、每筆平均 3 列子記錄、含分組與去重，單次查詢中位數 1 秒內（我的判斷）。要有 `Category=Benchmark` 測試，結果記進驗收文件。

**讀取必須帶的條件**：`DeleteFlag=0`。`RecordIndex` 在軟刪除時不清，引擎不可只查索引。可見範圍用 `EffectivePermissions.OwnerUserIds`（null 為全部）。

## 6. 計算規則

### 6.1 列的定義

每張報表要能回答「每一列代表什麼」，並顯示在設計器與下鑽頁：沒有合併時是「一筆訂單」，有合併時是「一筆出貨」。

### 6.2 合併

- **主模組**：一般模組。明細模組不能當主模組（現況不能單獨查詢）。
- **多對一帶欄位**：主模組與子模組各自可沿參照欄位帶對方欄位，各走一層，不能再往下鏈（我的判斷）。例：訂單 → 客戶．地區。實體目標（模具、客戶擴充的來源）只有 Title 可帶，與現有 `IReferenceProvider` 一致。
- **一對多**：最多一個子模組，只走一層。可選：主模組的任一明細模組，或有參照欄位指回主模組的模組（有多個參照欄位時要指定用哪個）。
- **同時合併兩個子模組會互相相乘**，去重救不回來，所以不提供。
- 合併是左合併：沒有子記錄的主記錄保留一列，子欄位為空。條件落在子欄位時，先篩子記錄，因此條件若把子記錄全篩掉，該主記錄的這列也消失（我的判斷）。

### 6.3 去重與彙總

- 彙總方式：加總、平均、最小、最大、筆數。加總與平均只限數字型別（整數、小數、金額、百分比、數值結果的公式）；最小與最大多收日期。使用 decimal，空值不計入。另提供「條件占比」：符合條件的筆數 ÷ 總筆數，用來做達成率這類指標（我的判斷）。
- **主模組與沿參照帶出的欄位，彙總時每筆主記錄在每個分組內只算一次**，以 `Record.Id` 判斷，不看 `OwnerUserId`（明細列的擁有者複製表頭）。
- 筆數分「主記錄筆數」與「子記錄筆數」，由使用者選。
- 分組欄位來自子模組時，同一筆主記錄可能落在多個分組，每組各算一次。**因此各組相加可能大於總計**。總計一律獨立重算（去重），不是把各組加起來。
- 多選欄位分組時每個選項一組，同樣規則。
- **必須對使用者說明**：只要報表有合併且彙總了主模組欄位，結果下方與下鑽頁顯示「訂單金額每張訂單只算一次，明細列相加不等於這個數字」。這是使用者接受去重的代價（§2），不能省略。

### 6.4 日期

- 相對區間：今天、本週（週一開始）、上週、本月、上月、今年、去年、近 N 天、近 N 週、近 N 月（我的判斷）。
- 以**基準日**計算：`IBusinessTime.Today`；Demo 站例外（§10）。區間在後端換算，不用瀏覽器日期。
- 日期時間欄位上界用「隔天 00:00 之前」，不能用現有含頭尾的 `between`。值是台北牆上時間，與現有一致。
- 分組可依日、週、月、季、年。
- 報表可指定一個**主要日期欄位**（可不設），報表的日期區間、儀表板篩選與期間比較都作用在它上面（我的判斷）。
- 區間只取一個，不取交集，優先順序：卡片自己的區間 > 儀表板暫時篩選 > 報表的區間。卡片有自己的區間時不受儀表板篩選影響，否則「近 12 個月趨勢」會被改壞；卡片上要標示實際套用的區間。沒有主要日期欄位的卡片不受篩選影響，並標示「不受日期篩選影響」。

### 6.5 金額與幣別

系統沒有幣別欄位，範本的「幣別」只是一般下拉，與金額欄位沒有關聯，引擎無從判斷。第一版照加，手冊說明混用幣別時要依幣別欄位分組或篩選（我的判斷）。這是已知會算出無意義數字的情況，列入路線圖。

### 6.6 特殊欄位

- **彙總欄位不提供**，直接或間接引用彙總欄位的公式也不提供：存的是全域值，不看讀者範圍，用了就違反 §7。要這個數字就合併子模組自己加總。`PermissionResolver` 已有「公式引用隱藏欄位就一併隱藏」的判斷，依賴分析先重用它，不夠才擴充。
- 其他公式欄位讀已存的值。
- 使用者欄位分組時顯示姓名；選項依觀看者語系顯示標籤，依選項順序排序。
- 長文字可顯示，不可分組。時間型別不可彙總（我的判斷）。
- 參照目標失效顯示「（已刪除）」，目標不在讀者範圍顯示「（無權限）」，兩者都自成一組，不混入其他組，也不帶對方欄位值。

## 7. 權限

一律呼叫現有 `IDynamicAccessGuard.AuthorizeAsync` 取 `EffectivePermissions`，不另寫一套。

- **模組**：要 Read。明細的動作軸與範圍來自表頭，欄位隱藏來自明細自己，與現有一致；非明細的子模組與參照目標各自授權。
- **記錄**：只算範圍內的。子記錄也依各自範圍過濾，看不到的子記錄不計入。主記錄照算。
- **欄位**：報表任何地方（欄位、分組、彙總、**條件**、排序、帶出欄位）用到觀看者看不到的欄位，**整張卡片顯示「無權限檢視」**，不回部分結果。條件也算，否則可用篩選推測隱藏值。金額權限隨 `CanSee` 一併生效。
- **模組權限與設計器的差異**：設計器只列看得到的；打開別人分享的報表時才可能遇到上面的情況，訊息要說是哪個模組或欄位造成的（只說看得到的名稱，看不到的欄位以「隱藏欄位」表示）。
- **規則隱藏不算權限**：現有讀取 API 也不套規則，報表不套。
- **下鑽**：明細走同一套範圍與欄位過濾，最多 500 列（我的判斷）。
- **匯出 Excel**：沿用 `XlsxWriter`，要有所有涉及模組的 PrintExport（我的判斷），沒有則按鈕停用。否則報表變成繞過匯出權限的路。
- **已知洞**：金額權限只管 `Currency` 型別，型別設成小數的「金額」不受控（既有行為），手冊註明。

**分享與指派**：

- 報表擁有者可分享給群組，對方只能看，要改就「另存一份」。
- 分享和指派只決定「看得到這張報表的定義」，不授予任何資料權限。
- 指派是第二條可看的路徑（我的判斷）：指派版與它的個人版上的卡片，不需要另外分享就能載入、下鑽、看唯讀定義，也能另存一份；但報表不會因此出現在「我的報表」。卡片的查詢走「儀表板＋卡片」這條 API，先驗這個人看得到該儀表板，不讓人拿任意報表 ID 來跑。
- 只有系統管理員（現有的 `AppUser.IsSystemAdmin`，用 `ISystemAdminRequest` 檢查）能建立指派版儀表板、指派給群組、調整順序。系統管理員也能看到與刪除所有共用報表（我的判斷），避免離職者留下的共用報表沒人能管。
- 報表被任何其他人的儀表板或指派版引用時不能刪；引用清單列給擁有者看。取消分享後，靠分享而放上自己儀表板的卡片顯示「此報表已不再分享」；指派版的卡片不受影響（我的判斷）。
- 擁有者被停用，報表留著，分享照常（我的判斷）。

## 8. 儀表板與個人版

- 指派版有版本號。一人屬多個群組時，看到所有指派給這些群組的儀表板，依管理員設定的順序。
- 使用者對指派版做任何排版或卡片異動，第一次存檔時另存個人版，清單標「已調整」。暫時的日期篩選不算異動。
- 管理員更新指派版時版本加一，不動任何個人版。個人版的基準版本較舊時顯示「儀表板已更新」，可按「還原成最新版」（丟棄個人調整）。
- 取消指派後，那張指派版與對應的個人版從清單消失；個人版資料保留，重新指派時恢復（我的判斷）。
- 使用者可建立自己的儀表板，不限張數；不能指派，也不能分享（第一版只分享報表）（我的判斷）。

## 9. 異常狀況

卡片各自載入、各自失敗，一張壞掉不影響其他張：

| 情況 | 卡片顯示 |
|---|---|
| 欄位被刪除或停用 | 「欄位已不存在：X」，可進設計器修 |
| 模組停用或刪除 | 「模組已停用」 |
| 無權限 | 「無權限檢視」 |
| 超過列數上限 | 「資料太多，請縮小條件」 |
| 沒資料 | 「這個區間沒有資料」 |
| 伺服器錯誤 | 「載入失敗」與重試 |

報表定義存欄位 ID，欄位改名不影響。設計器與工作階段異動互不鎖定，存檔以最新一次為準；指派版的同時編輯用版本號擋下後者（我的判斷）。

## 10. Demo

- 四個情境各附示範報表，並有給業務主管、設備、品保各一張的指派版儀表板，放在 `DemoStructure` 內由產生器以一般 Request 建立，`DemoPreflight` 一併檢查衝突。全新安裝沒有這些。
- **資料基準日**：Render 的 Demo 資料在映像建置時產生，日期停在那天（`poc/Dockerfile.demo`），若用今天當基準，「本月」久了就空了。產生器把產生日期寫進資料庫；Demo 登入開啟時，報表以此為基準日，頁面標示「資料基準日 yyyy-MM-dd」。其他情況一律用今天（我的判斷）。
- `docs/demo.md` 增加報表與儀表板的走法，含「業務一與業務主管看同一張儀表板，數字不同」和「現場人員看到無權限卡片」。

## 11. 交付順序

**第一段：報表**。查詢引擎、報表定義與 API、五步驟設計器、結果表格與圖表、下鑽、匯出、分享、Demo 示範報表。合併後站台就有可用的報表。

**第二段：儀表板**。儀表板與個人版資料模型、左側清單、拖放、指派管理、首頁、Demo 指派版。

各段獨立合併與部署。圖表與拖放套件尚未引入，由實作者挑選，條件是授權免費、可商用、維護中，並在計畫中寫明（留給實作者）。

## 12. 測試

查詢引擎是這份文件風險最高的部分，要有獨立於畫面的數字測試：

- **固定資料集的預期值表**：用手算好的數字驗去重、分組、總計、空值、左合併、子條件。例：訂單 100 萬分 3 次出貨，合併後訂單金額加總仍是 100 萬；依子欄位分組時各組相加大於總計。
- **權限矩陣**：同一報表以不同身分執行，涵蓋本人／同群組／全部範圍、隱藏欄位用在每一種位置（條件、分組、彙總、排序、帶出）、金額權限、參照目標無權限、子模組無權限、明細繼承。
- **失效**：欄位刪除、模組停用、參照目標刪除、軟刪除記錄不被計入。
- **日期**：週與月邊界、基準日、日期時間的上界。
- **分享與個人版**：取消分享、被引用不可刪、管理員更新後提示與還原。
- **實機走查**：Demo 全流程，尤其是兩個身分看同一張儀表板，以及拖放後重新載入版面不變。

## 13. Review Focus

最容易傷到人的輸入，審查時優先看：

1. 合併報表的總計與下鑽列數對不上時，畫面有沒有說明。
2. 條件或排序用到隱藏欄位時，有沒有整張卡片擋下，而不是默默略過條件（那會回傳不同的數字）。
3. 別人分享的報表，對方權限較少時的每種顯示。
4. 彙總欄位是否真的從欄位清單、帶出欄位、公式間接引用都排除。
5. 軟刪除的主記錄與子記錄是否都不計入。
