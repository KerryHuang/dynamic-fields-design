## 1. 問題與現況盤點

使用者已裁決（資料模型 §1.2 裁決 2、3）：CRM 與 MES 都開時，CRM 訂單是唯一的銷售訂單，確認後經整合建立 MES 工令；MES 與進銷存都開時，完工成品入庫，出貨只用進銷存出貨單。現況（以 `poc/backend/apps/*.app.json` 與程式為準）離這個目標還有這些落差：

## 2. 目標、不做、延後

**目標：**

1. CRM＋MES：CRM 訂單由草稿確認時，對自製品明細逐列建立草稿工令，工令追溯到訂單列；MES 的報價、訂單收掉。
2. MES＋進銷存：末道報工完工入庫；出貨只用進銷存出貨單，由銷售訂單轉換開立；MES 出貨單收掉，`stockOut` 移除。
3. 訂單明細有已完工量 `producedQty`、已出貨量 `deliveredQty`，由事實推算、換手不歸零（資料模型 §3.4 七原則全部落地）；訂單狀態的出貨段依履約量自動推進與退回（s2e-b，§4.9）。
4. 數量鏈一律小數 3 位；取消的下游單據不佔已轉量；上限在改量、過帳時重驗；有下游時擋下上游取消與刪除。
5. 每個應用程式仍能獨立開關；七種組合與中途開關都有明確行為（§8.2、§7）；`skip` 期間漏掉的連動有人工補連動（§5.2），成對整合能卸除（§5.2）。

**交付方式：** 兩個依序交付的工作單元（使用者裁決，§10.1）。**s2e-a** 做單據追溯到明細列、履約量核心、各應用程式單開時的適配；**s2e-b** 做應用程式間的成對整合、覆蓋收掉重複選單、完整的訂單到出貨鏈。每個合併點都驗完整既有行為（含 Demo），範圍與驗收見 §9。

**不做：** MRP、排程、預留（reservation）、訂單專屬庫存、出貨單自動產生、超交容許量、訂單變更單（確認後改明細；已排入路線圖的後續單元 s2f，見 §11）、多單位換算、存貨計價、`skip` 期間事件的自動回補（只做人工補連動）。

**延後：**

| 項目 | 延到 | 理由 |
|---|---|---|
| 銷項發票與 `invoicedQty`、開票政策、開票路徑共用計數 | s3c | 沒有發票就沒有第二條開票路徑；s2e 只把追溯建到列 |
| 「已開票的出貨不能取消」（資料模型 §11 情境 11） | s3c | s3c 之前沒有發票，不會發生；成立方式是發票追溯到出貨明細、被 §4.7 的下游檢查擋下，反方向的上游唯讀守衛也在 s2e 做好（§4.7） |
| 進項端：採購明細 `receivedQty`、`billedQty` | s3c | 同上；s2e 只讓取消的進貨單釋放採購剩餘量（缺口 7 的副作用） |
| 期初完工量（`producedQty` 的受控初始化） | 不排 | 目前流程沒有需求；`producedQty` 只由來源推算（§4.4） |
| 逐列轉換（缺口 E，一列轉一張單據） | 不排 | 工令改由事件逐列建立，第二個情境仍未出現 |
| 應用程式管理頁顯示覆蓋與整合狀態 | 階段 5 | 路線已排定 |
| 已開啟資料庫的套件升級 | 第一個客戶上線前 | 同 s2d §11、路線「套件更新入口」 |

## 3. 選定的方案與為什麼

**一句話：** 在核心補六個通用能力（取消類狀態、明細追溯與追溯槽、履約欄位、追溯守衛、整合擴充、依履約量自動轉移狀態），再用**三個成對整合**（每一對應用程式一個）把 CRM、MES、進銷存接起來；`stockOut` 移除。

具體上：

- **明細追溯（line trace）**：參照欄位新增受控的「指向明細列」關係，定義選取、帶值、資料範圍、欄位權限與刪除列的保護；**追溯槽**規定工令「有訂單來源就必須追溯到列」、多個來源互斥、品項一致、有下游後不能改掛（§4.3）。
- **履約欄位（trace total）是宣告式的**：訂單明細的 `producedQty`、`deliveredQty` 宣告「基準量＋各來源的合計」，來源是「追溯到這一列、未取消的某模組記錄的某欄位」。寫入管線在事件之後重算受影響的列，判斷一律用由來源事實重建的交易前、後快照（§4.4）。
- **成對整合**：同一個連動橫跨兩個擁有者（例如觸發在 CRM 訂單、追溯欄位在 MES 工令），兩邊各宣告一半、同代號、標 `pair`，安裝、停用、恢復、卸除作為一個單位（§5.2）。
- **組合覆蓋**由被收掉模組的擁有者在整合裡宣告：夥伴開著時收回新增、收掉選單、擋下指定的正向轉移（§6）。
- **自動轉移（auto transition）**：狀態機的轉移宣告條件，條件引用明細上的履約欄位；履約重算後在同一交易判斷，成立就推進、不再成立就退回（§4.9，s2e-b）。

**考慮過、不採用：**

| 做法 | 不採用的理由 |
|---|---|
| 履約量用事件效果回寫（資料模型原本的寫法） | 見下方說明 |
| 履約量用彙總欄位 | 彙總不能彙總彙總，也不能跨應用程式加總夥伴模組；放寬會影響所有模組（資料模型 §3.1 已排除） |
| 放寬一般參照，允許指向明細模組 | 影響所有模組的挑選、刪除、權限 |
| 下游存在守衛用既有跨記錄驗證 | 檢查只加總被寫入的模組，表達不了（見下方說明） |
| 整合直接加欄位到夥伴模組（不做成對） | 推翻 s2c「整合不改夥伴結構」的原則 |
| 改寫 `stockOut`（保留 MES 出貨扣庫存） | 進銷存開著時 MES 出貨單已收掉，留著就有兩條扣庫存的路 |
| 一個大整合涵蓋三個應用程式 | `with` 任一夥伴不在就整個暫停 |
| 每項連動各自一個整合（約 7 個） | 同組合下的連動彼此依賴，分開後可能只裝一半（我的判斷） |
| `skip` 期間的事件在夥伴重開後自動回補 | 見下方說明 |

說明：

- **事件回寫**：工令 `completedQty`、`shippedQty` 是彙總，彙總重算是靜默寫入、不觸發事件（事件設計 §4.5），所以「MES 出貨單取消」這類間接變化抓不到；每個來源都要配一組建立／取消／沖銷事件，漏一個就算錯。
- **放寬一般參照**：所有模組的參照挑選、刪除規劃、欄位權限都要改；明細追溯只開給套件與整合宣告的欄位（§4.3），一般參照照舊。
- **跨記錄驗證**：檢查只加總「被寫入的那個模組」（事件設計 §5.1、§5.4）；取消寫的是訂單，要數的是工令（資料模型 §6.2 缺口 11 要 s2e 驗證，結論是不夠）。
- **成對與 `stockOut`**：整合加欄位到夥伴模組時，夥伴關閉、刪除的清理範圍就不再明確；單開 MES 時也沒有庫存可扣（裁決 3）。
- **一個大整合**：CRM＋MES 不開進銷存時連工令都建不了。
- **自動回補**：關閉期間使用者可能已用其他方式處理（手動建工令、人工記出貨），自動補會重複；改由人逐筆補連動，有授權、有防重（§5.2）。

## 4. 單據流程與數量鏈

### 4.1 流程

```
CRM 訂單 draft ─確認→ confirmed ──（P1，自製品逐列）──→ MES 工令 draft → released → running → done
   │                                                      │報工（分錄）
   │                                                      ├─ 末道良品 ──（P3）──→ 進銷存庫存異動 in（完工入庫）
   │                                                      └─ 報工沖銷 R2 ──（P3，依 R1）──→ 沖銷入庫
   └──（P2 轉換，含明細部分轉換）──→ 進銷存出貨單 draft ─過帳→ shipped（inv-shipment-post 扣庫存）
訂單列 producedQty ← Σ 工令 completedQty；deliveredQty ← 基準量 ＋ Σ 進銷存出貨明細 ＋ Σ 工令 shippedQty
```

P1、P2、P3 是 §5.3 的三個成對整合（s2e-b）。單開 MES 時，工令由生管手動新增：有訂單的選 MES 訂單明細列，備庫的標「備庫」（§4.3）；出貨用 MES 出貨單。MES＋進銷存時，MES 訂單經 P3 轉成進銷存出貨單。

### 4.2 每個數量欄位的來源、守衛、取消／沖銷

| 欄位 | 值的來源 | 守衛 | 取消／沖銷 |
|---|---|---|---|
| 訂單列 `qty`（CRM、MES） | 使用者輸入；報價轉訂單 | 有事實時受事實鎖；降低時不得低於 `deliveredQty`（§4.4 max） | — |
| 訂單列 `producedQty` | Σ 追溯到本列、未取消工令的 `completedQty`；不可人工改 | 減少時不得低於 `deliveredQty`（min） | 報工沖銷、工令取消 → 重算減少 |
| 訂單列 `deliveredQty` | 基準量 ＋ Σ 追溯到本列、已過帳進銷存出貨明細 `qty` ＋ Σ 追溯到本列、未取消工令的 `shippedQty` | 增加時不得超過 `qty`（max） | 出貨單取消 → 重算減少 |
| 工令 `qty` | P1 由訂單列 `qty` 帶入；手動新增時使用者輸入 | 報工每道工序良品合計 ≤ `qty`（既有 `mes-report-within-wo-qty`） | — |
| 工令 `completedQty` | 彙總報工 `finalGood`（含沖銷的負值） | — | 沖銷報工即減少 |
| 工令 `shippedQty` | 彙總已出貨 MES 出貨單 `qty` | 既有 `mes-shipment-within-completed`（≤ `doneQty`） | MES 出貨單取消即減少 |
| 報工 `goodQty`／`defectQty` | 使用者輸入（分錄） | 同工令 `qty` | 只能沖銷（R2，`reverses` = R1） |
| 庫存異動 `qty`（完工入庫） | 報工 `finalGood` | 不得負庫存（既有 `inv-no-negative-stock`） | 依 R1 的事實沖銷（§4.6） |
| 進銷存出貨明細 `qty` | P2／P3 轉換或手動 | 轉換剩餘量在改量、過帳時重驗（§4.5）；訂單列 max；不得負庫存 | 取消 → 既有 `inv-shipment-cancel` 沖銷庫存，並釋放已轉量 |
| MES 出貨單 `qty` | 使用者輸入（沒開進銷存時） | 既有 ≤ `doneQty`；訂單列 max | 取消即釋放 |

### 4.3 明細追溯與追溯槽（s2e-a）

**明細追溯欄位（line trace）。** 參照欄位的關係 `relation` 新增 `lineTrace`（現有 `lookup`、`detail`），目標必須是明細模組。一般參照指向明細模組仍被 `FieldRules` 拒絕，只有 `lineTrace` 例外。

- **建欄：** 只能由套件或整合宣告；設計器可檢視，不能新增、不能改目標（我的判斷，同第 23 項）。可以是使用者可選的欄位（MES 工令 `salesLine`），也可以是唯讀、由事件寫入的欄位（P1 的 `crmLine`）。
- **選取：** 新端點 `GET /api/v3/dynamic/fields/{fieldId}/line-options?keyword=&page=`，只接受 `lineTrace` 欄位。候選列的條件是表頭未刪除、使用者對表頭模組有 Read、表頭在使用者的資料範圍內（`OwnerUserIds` 看表頭）；欄位設了既有的 `refGuard` 時，再依表頭狀態篩選。顯示文字是「表頭標題 #列次 · 列標題」，例如「SO-0012 #2 · 上模座」：列次取明細模組依表頭編號的自動編號欄位（CRM `order-line.seq`、MES `line.seq`，同一張表頭內穩定、不重複），沒有自動編號的明細改用列 Id。欄位可宣告補充顯示的列欄位 `pickerFields`（例如 `qty`、`price`），每一欄依讀者的欄位可見性決定顯示與否，沒有權限就不出現；辨識只靠列次，不靠品名與數量。上限沿用 `records/light` 的 50 筆；`records/light` 對明細模組仍回 404，不變。
- **寫入驗證：** 使用者存檔時，伺服器用同樣的條件重驗（列存在且未刪除、表頭可讀且在範圍內、符合 `refGuard`），不符回 400。系統身分寫入（事件 `$row`）不受資料範圍限制，同既有事件寫入。
- **帶值後重驗：** 帶值（`derive`、`ReferenceFill`，含 `lock` 把追溯欄位複製到目的列，如 MES 出貨單 `salesLine`）完成後，伺服器以**原操作者**身分對目的列重驗：對目的列所指表頭模組的 Read、表頭資料範圍、欄位的 `refGuard`，任一不通過就整筆拒絕（不是只丟掉帶入的值）。帶值寫入用的系統鍵只負責寫欄位，不構成授權例外；事件 `$row` 的系統身分寫入不在此列（見上）。
- **帶值：** 既有規則禁止帶值的目的是參照欄位（`FieldRules`），而且 `lock` 的目的必須整欄唯讀、參照沒變時會丟掉使用者送的值（`ReferenceFill`），不適合「有時有來源、有時沒有」的欄位。所以從列推得表頭與品項不用 `fill`，改由追溯槽的 `derive` 負責（見下）。`fill` 只放寬一種目的：`lock` 可以把一個 `lineTrace` 值複製到另一個指向同一明細模組的唯讀 `lineTrace` 欄位（MES 出貨單 `salesLine` 取自工令 `salesLine`），其他參照目的照舊拒絕，且複製後仍要通過上面的「帶值後重驗」（我的判斷）。
- **顯示與欄位權限：** 記錄回應帶列的顯示文字；讀者對表頭模組沒有 Read 時，照核心既有的參照隱藏規則處理。
- **刪除明細列：** `DetailWriter` 軟刪明細列前，查有沒有未刪除的記錄追溯到這一列，有就 409 並列出下游（§4.7）。「追溯」包括三種欄位：`lineTrace` 欄位、轉換的明細追溯（`lines.sourceLineField`，唯讀整數）、履約來源的 `trace`。這三種欄位一律自動設為可篩選，並回填索引（同檢查規則的做法），查詢走索引。
- **刪除模組或欄位：** `DeletePlanner` 既有的參照欄位檢查不排除停用欄位，照樣涵蓋 `lineTrace`。

**追溯槽（trace slot）。** 模組可以宣告追溯槽，把「指向上游明細列」的幾個欄位綁成一組，核心在寫入時驗證：

```json
"traceSlots": [ { "code": "salesSource", "exemptWhen": { "field": "sourceKind", "op": "eq", "value": "stock" } } ]
```

成員欄位在 `config.traceSlot` 宣告所屬的槽、一致欄位與是否推得，例如 `{ "slot": "salesSource", "match": { "order": "order", "item": "item" }, "derive": true }`。`match` 的鍵是本記錄的欄位，值是追溯列上的欄位（讀一層），兩邊可以是參照欄位。規則：

1. **互斥：** 槽內最多一個成員有值。
2. **必填：** `exemptWhen` 不成立時，恰好一個成員有值；成立時，全部成員必須為空。
3. **一致與推得（綁在目前有值的成員）：** 只有「寫入後有值的那個成員」的 `match` 生效。
   - `derive: true`（使用者可選的成員，例如 `salesLine`）：成員在本次寫入被設定或改變時，核心從追溯列寫入每個 `match` 欄位（系統鍵），這一步排在帶值（`ReferenceFill`）之前，所以推得的 `item` 仍會觸發 `item` 自己的預設帶值（`itemNo`、`itemName`）。成員沒變時，使用者送來與追溯列不同的 `match` 欄位值回 400，不靜默覆蓋。
   - `derive: false`（只由受控事件寫入的唯讀成員，例如 P1 的 `crmLine`）：寫入者必須自己帶齊 `match` 欄位，核心驗證等於追溯列，不符時事件失敗（fail closed）；之後使用者改 `match` 欄位同樣 400。
   - **所有成員都為空時**（備庫），`match` 欄位中只能由列推得的（宣告 `derivedOnly`，工令的 `order`）必須為空，送值回 400；其餘 `match` 欄位（`item`）不受槽約束，照既有欄位權限由使用者填寫。`derivedOnly` 欄位只有 `derive: true` 的成員能寫入（由列推得）；`sourceKind = stock` 或 CRM 來源（`derive: false` 的 `crmLine`）時一律須為空。
   - 成員在本次寫入被清空（只有凍結前可以）時，`derive` 寫過的欄位中，`derivedOnly` 欄位（`order`）清空，其餘（`item`）改採本次請求送來的值，沒送就清空。
   - 這些欄位在套件裡**不設**唯讀；記錄回應依「目前是否有成員有值」帶出逐欄的可編輯旗標，前端據以鎖住。不全域放寬唯讀，也不略過權限：使用者能改的範圍只會比一般欄位權限更小。
4. **凍結：** 記錄有事件事實，或有任何未刪除記錄以參照或追溯指向它之後，槽成員與 `exemptWhen` 引用的欄位都不能再改（409）。工令有報工或 MES 出貨單之後就不能改掛來源。

成員可以是擁有者套件的欄位，也可以是**擁有者自己那一半整合**新增的欄位（P1 的 MES 半新增 `crmLine`）；不能加入別的擁有者的槽。成員所屬的整合 `Disabled`、`Suspended` 時，欄位仍算在槽內，已有值的工令不會因此變成「沒有追溯」。

**持久化：** 槽的定義存在新表 `Dynamic_TraceSlot`（§5.6），一列一個槽：模組、代號、`exemptWhen`（規則條件格式，存欄位 Id）。成員設定存在各成員欄位的 `Config`（既有 JSON）。開啟應用程式時由套件寫入；`IModuleRepository` 載入模組（`includeChildren`）時一併載入槽，執行期只讀資料庫，不回頭讀套件檔；匯出時輸出 `traceSlots[]`（欄位以代號表示），匯入時照開啟流程寫入；模組刪除時隨之刪除。`exemptWhen` 引用的欄位與成員欄位受保護：不能停用、改型別、刪除（`SetFieldStatusHandler`、`DeletePlanner`）。成員設定的 `slot` 必須對得到同模組的一個槽，否則套件驗證 400。設計器可檢視槽，不能新增或修改（同第 23 項）。選專表而不是模組上的 JSON 欄位，見第 41 項。

**套用到工令：** 工令加 `sourceKind`（來源：訂單 `order`／備庫 `stock`，必填，預設 `order`），宣告槽 `salesSource`，`exemptWhen` 為 `sourceKind = stock`。三種來源各自的建立方式：

| 來源 | 誰設定 | 成員 | 表頭與品項 |
|---|---|---|---|
| MES 訂單 | 生管手動選列 | `salesLine`（`derive: true`，`match: { order, item }`） | 由列推得並鎖住 |
| CRM 訂單 | P1 事件（s2e-b） | `crmLine`（`derive: false`，`match: { item }`） | 事件寫 `item`，核心驗一致；MES 的 `order` 留空 |
| 備庫 | 生管手動 | 全部為空，`sourceKind = stock` | `order` 必須為空（送值 400）；只開放自選品項 |

結果是：有訂單來源的新工令必須追溯到列，表頭由列推得；CRM、MES 兩種來源互斥；真正沒有訂單的備庫工令明確標成 `stock`，與「漏填追溯」分開（漏填會被必填擋下）。

### 4.4 履約欄位（缺口 5；核心在 s2e-a，整合來源在 s2e-b）

**值的定義：** `F = 基準量 ＋ Σ 來源合計`。

- **來源：** 「`module` 中 `trace` 等於本列 Id、狀態符合 `states`（預設為所有非取消類狀態；明細模組看其表頭的狀態）、未刪除的記錄，其 `sum` 欄位的合計」。來源可以來自擁有者套件自己（MES 明細從 MES 工令，s2e-a），或擁有者在整合裡宣告的夥伴模組（CRM 明細從進銷存出貨明細，s2e-b）。**只有擁有者能為自己的欄位宣告來源**，這就是資料模型原則 4 的「擁有者指定可寫入的整合」。
- **計入所有已安裝的來源，不看整合目前的狀態：** 整合 `Suspended`、`Disabled`、夥伴關閉時，夥伴已有的事實照算（資料是唯讀保留，不是消失）。這是原則 1「換手不歸零」的落地方式。
- **人工修改政策逐欄宣告：** `traceTotal.manual` 為 `baseline`（可人工記基準量）或 `none`（只由來源推算，預設）。

  | 欄位 | `manual` | 理由 |
  |---|---|---|
  | CRM `order-line.deliveredQty` | `baseline` | 只開 CRM、或外購品沒有出貨單時要人工記 |
  | CRM `order-line.producedQty` | `none` | 完工只來自工令；只開 CRM 時永遠是 0 |
  | MES `line.producedQty`、`deliveredQty` | `none` | 來源是 MES 自己的工令，始終可用，沒有換手情境（我的判斷） |

  `none` 的欄位沒有基準量，使用者修改回 400。期初完工量若之後需要，另立受控的初始化規則（§2 延後）。
- **基準量**（`manual: baseline` 才有）存在核心旁表（§5.6），不是套件欄位。這一列**沒有適用的 `Active` 來源**時，使用者可以改 `F`：系統把基準量設為「輸入值 − Σ 來源合計」，結果小於 0 回 400。之後有了適用的 `Active` 來源（例如開了進銷存），基準量就鎖住，成為資料模型所說的「期初履約事實」；來源再次不 `Active` 時又開放人工改。「只開 CRM 手記 6 件 → 開進銷存再出 4 件」得到 10，不會被重算成 4（資料模型 §11 情境 10）。
- **適用範圍 `applies`：** `always`（每一列都適用，進銷存出貨屬此類）或 `traced`（至少有一筆來源記錄追溯到這一列才適用，工令屬此類）。CRM＋MES 沒開進銷存時，外購品列沒有工令，所以可人工填出貨量；自製品列有工令，就不能填（情境 6）。用 `traced` 而不是「品項是自製」，是因為 MES 關閉期間確認的訂單不會有工令，若依品項判斷，這些列就永遠無法記出貨（我的判斷）。

**上下限。** 兩種都比較「寫入後」的值，差別在什麼時候檢查：

- **`max: { field }`**：寫入後 `F ≤ 上限`。在 `F` 增加（含基準量增加）**或上限欄位減少**時檢查。例：只開 CRM，訂購 10、人工已交貨 6，把訂購量改成 5 → 上限減少 → 6 ≤ 5 不成立 → 409。
- **`min: { field }`**：寫入後 `F ≥ 下限`。只在 `F` 減少時檢查；**下限欄位增加時不檢查**：出貨從庫存先出、工令後完工時，`deliveredQty > producedQty` 是合法的中間狀態，若下限增加也檢查，先出貨就會被擋（我的判斷）。完工量因沖銷而減少到低於已交貨量就擋下（情境 3）。
- 上下限欄位本身是另一個履約欄位時（`producedQty` 的下限是 `deliveredQty`），它的前後值同樣由快照算。
- 違反時整筆 409。訊息依讀者權限組成（同 §4.7）：讀者能讀該訂單時，單據標題、列次、欄位名稱、前後值各自依讀者的欄位可見性逐欄決定輸出，看不到的欄位不輸出（其餘看得到的照列）；不能讀該訂單時只說「超過來源訂單列的上限（你無權檢視該單據）」，不帶標題與數量。

**判斷用的快照。** 增減方向與上下限比較，一律用由來源事實重建的值，**不讀目標上保存的履約值**：

- **交易前快照：** 本次請求寫入日誌中每筆記錄第一次寫入前的值（含彙總造成的靜默寫入、刪除、狀態轉移）；日誌以外的記錄用資料庫現值（本交易沒動過，等於交易前）。
- **交易後快照：** 日誌中每筆記錄的最終值。
- **受影響的列：** 先決定「受影響的來源記錄」，再取它們在交易前、後快照中 `trace` 指向的列的聯集。受影響的來源記錄包括：
  - 日誌中屬於來源模組的記錄（改掛、刪除、取消、改 `sum`、自身狀態變化）。
  - **明細來源的表頭展開：** 日誌中某筆記錄是明細來源模組的表頭，且它的狀態改變、被刪除或還原時，展開它的**所有**明細列（含本次被刪的列），即使這些列本身沒有寫入。進銷存出貨單過帳、取消只改表頭，訂單列的追溯卻在出貨明細的 `crmLine`／`mesLine`，靠這一步找到。
  - 明細列的表頭參照改變時（換到另一張表頭），新舊表頭的狀態各自套用。
  - 訂單列自己被寫入（改 `qty`、改基準量）時，該列本身也算。

  `UnitOfWork` 只登記實際寫入的記錄，展開由履約重算步驟自己查（依表頭 Id 讀明細，走表頭參照的索引）。來源資格（狀態是否計入）一律用**各自快照**裡的表頭狀態：交易前快照看表頭寫入前的狀態，交易後快照看最終狀態。
- 對每個受影響的列，用兩份快照各算出同列所有履約欄位與上下限的值，基準量用旁表在交易前、後的值。保存值只用來決定要不要寫回（相同就不寫），不參與任何判斷。

**重算時點。** 寫入管線在事件階段之後、寫入後盾之前，新增「履約重算」步驟：取本次寫入日誌、建兩份快照、算受影響的列、比對上下限，以系統身分寫回。重算只讀一層追溯、在 C# 以 `decimal` 加總，量小（一列的下游通常是個位數）。這一步能否看到彙總的靜默寫入與其終值，是 s2e-a 的第一道門檻 V1（§9.2）。

**來源失效時 fail closed。** 一個履約欄位的依賴是：目標欄位、上下限欄位、每個來源的模組、`trace` 欄位、`sum` 欄位、明細來源的表頭參照，以及**決定哪些記錄計入的狀態定義**。狀態定義分兩種登記（`Dynamic_TraceTotalSource.StatesMode`）：

- `explicit`（宣告了 `states`）：依賴列出的那些狀態。
- `nonCancelled`（省略 `states`，預設「所有非取消類狀態」）：依賴的是隱含的整套分類，即狀態判斷所在模組（來源模組，明細來源則是表頭模組）的狀態機、狀態欄位，以及**每一個**狀態的 `cancelled` 旗標。

以上依賴都登記進來源表，保護規則如下：

- **欄位：** 被任何來源引用的欄位，不論來源屬於套件或整合、整合是 `Active`、`Disabled`、`Suspended` 還是 `Blocked`，都不能停用（`SetFieldStatusHandler` 新增檢查，400「此欄位被履約來源引用」）、不能改型別、改位數、改彙總或公式設定。`DeletePlanner` 新增阻擋種類 `TraceTotalSource`。
- **狀態定義：** 會改變計入集合的變更一律拒絕（400），不做受控重算（範圍控制，我的判斷）。具體是：刪除狀態機（`DeleteWorkflowHandler` 新增檢查）、更換狀態欄位、刪除狀態；`nonCancelled` 時改任何狀態的 `cancelled` 旗標，`explicit` 時改列出狀態的 `cancelled` 旗標；來源模組（或表頭模組）原本沒有狀態機時，不能新增狀態機。新增狀態不影響既有記錄，照常允許。
- **執行期：** 重算時任一依賴不可用（欄位不是 Active、型別不符、模組或狀態不存在），**本次會重算到這個欄位的寫入**回 409，不當 0、不沿用保存值；沒有影響到的寫入照常。
- 來源模組所屬的應用程式關閉，不算失效：資料唯讀保留，照算（原則 1）。

**寫入目標關閉時（s2e-b 才會發生，例如 CRM 關閉、MES 繼續報工或沖銷）：** 仍用快照照算並檢查上下限，但不寫回（目標唯讀）。該應用程式重開時，在同一個交易內對它**所有含履約欄位的模組的每一列**重算一次並寫回差異，不只目前有來源的列，關閉期間來源全被取消到零的列也會歸位（我的判斷）。重算碰到失效的依賴時，重開回 409 並說明原因。

**其他：**

- **列層級的事實鎖例外：** `EventFactLock` 對「只改到可人工改的履約欄位」的明細修改放行，其他欄位、其他列照鎖。履約欄位在套件宣告為 `readOnly`；可人工改時，記錄回應帶出逐列的可編輯旗標，前端據以開放。
- 履約欄位不能再當其他履約欄位或事件 `from` 的來源，避免連鎖重算與事實漂移，定義時擋下。

### 4.5 已轉量、上限重驗（缺口 7、10 的出貨部分）

1. **取消類狀態不佔已轉量（s2e-a）。** `ConversionLedger` 只計目標表頭不在取消類狀態的；表頭轉換（沒有明細）的「已轉換過」也一樣。進銷存「取消進貨單不釋放採購單剩餘量」的既有限制隨之修掉。
2. **改量時重驗（s2e-a）。** 新的寫入步驟對「本次寫入的轉換目標明細列」（改量、新增帶追溯值的列）重算對應來源列的剩餘量，小於 0 回 409。s2e-a 以單一應用程式內的轉換驗收（採購轉進貨、報價轉訂單）；訂單 10 件轉出貨草稿後改成 20 被擋（情境 2）在 s2e-b 驗收。過帳時由 `deliveredQty` 的 max 再擋一次。併發由既有的 `WriteGate`（SQLite `BEGIN IMMEDIATE`）序列化所有寫入，同一交易內重算即可，不另上鎖。
3. **轉換剩餘量扣基準量與其他來源（s2e-b）。** 轉換的明細可宣告 `fulfills`（指向來源列上的履約欄位），這時剩餘量 = `qty` − 基準量 − 其他來源已履約量 − 本轉換未取消的目標量。沒有 `fulfills` 的轉換維持「`qty` − 本轉換未取消的目標量」。這是共用計數（缺口 8）在出貨上的子集，開票部分留給 s3c 擴充（第 7 項）。

### 4.6 沖銷依沖銷對象查事實（缺口 6，s2e-b）

- `reverse` 效果新增 `ofRecord`（來源模組上的參照欄位，例如 `report.reverses`）：有值時依它指向的原記錄（R1）查事件事實，沖銷 R1 建立的目標；沒有值時沿用現行行為。
- `IntegrationGuardStage` 判斷「這次寫入是不是反向、來源是否已連動」時，若事件的 `reverse` 效果有 `ofRecord`，改查 R1 的事實。整合停用後建立 R2：守衛查到 R1 已連動，回 409，R2 不成立；整合恢復後再沖銷，`reverse` 依 R1 找到入庫並沖銷（情境 1）。
- R2 照分錄規則建立（`ReverseRecordHandler`），完工入庫事件的 `when` 是 `finalGood > 0`，R2 的 `finalGood` 為負，所以不會再入庫一次。

### 4.7 取消與刪除上游：追溯守衛（缺口 11，s2e-a）

使用者裁決全面生效：所有有追溯的單據，都要先取消下游才能取消上游（§10.1）。

- **「下游」的定義：** 以下列欄位指向上游記錄或其明細列的記錄：轉換的表頭追溯（`header.sourceField`）、轉換的明細追溯（`lines.sourceLineField`）、`lineTrace` 欄位、履約來源的 `trace`。
- **取消：** 上游轉移到取消類狀態時，有任何未刪除、不在取消類狀態的下游，回 409。
- **刪除：** 刪除上游記錄或其明細列時，有任何未刪除的下游（**含已取消的**）就回 409：刪掉之後，下游的追溯值會指向不存在的列（我的判斷）。
- **判斷與訊息分開：** 判斷一律檢查全部下游，不看操作者權限。錯誤訊息只對操作者**可讀**的下游列出明細（模組名稱、單據標題、目前狀態，最多 20 筆），可讀是指同時符合下游模組的 Read 與資料範圍。可讀的記錄也逐欄過濾：標題、狀態與其他要輸出的欄位，各自依操作者的欄位可見性決定，與既有記錄回應的 `CanSee` 一致（標題的規則同 `ReferenceResolver` 隱藏參照標題）；不可見的欄位不輸出，也不用其他欄位或佔位文字暗示其值（例如狀態不可見時不列狀態）。不可讀的只合計成「另有 N 筆你無權檢視的下游單據」，不帶模組、標題或狀態。不會為了顯示訊息自動加任何權限；看不到的下游要請有權限的人處理。`DetailWriter` 刪列、成對卸除的阻擋訊息用同一套規則。
- 判斷位置在入口守衛同一層（事件之前）。

例：MES 訂單有一張草稿工令（`salesLine` 指向它的列），`producedQty`、`deliveredQty` 都是 0，取消訂單仍被擋；CRM＋MES 時同理（情境 7）。CRM 主管沒有 MES Read 時，取消被 P1 工令擋下，訊息只說「另有 1 筆你無權檢視的下游單據」。只開進銷存時，有未取消進貨單的採購單不能取消，訊息列出那幾張進貨單。

**上游唯讀守衛（反方向，s2e-a；使用者裁決，§10.1 第 5 項）：** 上游是唯讀的結案狀態時，擋下追溯到它的下游取消、沖銷與刪除。原因：結案是人按當時的事實做的判斷（出貨數量、狀態都已定案），下游一取消，履約量變少、狀態卻停在結案，兩者不一致；而唯讀的上游不能被自動轉移改回（§4.9）。核心只用狀態分類和追溯欄位，不寫業務名詞。

- **鎖定狀態：** 上游表頭目前所在的狀態同時符合三點：標了 `readOnly`；不是取消類；至少有一條轉出轉移通往非取消類的狀態（可以重開）。從狀態機宣告推得，不看狀態名，也不看轉移的群組（有沒有人能執行不影響分類）。理由（我的判斷，第 53 項）：只看 `readOnly` 會讓「過帳即唯讀、只能轉取消」的單據（進銷存出貨單、進貨單）也成為鎖定上游，而它們正是 s3c 發票的上游，結果取消發票要先取消出貨、取消出貨又被發票擋，互相卡死；這類狀態的出口只有取消，已由上面的下游檢查管。
- **追溯到：** 同上面「下游」的四種欄位。表頭追溯看來源表頭；明細追溯、`lineTrace`、履約來源的 `trace` 看那一列所屬的表頭；一筆下游追溯到多張上游時，任何一張處於鎖定狀態就擋。只看直接上游，不沿鏈往上（間接影響見 §11）。
- **擋的操作：** (1) 下游表頭轉到取消類狀態；(2) 刪除下游記錄或明細列；(3) 沖銷：建立以 `ofRecord`（或分錄的 `reverses`）指向原記錄 R1 的新記錄，上游依 R1 的追溯欄位找。下游已在取消類狀態時，取消、刪除都不再改變任何履約量，放行；上游自己在取消類時下游本來就全部取消，所以不受此守衛影響。下游是草稿也一樣擋（不分狀態，規則最簡單；要清草稿先重開上游，我的判斷，第 54 項）。
- **判斷與訊息：** 規則同「判斷與訊息分開」（第 45 項）：判斷一律看全部上游，不看操作者權限；訊息只對可讀的上游列模組、標題、狀態（逐欄過濾，最多 20 筆），不可讀的合計成「另有 N 筆你無權檢視的上游單據」，不帶模組、標題或狀態；訊息的處置提示只說「請先將上游重開（退出唯讀狀態），再取消或刪除這筆」，不列轉移名稱或目標狀態（它們可能隱含不可見的資訊）。同樣不自動加任何權限。
- **位置：** 與取消上游的檢查同一層（事件之前、履約重算之前）。被擋時整筆回 409，事件與履約都沒有動。
- **與自動轉移（§4.9）：** 自動轉移的兩端都不是唯讀，上游在 `to` 時不是鎖定狀態，取消出貨照常進行並自動退回。上游被人結案之後（CRM `completed`、MES `closed`）取消出貨先 409；做法是重開上游到 `confirmed`（`to` 不能手動進入）、同一交易自動評估、取消出貨、自動退回，必要時再結案。
- **套件補一條重開轉移（s2e-a）：** CRM 訂單 `completed → confirmed`（業務主管）、MES 訂單 `closed → confirmed`（業務主管），不然守衛的處置提示沒有出口（§5.4）。進銷存採購單的 `closed` 沒有重開轉移，不屬鎖定狀態，不受此守衛管（§11）。
- **與 s3c「已開票的出貨不能取消」：** 那條是上游（出貨）被下游（發票）擋，本來就是上面的下游檢查，s3c 只要讓發票明細宣告追溯到出貨明細（或訂單列）就成立，不需另寫規則。本守衛是它的反方向，用同一組追溯欄位與同一套訊息規則。s3c 要記得兩件事：作廢發票時，若發票追溯到的訂單處於鎖定狀態，要先重開訂單（寫進 s3c 設計）；出貨單過帳狀態不是鎖定狀態，作廢發票不需要先取消出貨。
- **與依賴登記（第 43 項）：** 不新增登記。守衛執行時才讀上游目前的狀態分類，不存任何由它推得的資料，所以改狀態機不會讓已存的值失效；追溯欄位本身已受 §4.3、§4.7 保護。代價：設計器若刪掉某個鎖定狀態的唯一重開轉移，該狀態就不再算鎖定，守衛隨之放行（§11）。
- **與補連動、沖抵調整、卸除：** 補連動只建立下游（P1 對 `confirmed`、`shipped` 的訂單建工令），不是取消，也不碰鎖定狀態（`completed` 不在補連動的狀態內）。P3 的沖抵調整取消的是盤點調整單，它沒有追溯到任何上游（沒有連到原報工），不經過本守衛；因此結案後的「補連動並沖抵」仍可執行，原報工之後的沖銷由工令的 `done` 唯讀與既有重開規則管（不在本守衛範圍）。成對卸除與整組刪除要求沒有歷史資料，沒有下游記錄可言。
- **既有流程逐一檢查（沒有因此卡死的）：** 結案後取消 MES 出貨單、進銷存出貨單、取消或刪除工令：先重開訂單（上面的做法）。結案後沖銷完工入庫：報工沖銷追溯到工令、不直接追溯到訂單列，不經過本守衛，工令 `done` 時本來就不能沖銷，要先重開工令（既有規則）。取消進貨單：進貨單追溯的是採購單，採購單 `confirmed` 時照常；`closed` 沒有重開轉移，不是鎖定狀態（§11）。

### 4.9 依履約量自動轉移狀態（s2e-b）

使用者裁決（§10.1 第 3 項，推翻原第 21 項）：訂單狀態的出貨段跟著履約量走。做成核心通用能力**自動轉移**（auto transition）：狀態機的一個轉移宣告條件，條件引用明細上的履約欄位；核心重算履約後判斷，條件成立就推進，不再成立就退回。核心程式只用 auto transition、trace total、line 這類詞（`NoBusinessWordsTests`）。

**宣告（格式 8）：**

```json
"transitions": [
  { "from": "confirmed", "to": "shipped",
    "auto": { "lines": "order-line", "match": "all",
              "field": "order-line.deliveredQty", "op": "gte", "compareTo": { "field": "order-line.qty" } } },
  { "from": "shipped", "to": "completed", "groups": [] } ]
```

- `lines` 是本模組的明細模組；`field` 必須是該明細上宣告了 `traceTotal` 的欄位；`op` 為 `gte` 或 `gt`；`compareTo` 是同一明細的數字欄位（`{ "field" }`）或常數（`{ "value" }`）。
- `match`：`all` 是每一列都成立，`any` 是至少一列成立。表頭沒有未刪除的明細列時，兩種都算不成立（空訂單不會被推進）。
- 語意是一對互逆的轉移：表頭在 `from` 且條件成立，轉到 `to`；表頭在 `to` 且條件不成立，退回 `from`；其他狀態一律不動。每個自動轉移只有一個 `from`，所以退回目標固定，不需要記住「從哪裡來」。
- 只能由擁有者套件宣告；整合不能宣告，設計器可檢視、不能新增或修改（同第 23 項）。設計器儲存狀態機時自動轉移原樣保留，送來的變更回 400。匯出時輸出在原轉移上，匯入照開啟流程寫入。
- 持久化：加在 `WorkflowTransition`（狀態機既有的 JSON 欄位，同 V9），不需要結構異動。

**套件驗證（400）：** `from`、`to` 是同一狀態機的不同狀態，都不是唯讀或取消類，`to` 不是起始狀態；每個狀態最多出現在一個自動轉移裡；沒有其他以 `to` 為目標的手動轉移，也沒有 `to → from` 的手動轉移；本模組不能是任何履約來源的狀態判斷模組（`StateModuleId`），避免狀態改變又改到履約值；沒有任何 `transition` 事件（套件或整合宣告的）以這一對（任一方向）為觸發；覆蓋的 `blockTransitions` 不得列出這一對。整合安裝時也跑後三項，不符的整合 `Blocked`。

**觸發點與執行：**

- **時點：** 履約重算步驟（§4.4）寫回之後、寫入後盾之前，同一交易。
- **評估哪些表頭：** 本次受影響的列所屬的表頭，加上本次寫入日誌中宣告了自動轉移的模組的記錄（例如手動 `draft → confirmed`、增刪明細列、改 `qty`）。
- **取值：** 條件裡的履約欄位用交易後快照（由來源事實重算），同一張表頭裡本次沒受影響的列也一樣重算，不讀保存值（同 §4.4）；`compareTo` 欄位用交易後的值。
- **寫入：** 狀態要改時以系統身分只寫狀態欄位。
- **不觸發事件：** 同彙總的靜默寫入，排在事件階段之後；所以驗證拒絕以這一對為觸發的 `transition` 事件，否則那個事件永遠不會執行。
- **只評估一次：** 狀態不是條件的輸入，本模組又不能是履約來源的狀態判斷模組，改狀態不會回頭改變任何履約值，不連鎖。
- **冪等：** 結果只由交易結束時的事實決定；狀態已相符就不寫、不記歷程。重送同一請求（事實唯一索引防重，履約重算結果相同）、目標重開時整批重算，都不會多一筆轉移；取消再重轉，每次實際改變各記一筆。
- **目標唯讀時：** 目標應用程式關閉時，照 §4.4 只檢查、不寫回，自動轉移也不寫；重開時在整批重算的同一交易內，對每一張表頭評估一次，狀態隨數量歸位。
- **失敗時 fail closed：** 狀態寫入被寫入後盾或檢查擋下時，整筆寫入回 409（觸發它的過帳或取消也不成立），訊息依 §4.7 的權限規則組成。

**與追溯守衛、取消類狀態、事實鎖的互動：**

- **追溯守衛**只管轉到取消類狀態；自動轉移的兩端都不是取消類（驗證保證），守衛不受影響。下游出貨單取消照常判斷（它沒有下游），造成的退回與取消同一交易；上游退回 `from` 後，轉換（P2、P3 的來源狀態含 `confirmed`）可以再轉。
- **取消類與其他狀態：** 處在取消類、`completed`、`closed` 等不屬於這一對的狀態時不評估；上游取消（`confirmed → cancelled`）照追溯守衛判斷，與自動轉移無關。
- **上游唯讀守衛（§4.7）：** `completed`、`closed` 是鎖定狀態，訂單在那裡時取消出貨先回 409，所以「結案後取消出貨使狀態與數量不一致」不會發生；要取消得先重開（`completed → confirmed`、`closed → confirmed`，`confirmed` 是 `from`，手動進入後同一交易評估，條件仍成立就直接回到 `to`）。
- **事實鎖**本來就放行狀態欄位；兩端都不是唯讀，不碰唯讀鎖。CRM 訂單確認後有 P1 的事件事實，照樣能自動轉移。
- **覆蓋：** 自動轉移不受覆蓋影響；被收掉模組的未結記錄照樣自動轉移（未結 MES 訂單經 P3 出貨後轉 `shipping`）。

**權限與操作者：**

- **不代授權限**（同 s2c §7、§6.2）：自動轉移不屬於任何群組，轉移端點對這一對的兩個方向一律 409「此狀態由系統依數量推進」，系統管理員也一樣；不改任何群組的權限列。
- **觸發權限就是觸發操作本身的權限**（過帳或取消出貨單、記基準量、建立 MES 出貨單）：觸發者不需要表頭模組的轉移權限或 Read，也不因此取得；狀態寫入以系統身分進行，同履約寫回。
- **記錄操作者：** 稽核欄位記觸發的使用者（系統身分的既有規則）；表頭歷程加一筆「自動轉移」，內容是轉移、觸發的使用者、操作識別、觸發記錄。觸發記錄依讀者權限顯示，規則同 §4.7：讀不到的只寫「另一張你無權檢視的單據」，不帶模組與標題。

**與手動轉移的衝突：**

- **手動推進、退回都不行：** 這一對只由系統執行，使用者手動推進（`from → to`）或退回（`to → from`）回 409，訊息指引改記出貨量或取消出貨單。`to` 不能是起始狀態、也沒有其他手動轉移以它為目標，所以只會經自動轉移進入。
- **離開 `to` 的其他手動轉移照常**（CRM `shipped → completed`、MES `shipping → closed`）；離開後不再自動退回，但處在結案狀態時下游取消、沖銷、刪除被上游唯讀守衛擋下（§4.7），數量不會在結案後變動。
- **手動進入 `from` 後同一交易評估一次**（CRM `draft → confirmed`）：草稿時已記足量基準量的訂單，確認後直接轉 `shipped`。
- **考慮過、不採用：**「允許手動推進，只自動退回由系統推進的」要為每筆記錄保存是誰推進的標記，而手動推進的記錄又回到狀態與數量不一致，正是裁決要消除的（我的判斷，第 47 項）。用事件推進狀態（像 `mes-report-progress`）也不採用：彙總是靜默寫入、不觸發事件，MES 出貨單取消這類間接變化抓不到，理由同 §3 的「事件回寫」。

**依賴保護（第 43 項的延伸）：** 自動轉移本身也是依賴，宣告就是它的登記（在狀態機的轉移定義裡）；依賴檢查從被引用欄位所在的明細模組找到表頭模組的狀態機即可查到，不需要新表。下列變更拒絕（400）：刪除狀態機、更換狀態欄位、刪除 `from` 或 `to` 狀態、把它們標成唯讀或取消類；停用、改型別、改位數、刪除 `field` 或 `compareTo` 欄位；移除 `field` 的 `traceTotal` 宣告（本來就不能在設計器改，第 23 項）；刪除明細模組或它的表頭參照。`DeletePlanner` 新增阻擋種類 `AutoTransition`。新增狀態、新增不以 `to` 為目標的手動轉移照常允許。

**套用到內建套件（s2e-b，步驟 b3）：**

| 模組 | 自動轉移 | 條件 | 仍由人執行 |
|---|---|---|---|
| CRM 訂單 | `confirmed` ⇄ `shipped` | 每一列 `deliveredQty` ≥ `qty` | `shipped → completed`、取消 |
| MES 訂單 | `confirmed` ⇄ `shipping` | 至少一列 `deliveredQty` > 0 | `shipping → closed`、取消 |

對應理由（我的判斷，第 48、49 項）：CRM `shipped` 的意思是已出貨，對應全交；CRM 沒有「部分出貨」的狀態，部分出貨停在 `confirmed`，進度看數量。MES `shipping` 的意思是出貨中，對應開始出貨；MES 沒有「已全交」的狀態，全交後停在 `shipping` 等結案。CRM `completed`、MES `closed` 是唯讀的結案，代表人的判斷（短交結案、驗收，之後還有開票），進入後記錄被鎖，自動退回會推翻人的決定，所以維持手動。原本的手動轉移 CRM `confirmed → shipped`（有 Edit 的人都可以）、MES `confirmed → shipping`（業務、業務主管）移除。兩個條件都只讀 `deliveredQty`，所以不論出貨量來自基準量、MES 出貨單或進銷存出貨單，七種組合都成立。

## 5. 核心、格式與套件的改動

### 5.1 格式 6 → 7（s2e-a）→ 8（s2e-b）

s2e-a 把 `CurrentFormatVersion` 提高到 **7**，s2e-b 再提高到 **8**（s2d 是 6；我的判斷，取代原第 24 項）。每個版本新增的鍵，出現在較舊格式的檔案裡一律整份拒絕（fail closed，同 s2c §3.1）；`AppJson.StrictOptions` 已拒絕未知成員（`UnmappedMemberHandling.Disallow`），所以 s2e-a 版本讀到 s2e-b 匯出的檔案會整份拒絕，不會靜默略過。兩個合併點各自讓三個內建套件升到當時的版本。

| 位置 | 新鍵 | 用途 | 版本 |
|---|---|---|---|
| `workflows[].states[]` | `cancelled: true` | 取消類狀態（必須同時 `readOnly`） | 7 |
| 參照欄位 `config` | `relation: "lineTrace"`、`pickerFields?` | 明細追溯與挑選的補充欄位（§4.3） | 7 |
| 模組 | `traceSlots[]` | 追溯槽（§4.3） | 7 |
| 欄位 `config` | `traceSlot: { slot, match?, derive? }` | 加入追溯槽 | 7 |
| 欄位 `config` | `traceTotal: { manual?, max?, min?, sources?[] }` | 履約欄位（§4.4） | 7 |
| `conversions[].lines` | `fulfills` | 剩餘量扣履約（§4.5） | 8 |
| 事件 effect | `eachWhere`；`set[].from.field = "$row"`；`set[].from.via` | 逐列篩選、目前列、經一層參照讀值（§5.2） | 8 |
| 事件 `reverse` effect | `ofRecord` | 依沖銷對象查事實（§4.6） | 8 |
| 事件 | `catchUp: { states?, offset? }` | 補連動與沖抵調整（§5.2） | 8 |

### 5.2 整合層擴充（缺口 1～4，s2e-b）

**成對整合（缺口 1）。** 兩份套件各宣告一個同 `code`、`"pair": true` 的整合，`with` 只能有一項，就是對方。規則：

- 一半可以引用另一半新增的欄位（夥伴符號，例如 CRM 這一半寫 `mes-mold/workorder.crmLine`）；不能引用其他整合的欄位（s2c 的限制不變）。
- **一個單位：** 兩半的狀態一起推導（兩個擁有者都 Open、兩半都 enabled 才 `Active`）；安裝時兩半的欄位先建、再建兩半的事件、檢查、轉換、履約來源，全在同一個 savepoint；任一半完整性失敗，兩半都 `Blocked`。另一半不存在（例如對方是舊版套件開啟的）時是 `Waiting`，原因 `pairMissing`。
- 目錄層對帳：內建套件的每個成對整合，對方套件必須有同代號的另一半，否則拒絕啟動。

**成對卸除與整組刪除。** 現行 `DeletePlanner` 檢查外部參照時不排除停用欄位，事件引用也不因停用而消失：即使空庫，P1 的 MES 半參照欄位會擋刪 CRM，CRM 半的建工令事件會擋刪 MES，停用兩半解除不了結構引用。所以新增：

- **卸除：** `DELETE /api/v3/dynamic/apps/{key}/integrations/{code}`，對成對整合一次處理兩半，權限同 retry（設計器 Edit 加系統管理員）。前提有兩個：兩半都 `Disabled`（先停用，卸除途中不會觸發）；沒有歷史資料，也就是兩半新增的欄位在任何記錄（含軟刪除）都沒有值、兩半的事件沒有事件事實。轉換產生的目標都帶夥伴追溯欄位的值，已由第一個條件涵蓋。成立時，同一交易刪除兩半的欄位、事件、檢查、轉換、履約來源與覆蓋；兩邊的 `IntegrationsJson` 保留宣告、維持 `Disabled`，重新啟用就重新安裝。
- **有歷史資料時拒絕：** 409，逐項列出阻擋（哪個欄位有幾筆值、哪個事件有幾筆事實），並說明保留條件：整合只能維持停用，資料唯讀保留；兩個應用程式都不能刪，只能關閉。
- **刪除應用程式：** `DeleteApp` 對它參與的每個成對整合先做卸除判斷。可卸除的，兩半一起併入同一個刪除交易：`DeletePlanner` 把兩半的項目當作「一起刪除的集合」，與既有 `alsoDeleting` 同一機制。刪除應用程式時它已關閉，整合是 `Suspended`，不需要先手動停用。不能卸除的，回新的阻擋種類 `PairHistory`，訊息同上。
- 非成對的整合維持 s2c §5.5。

**整合收轉換（缺口 2）。** `integrations[].conversions[]` 格式同一般轉換，來源是擁有者模組，目標與追溯欄位可以是夥伴（另一半新增的）欄位。轉換在安裝時建立、隨整合啟用與停用（`Active` 同步）；整合不是 `Active` 時，轉換不出現在記錄頁，呼叫回 404。轉換登記在 `ItemsJson.conversions`，完整性檢查涵蓋它。`ConversionValidator` 現行規則照用：表頭追溯是指向來源模組的唯讀參照，明細追溯是唯讀整數。

**`each` 提供目前列與篩選（缺口 4），加經參照讀值：**

```json
{ "code": "wo", "kind": "create", "target": "mes-mold/workorder", "each": "order-line",
  "eachWhere": { "via": "order-line.item", "field": "item/item.supplyType", "op": "eq", "value": "make" },
  "set": [
    { "to": "mes-mold/workorder.crmLine", "from": { "side": "line", "field": "$row" } },
    { "to": "mes-mold/workorder.sourceKind", "const": "order" },
    { "to": "mes-mold/workorder.item",    "from": { "side": "line", "field": "order-line.item" } } ] }
```

- `$row` 是目前列的記錄 Id，只能寫到指向該明細模組的 `lineTrace` 欄位或唯讀整數欄位。
- `eachWhere` 是規則條件格式，作用在列上；可加 `via`（列上的參照欄位）讀一層參照目標的欄位。經 `via` 讀到的值為空時，整個事件失敗並列出是哪幾列（fail closed）：`supplyType` 是空值的品項不會被靜默略過（s2d §5.3）。
- `set[].from.via` 同理，供完工入庫從報工經工令讀品項與入庫倉。只讀一層，不鏈接。
- `via` 讀到的欄位也受事件設計 §4.7 限制：不得是彙總或依賴彙總的公式。

**整合宣告的履約來源：** `integrations[].traceTotals[]`，每項 `{ field, module, trace, sum, states?, applies }`。`field` 必須是**擁有者自己**宣告了 `traceTotal` 的欄位；`module`、`trace`、`sum` 可以是夥伴（含另一半新增）的符號。安裝時寫入核心的來源表（§5.6），登記在 `ItemsJson.traceTotals`；依賴保護見 §4.4。

**補連動（`skip` 的人工補救）。** `skip` 不回補（s2c §5.3 的既有語意不變）；另外提供逐筆、人工觸發的補連動，讓關閉期間漏掉的連動回到原鏈：

- **入口：** `POST /api/v3/dynamic/records/{id}/catch-up`，body `{ "event": "<事件代號>" }`；`GET .../integrations/{code}/catch-up-candidates` 列出符合下列前提的來源記錄。記錄頁的可補連動清單由 API 決定（同轉換清單），前端顯示按鈕。
- **適用：** 整合事件，效果全是 `create` 的才可補；`reverse` 類事件不補。整合目前必須 `Active`。
- **前提：** (a) 該事件對這筆記錄沒有事實（事實的唯一索引防重，重送得到同一結果）；(b) 記錄狀態在事件宣告的 `catchUp.states` 內（預設為觸發轉移的目標狀態），不在取消類；(c) 事件 `when` 對目前值成立；(d) 沒有任何記錄以 `ofRecord` 指向它（已沖銷的報工不補）；(e) 有 `each` 時照目前的列與 `eachWhere` 跑。
- **授權：** 呼叫者要有觸發這個事件的那個操作的權限（CRM 訂單的確認轉移、新增報工），而且記錄在資料範圍內；效果照常以系統身分寫入。
- **追溯：** 事實照常寫入，`OperationId` 用補連動請求的操作識別；來源記錄的歷程加一筆「補連動」（事件、操作者、時間）。不需要結構異動。
- **取消與沖銷：** 補出來的連動與一般連動完全相同。補建的工令照常取消（受追溯守衛），補入的完工入庫依原報工沖銷（`ofRecord`），入口守衛也一樣查得到事實。
- **盤點調整本身不是復原路徑：** 調整單沒有連到原報工，之後沖銷原報工時找不到它，完工量歸零但庫存仍多。直接補連動又會再入庫一次（事實唯一索引只防同一事件重複，認不出調整單）。已用盤點補過的，走下面的「補連動並沖抵調整」。

**補連動並沖抵調整（offset）。** 進銷存關閉期間報工 10、未入庫；重開後有人先用調整單補入 10，接著出貨 10，庫存為 0。此時「先取消調整單」會讓庫存變 −10，被 `inv-no-negative-stock` 擋下；直接補連動又重複入庫。所以把兩步合成一個操作：

- **入口：** 同一個端點，body 加 `{ "offset": <調整單 Id> }`。只有事件宣告了 `catchUp.offset` 才接受。P3 的完工入庫事件宣告：

  ```json
  "catchUp": { "offset": {
    "module": "inventory/adjust", "cancel": { "from": "posted", "to": "cancelled" }, "lines": "adjust-line",
    "match": [ ["move.item", "adjust-line.item"], ["move.warehouse", "adjust.warehouse"], ["move.qty", "adjust-line.qty"] ] } }
  ```

- **核驗：** 先照補連動前提 (a)～(e) 算出這次要建立的目標（例如一筆入庫 `move`）；調整單必須是 `posted`，它的明細與要建立的目標**一對一**相符（品項、倉庫、數量都相等，列數相同），不符回 409 並列出差異。調整單包含其他品項（混合品項）時不支援這條路：回 409 並提示人工處理（例如請有權限的人自行處理該調整單），系統不補連動、不沖抵（我的判斷，第三輪修訂）。
- **授權：** 補連動的權限（觸發操作本身），加上調整單的取消轉移權限（進銷存），兩邊的資料範圍都要符合。任一不符 403，不代授權限。
- **同一交易：** 先補入原鏈（建立入庫、寫事實），再把調整單轉到 `cancelled`（照既有 `inv-adjust-cancel` 沖銷它的庫存異動）；檢查以交易結束時的最終值判斷，庫存淨變化是 0，負庫存檢查看的是最終庫存（V13）。任一步失敗整筆回滾。
- **追溯與防重：** 兩筆記錄的歷程各記一筆「補連動並沖抵」並互相指向；調整單取消後不能再被沖抵（已不是 `posted`），原報工已有事實不能再補。之後沖銷原報工，依事實沖掉補入的入庫，受負庫存與 `producedQty` 下限檢查，與一般連動完全相同。

例（P1）：MES 關閉期間確認的 CRM 訂單沒有工令；MES 重開後，業務對該訂單補連動，自製品列建出草稿工令（帶 `crmLine`），再補一次不會重複。例（P3）：進銷存關閉期間報工 R1；重開後對 R1 補連動，完工入庫；之後沖銷 R1，依 R1 的事實沖掉入庫。若 R1 在關閉期間已被 R2 沖銷，R1 不能補（前提 d），兩邊都沒有入庫，一致。

### 5.3 三個成對整合（s2e-b）

| 整合 | 兩半 | `onPartnerClosed` |
|---|---|---|
| P1 `salesWorkOrder` | CRM ↔ MES | `skip` |
| P2 `salesShipment` | CRM ↔ 進銷存 | `skip` |
| P3 `productionStock` | MES ↔ 進銷存 | `skip` |

**P1 `salesWorkOrder`（CRM ↔ MES）：**

- CRM 半：訂單 draft → confirmed 時，對自製品列建草稿工令（§5.2 的事件，`catchUp.states: ["confirmed", "shipped"]`）；`producedQty` 來源工令 `completedQty`、`deliveredQty` 來源工令 `shippedQty`，兩者都是 `traced`。
- MES 半：工令欄位 `crmLine`（`lineTrace`，唯讀，指向 CRM 訂單明細，加入追溯槽 `salesSource`，`match: { item: item }`、`derive: false`：建工令事件自己寫 `item`，核心驗一致）；覆蓋收掉 MES `quote`、`order`。

**P2 `salesShipment`（CRM ↔ 進銷存）：**

- CRM 半：轉換「CRM 訂單轉出貨單」（來源狀態 confirmed、shipped；明細 `fulfills: order-line.deliveredQty`）；`deliveredQty` 來源出貨明細 `qty`（`states: ["shipped"]`，`always`）。
- 進銷存半：出貨單欄位 `crmOrder`（表頭追溯）、出貨明細欄位 `crmLine`（明細追溯）。

**P3 `productionStock`（MES ↔ 進銷存）：**

- MES 半的欄位與檢查：工令欄位 `stockWarehouse`（入庫倉）；檢查「工令下達時必須有入庫倉」。
- MES 半的事件：「末道報工完工入庫」（報工 create，`when` `finalGood > 0`，建 `inventory/move` kind in，品項與倉經 `via` 讀工令；可補連動，並宣告 `catchUp.offset` 沖抵盤點調整單）；「報工沖銷沖銷入庫」（報工 create，`when` `reverses` 不為空，`reverse` 帶 `ofRecord: report.reverses`）。
- MES 半的轉換與來源：轉換「MES 訂單轉出貨單」（來源狀態 confirmed、shipping，`fulfills: line.deliveredQty`）；`deliveredQty` 來源出貨明細。
- MES 半的覆蓋：收掉 MES `shipment`，並擋 draft → shipped。
- 進銷存半：出貨單 `mesOrder`、出貨明細 `mesLine`。

三者全開時，P1、P2、P3 同時 `Active`。P3 的「MES 訂單轉出貨單」仍 `Active`：MES 訂單已不能新增，但組合改變前留下的未結 MES 訂單要靠它出貨（資料模型 §4.2）。

## 6. 權限與選單收斂（s2e-b）

### 6.1 組合覆蓋（缺口 3）

```json
"overrides": [
  { "module": "quote", "add": false },
  { "module": "order", "add": false },
  { "module": "shipment", "add": false,
    "blockTransitions": [ { "from": "draft", "to": "shipped" } ],
    "message": { "zh-TW": "進銷存已開啟，請改用進銷存出貨單出貨" } } ]
```

- 宣告在**被收掉模組的擁有者**（MES）那一半；前兩項在 P1、第三項在 P3。
- **套用條件只看組合：** 擁有者與該半的夥伴都 Open（夥伴模組 Active）就套用，與整合是否 enabled、`Blocked` 無關，否則整合一壞 MES 訂單選單就冒出來（資料模型 §6.2 缺口 3）。
- **效果：** (a) 選單不列該模組，模組回應帶 `canAdd: false`，前端隱藏「新增」；(b) 新增記錄、匯入、轉換**到**該模組、事件建立該模組記錄一律 409，訊息指出改用哪張單據；(c) `blockTransitions` 列出的轉移 409；取消類轉移一律不擋。對所有人生效，含系統管理員（第 13 項）。
- **不影響讀取：** 既有記錄可讀、可沿原網址開啟、參照欄位仍選得到、反向關聯照常；未結的 MES 訂單可以繼續推進狀態、手動建工令（選它的列）、經 P3 轉出貨，直到結案（資料模型 §9 第 3 題）。
- 判斷位置在入口守衛同一層（事件之前），依保存的宣告與當下推導的組合，不信任儲存的狀態；只讀已開啟應用程式的狀態，沒有任何覆蓋時零成本。
- 單開 MES 時已核准的 MES 報價，在 CRM＋MES 時不能再轉成 MES 訂單（轉換到被收掉的模組）；要在 CRM 重新報價（列入 §11）。

### 6.2 群組與權限

- **整合不替任何群組授權**（s2c §7 不變）。系統身分只用在事件效果、履約重算的寫回。
- **觸發權限就是操作本身的權限：** 誰能確認 CRM 訂單，誰就能讓工令被建立，也能對它補連動；誰能過帳進銷存出貨單，誰就能讓 CRM 訂單列的 `deliveredQty` 變動。
- **轉換到夥伴模組：** 要有來源 Read 與目標 Add（既有 `ConvertRecordHandler`）。照 ERP 慣例由倉管依訂單開出貨單：倉管需要 CRM、MES 的 Read，所以兩份套件各加 `viewer` 群組；Demo 把倉管帳號對應進去（第 20 項）。業務要自己開出貨單，須由管理員另外授予進銷存出貨單的新增權限。
- **看得到追溯：** 生管要看工令的 `crmLine`，需要 CRM `viewer`；沒有 Read 的人看到明細追溯欄位，照核心既有的隱藏規則顯示（§4.3）。
- **基準量的人工修改**需要該明細所屬模組的 Edit（一般欄位權限），不另設權限。
- **成對卸除**的權限同 retry（設計器 Edit 加系統管理員）。
- **自動轉移**不屬於任何群組，誰都不能手動執行；能讓它發生的是觸發操作的權限（過帳出貨單的人讓 CRM 訂單轉 `shipped`），系統身分只寫狀態欄位，稽核與歷程記觸發的使用者（§4.9）。
- 覆蓋是權限層之外的另一道閘，不改任何群組的權限列，不 fail-open。

## 7. 既有資料與已開啟應用程式的遷移

- **不寫舊資料庫的資料遷移**，與 s2d §11 相同：s2d 已要求重建（舊庫不會轉成共用主檔），s2e 建立在 s2d 之上，一樣只對重建的資料庫生效。Demo 每次部署重建。EF migration 只負責 §5.6 的結構。
- **已開啟的應用程式**保存的是開啟當時的套件內容與 `IntegrationsJson`，不會自動換成新版：舊庫的 `stockOut` 照舊；舊庫若之後才開新版 CRM，P1 的 CRM 半找不到 MES 半，停在 `Waiting`（`pairMissing`），不會只裝一半。
- **s2e-a 合併後、s2e-b 之前的使用者可見變化**（每項都隨 s2e-a 一起改 Demo）：CRM 訂單多一個草稿與確認；MES 建工令要選來源（訂單列或備庫）；數量顯示 3 位；有下游時取消、刪除上游或刪明細列會被擋並列出下游；訂單結案（已完成、已結案）後，取消、刪除它的下游工令與出貨單會被擋，要先重開訂單（新增重開轉移）；CRM 訂單明細可人工記 `deliveredQty`。其餘行為（含 `stockOut` 扣庫存、三個應用程式互不連動）與合併前相同。
- **組合中途改變時的既有單據**（新庫內，s2e-b 之後）：

| 變化 | 既有單據的處理 |
|---|---|
| 單開 MES 用一段時間後開 CRM | MES 報價、訂單停止新增；未結的 MES 訂單繼續走完；工令保留 `salesLine` |
| 單開 MES 後開進銷存 | MES 出貨單停止新增；草稿只能取消；已出貨的不動；之後出貨經 P3 轉換 |
| 只開 CRM 人工記了出貨量後開進銷存 | 人工量成為基準量鎖住，進銷存只能出剩餘量 |
| CRM＋進銷存關掉進銷存 | 已過帳出貨仍計入 `deliveredQty`；進銷存唯讀，出貨單不能取消；基準量重新開放人工記，但總量仍受 max 限制 |
| MES＋進銷存關掉進銷存 | MES 出貨單回來；`deliveredQty` 含進銷存出貨，MES 不能對同一批再出（max）；期間的報工不入庫，重開後補連動 |
| CRM＋MES 關掉 MES | 已建工令唯讀保留，`producedQty` 停在最後的值；新確認的訂單不建工令，自製品列可人工記出貨量（沒有工令就沒有 `traced` 來源）；MES 重開後可對這些訂單補連動 |
| 關掉 CRM | MES 報價、訂單選單回來；由 CRM 訂單建立的工令保留 `crmLine`，唯讀可查；MES 繼續報工時用快照照算 CRM 訂單列的上下限，CRM 重開時整批重算寫回，訂單狀態依重算結果自動轉移（§4.9） |

- **Demo（s2e-a）：** CRM 情境的訂單改為先草稿再確認（`OrderPath` 加確認步驟），加一張草稿直接取消；MES 情境的工令改選 MES 訂單列，另有一兩張標成備庫；數量含一筆小數。`stockOut` 的 Demo 步驟照舊。**工令時序與內容：** 現在 `MesProductionScenario` 的工令建立時間是獨立抽的，`OrderScenario` 在訂單日期後一天確認，同一天可能先建工令、後確認；`Facts["status"]` 是規劃的終態，不是建立當下的狀態。a3 要改成：工令建立時間排在來源訂單**實際確認步驟之後**（不是由日期推論），品項取所選訂單列的品項（不再另抽 `Items`），數量不超過該列訂購量；備庫工令才自選品項。這些在 a3 實際跑 Demo 驗證，不以推論代替。
- **Demo（s2e-b）：** 加一張同時有自製品與外購品的 CRM 訂單；三者全開時，MES 情境的工令來自 CRM 訂單（不再另建 MES 訂單），生管設入庫倉、下達、報工，末道報工完工入庫，其中一筆報工沖銷；進銷存情境由倉管依 CRM 訂單轉出貨單並過帳，含一次分批出貨與一次取消後重轉。移除 `stockOut` 相關的 Demo 步驟，「進銷存查詢組」對應調整（s2c §10.3）。訂單的出貨段改為自動轉移（§4.9）：CRM `OrderPath` 拿掉手動 `confirmed → shipped`，改由出貨量推進（只開 CRM 時記基準量、其他組合靠出貨單），再由人轉 `completed`；MES 情境拿掉手動 `confirmed → shipping`，改由第一張出貨單推進；分批出貨的那張訂單在部分出貨時仍是 `confirmed`、全交後轉 `shipped`，取消後重轉的那張先退回 `confirmed` 再轉回。資料一律虛構。

- **前端：** s2e-a 有明細列挑選器（顯示「表頭 · 列」）、履約欄位逐列可編輯、追溯守衛的 409 訊息；s2e-b 有選單與新增鈕依覆蓋、補連動按鈕、卸除整合的確認。記錄頁的轉換清單本來就由 API 決定，整合轉換不需新畫面。

## 8. ERP 對照與開關組合

### 8.1 Odoo 與 SAP 的做法

- **Odoo：** `sale.order` 確認時依品項路線產生需求；路線含「依訂單製造」與「製造」時，每個需求產生一張 `mrp.production`，並自動產生出貨單（`stock.picking`）。製造單完工時成品以庫存移動入庫；訂單明細的 `qty_delivered` 由出貨的庫存移動計算，`qty_invoiced` 由發票明細計算；取消已有完成出貨的訂單要先處理出貨。
- **SAP S/4HANA：** 銷售訂單（VA01）的需求經 MRP 或依訂單生產產生生產訂單；報工確認（CO11N）、成品收貨（移動類型 101，沖銷 102）；交貨單（VL01N）參照訂單項目，發貨過帳（601）更新訂單的交貨狀態；單據流（VBFA）記到項目層級，沖銷以反向移動類型表達，不刪原單。

| 面向 | Odoo | SAP | Formwright |
|---|---|---|---|
| 訂單確認產生工單 | 依路線，逐需求 | 經 MRP 或依訂單生產 | 自製品逐列，不經 MRP |
| 追溯層級 | 明細（`sale_line_id`） | 項目（單據流） | 明細列 |
| 備庫生產 | 補貨規則產生，無銷售來源 | 計畫訂單，無銷售項目 | 工令標「備庫」 |
| 完工入庫 | 庫存移動 | 101／102 | 進銷存庫存異動，沖銷依原報工 |
| 出貨單產生 | 確認時自動 | 使用者建立交貨單 | 使用者由訂單轉換 |
| 已交貨量 | 由庫存移動計算 | 單據流與交貨狀態 | 由追溯事實計算，換手不歸零 |
| 有下游時取消訂單 | 要先處理出貨與製造單 | 有後續單據時不能刪項目 | 追溯守衛擋下並列出下游 |
| 超交容許 | 可設 | 可設容差 | 不做（上限＝訂購量） |

相同的是單據擁有者（銷售擁有訂單、製造擁有工單、庫存擁有出貨）與明細層級的追溯；簡化的是不經 MRP、不自動產生出貨單、不做預留與超交容許。理由：目標客戶是 50 人以下的模具廠，訂單通常一列一模、少量；自動產生出貨單會讓「確認」帶出使用者沒開的單據，由轉換開立又自然支援分批出貨（資料模型 §5.2）。

### 8.3 會計影響（設計檢核第 7 題）

s2e 不產生傳票：完工入庫、出貨都是庫存異動，不進傳票（資料模型 §3.5）。s3c 需要的前提由 s2e 備好：工令、進銷存出貨明細、MES 出貨單都追溯到訂單列，開票可以算到列；取消類狀態、上限重驗、追溯守衛已存在，s3c 只需加 `invoicedQty` 的來源、開票政策上限與「已開票的出貨不能取消」。

核心能力與各自的兩個以上不相干情境：

- 取消類狀態：訂單、採購、進貨各自的重轉。

**測試清單（核心能力，用測試專用套件）：**

- **T-A1 取消類狀態：** 取消的目標不佔已轉量，可重轉；表頭轉換取消後可再轉；`cancelled` 未同時 `readOnly`、標在非狀態選項上，套件驗證 400。
- **T-A2 改量重驗：** 採購 10 轉進貨草稿 10，改成 20 存檔 409；取消後重轉。
- **T-A3 追溯守衛：** 轉換表頭、轉換明細、`lineTrace` 三種各一；取消上游只看未取消的下游；刪除上游記錄與刪除明細列，已取消的下游也擋；下游全取消後可取消、全刪除後可刪；訊息列出可讀下游的模組、標題、狀態，超過 20 筆附總數。訊息權限：下游模組沒有 Read、記錄不在資料範圍兩種各一，訊息都只有「另有 N 筆你無權檢視的下游單據」，不含標題與狀態；欄位逐欄過濾：標題不可見、狀態不可見、兩者都不可見各一，不可見的欄位不出現在訊息，可見的照列；可讀與不可讀混合時分開列；判斷不因權限而放行；上下限違規訊息對不可讀的訂單同樣不帶標題與數量。
- **T-A4 明細追溯：** 一般參照指向明細仍 400；`lineTrace` 指向非明細 400；設計器不能新增 `lineTrace`；挑選只列可讀且在資料範圍內的表頭的列、`refGuard` 限表頭狀態；同一張訂單兩列同品名、同數量、單價不同時，挑選文字以列次區分（「SO-0012 #1 · 上模座」「SO-0012 #2 · 上模座」），`price` 只對看得到單價的讀者出現；寫入看不到的列 400；`lock` 把工令 `salesLine` 複製到 MES 出貨單；**可讀工令、不可讀訂單的使用者建出貨單被拒**（複製後以原操作者重驗表頭 Read 失敗，整筆 400，不建出貨單）；表頭不在資料範圍、`refGuard` 不符各一同樣被拒；系統鍵不構成例外；`lock` 指向其他參照欄位仍 400；讀者沒有表頭 Read 時隱藏；`records/light` 對明細仍 404。
- **T-A5 追溯槽：** 兩個成員都有值 400；不豁免時全空 400；豁免時有值 400；有下游記錄或事件事實後改成員、改豁免欄位 409。三種來源各自的建立：(1) 備庫：`sourceKind = stock`、使用者自選 `item` 存檔成功，`item` 依一般權限可改，`itemNo`、`itemName` 照預設帶值；**備庫工令送 `order` 被拒（400）**，CRM 來源工令送 `order` 同樣 400；(2) MES 來源：選 `salesLine` 後 `order`、`item` 由列推得、`itemNo` 隨之帶值，送不同的 `item` 400，改選另一列（凍結前）時重新推得；(3) 系統事件寫入、`derive: false` 的成員（測試專用套件模擬 P1）：事件帶的 `item` 與列一致時成功、不一致時事件失敗，之後使用者改 `item` 400。成員清空改成備庫時，推得的 `order` 清空，`item` 改採本次送來的值。**持久化：** 開啟應用程式後重建 `DbContext`（或重啟測試主機）重新載入模組，互斥、豁免、凍結仍照樣擋；匯出再匯入空庫後同樣成立；停用或刪除 `exemptWhen` 引用的欄位 400；成員設定指向不存在的槽，套件驗證 400。
- **T-A6 上下限：** max：F 增加超過 409；上限降低到低於 F 409（訂購 10、交貨 6、改訂購 5）；min：F 減少到低於下限 409；下限增加超過 F 放行；違規訊息帶列與前後值。
- **T-A7 人工政策與基準量：** `manual: none` 的欄位改值 400；`baseline` 小於 0 被拒；有適用 `Active` 來源時基準量鎖住、來源不 `Active` 後重開放；`always` 與 `traced`；列層級事實鎖只放行可人工改的欄位。
- **T-A8 快照：** 同一交易內改掛來源、取消、刪除、改 `sum` 值並存時，前後值正確；**只改表頭**：明細來源（測試專用套件的表頭＋明細，明細帶 `trace`）在完全不改明細的情況下，表頭過帳後被追溯的列增加、表頭取消後減少、表頭刪除後減少，三種都找到正確的列；明細換表頭時，新舊表頭狀態各自套用；判斷不讀保存值（夾具先把保存值改成錯的，判斷仍正確，寫回後保存值被修正）；重送與沖銷冪等。

- **T-B1 成對整合：** 任一半缺席 `Waiting`（`pairMissing`）；一半完整性失敗兩半 `Blocked`；兩種開啟順序結果相同；匯出兩份、匯入空庫兩種順序都 `Active`；引用另一半欄位可以、引用無關整合的欄位 400。

- **T-B8 自動轉移（核心用測試專用套件，對應用內建套件）：**
  - **全交轉狀態：** 每一列達標時，同一交易內轉到 `to`；稽核欄位記觸發的使用者，表頭歷程有一筆「自動轉移」帶操作識別與觸發記錄。
  - **部分出貨不轉：** 一列達標、另一列未達標時停在 `from`；表頭沒有明細列時不轉。
  - **取消出貨退回：** 取消一張出貨單使任一列低於訂購量時退回 `from`；再轉一張出貨並過帳，轉回 `to`；只取消表頭、不改明細（明細來源的表頭展開）同樣退回。
  - **其他觸發：** 狀態在 `to` 時新增明細列或調高 `qty`（沒有事實鎖的情況）退回 `from`；手動 `draft → confirmed` 時已足量的，同一交易轉到 `to`。
  - **權限：** 沒有表頭模組 Read 與轉移權限的使用者過帳出貨單，照樣觸發轉移，之後仍不能手動執行任何轉移；這一對的兩個方向手動執行都 409，系統管理員也一樣；觸發記錄對讀不到它的讀者只顯示「另一張你無權檢視的單據」；轉移失敗的 409 訊息照 §4.7 過濾。
  - **冪等：** 重送同一請求不多寫狀態、不多記歷程；狀態已相符時不寫；取消再重轉各記一筆。
  - **結案後取消出貨（上游唯讀守衛，§4.7）：** `to` 之後手動轉到 `completed`（MES 為 `closed`），取消出貨單（進銷存出貨單、MES 出貨單各一）409，訊息提示先重開，狀態與 `deliveredQty` 都不變；無權讀訂單的操作者（C＋I，有進銷存出貨單的權限、沒有 CRM Read）取消同一張出貨單得到的訊息只有「另有 1 筆你無權檢視的上游單據」；訂單重開到 `confirmed` 後同一交易自動回到 `to`（數量仍足），此時取消出貨單成功並自動退回 `confirmed`；再轉一張出貨並過帳後轉回 `to`，人再結案。重開轉移不屬於自動轉移的那一對，驗證不受影響；`to` 仍不能手動進入。
  - **驗證與依賴保護：** `from`／`to` 是唯讀或取消類、`to` 是起始狀態、另有以 `to` 為目標的手動轉移、同一狀態出現在兩個自動轉移、`field` 不是履約欄位、以這一對為觸發的 `transition` 事件、`blockTransitions` 列出這一對、本模組是履約來源的狀態判斷模組，各 400；整合安裝時遇到後三種，整合 `Blocked`。刪除狀態機、刪除 `from`／`to`、標唯讀或取消類、更換狀態欄位、停用或改位數 `field`／`compareTo` 各 400；`DeletePlanner` 列出 `AutoTransition`；新增狀態放行；設計器改自動轉移 400；匯出匯入往返後照樣運作。
  - **目標關閉：** 目標應用程式關閉期間出貨全交，狀態不變；重開後整批重算的同一交易內轉到 `to`；關閉期間取消到不足量的，重開後退回。
  - **fail closed：** 夾具讓狀態寫入被寫入後盾擋下時，觸發它的過帳整筆 409，出貨單不成立。
  - **內建套件：** 只開 C 記基準量全交轉 `shipped`、改回不足退回 `confirmed`、手動 `confirmed → shipped` 409；C＋I 分批出貨：第一批不轉、第二批全交轉 `shipped`、取消第二批退回；C＋M（沒開 I）自製品經 MES 出貨單、外購品記基準量，兩列都足量才轉；只開 M 第一張 MES 出貨單轉 `shipping`、取消它退回 `confirmed`、手動 `confirmed → shipping` 409、`shipping → closed` 由業務主管照常執行；M＋I 經 P3 的進銷存出貨單過帳後 MES 訂單轉 `shipping`。
- **套件與其他：** `supplyType` 空值的品項，確認訂單 409 並列出列；三者全開跑通：報價 → 訂單 → 確認 → 工令 → 報工 → 入庫 → 轉出貨（分批）→ 取消一張後重轉 → `deliveredQty` 等於訂購量、訂單自動轉 `shipped`；目錄層：成對整合的兩半齊全、引用的另一半欄位存在、事件圖無環；原 `MesInventoryIntegrationTests` 的機制案例移到測試專用套件後全綠；`NoBusinessWordsTests`。

### 10.3 審查修訂新增的判斷

2026-11-09 使用者確認的項目見 §10.2 開頭（本節的第 33、35、43、45 項維持）；其餘項目為技術判斷，由主控裁決。第 47～52 項是依 §10.1 第 3 項裁決新增的判斷，第 53～57 項是依 §10.1 第 5 項裁決新增的判斷。

28. **明細追溯用新的參照關係 `lineTrace`，不放寬一般參照；只能由套件、整合宣告。** 理由：一般參照指向明細，會牽動所有模組的挑選、刪除規劃與權限；只開受控的一條，範圍可以完整定義與測試。代價：客戶不能在設計器自己建「指向明細列」的欄位。
29. **新增核心能力「追溯槽」；工令以 `sourceKind`（訂單／備庫）區分備庫與漏填。** 理由：CRM 來源欄位 `crmLine` 由整合新增，套件規則引用不到，互斥、必填、品項一致、有下游後凍結都要跨「套件欄位＋自己那一半整合的欄位」判斷；同一需求 s3c 發票明細（訂單列或出貨列）也會遇到。代價：多一個核心概念；生管手動建工令多一個欄位（預設訂單，備庫要明確選）。
30. **下限欄位增加時不檢查 min。** 理由：從庫存先出貨、工令後完工時，已交貨量超過完工量是合法的中間狀態；只在完工量減少時擋。代價：「交貨超過完工」不會在出貨當下提醒，要到沖銷報工時才擋。
31. **目標應用程式重開時，整批重算它所有含履約欄位的模組的每一列，不只目前有來源的列。** 理由：關閉期間來源全被取消到零的列不在任何來源清單裡，只重算有來源的列會留下舊量。代價：重開時間與列數成正比；以目標客戶的量可接受，大量資料時要量測（§11）。
32. **履約依賴的欄位與狀態一律不能停用、改型別或刪除，不論整合狀態；執行期依賴失效時擋下會重算到它的寫入。** 理由：fail closed，不默認零、不沿用舊值；停用整合的歷史來源仍算數，所以仍受保護。代價：要改這些欄位得先卸除整合；套件自己的來源只能隨應用程式刪除。
33. **補連動：逐筆、人工觸發，只補 `create` 類整合事件，權限等於觸發操作本身，已沖銷的不補。** 理由：不自動重播，避免和關閉期間的人工處理重複；沿用事實唯一索引防重，補出的連動與一般連動完全相同，取消與沖銷不需要新規則。代價：要有人逐筆補；已用盤點調整補過的，系統偵測不到這種重複，要由操作者指定調整單走沖抵路徑（第二輪修訂，見第 44 項）。
34. **成對卸除要求兩半先停用、沒有歷史資料；刪除應用程式時可卸除的成對整合自動一起清。** 理由：有資料時拆掉會讓追溯值、事件事實與欄位對不上；沒資料時一起清，刪除才真的可用。代價：有歷史資料的成對應用程式只能關閉、不能刪除。
35. **刪除上游（記錄或明細列）時，已取消的下游也擋；取消上游只看未取消的下游。** 理由：刪除會讓下游的追溯值指向不存在的列；取消不會。代價：要刪訂單得先刪掉已取消的工令。
36. **格式版本：s2e-a 提高到 7，s2e-b 再提高到 8（取代第 24 項）。** 理由：兩個合併點各自 fail closed，s2e-a 版本讀到 s2e-b 的檔案整份拒絕，比「同一版本中途加鍵」清楚。代價：多一次版本號。
37. **`ofRecord`、`fulfills` 放在 s2e-b。** 理由：只有整合用到（P3 沖銷入庫、P2／P3 轉出貨）；s2e-a 單開時沒有情境可驗收。代價：`ConversionLedger` 在兩個單元各改一次（a 排除取消、b 扣履約）。
38. **MES 訂單明細兩個履約欄位都是 `manual: none`。** 理由：來源是 MES 自己的工令，應用程式開著就可用，沒有換手情境。代價：單開 MES 時不能記沒有工令的交貨；MES 出貨單本來就必須參照工令，現況也記不了。
39. **期初完工量的受控初始化列為不排。** 理由：目前流程沒有需求；審查允許延後。代價：從只開 CRM 換到 C＋M 時，換手前的完工量記不進 `producedQty`（出貨量可以，靠基準量）。

第二輪審查後新增：

40. **追溯槽成員以 `derive`／`match` 推得並鎖住表頭與品項，不用 `fill.mode: lock`；成員沒變時使用者送不同值回 400，不靜默覆蓋。** 理由：既有 `lock` 要求目的整欄唯讀、參照沒變就丟掉使用者輸入，也不能以參照欄位為目的，會讓備庫工令無法選品項、P1 事件寫的品項被移除；綁在「目前有值的成員」才同時容得下三種來源。第三輪補充：`order` 宣告 `derivedOnly`，備庫與 CRM 來源時必須為空（送值 400），備庫只開放自選品項。代價：核心多一個寫入步驟（排在帶值之前）；鎖定改為逐記錄的可編輯旗標，前端要依旗標鎖欄。
41. **追溯槽定義存專表 `Dynamic_TraceSlot`，不在 `Dynamic_Module` 加 JSON 欄位。** 理由：同 `Rule`、`Workflow` 是模組的子實體；`exemptWhen` 存欄位 Id，停用與刪除檢查要能依模組查出「哪個槽引用了這個欄位」，專表有索引，不必每次解析模組 JSON；也不動最常讀的模組主表。代價：多一張表、一個導覽屬性，載入、匯出匯入、刪除各補一處。
42. **`fill` 的目的只放寬一種：`lineTrace` 複製到指向同一明細模組的唯讀 `lineTrace`。** 理由：MES 出貨單要帶工令的訂單列給 s3c 開票；工令有出貨單後槽已凍結，複製值不會分歧。其他參照目的照舊拒絕；帶值（含複製）後以原操作者對目的列重驗 Read、表頭資料範圍與 `refGuard`，不通過整筆拒絕（第三輪修訂）。代價：`FieldRules` 多一個例外分支；若 V5 不成立，改由 MES 事件寫入。
43. **省略 `states` 的來源，依賴整套狀態分類：會改變計入集合的狀態定義變更一律拒絕，不做受控重算。** 包括刪除狀態機、更換狀態欄位、刪除狀態、改任何狀態的取消旗標、對原本沒有狀態機的來源模組新增狀態機；新增狀態照常允許。理由：fail closed，範圍控制（受控重算要另外定義重算範圍、權限與失敗處理）。代價：工令、出貨單等來源模組的狀態機在有履約來源後幾乎不能調整，要調整得先刪應用程式重開。
44. **補連動並沖抵調整：由操作者指定調整單，一對一核驗品項、倉庫、數量，先補入原鏈、再取消調整單，同一交易、以最終庫存驗證；調整單含其他品項時不支援（409，提示人工處理）。** 理由：審查反例中「先取消調整單」會負庫存；一對一比對最容易驗證、也最不會沖錯；原本「另開調整單補回其餘品項」的做法，會讓那張新調整單再入庫一次，仍與補連動重複，第三輪刪除。代價：只涵蓋 P3 的盤點調整（宣告在事件的 `catchUp.offset`）；混合品項的調整單只能人工處理，系統不協助。
45. **追溯守衛與上下限的錯誤訊息只列可讀記錄，不可讀的只給筆數；可讀記錄的每個欄位（標題、狀態、其他）再依操作者的欄位可見性逐欄過濾（第三輪修訂）；判斷仍看全部。** 理由：與 `ReferenceResolver` 隱藏無權參照標題的規則、既有記錄回應的 `CanSee` 一致，不洩露其他應用程式的單據，也不經由狀態等欄位洩露。代價：操作者可能只知道「另有 N 筆」卻看不到是哪幾張，要找有權限的人處理。
46. **明細列挑選以明細的自動編號當列次，補充欄位由 `pickerFields` 宣告並依欄位可見性顯示。** 理由：同單、同品、同量的兩列只有列次能穩定區分；單價等資訊不是每個人都能看。代價：沒有自動編號的明細只能顯示列 Id。

使用者裁決（§10.1 第 3 項）後新增：

47. **自動轉移的一對（`from → to` 與退回）只由系統執行，手動推進與退回一律 409，含系統管理員；`to` 只能經自動轉移進入。** 理由：裁決的目的是狀態與數量一致；允許手動推進，就要為每筆記錄保存「誰推進的」標記來決定能不能自動退回，手動推進的記錄又回到不一致。代價：要提早標「已出貨」只能先記出貨量；原本的 CRM `confirmed → shipped`、MES `confirmed → shipping` 手動轉移移除，Demo 與既有測試要改。
48. **CRM `completed`、MES `closed` 維持手動，驗證也禁止自動轉移的兩端是唯讀或取消類狀態。** 理由：兩者是唯讀的結案，代表人的判斷（短交結案、驗收，之後還有開票）；進入後記錄被鎖，自動退回會推翻人的決定、解開已鎖的記錄。代價：結案後再取消出貨單，狀態停在結案、數量變少（§11）。
49. **MES 訂單：至少一列 `deliveredQty` > 0 時 `confirmed` 轉 `shipping`，全部歸零時退回；全交沒有對應狀態。** 理由：`shipping` 的標籤是「出貨中」，對應開始出貨；CRM `shipped` 的標籤是「已出貨」，對應全交。兩者語意不同，硬套同一條件會讓 MES 部分出貨時看起來沒動。代價：核心的條件要支援 `all`、`any` 兩種；MES 全交後要靠數量判斷，或由業務主管結案。
50. **自動轉移排在履約重算之後、寫入後盾之前，只寫狀態欄位、不觸發事件，依交易後快照判斷。** 理由：同彙總的靜默寫入，避免連鎖；判斷用重算值與 §4.4 一致，目標重開時自然歸位。代價：不能在這一對轉移上掛 `transition` 事件（驗證 400）；同一張表頭的其他列也要重算，量與列數成正比。
51. **自動轉移的宣告放在狀態機的轉移定義（既有 JSON），依賴檢查由明細模組找表頭的狀態機，不另建表。** 理由：條件只能引用本模組明細上的欄位，從欄位一步就找得到唯一的狀態機，不需要像追溯槽一樣跨模組查索引（第 41 項）。代價：若之後允許條件引用其他模組的欄位，要改成專表登記。
52. **觸發者不需要也不取得表頭模組的權限；稽核與歷程記觸發的使用者，觸發記錄依讀者權限顯示。** 理由：s2c 不代授權限，觸發權限就是操作本身的權限（同 §6.2）；歷程的觸發記錄若照列標題，會洩露其他應用程式的單據（同第 45 項）。代價：讀不到觸發記錄的人只知道是「另一張單據」造成的轉移。
53. **「上游唯讀」精確定義為鎖定狀態：`readOnly`、非取消類、至少有一條轉出轉移通往非取消類狀態；從狀態機宣告推得，不看狀態名與轉移群組。** 理由：只看 `readOnly` 時，「過帳即唯讀、只能轉取消」的單據（進銷存出貨單、進貨單）也會鎖住下游；s3c 的發票追溯到它們，取消發票要先取消出貨、取消出貨又被發票擋，互相卡死。這類狀態的出口只有取消，已由既有的下游檢查管。代價：分類是推得的，設計器刪掉唯一的重開轉移會讓守衛放行（§11）；沒有任何轉出轉移的唯讀狀態（採購單 `closed`）不鎖定，因為「先退出唯讀」無法做到，會變成永久鎖死。若主控要明確標記，可改為狀態上的旗標，守衛與測試不變。
54. **守衛擋的是所有非取消類下游的取消、刪除與沖銷，含草稿；已在取消類的下游刪除放行。** 理由：規則最簡單，不必定義「草稿」這個核心不認得的概念；已取消的下游不再貢獻任何履約量，刪除不改變事實。代價：結案訂單底下殘留的草稿出貨單，得先重開訂單才能清。
55. **只看直接上游，不沿追溯鏈往上。** 理由：裁決的範圍是「追溯到唯讀上游的下游」；報工追溯到工令、不直接追溯到訂單列，沿鏈判斷要定義多層與環的處理。代價：報工沖銷會改變結案訂單的 `producedQty`（見 §11）；`producedQty` 不驅動任何狀態，影響較小。
56. **CRM 訂單補 `completed → confirmed`、MES 訂單補 `closed → confirmed`（業務主管），s2e-a 就加。** 理由：守衛的處置是「先退出唯讀狀態」，沒有出口就無從處置；目標用 `confirmed` 是因為 `to`（`shipped`、`shipping`）不能手動進入（第 47 項），而進入 `confirmed` 後同一交易會自動評估。代價：已結案的訂單可以被主管重開，要靠權限與歷程控管；Demo 與權限測試多一條轉移。
57. **間接影響與採購單 `closed` 不納入，列入 §11；不新增依賴登記。** 理由：守衛執行時才讀上游狀態分類，不存推得資料（第 43 項的登記是為了已存的計入集合）。代價：見 §11。

## 11. 風險與已知限制

- **新增的核心能力多**（取消類狀態、明細追溯、追溯槽、履約欄位、追溯守衛、成對、覆蓋、`each` 擴充、`via`、`ofRecord`、補連動、卸除、自動轉移），s2e 整體比 s2d 大，所以拆成兩個單元。V1 不成立時 s2e-a 停在第一步、重新設計來源格式；s2e-b 的 V3 卡住時 P1～P3 都做不了，s2e-a 的成果仍可獨立使用；V14 卡住時自動轉移停下回報，其餘 s2e-b 項目不受影響。
- **自動轉移只管出貨段：** CRM `completed`、MES `closed` 仍由人執行（第 48 項）。結案後再取消出貨單造成的狀態與 `deliveredQty` 不一致，已由上游唯讀守衛處理（§4.7，§10.1 第 5 項）：結案狀態下取消、沖銷、刪除下游一律 409，要先重開訂單。要提早標「已出貨」只能先記出貨量，不能手動推進（第 47 項）。自動轉移不觸發事件，這一對轉移上不能掛 `transition` 事件。
- **上游唯讀守衛的邊界（§4.7，第 53～57 項）：** (a) 只看直接上游：報工沖銷（追溯到工令）會改變結案 MES 訂單列的 `producedQty`，不被擋，`producedQty` 不驅動任何狀態；(b) 採購單 `closed` 沒有重開轉移，不算鎖定狀態，結案後仍可取消進貨單，s3c 加入 `receivedQty`、`billedQty` 時要決定是否補重開轉移；(c) 鎖定狀態是從狀態機推得的，設計器刪掉唯一的重開轉移會讓守衛放行，要靠設計器權限與審查控管；(d) 結案後要作廢出貨、工令或（s3c）發票，都得先重開訂單，操作多一步；(e) s3c 的設計要明寫「作廢發票遇到鎖定的訂單要先重開」。
- **`skip` 的空窗靠人補：** 補連動要有人發現並逐筆執行（有候選清單）；已用盤點調整補過庫存的，系統偵測不到重複，要靠操作者指定調整單走沖抵路徑。混合品項的調整單不支援沖抵（409，提示人工處理）。
- **P1 的人工備庫工令不能轉掛：** MES 重開後、補連動之前，若生管已手動建了備庫工令代替，補連動會另建帶 `crmLine` 的工令；備庫工令有報工後槽已凍結，不能改掛到 CRM 訂單列，要由人判斷取消哪一張。沖抵路徑只涵蓋 P3 的盤點調整。
- **有歷史資料的成對應用程式不能刪除**，只能關閉（§5.2）。
- **訂單確認後不能改明細**（事實鎖）：要改量只能取消工令、取消訂單、重開新單。使用者接受為第一版限制（§10.1 第 4 項）；ERP 的變更單已排入路線圖的後續單元 s2f「訂單變更單」（已確認訂單改量並連動下游）。
- **C＋I 關閉進銷存後**，已過帳的進銷存出貨單唯讀、不能取消；要沖銷得重開進銷存。
- **重算量：** 履約重算是同步的，一次寫入影響的訂單列數與下游筆數成正比；以模具廠的量（一列個位數下游）不成問題，大量匯入出貨單時要量測。目標應用程式重開時的整批重算與列數成正比，同樣要量測。
- **刪除比以前嚴：** 已取消的下游也會擋刪上游；明細列被追溯後不能刪。
- **舊資料庫不升級**：已開啟的應用程式保有舊整合與舊位數，要重建才會套用 s2e。
