# 階段 2 設計：內建「進銷存」與「MES 模具廠」、四個範本併入 MES、Demo 資料

> 2026-11-08｜路線階段 2 的應用程式部分｜前置：[路線](2026-11-06-erp-roadmap-design.md)、[事件、檢查、分錄](2026-11-08-events-ledger-design.md)、[CRM 應用程式](2026-11-07-crm-app-design.md)、[應用程式套件](2026-11-06-app-package-design.md)、[單據能力](2026-11-06-document-flow-design.md)、[Demo 資料](2026-11-05-demo-data-design.md)
> 標「（我的判斷）」的是我代為決定、可以改的，彙整在 §14。這份文件只寫決定與理由，細節以程式與測試為準。

## 1. 範圍與原則

兩個內建應用程式，隨 WebAPI 發行，由 `AppCatalog` 啟動時載入驗證，沒開啟之前不產生任何模組、選單或資料（同 CRM）：

| 應用程式 | 檔案 | id | 模組鍵前綴 |
|---|---|---|---|
| 進銷存 | `poc/backend/apps/inventory.app.json` | `inventory` | `inv-` |
| MES 模具廠 | `poc/backend/apps/mes-mold.app.json` | `mes-mold` | `mes-` |

另外：現有四個內建範本（訂單、故障報修、模具保養含客戶擴充、品質異常）併入 MES，不再出現在「從範本建立」；Demo 資料併入並擴充；補工令單與出貨單列印範本。

**核心程式不新增任何業務邏輯。** 兩個應用程式全部是 `apps/*.app.json`（格式 4）加測試。核心唯一的改動是 §9 的兩個小項（缺口 A：`TemplateCatalog` 容忍缺目錄；缺口 D：一個通用的日期篩選運算子），兩者都與業務無關，且 `NoBusinessWordsTests` 照跑。

**這份設計沒有發現必須先補的通用能力。** 階段 2 前置的事件、跨記錄驗證、不可修改分錄，加上階段 1 的單據轉換、狀態機、帶值、列印，足以表達兩個應用程式。§9 列出四個「有缺口但不阻擋」的項目：兩項這次做（A、D），兩項只寫清楚缺什麼、留給使用者決定（B、C）。

## 2. 跨應用程式的決定

### 2.1 每個應用程式都能獨立開關

- **MES 不依賴 CRM，也不依賴進銷存。** MES 自帶報價單與訂單；它的 `requires` 只有既有實體（`design.mold`、`sales.customer`，沿用四個範本現在的做法），沒有 `requires.apps`。
- **進銷存不依賴 MES，也不依賴 CRM。** 自帶品項、倉庫、供應商、客戶；`requires` 為空。
- 三個應用程式（CRM、MES、進銷存）兩兩之間沒有任何參照欄位、事件、檢查或轉換。套件設計 §7.4 禁止跨應用程式引用欄位，事件與檢查也只能指向同一份套件的模組（事件設計 §1），所以「不依賴」是格式本身保證的，不靠約定。
- 開啟順序任意，三個可以只開任何一個、任兩個、全部。關閉任何一個，其他的與自己的既有資料仍可查閱（套件設計 §6.3，唯讀）；沒有誰擋住誰關閉，因為沒有 `requires.apps`。
- 事件與檢查的 `code`（全站唯一的 `Key`）、報表與列印範本代碼一律以 `inv-`／`mes-` 當前綴，三個應用程式並存不撞名。模組 `Code`（應用程式內唯一）可以重複（CRM、MES 都有 `order`），因為資料庫識別用的是 `Key`，Demo 產生器沿用 CRM 的做法另存一份代號對照。

### 2.2 出貨：兩邊各有一個，彼此不連動（我的判斷）

- MES 的出貨單：依**工令**交貨給客戶，記數量、日期、狀態；不動庫存。模具廠的工令成品多半直接交貨，不入成品倉。
- 進銷存的出貨單：依品項與倉庫出庫，經事件產生庫存異動，餘額不可為負。
- 兩邊的模組名稱都叫「出貨單」，靠選單的應用程式分組區分；程式裡一個是 `mes-shipment`、一個是 `inv-shipment`。
- 錯了的代價：如果使用者要的是「MES 出貨自動扣進銷存庫存」，需要先有「可選相依」這個通用能力（§9 缺口 B），再把兩邊接起來。目前兩邊各自正確，同時開啟也互不干擾。驗收裡「完工量與庫存都對」，我解讀為：MES 的完工量與出貨量對，進銷存的庫存餘額對，兩者同庫並存時各自仍對。

### 2.3 品項不共用（我的判斷）

進銷存的「品項」是自己的模組（`inv-item`）。MES 的訂單明細、工令的品項欄位沿用現有做法，用文字欄位記料號與品名（四個範本的訂單明細本來就是這樣）。理由：共用要嘛讓 MES 依賴進銷存（違反獨立），要嘛靠欄位層級跨應用程式引用（套件設計 §7.4 不允許）。錯了的代價：同一個料號在兩邊各打一次，使用者之後想串接時要靠 §9 缺口 B。

### 2.4 客戶主檔不統一（需要使用者決定，見 §15）

三處都有「客戶」：CRM 的 `crm-customer`（動態模組）、MES 的客戶（既有實體 `sales.customer`，在 POC 裡是模擬的外部客戶主檔）、進銷存的 `inv-customer`（動態模組，只放出貨需要的基本資料）。各自獨立是目前最小的做法，也讓三個應用程式能單獨使用。但真實客戶會問「客戶資料以誰為準」，這是產品方向，不由我決定。

### 2.5 群組

套件各自宣告群組代號，開啟時由管理員對應。Demo 開啟時的對應見 §11.2。

- MES：沿用四個範本現有的代號 `sales`、`sales-manager`、`floor`、`maint`、`qa`，新增 `planner`（生管）。
- 進銷存：`buyer`（採購）、`keeper`（倉管）、`manager`（進銷存主管）。

## 3. 進銷存

### 3.1 模組與欄位

鍵 `inv-` 開頭，欄位標籤四語系（th、vi 為機器翻譯，標明待校對）。除註明外，下拉選項代號與標籤在 JSON 內定義。

**基本資料**（section「進銷存基本資料」）

- `inv-item` 品項：`no` 自動編號 `ITM-{0000}`、`name` 文字必填（標題）、`category` 下拉（raw 原料／part 零件／finished 成品／consumable 耗材）、`unit` **文字**（pcs、set、kg、box 等，自行輸入；帶值與轉換都不能複製下拉，見 §3.3）、`price` 金額（參考單價）、`safetyStock` 小數（安全庫存）、`active` 布林。
- `inv-warehouse` 倉庫：`code` 文字必填、`name` 文字必填（標題）、`location` 文字、`active` 布林。
- `inv-supplier` 供應商：`name`（標題）、`contact`、`phone`、`email`、`terms`（付款條件）。
- `inv-customer` 客戶：`name`（標題）、`contact`、`phone`、`email`、`address`。

**採購**（section「採購」）

- `inv-po` 採購單：`no` `PO-{yyyyMM}-{0000}`、`supplier` 參照必填、`warehouse` 參照（預定入庫倉）、`orderDate` 預設今天、`expectedDate`、`status` 下拉（draft／confirmed／closed／cancelled）、`subtotal` 彙總（明細金額加總）、`taxRate` 百分比預設 5、`tax` 公式、`total` 公式、`remark`。規則：預定交期不得早於採購日期；取消時備註必填。
- `inv-po-line` 採購明細（明細）：`po` 明細參照、`seq`、`item` 參照必填（帶值 `default`：品名、單位、單價）、`itemName`、`unit`（文字）、`qty` 小數必填、`price` 金額、`amount` 公式。
- `inv-receipt` 進貨單：`no` `RC-{yyyyMM}-{0000}`、`fromPo` 參照採購單（唯讀，轉換追溯）、`supplier` 參照必填、`warehouse` 參照必填、`receiptDate` 預設今天、`status` 下拉（draft／posted／cancelled）、`remark`。
- `inv-receipt-line` 進貨明細：`receipt`、`seq`、`item` 參照必填（帶值：品名、單位）、`itemName`、`unit`（文字）、`qty` 小數必填且須大於 0（驗證規則）、`price` 金額、`amount` 公式、`sourceLine` 整數唯讀（轉換追溯）。

**庫存**（section「庫存」）

- `inv-shipment` 出貨單：`no` `SH-{yyyyMM}-{0000}`、`customer` 參照必填、`warehouse` 參照必填（出庫倉）、`shipDate` 預設今天、`status` 下拉（draft／shipped／cancelled）、`remark`。
- `inv-shipment-line` 出貨明細：`shipment`、`seq`、`item` 參照必填（帶值）、`itemName`、`unit`（文字）、`qty` 小數必填且大於 0、`price` 金額、`amount` 公式。
- `inv-adjust` 盤點調整單：`no` `AJ-{yyyyMM}-{0000}`、`warehouse` 參照必填、`adjustDate` 預設今天、`reason` 下拉（count 盤點／damage 損耗／opening 期初／other）、`status` 下拉（draft／posted／cancelled）、`remark`。
- `inv-adjust-line` 調整明細：`adjust`、`seq`、`item` 參照必填、`qty` 小數必填（盤盈為正、盤虧為負，不可為 0）、`note`。
- `inv-move` 庫存異動（**分錄**）：`item` 參照必填、`warehouse` 參照必填、`qty` 小數必填（入庫正、出庫負）、`kind` 下拉（in／out／adjust）、`moveDate` 日期、`docNo` 文字（來源單號）、`reverses` 參照庫存異動自己（唯讀）、`note`。`item`、`warehouse`、`qty` 設為可篩選（檢查引用，套件開啟時就設好，不靠儲存檢查時自動打開）。

### 3.2 狀態機

- 採購單：draft → confirmed（採購、主管）、confirmed → closed（採購、主管；手動結案）、draft／confirmed → cancelled（主管）。closed、cancelled 唯讀。
- 進貨單、出貨單、盤點調整單：draft → posted／shipped（倉管、主管）、posted／shipped → cancelled（**主管**）、draft → cancelled（倉管、主管）。posted／shipped、cancelled 唯讀。

草稿單據可以編輯與刪除，過帳後全單唯讀（事實鎖加唯讀狀態雙重保證）。要更正就取消，事件沖銷庫存，再重開一張。

### 3.3 單據轉換

- `inv-po-to-receipt`：採購單（confirmed）轉進貨單，含明細的部分轉換，數量用 `qty`、追溯欄位 `fromPo`／`sourceLine`。表頭複製供應商、倉庫（參照欄位，目標相同才能複製）；明細複製品項（參照）、品名、單位（文字）、單價。剩餘量、併發互斥沿用單據能力 §4。
- **單位為什麼是文字（審查第一輪 #3）：** `FieldRules.CopyCompatible` 不允許帶值或轉換複製下拉欄位（選項 Id 每個模組不同），所以凡是要被帶值或轉換複製的欄位都不能是下拉。CRM 刻意把單位設成文字，這裡照做。**已知限制（沿用單據能力 §4.3）：** 取消目標單據不釋放已轉量；已過帳的進貨單取消後，採購單剩餘量不會回來，要補收請直接開進貨單（不經轉換）。

出貨與盤點不經轉換（沒有上游單據）。

### 3.4 事件（`code` 即全站唯一鍵）

| 事件 | 來源與觸發 | 效果 |
|---|---|---|
| `inv-receipt-post` | 進貨單 `transition` → posted | `post`：`create` 庫存異動，`each` 進貨明細：品項 ← 明細品項、倉庫 ← 表頭倉庫、數量 ← 明細數量、`kind` = in、`moveDate` = today、`docNo` ← 表頭單號 |
| `inv-receipt-cancel` | 進貨單 `transition` posted → cancelled | `reverse`：沖銷 `inv-receipt-post` 的 `post` |
| `inv-shipment-post` | 出貨單 → shipped | 同上，數量用公式 `-{明細數量}`，`kind` = out |
| `inv-shipment-cancel` | 出貨單 shipped → cancelled | `reverse` |
| `inv-adjust-post` | 盤點調整單 → posted | 數量 ← 明細數量（已含正負），`kind` = adjust |
| `inv-adjust-cancel` | 盤點調整單 posted → cancelled | `reverse` |

事件循環圖：來源模組是三種單據，效果寫入的庫存異動沒有事件，無環。庫存異動的明細欄位（品項、數量）沒有被任何群組隱藏，`allowHiddenSource` 不需要。事件不複製單價，異動不存金額。

### 3.5 檢查與分錄

- 檢查 `inv-no-negative-stock`：模組庫存異動，`groupBy` [品項, 倉庫]，`sum(qty) ≥ 0`，訊息「庫存不足，不能出庫」。出貨過帳、盤虧、取消進貨都經過它，所以三種情境都不會透支。
- 分錄 `inv-move`：沖銷欄位 `reverses`，`negate` [`qty`]，無 `swap`。庫存異動不能修改、刪除，只能沖銷；沖銷後同品項同倉庫的加總同樣受檢查約束（沖銷一筆已被出貨消耗的進貨，會因餘額為負被擋，這是對的）。
- **沒有任何業務群組對庫存異動有 Add 權限（審查第一輪 #11）。** 異動只由事件（系統身分，不看目標權限）產生，所以不可能出現沒有單據的入庫，也不可能有人手動沖銷某張進貨的異動而讓單據仍是 posted、庫存卻已回補（之後取消該單據，`reverse` 效果會因為已沖銷而略過，單據狀態與庫存脫鉤）。更正一律走「取消單據」，由事件沖銷。期初庫存用盤點調整單（reason = opening）入帳。系統管理員仍可手動沖銷，屬維運手段，沖銷後單據與庫存會脫鉤，文件與畫面都不鼓勵；這是已知限制，不另做通用能力（目前只有這一個情境需要「分錄只能經事件建立」，不符合兩個以上情境的鐵則）。

### 3.6 權限

- **三個群組都有金額權限（審查第一輪 #10）。** 帶值只帶「使用者看得到的欄位」（`ReferenceFill` 用使用者的有效權限），倉管若沒有金額權限，他建的出貨明細與進貨明細單價會是空的，出貨金額報表與列印全空，所以不做金額隱藏。理由也包括：小型企業的倉管本來就看得到出貨單金額。
- 品項、倉庫、供應商、客戶：採購、主管可新增修改；倉管唯讀。
- 採購單與進貨單：採購、主管為主；倉管可讀採購單、新增修改進貨單並過帳。
- 出貨單、盤點調整單：倉管、主管可新增修改與過帳，採購唯讀。
- 庫存異動：全部群組唯讀，沒有任何群組有 Add（§3.5）。
- 資料範圍全部 `all`；沒有依人員隔離的需求。

### 3.7 報表（隨套件）

報表引用規則同 CRM：彙總欄位不能直接進報表，所以對明細或異動求聚合。

- `inv-stock-balance` 庫存餘額（品項 × 倉庫）：主模組異動，分組 [品項, 倉庫]，度量 `sum(qty)`，表格。
- `inv-flow-monthly` 月別進出量：分組 [`moveDate` 月, `kind`]，度量 `sum(qty)`，長條圖（出庫為負值）。
- `inv-po-status` 採購單狀態分布：圓環圖。
- `inv-purchase-by-supplier` 各供應商採購金額（未稅）：主採購單、子採購明細，分組供應商，度量 `sum(amount)`，長條圖。
- `inv-ship-by-customer` 各客戶出貨金額（未稅）：同上，主出貨單。

### 3.8 列印範本

- `inv-ship-sheet` 出貨單（掛在 `inv-shipment`）：客戶、出庫倉、日期、單號、`{{#each inv-shipment-line}}` 明細表（項次、品名、單位、數量、單價、金額）、合計、備註。沿用 CRM 報價單的寫法，值一律跳脫。

## 4. MES 模具廠

### 4.1 流程

```
報價單 ──轉換──▶ 訂單 ┄┄參照┄┄▶ 工令（一張一品項，製程為明細）◀── 報工（分錄，只能沖銷）
 (mes-quote)    (mes-order)       (mes-workorder)                  (mes-report)
                                         ▲
                                   出貨單 (mes-shipment，一張對應一張工令)
```

另有故障報修、模具保養（含模具與客戶擴充）、品質異常，原樣併入。

**訂單到工令不用單據轉換，改為工令以參照選訂單（審查第一輪 #6，我的判斷）。** 審查裁決工令一張一品項、品項放表頭。轉換引擎做不到「每一列訂單明細各產生一張工令」：有 `lines` 的轉換一次只產生**一張**目標表頭，而且要求目標有明細模組承接數量；沒有 `lines` 的是表頭轉換，同一張來源最多轉一次。要讓工令表頭自己有品項與數量（§4.7 的檢查需要工令上有一個真正的數量欄位當上限，見下），就不能走有明細的轉換。所以工令由生管新增，選一張訂單當來源（帶值 `default` 把訂單交期帶成工令交期），品項與數量自行填。代價：系統不追蹤「訂單某一列已排了多少工令」，也不防止超排；訂單頁的「反向關聯」分頁仍列得出這張訂單的所有工令，由生管對照。這個缺口寫在 §9 缺口 E（逐列轉換），留給 s2c 評估。

### 4.2 併入的八個模組（四個範本）

鍵加 `mes-` 前綴，其餘維持原樣（欄位、選項、規則、檢視、權限、順序），做為遷移的**逐項等價**基準（§6.2 有等價測試）：

- 訂單 `mes-order`、訂單明細 `mes-order-line`（section「接單」）
- 故障報修 `mes-repair`（section「設備」）
- 模具擴充 `mes-mold-info`、客戶擴充 `mes-customer-info`、模具保養 `mes-mold-care`、更換零件 `mes-mold-care-part`（section「設備」，客戶擴充放「接單」）
- 品質異常 `mes-quality`（section「品質」）

對這八個模組做的**改動**只有下面幾項，其餘不碰；等價測試的白名單就是這份清單：

1. 訂單：新增 `fromQuote` 參照（唯讀，轉換追溯）；新增狀態機（見 §4.4）並拿掉原本「已結案、已取消時整單唯讀」的規則，改由狀態機的唯讀狀態達成（效果相同，一處表達）；新增「品質異常筆數」彙總欄位（Demo 原本在建立後用指令補加，現在是套件的一部分）。
2. 訂單明細：新增 `sourceLine` 整數唯讀（報價轉訂單的追溯）；**`unit` 由下拉改為文字**（審查第一輪 #3）：報價單轉訂單要把單位帶過去，而轉換不能複製下拉欄位（`FieldRules.CopyCompatible`）。這是唯一改變既有欄位型別的地方；舊範本的單位選項只有 pcs、set、kg，Demo 情境與測試改用同樣的字串值。
3. 品質異常：新增 `workOrder` 參照（選填），讓異常能掛到工令。
4. 原本 Demo 在範本套用後用指令補的權限（品保可讀訂單；品質異常的 `responsibleUnit` 對業務唯讀、`defectRate` 對現場隱藏、`critical` 選項只開給品保），搬進套件自己的 `permissions`／`fieldAccess`／`optionScopes`。
5. 四語系：範本只有繁中與英文，th、vi 為機器翻譯補齊。

### 4.3 新增的模組與欄位

**接單**

- `mes-quote` 報價單：`no` `QT-{yyyyMM}-{0000}`、`customer` 實體參照（`sales.customer`）必填、`quoteDate` 預設今天、`validUntil`、`status`（draft／pending／approved／rejected）、`owner` 使用者、`subtotal` 彙總、`taxRate`、`tax` 公式、`total` 公式、`remark`。
- `mes-quote-line` 報價明細：`quote`、`seq`、`itemNo`、`itemName` 必填、`qty` 小數必填、`unit` **文字**、`price` 金額、`amount` 公式。

**生產**

- `mes-workorder` 工令（**一張一品項**）：
  - `no` `WO-{yyyyMM}-{0000}`、`order` 參照訂單（選填，帶值 `default`：訂單交期 → 工令交期）、`itemNo` 文字、`itemName` 文字必填、`qty` **整數必填**（工令數量，輸入欄位；檢查拿它當上限，必須是真正的數字欄位而不是彙總或公式，見 §4.7）、`unit` 文字、`plannedStart`、`dueDate`、`priority` 下拉（normal／urgent）、`status` 下拉（見 §4.4）、`holdReason` 下拉（shortage 缺料／equipment 設備／change 客戶變更／other），狀態為 hold 時顯示且必填。
  - 彙總：`completedQty`（**已完工量**）= 報工良品數加總，條件「末道工序」為真；`defectTotal` = 報工不良數加總（全部工序）；`shippedQty` = 出貨單數量加總，條件狀態為 shipped。`remainingQty` 公式（`qty − completedQty`）。
  - `lastReportDate` 日期（唯讀，事件寫入）、`remark`。
  - 驗證規則：交期不得早於預計開工；狀態轉為「完工」時已完工量須 ≥ 工令數量（`fieldRef` 比較），短交請走「短交結案」。
- `mes-wo-op` 製程（工令**唯一**的明細模組）：`workorder`、`seq`（工序序號，明細內自動編號）、`process` 下拉（material 備料／rough 粗加工／cnc 精加工／edm 放電／wire 線割／heat 熱處理／polish 拋光／assemble 組裝／trial 試模）、`workstation` 文字、`plannedHours` 小數、`plannedStart`、`plannedEnd`。
- `mes-report` 報工（**分錄**，建立後不能改、不能刪，更正用沖銷）：
  - `no` `RP-{yyyyMM}-{0000}`、`workOrder` 參照工令必填、`opSeq` 整數必填（對應製程的序號）、`process` 下拉必填、`reportDate` 預設今天、`worker` 使用者。
  - `goodQty` **整數必填**（良品數，輸入欄位；檢查與完工量都用它）、`defectQty` 整數預設 0、`totalQty` 公式（`goodQty + defectQty`，僅顯示）、`defectReason` 下拉（dimension 尺寸／scratch 刮傷／burr 毛邊／crack 裂紋／material 材料／other），不良數大於 0 時顯示且必填、`final` 布林（末道工序；為真時這筆的良品數計入工令完工量）、`hours` 小數（工時）、`remark`、`reverses` 參照報工自己（唯讀，沖銷追溯）。
  - 為什麼是分錄（審查第一輪 #12）：報工若可修改，現場可以事後把末道報工從 100 改成 50，完工量就掉到比已出貨量低，沒有檢查擋得住。分錄型不能修改、刪除，只能沖銷；沖銷是一筆 `goodQty`、`defectQty`、`hours` 取負號的新報工（`negate`），累計檢查與彙總都自然把它算進去。沖銷需要 Add 權限，現場有。
  - 不加「良品數必須大於 0」之類的驗證規則，因為沖銷分錄的數量是負的，規則會擋住沖銷。
  - 不良數的記錄與報表：`defectQty`、`defectReason` 都是輸入欄位，報表直接引用。

**出貨**

- `mes-shipment` 出貨單：`no` `SP-{yyyyMM}-{0000}`、`workOrder` 參照工令必填（帶值 `lock`：工令已完工量 → `doneQty`）、`doneQty` 整數唯讀（建立或改選工令時的**完工量快照**，檢查拿它當上限，見 §4.7）、`customer` 實體參照必填（使用者自選；帶值不能寫進參照欄位，`FieldRules.cs` 的限制）、`shipDate` 預設今天、`qty` 整數必填且大於 0、`carrier` 文字、`status`（draft／shipped／cancelled）、`remark`。一張出貨單對應一張工令（分批出貨就開多張）。

### 4.4 狀態機

- 報價單：draft → pending → approved／rejected（核准與退回只有 `sales-manager`）、pending → draft（主管）、rejected → draft。approved 唯讀。
- 訂單：draft → confirmed（業務、業務主管）、confirmed → shipping（業務、業務主管、生管）、shipping → closed（業務主管）、draft／confirmed → cancel（業務主管）。closed、cancel 唯讀。訂單狀態由人推進，沒有事件寫它（審查第一輪 #1 之後拿掉出貨事件）。
- 工令：draft → released（生管）、released → running（生管）、running → done／short（生管）、draft／released／hold → cancelled（生管）、released／running → hold（生管）、hold → released（生管）、**done／short → running（生管；重開，供更正報工用）**。done、short（短交結案）、cancelled 唯讀。
  - `released → running` 的群組只給生管，現場人員不能手動推進；實際推進由報工事件做（事件不檢查群組，但轉移必須已定義）。
  - `hold → running` **刻意不定義**，所以暫停中的工令收到報工（含沖銷）會整筆被擋；要先由生管恢復到 released。
  - 工令進入 done 後唯讀，報工事件寫不進去，所以**完工後不能再報工、也不能沖銷報工**；要更正先由生管重開（done → running）。
- 出貨單：draft → shipped（生管、業務）、shipped → cancelled（生管；退貨）、draft → cancelled。shipped、cancelled 唯讀。

### 4.5 單據轉換

- `mes-quote-to-order`：報價單（approved）轉訂單，含明細的部分轉換（報價明細 → 訂單明細，`qty`，複製品號、品名、單位（文字）、單價；表頭複製客戶（實體參照，目標相同才能複製）、業務），追溯 `fromQuote`／`sourceLine`。

這是 MES 唯一的轉換。訂單到工令為什麼不轉換，見 §4.1。

### 4.6 事件

| 事件 | 來源與觸發 | 效果 |
|---|---|---|
| `mes-report-progress` | 報工 `create`（含沖銷分錄） | `touch`：`update` 經 `workOrder`，工令 `status` ← running、`lastReportDate` ← today |

說明與取捨（我的判斷）：

- **已完工量用彙總，不用事件回寫。** 任務原文寫「報工回寫工令已完工量（連動事件）」，但事件設計 §1 已決定事件不做累加（重送與修改時不冪等），可由彙總算出的值一律用彙總。報工新增或沖銷後工令的已完工量即時更新，行為上等於回寫，且天然冪等。事件只做彙總做不到的事：把工令推進到生產中、記最後報工日。
- 報工事件的轉移檢查：工令必須在 released 或 running 才收得下報工（含沖銷）。draft、hold 的工令，`update` 效果的轉移未定義；done、short、cancelled 的工令是唯讀，`EffectWriter` 會回「目標記錄處於唯讀狀態，無法更新」；兩種都是整筆回滾，訊息是「連動事件「報工推進工令」失敗」加原因。
- **沒有出貨事件（審查第一輪 #1）。** 原設計的出貨事件要寫工令與訂單：工令在 done／short 時唯讀，寫入會被擋，完工的工令永遠出不了貨；訂單若已 closed，`closed → shipping` 未定義，同樣擋住出貨。出貨既然不需要回寫任何東西（出貨量由工令的彙總 `shippedQty` 算），就不設事件。
- 報工事件的 `update` 效果不產生事件事實，不鎖來源；報工靠分錄不可修改。
- 事件圖：報工 → 工令；沒有以工令為來源的事件，無環。

### 4.7 檢查

審查第一輪 #2：檢查的上限欄位（`limit.field` 或 `via` 之後的欄位）只收整數、小數、金額的**輸入欄位**，彙總與公式都拒（`CheckValidator`），事件也不能寫彙總或公式欄位。所以上限一律是真正的輸入欄位。

- `mes-report-within-wo-qty`：模組報工，`groupBy` [工令, 工序序號]，`sum(goodQty) ≤` 經 `workOrder` 取工令的 `qty`（輸入欄位）。訊息「此工序累計良品數超過工令數量」。每道工序各自累計（工令 100 件，每道工序的良品都可以報到 100，不是全部工序合計）。沖銷分錄是負數，自然把累計減回去。
  - **只算良品，不算不良（審查第一輪 #4）。** 原設計加總「含不良的報工數」，工令 100 件、末道報 100 件其中不良 1，補做 1 件就被擋，良品永遠到不了 100，工令無法完工。改成只加總良品數：不良件可以另外補做，累計良品仍不超過工令數量，完工條件（已完工量 ≥ 工令數量）也就達得到。不良數不設上限（它本來就不是產出）。
- `mes-final-once`（審查第一輪 #5）：模組報工，`groupBy` [工令]，`where` 末道工序為真，`sum(goodQty) ≤` 工令的 `qty`。擋住「兩道工序都勾末道、各報 100 件，完工量被算成 200、出貨放行 200」。沖銷分錄複製 `final` 並把良品取負，所以同樣抵銷。
- `mes-shipment-within-completed`：模組出貨單，`groupBy` [工令]，`where` 狀態為 shipped（審查第一輪 #7：草稿不佔用可出貨量，也不被檢查擋，所以「完工量不足、暫緩出貨」的草稿可以存；真正擋的是轉為 shipped 的那一刻），`sum(qty) ≤` **自己這筆的 `doneQty`**（`limit.field`，本筆的輸入欄位）。訊息「出貨數量超過工令已完工量」。取消的出貨單不計入，取消即釋放數量。
  - **`doneQty` 是帶值快照。** 工令的已完工量是彙總，不能當檢查上限；但帶值可以把彙總的值複製進本筆的唯讀輸入欄位（`CopyCompatible`：彙總的結果型別為數字時可帶進整數欄位），選擇或改選工令的那一刻把當時的完工量記下來。
  - **已知限制（要在驗收時說清楚）：** 快照在選工令時固定，之後工令又報了工，這張出貨單的上限不會自動更新，要改選一次工令（或刪掉重開）才會刷新；反過來，快照之後才沖銷了報工，這張草稿出貨單會用過期的偏高上限通過。緩解：工令轉為 done 才算完工，唯讀後不能再報工或沖銷（§4.4），所以出貨通常在 done 或最後一批報工之後才開；草稿單拿到的是開單當下的值。這是用現有能力做出的近似，精確版需要「檢查可以引用另一個模組的彙總」，目前沒有第二個情境需要，不列為缺口。
- 其他已知限制（沿用事件設計 §5.4）：工令數量事後被調低不會重新觸發檢查。

**為什麼選跨記錄驗證而不是既有剩餘量檢查**（任務要求說明）：剩餘量檢查是單據轉換專用，只管「來源明細列被轉成目標明細列」的數量；報工不是轉換產物，是反覆新增的獨立流水記錄，也不依單一來源列計量。跨記錄驗證天生處理新增、移組、刪除與併發。

### 4.8 權限（摘要，以套件 JSON 為準）

| 模組 | 生管 `planner` | 現場 `floor` | 業務／主管 | 品保／設備 |
|---|---|---|---|---|
| 報價、訂單 | 訂單可讀 | 訂單可讀 | 沿用現有 | 品保可讀訂單 |
| 工令、製程 | 全權 | 可讀 | 可讀 | 可讀 |
| 報工 | 全權（含沖銷） | 新增（含沖銷），不能改刪 | 可讀 | 品保可讀 |
| 出貨單 | 全權 | 可讀 | 可讀、業務可新增 | 無 |

報工的資料範圍設為「群組」：同組現場人員互相看得到，比照故障報修現有做法。金額欄位（訂單、報價）維持原有的金額權限。

### 4.9 報表（隨套件）

- `mes-wo-status` 工令狀態分布：圓環圖。
- `mes-output-monthly` 月別完工量：主模組報工，分組報工日期（月），度量 `sum(goodQty)`，條件「末道工序」，折線圖。
- `mes-defect-reason` 不良原因分布：度量 `sum(defectQty)`，分組不良原因，圓環圖。
- `mes-defect-by-process` 各工序良品與不良：分組工序，度量 `sum(goodQty)`、`sum(defectQty)`，表格（不良率由兩欄看出；報表目前沒有比率度量，不為此新增）。
- `mes-ship-monthly` 月別出貨量：主模組出貨單，條件狀態 shipped，分組出貨日期（月），度量 `sum(qty)`，長條圖。
- `mes-overdue-wo` 逾期未完工工令：主模組工令，條件「交期早於今天」且狀態在 released／running／hold，表格。需要 §9 缺口 D 的「早於今天」運算子。

報表只引用輸入欄位（`goodQty`、`defectQty`、`qty`），不依賴「彙總或公式能不能進報表」的細節。Demo 既有的示範報表（`DemoReports`，訂單、報修、保養、品質）不屬於套件，原樣保留；它們引用的是四個範本模組，併入 MES 後改由 MES 的代號對照解析，內容不變。

### 4.10 列印範本

- `mes-wo-sheet` 工令單（掛在 `mes-workorder`）：工令號、訂單號、品號與品名、數量、單位、交期、優先度；`{{#each mes-wo-op}}` 製程表（序號、工序、工作站、預計工時、預計起訖）；已完工量、備註；底部簽核欄。
- `mes-ship-sheet` 出貨單（掛在 `mes-shipment`）：出貨單號、客戶、工令號、數量、出貨日期、運送方式、備註、簽收欄。出貨單本身不存品名，單據上以工令號對照。

**製程為工令的明細。** 單據能力 §5 的做法 A（製程為明細、報工指向工令）才印得出「含製程明細」：列印引擎只迴圈明細模組。因為工令一張一品項（§4.1），製程成為工令唯一的明細模組，原先「工令有兩個明細模組」的假設也不再需要。代價是報工用 `opSeq` 整數加 `process` 下拉對應製程，系統**不驗證**報工的序號存在於該工令的製程，也不在製程列上累計報工量（要看某工序累計，從報工清單依 `opSeq` 篩選，或看 `mes-defect-by-process`）。做法 B（製程獨立）能補這兩點，但需要列印引擎能迴圈「參照本單據的非明細模組」，那是新的通用能力，這次不做（§9 缺口 C）。

## 5. 開關與組合行為

| 組合 | 行為 |
|---|---|
| 只開 MES | 看得到 MES 的選單與全部功能；沒有進銷存模組。工令、報工、出貨完整可用 |
| 只開進銷存 | 同理；採購、進貨、出貨、盤點、庫存報表可用 |
| 兩者都開 | 兩組選單並存，互不影響；各自的事件、檢查、報表照常 |
| 關閉其中一個 | 該應用程式唯讀可查；另一個不受影響，仍可寫入；重新開啟後資料仍在 |
| 三個全開（含 CRM） | 模組鍵、事件鍵、報表代碼、列印範本代碼全站唯一；各自的群組對應獨立 |

「單獨開啟 MES」的前提是環境有 `design.mold`、`sales.customer` 兩個實體提供者（POC 內建模擬提供者，真實部署由整合提供）；缺少時開啟回 409 的 `missingDependencies`，原因 `entityMissing`（套件設計 §7.2）。這與四個範本現在的行為相同。

## 9. 通用能力缺口

### A. `TemplateCatalog.Load` 容忍缺目錄（做，很小）

內建範本全部搬走後，輸出目錄沒有 `templates/`，目前丟例外使站台啟動失敗。改成目錄不存在視為空 catalog。所有情境（沒有內建範本的部署、測試）都受益，不涉及業務。

### B. 可選相依（不做，需要使用者決定）

缺什麼：應用程式宣告「若 X 存在則連動，否則略過」。現在 `requires` 只有硬相依，事件與檢查又只能指向同一份套件。為什麼兩個以上情境需要：MES 出貨扣進銷存庫存、CRM 訂單產生 MES 工令、階段 3 的會計過帳都是同一個需求。為什麼這次不做：它牽動套件格式、相依檢查、事件圖、關閉規則，是產品方向（應用程式要不要有「整合」這一層）而不是這次的實作問題。目前的設計不依賴它。見 §15。

**主控裁決（審查第一輪）：** 這次不做，另開工作單元 s2c 排在階段 3 前。本設計維持三個應用程式互相獨立，也沒有寫死會擋住 s2c 的東西：套件沒有 `requires.apps`、事件與檢查的代碼用應用程式前綴、兩個套件之間沒有共用模組或欄位，s2c 要加「可選相依」時，這些都不需要拆。

### C. 列印迴圈「參照本單據的非明細模組」（不做）

缺什麼：列印範本只能迴圈明細模組。為什麼可能有兩個情境：MES 製程獨立成模組（做法 B）、發票列印收款紀錄。為什麼這次不做：做法 A 已能滿足「工令單含製程明細」，而這個能力要處理迴圈模組的權限與資料範圍，風險不小，等真的有第二個情境再做。

### E. 逐列轉換：來源明細列各轉成一張目標單據（不做，留給 s2c 評估）

缺什麼：現有轉換只有兩種——表頭轉換（一張來源最多轉一次）、含明細的部分轉換（選若干來源明細列，產生**一張**目標表頭與其明細）。沒有「每一列來源明細各產生一張目標單據，並追蹤每列剩餘量」。為什麼兩個以上情境需要：MES 的訂單明細各排一張工令（工令一張一品項）；銷售訂單明細各出一張出貨單、採購單明細各開一張請購轉單，都是同一個形狀。為什麼這次不做：它要新的轉換型別（來源列 → 目標表頭，剩餘量按來源列計），牽動轉換定義、驗證、互斥鎖與畫面；而 MES 的替代做法（工令以參照選訂單）雖然少了排程剩餘量追蹤，仍可運作（§4.1）。

### D. 日期「早於今天」篩選運算子（做，小而獨立，列為可砍項）

缺什麼：現有日期篩選只有「未來／過去 N 天內」，視窗含今天（`ConditionEvaluator`、`DynamicQueryBuilder`、`ReportRunner` 都是 [今天 − N, 今天]）。「逾期」要的是嚴格早於今天，用「過去 N 天內」只能近似，而且會把今天到期的算進去。為什麼兩個以上情境需要：MES 逾期未完工工令、進銷存逾期未到貨的採購單；CRM 的逾期活動、階段 3 的應收帳齡同理。

做法：新增篩選運算子 `beforeToday`（日期欄位值 < 業務日），只用於檢視、報表、儀表板篩選與規則條件；改動集中在 `FilterOperator`、`ConditionParser`、欄位處理器的運算子白名單、`DynamicQueryBuilder`、`ReportRunner.Conditions`、`ConditionEvaluator`，前端條件編輯器加一個選項與四語系文案。**這項若實作時遇到預期外的阻礙，就退回「過去 N 天內」近似並寫進結果檔，不拖住其他項目。**

- **被擋下的紀錄：** 產生器新增「預期被拒」步驟：送出一個應該被擋的請求，斷言回 400 或 409，不寫入任何東西；失敗就是 Demo 產生失敗（等於把檢查在 Demo 資料上驗證一次）。放 5 個：兩次超過工令數量的報工（`mes-report-within-wo-qty`）、一次兩道工序都勾末道造成完工量超過數量的報工（`mes-final-once`）、兩次超過完工量快照的出貨轉 shipped（`mes-shipment-within-completed`）。被擋的結果不會留下記錄，所以另外留兩張**草稿出貨單**（草稿不受檢查，存得進去），備註寫「完工量不足，暫緩出貨」，讓訪客在清單上看得到卡關的樣子。

## 14. 我代為決定的事

1. **MES 獨立、進銷存獨立、兩者與 CRM 兩兩獨立（§2.1）。** 理由：鐵則要求每個應用程式能獨立開關，而跨應用程式引用欄位、事件、檢查都不允許。錯了的代價：要整合就得先做缺口 B（s2c）。
2. **出貨在兩邊各有一個且不連動（§2.2）；品項不共用（§2.3）。** 錯了的代價同上，另外料號要打兩次。
3. **已完工量用彙總（末道工序報工的良品數）不用事件。** 理由：事件設計已決定不做累加，彙總天然冪等。錯了的代價：使用者用「事件回寫」的字面理解，會覺得不是事件；行為等價。
4. **報工是分錄（只能沖銷），上限用跨記錄驗證，只加總良品數（§4.3、§4.7）。** 理由：審查第一輪 #4、#12。錯了的代價：現場改報工要走沖銷再重報，多一步。
5. **工令一張一品項，品項與數量放表頭；訂單到工令不用轉換，改以參照選訂單（§4.1）。** 理由：審查裁決，加上檢查上限必須是輸入欄位。錯了的代價：不追蹤訂單明細已排工量（缺口 E）。
6. **製程為工令唯一的明細（做法 A）。** 錯了的代價：報工序號不被驗證存在、製程列沒有累計報工量（§4.10、缺口 C）。
7. **「末道工序」用報工上的布林欄位，加上 `mes-final-once` 檢查防重複。** 錯了的代價：使用者忘記勾末道，工令完工量不增；轉 done 的規則會擋住並提醒。
8. **出貨檢查用建立時的完工量快照當上限（§4.7）。** 錯了的代價：快照過期時要改選工令刷新；精確版需要新的通用能力，目前不做。
9. **暫停（hold）中的工令不收報工（`hold → running` 不定義）；done 之後要重開才能更正（`done／short → running`）。**
10. **沒有出貨事件、沒有業務群組能新增庫存異動、進銷存全部群組有金額權限（§4.6、§3.5、§3.6）。** 理由：審查第一輪 #1、#10、#11。
11. **單位一律文字（§3.3、§4.2）。** 錯了的代價：單位沒有下拉選項、可能不一致。
12. **MES 模組鍵加 `mes-` 前綴，訂單改用狀態機取代唯讀規則，新增追溯與彙總欄位（§4.2）。** 錯了的代價：已經用舊範本建立了 `order` 等模組的客戶，新舊並存（需自行處理重複），且已建過模具或客戶擴充的資料庫無法開 MES（§5）。
13. **Demo 開啟三個應用程式、新增四個示範帳號與群組（§10.2）；新增三張儀表板（§10.5）。** 錯了的代價：Demo 帳號多四個；要撤回只需刪 `DemoPeople` 幾行與群組對應。
14. **「早於今天」運算子做成通用能力（缺口 D）。** 錯了的代價：多一個篩選運算子；可砍，退回近似。
15. **被擋下的情境以「預期被拒步驟＋草稿單備註」呈現，不新增紀錄「被擋事件」的機制。** 理由：失敗的請求整筆回滾，系統本來就不記，不為 Demo 破例。
16. **出貨單在 MES 一張只對一張工令。**
17. **列印範本三份：工令單、MES 出貨單、進銷存出貨單。**
18. **Demo 資料量**（§10.3、§10.4）是我估的，以「訪客一眼看得到跨月、異常、報表有內容」為目標，實作時可微調。

## 16. 風險與已知限制

1. §8 的十項假設沒實跑；其中 1（彙總帶條件）、3（帶值彙總進唯讀整數欄位）、5（分錄沖銷與事件、檢查互動）影響最大，備案已寫。
2. 沿用事件設計的限制：新增檢查不回頭掃描、限額被調低不觸發、事件不回補既有單據。
3. 單據能力 §4.3 的限制：取消目標單據不釋放已轉量；目標單據事後改大數量可能超轉。
4. MES 的報工序號不驗證存在於製程；工令不核對訂單明細已排量（缺口 E）；出貨檢查用完工量快照（§4.7），快照可能過期。
5. 系統管理員可以手動沖銷庫存異動，使單據狀態與庫存脫鉤（§3.5）。
6. 模具廠的資料量遠小於負載報告的門檻；庫存餘額的聚合在熱門品項上的耗時，沿用事件設計 §5.5 的量測，必要時用結轉。
7. th、vi 為機器翻譯，術語（如「工令」「報工」「製程」）可能不符當地習慣，待母語者校對。
8. 舊版 Demo 資料庫需要重建（§6.3）；已建過模具或客戶擴充的資料庫無法開 MES（§5）。
