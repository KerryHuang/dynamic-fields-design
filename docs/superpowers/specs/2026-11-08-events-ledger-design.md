# 事件、跨記錄驗證、不可修改分錄 設計文件

## 1. 範圍與鐵則

三項都是**由定義宣告的通用能力**，核心程式碼不出現庫存、工令、傳票這類業務名詞（§14 有掃描測試）。每項至少用兩個不相干的情境驗收，情境只存在於測試資料：

| 能力 | 情境 A（進銷存味） | 情境 B（人事味） |
|---|---|---|
| 事件 | 出貨單轉為「已出貨」時，依每列明細新增庫存異動；轉為「已取消」時沖銷這些異動 | 請假單核准時，把對應的假別餘額記錄的「最後核准日」設成今天 |
| 跨記錄驗證 | 同一品項與倉庫的異動數量加總不可小於 0 | 同一個假別餘額記錄下已核准的請假天數加總不可超過該餘額的額度 |
| 不可修改分錄 | 庫存異動：數量取負號沖銷 | 傳票（含借貸明細）：借貸互換沖銷 |

沿用核心反目標：不做執行期 DDL（新資料表只走 EF migration）、權限不 fail-open、不替個別模組手寫頁面、驗證不只做在前端。

**不做：** 腳本執行環境（只留擴充點，§4.9）、多層簽核、對外 Webhook、計算類（MRP、折舊、計薪公式）、事件觸發刪除、事件對明細模組當來源、跨應用程式的事件與驗證（定義只能指向同一份套件的模組，理由同套件規格 §7.4）。

**預期的用法（我的判斷）：** 「可由彙總算出的值」仍用既有的彙總欄位（例如工令的已完工量 = 報工數量加總，報工新增、修改、刪除後即時更新）。事件不提供「累加」運算，因為累加在重送與修改時不是冪等的；事件只做兩件彙總做不到的事：新增其他模組的記錄（帳務、通知性質的單據），以及把其他記錄的欄位**設成**某個值（設值重做一次結果相同，天然冪等）。

## 2. 一次寫入的完整順序

這是整份設計的主線。所有寫入都在**同一個交易**內，交易一開始就持有 SQLite 寫入鎖（§8）。MediatR 管線由外而內：

```
DesignerAccess → SystemAdmin → Validation → Transaction（WriteGate 排隊、BEGIN IMMEDIATE）
  → Idempotency（新增，§3.2）
    → handler（既有，步驟 1 到 7）
      → RecordEffects（新增：步驟 8 到 10）
        → 寫入操作紀錄（§3.2）
  → 提交或回滾
```

| 步驟 | 內容 | 失敗時 |
|---|---|---|
| 1 | 權限、模組狀態（Closed 閘）、資料範圍 | 403／404／409 |
| 2 | **分錄閘**：目標是分錄模組（或其明細）的修改與刪除一律擋（§6.4）；**事實鎖**：來源記錄已產生事件事實時只能動狀態欄位（§4.7） | 409 |
| 3 | `rowVersion` 比對（樂觀鎖，先於一切寫入） | 409 |
| 4 | 全單唯讀規則、狀態機唯讀狀態 | 400 |
| 5 | 帶值、狀態機起始狀態、明細 Prepare、`Process`（正規化、公式、規則、必填）、狀態機轉移檢查 | 400 |
| 6 | 寫入本筆：記錄、索引、歷程、明細列 | 例外回滾 |
| 7 | 既有彙總重算（`RollupRecalc`），沿用既有的 `SaveChanges`；步驟 1 到 7 都是既有流程，這份設計不改它們的順序 | 例外回滾 |
| 8 | **事件**：依寫入日誌（§3.3）找出該觸發的事件，逐個執行效果；效果寫入的記錄又進日誌，繼續找下一層，直到沒有新寫入（廣度優先、有深度上限，§4.6） | 400／409 |
| 9 | **寫入後盾**：日誌裡有「這次請求之前就存在的」分錄記錄，或「請求開始前就有事件事實的」來源記錄，被修改（來源記錄只看除狀態欄位以外的值）或軟刪除，整筆回滾（§6.4） | 409 |
| 10 | **跨記錄驗證**：對本次請求寫過的每一筆記錄（來源、明細、事件寫入的目標、被彙總更新的父記錄）求值（§5） | 400 |
| 11 | 寫入冪等操作紀錄 | 例外回滾 |

排序的理由：

- `rowVersion` 在最前面，因為它代表使用者看到的舊畫面；舊畫面上的操作不該連帶觸發事件。
- 事件在彙總之後：彙總更新過的父記錄也是事件的來源候選（但不觸發，§4.5）；事件看到的是本筆已經算完的終值。
- **驗證在事件與彙總之後、提交之前**：「庫存不可為負」要檢查的正是事件剛新增的異動；先驗再寫會漏掉。驗證用「寫完後的狀態」求值，所以不必推算「現有加上變動量」，也不用處理同一請求內多筆記錄互相影響。代價是違規時已經白寫了一輪（隨即回滾），可接受。
- 驗證失敗、事件失敗、分錄後盾失敗都回傳非成功的 `ServiceResult`，`TransactionBehavior` 既有的邏輯會整筆回滾；操作紀錄在最後才寫，失敗的請求不留痕跡，重送時重新執行。

## 3. 共用基礎

### 3.1 操作識別（OperationId）

每個寫入請求有一個操作識別 `OperationId`：客戶端帶 `Idempotency-Key` 標頭（8 到 64 字，`[A-Za-z0-9_-]`）就用它，沒帶則伺服器產生一個 GUID。它放在 scoped 的 `IOperationContext`，事件執行時所有串聯寫入共用同一個值，寫進事件事實表（§4.4），所以一個請求造成的所有連動都查得到。

### 3.2 冪等：重送不重複生效

路線風險 3 的「重送請求可能重複扣庫存」分成兩層處理：

1. **請求層（`Idempotency-Key`）。** 適用 `POST /modules/{key}/records`、`PUT /records/{id}`、`DELETE /records/{id}`、轉換、沖銷、**確認匯入**。匯入的請求雜湊涵蓋模組鍵與整份檔案內容：同一把 key 重送同一份檔案只生效一次（事實唯一約束替匯入去不了重，因為匯入的每一列都是新記錄）；同一把 key 換了檔案回 422。資料表 `Dynamic_Operation`，主鍵 `(UserId, Key)`，存請求雜湊（請求型別加路由參數加本文的 SHA-256）、結果種類與結果 JSON、建立時間。
   - `Idempotency` 管線行為在交易**內**、handler 之前，所以查詢與後面的寫入在同一把鎖之下：兩個帶同一把 key 的請求同時進來，後者排隊等到前者提交後，查到紀錄，直接回放。
   - 找到相同 key 且雜湊相同：不執行任何東西，回放當時的結果，回應加標頭 `Idempotent-Replay: true`。
   - 相同 key 但雜湊不同：回 422（「同一個操作識別碼用在不同內容」）。
   - 只有成功的結果會存；失敗的請求整筆回滾，沒有紀錄，重送會重新執行，這是對的。
   - 紀錄保留 7 天；每次寫入紀錄時順手刪除 7 天前的（`CreatedTime` 有索引，單筆刪除）。
2. **效果層（事件事實唯一約束，§4.4）。** 不論有沒有 key，同一個事件對同一筆來源記錄（與明細列）的同一個「新增」效果，資料庫唯一索引保證最多生效一次。這是最後防線：即使請求層漏了，也不會對同一張單據重複記帳。

為什麼修改請求本來就不怕重送：`PUT /records/{id}` 帶 `rowVersion`，第一次成功後版本已換，第二次必然 409；有 key 時重送會拿到第一次的成功結果，不是令人困惑的 409。**真正需要 key 的是新增與匯入**：兩次新增是兩筆合法的不同記錄，伺服器無從分辨。因此前端表單每次開啟產生一個 key，送出失敗（網路逾時）重送沿用同一個，成功後才換新（§13.2）。直接呼叫 API 的人不帶 key 就沒有請求層保護；要不要強制帶見 §16 待決。

### 3.3 寫入日誌（`IWriteJournal`）

事件與驗證都要知道「這次請求寫過哪些記錄、寫之前是什麼值」。不在每個寫入點手動登記（漏一個就漏掉），而是在 `UnitOfWork.CommitAsync` 呼叫 `SaveChanges` 之前，掃 EF 的 change tracker 裡狀態為 Added 或 Modified 的 `Record`，連同 `OriginalValues`（`ValuesJson`、`DeleteFlag`）寫進 scoped 的 `IWriteJournal`。這樣任何現在或未來的寫入路徑（含彙總重算、明細、匯入、轉換）都自動進日誌。

日誌是**依時間排序的原始項目清單**，每次 `SaveChanges` 前掃到的每筆記錄一項：`(序號, 記錄, 寫入前的值 或 null, 寫入後的值, 種類)`。EF 的 `OriginalValues` 是「上一次存進資料庫的值」，所以每一項本身就是這一次儲存的精確增量，不需要也不應該預先合併。消費者各自決定怎麼看：

- **事件（看增量，按輪處理）。** 事件分輪執行：第 0 輪處理 handler 結束時日誌裡已有的所有項目；第 0 輪的效果寫入產生新項目，這些是第 1 輪的輸入，依此類推（游標：每輪記下開始時的日誌長度，下一輪只處理游標之後的項目，直到一輪沒有新項目）。**一輪之內**同一筆記錄的多個項目才合併（寫入前取第一項、寫入後取最後一項、種類以第一項為準），**跨輪不合併**。例：A 在第 0 輪新增（觸發 `create` 事件），第 0 輪某事件的效果把 A 從 draft 改成 approved，這是第 1 輪的一項「A：draft → approved」，會觸發 A 所在模組的 `transition` 事件；若像先前那樣整次請求一路合併成「寫入前 = null」，這次轉移就漏掉了。輪數就是深度（§4.6）。
- **跨記錄驗證與分錄後盾（看整次請求的合併結果）。** 兩者關心的是「這次請求最終改了什麼」：同一筆記錄的所有項目合併，寫入前取最早一項（新增則為 null）、寫入後取最後一項。分錄後盾用「最早一項是新增」判斷這筆記錄是不是這次請求新增的。

`RollupRecalc` 重算父記錄時標記該記錄為「靜默」：仍列入驗證，但不觸發事件（§4.5）。

### 3.4 `RecordEffects` 管線行為

放在 `Transaction` 與 `Idempotency` 之內，只處理實作 `IRecordWriteRequest` 的請求（新增、修改、刪除記錄、匯入、轉換、沖銷），對其他請求（設計器、帳號）直接放行。依序做 §2 的步驟 8 到 10，任何一步失敗就把回應換成失敗的 `ServiceResult`。

## 4. 事件

### 4.1 宣告

資料表 `Dynamic_Event`：`Key`（全站唯一，2 到 40 字，慣例以應用程式 id 當前綴）、名稱（多語系）、`SourceModuleId`、`Active`、`DefinitionJson`、稽核欄位。來源模組必須是啟用中的獨立模組（不是明細、不是擴充）。

```json
{
  "trigger": { "on": "transition", "fromStates": [11], "toState": 12 },
  "when": { "all": [ { "field": 21, "op": "gt", "value": 0 } ] },
  "effects": [
    { "code": "post", "kind": "create", "targetModuleKey": "stock-move", "each": "ship-line",
      "set": [
        { "to": 71, "from":    { "side": "line",   "fieldId": 41 } },
        { "to": 72, "formula": { "side": "line",   "expr": "-{qty}" } },
        { "to": 73, "from":    { "side": "header", "fieldId": 22 } },
        { "to": 74, "const": "opt_55" }
      ] },
    { "code": "touch", "kind": "update", "targetModuleKey": "balance", "via": 33,
      "set": [ { "to": 61, "const": "today" } ] }
  ]
}
```

**觸發（`trigger.on`）**

| 值 | 何時觸發 | 附加條件 |
|---|---|---|
| `create` | 來源記錄新增（含轉換產生、匯入以外的所有新增，匯入見 §4.8） | 無 |
| `update` | 來源記錄修改且值有實際變動 | `watch`：欄位 Id 清單，只在這些欄位有變時觸發；省略代表任一欄位 |
| `transition` | 來源記錄的狀態欄位從 `fromStates` 之一（省略代表任一）變成 `toState` | 來源模組必須有狀態機；新增時的起始狀態不算轉移 |

`when` 是選用條件，格式與求值器就是規則條件（`ConditionParser`／`ConditionEvaluator`），對**寫入後**的來源值求值；不成立就不觸發。

**效果（`effects[]`，至多 10 個，依序執行）**

| `kind` | 做什麼 |
|---|---|
| `create` | 在 `targetModuleKey` 新增一筆記錄；有 `each`（來源表頭的明細模組代號）時，對來源的每個未刪除明細列各新增一筆（至多 200 列，同 `DetailWriter.MaxRows`） |
| `update` | 找到來源記錄上參照欄位 `via` 指向的目標記錄（`via` 的參照目標必須是 `targetModuleKey`），把 `set` 的欄位設成指定值；`via` 為空就略過這個效果，不算錯誤 |
| `reverse` | 沖銷先前由 `ofEvent` 的 `ofEffect` 為這筆來源記錄新增的分錄（§6.5）；已經沖銷過的略過，全部都沖銷過就不做事 |
| `custom` | 擴充點，見 §4.9 |

`set[]` 每項的值來源三擇一：`from`（複製來源欄位值，`side` 為 `header` 或 `line`，`line` 只能用在有 `each` 的 `create`）、`const`（常數；下拉用 `opt_<選項 Id>`；日期欄位可用字串 `"today"` 代表業務日）、`formula`（沿用公式語法 `{欄位代號}`，對 `side` 指定的那一邊的模組求值，例如明細的 `-{qty}`）。目的欄位 `to` 必須是目標模組啟用中、非公式、非彙總、非自動編號的欄位；型別相容規則同帶值（單據能力設計 §2.4）。

### 4.2 值的寫法與權限語意

**效果一律用系統身分寫入**，這是事件的意義：倉管員不能直接改庫存異動，但出貨要能扣庫存。具體語意：

| 項目 | 規則 |
|---|---|
| 觸發資格 | 使用者做得了來源記錄的那個動作（既有的 Add／Edit 權限、資料範圍、欄位權限、狀態機轉移群組）。事件**不新增**權限判斷，也不因使用者沒有目標模組權限而失敗 |
| 目標的動作權限、資料範圍 | 不檢查 |
| 目標欄位寫入 | `set` 裡列出的欄位視為系統填入（同單據轉換的 `SystemKeys`）：不受 `Config.ReadOnly`、欄位唯讀或隱藏權限、規則唯讀限制；**仍**走型別 `Normalize`（長度、小數位、15 位有效數字）、規則的驗證與必填、下拉可選範圍。沒列在 `set` 裡的欄位只套預設值，使用者的任何輸入都進不來 |
| 來源值的可見性（**使用者裁決：預設擋下，需明確允許**） | 執行時以系統身分複製，**不看**使用者的欄位隱藏權限（事件是模組間的固定管線；若依使用者可見性複製，倉管員看不到單價就會讓異動缺值）。但**定義時預設擋下**：`from` 與 `formula` 引用的來源欄位，只要對任何群組設了隱藏，儲存事件回 400 並指出欄位與效果；設計者要在該 `set` 項加 `"allowHiddenSource": true` 才放行。設計器對這個勾選顯示說明：「會把被隱藏的值複製到目標模組，看得到目標的人就看得到。」。隱藏設定是事後才加的情況，見下方「事後隱藏」 |
| 狀態機 | 效果新增的記錄從起始狀態開始；效果修改狀態欄位時，轉移必須是**已定義**的（`from → to` 存在），但**不檢查群組**。沒定義的轉移，整個請求失敗 |
| 唯讀狀態的目標 | 目標記錄處於狀態機唯讀狀態時，除狀態欄位外無法寫入。`update` 效果寫完後會回讀，`set` 的值沒生效（被唯讀擋掉）就整個請求失敗，訊息指出目標記錄處於唯讀狀態，不會默默略過 |
| 擁有者與稽核 | 新增的記錄 `OwnerUserId` 取**來源記錄的擁有者**（資料範圍設為「本人」時，單據與它產生的帳務屬於同一人）；`CreatedBy`／`ModifiedBy` 是觸發的使用者 |
| 模組狀態 | 目標模組 Closed（應用程式已關閉）或未啟用：整個請求回 409，不略過 |

**事後隱藏（我選的做法：拒絕儲存）。** 儲存欄位權限（把某欄位對某群組設為隱藏）時，若有任何事件的 `set` 項引用該欄位（`from.fieldId` 或 `formula` 的 `{代號}`，含停用的事件）且該項沒有 `allowHiddenSource`，整個儲存回 400，訊息列出事件鍵、效果代號與欄位，要求設計者先到事件把該項明確允許、或移除引用。選拒絕而不是「要求確認」的理由：確認式流程要多一個狀態與 API 往返，拒絕是 fail-closed、最簡單，代價只是設計者要多走一步。套件匯入與開啟應用程式同樣檢查：套件內的欄位隱藏設定與事件 `set` 項不得違反此規則，違反則整包拒絕。

### 4.3 定義時驗證

儲存事件（`PUT`／`POST /events`）時檢查，任一項不成立回 400 並指出欄位：

- 來源是啟用中的獨立模組；`Key` 格式與唯一；效果 `code` 在事件內唯一（`^[a-z][a-z0-9-]{0,39}$`）。
- `trigger`：`transition` 需要來源有狀態機，`fromStates`／`toState` 在其 `states` 內；`watch` 的欄位屬於來源模組。
- `when` 的條件能通過 `ConditionParser`（欄位屬於來源模組）。
- 每個 `set` 項的 `from`／`formula` 引用的來源欄位若對任何群組設有隱藏，且沒有 `allowHiddenSource: true`，回 400（§4.2）。
- `set` 的 `from`／`formula` 不得引用彙總欄位或依賴彙總的公式欄位（§4.7）。
- 每個效果：目標模組存在、啟用、獨立、非明細；`each` 是來源的明細模組；`set` 的 `to` 不重複、屬於目標、型別相容；`from.fieldId`／`formula` 引用的欄位屬於對應的那一邊；`create` 的目標模組有必填欄位沒被 `set` 涵蓋也沒有預設值時給警告（不擋，因為執行時規則才是權威）。
- `update` 的 `via` 是來源模組啟用中的參照欄位，參照目標就是 `targetModuleKey`。
- `reverse` 的 `targetModuleKey` 是分錄模組；`ofEvent`／`ofEffect` 存在、其效果是 `create` 且目標相同。
- **循環（§4.6）。**
- 上限：每個來源模組至多 20 個事件，每個事件至多 10 個效果，每個效果至多 50 個 `set`。

### 4.4 事件事實與冪等約束

資料表 `Dynamic_EventFact`：

| 欄位 | 說明 |
|---|---|
| `Id` | |
| `EventKey`、`EffectCode` | 用字串而不是外鍵：事件之後被改名效果、刪除，事實仍可讀 |
| `SourceRecordId` | 來源記錄 |
| `ItemKey` | `create`：`each` 時是明細列 Id，否則 0；`reverse`：被沖銷的分錄記錄 Id |
| `TargetRecordId` | 新增或沖銷產生的記錄 |
| `OperationId`、`CreatedTime` | 追溯一個請求造成的全部連動 |

唯一索引 `(EventKey, EffectCode, SourceRecordId, ItemKey)`。`create` 與 `reverse` 效果寫一列；`update` 效果因為設值本來就冪等，不寫（避免事實表隨每次修改膨脹）。

同一個事件對同一筆來源最多新增一次，是刻意的限制：狀態 A→B→A→B 反覆轉移不會重複記帳。需要重複記帳的情境要設計成每次產生新的來源記錄。

### 4.5 哪些寫入會觸發事件

| 寫入來源 | 觸發 |
|---|---|
| 使用者的新增、修改（含轉換產生的目標單據） | 是 |
| 事件效果寫入的記錄 | 是（串聯，受 §4.6 限制） |
| 彙總重算寫入的父記錄 | **否**（靜默） |
| 明細列的變更 | 否（事件的來源不能是明細；表頭是否「有變」只看表頭自己的值） |
| 刪除 | 否 |

（我的判斷）彙總重算不觸發：否則「報工 → 彙總更新工令 → 觸發工令的事件 → …」會讓串聯行為依賴彙總的重算順序，難以推理。想要「完工量達標就結案」，把事件放在報工模組上、條件寫在 `when`。

### 4.6 循環防護與深度上限

**定義時（儲存事件時）：** 把所有啟用中的事件當節點，若事件 E 的某個效果「可能觸發」事件 E'，就建一條 E→E' 的邊：

- `create` 或 `reverse` 效果（目標模組 T）→ 所有來源為 T 且 `trigger.on = create` 的事件。
- `update` 效果（目標 T）→ 所有來源為 T 且 `on = update` 的事件；若 `set` 含 T 的狀態欄位，再加上 `on = transition` 的事件。
- `custom` 效果：由 handler **宣告**它會寫哪些模組與怎麼寫（`DeclareWrites(args)`，§4.9），依宣告建邊，規則同上面的 `create`／`update`。宣告空清單的 handler（不寫資料）不產生任何邊，也不會被拒。handler 在執行時只能透過受限寫入器寫，寫入器只放行宣告過的（模組，create／update）組合，宣告以外的寫入立刻失敗並整筆回滾。

找到環（含自己指向自己）就拒絕儲存，錯誤訊息列出環上的事件鍵。這是保守的：模組層級看有環但資料上永遠走不到的設計也會被擋，使用者需要改成不繞回來的結構。切換事件為啟用、匯入套件、開啟應用程式時同樣檢查（套件內的事件與資料庫裡既有事件一起算）。

**執行時（防禦性，資料與定義可能在定義檢查之後改變）：**

1. **深度上限 5**（與連帶刪除的 5 層一致）。使用者請求的寫入是深度 0，它觸發的事件效果寫入是深度 1，依此類推；超過就整筆失敗，訊息說明串聯過深。
2. **造訪集合：** 一次請求內 `(EventKey, SourceRecordId, 觸發種類)` 第二次出現就整筆失敗（訊息「連動事件形成循環」）。
3. **總量上限：** 一次請求內事件效果寫入的記錄不超過 500 筆。

三者任一觸發都是整筆回滾，回 409。

### 4.7 事件事實鎖

一筆來源記錄只要產生過 `create` 或 `reverse` 事實，就視為**已記帳**：之後除了狀態欄位（模組有狀態機時）外不能修改、不能刪除，行為同狀態機的唯讀狀態（單據能力設計 §3.3），回應帶 `frozenByEffects: true` 讓前端隱藏編輯鈕。理由：帳務已經依這筆單據的內容記下，單據事後被改，兩邊會對不上；要更正就走「轉移到取消狀態 → `reverse` 效果沖銷」。

實作：`Process` 增加一個參數表示該記錄被事實鎖住，與 `IsWorkflowLocked` 同一處判斷；`UpdateRecordHandler`、`DeleteRecordHandler`、明細寫入在這之前以索引查詢 `Dynamic_EventFact(SourceRecordId)` 取得。**一律查，不看模組目前有沒有事件定義**：事實鎖看的是資料（這筆記錄已經記過帳），不是定義；刪掉模組最後一個事件、或停用事件，已記帳的來源仍然鎖著。成本是每次修改或刪除多一次索引點查詢（`SourceRecordId` 有索引，一筆記錄一次），可忽略。

**公式不再重算（第二輪審查 C1）。** 已有事實的來源記錄，公式欄位**不再重算**，保留記帳當時的值：單筆寫入（只能動狀態欄位，其他值本來就不會變，公式也就不會因輸入變動而變）、狀態轉移、定義變更（§10.4）都一樣。理由：公式可能引用日期或其他記錄（例如經參照的單價），重算會讓來源的值與已寫進帳務的值漂移。

**彙總欄位仍隨子記錄更新。** 已記帳的單據上，彙總（例如應收單的已收款加總）仍可隨子記錄更新，這是需求；因此事件的 `from`／`formula` **不得引用彙總欄位，也不得引用依賴彙總的公式欄位**（`ModuleRelations.DependsOnRollup`），定義時回 400（§4.3）：事件複製出去的值必須是記帳後不會再變的值。

後果：用 `trigger.on = create` 且帶 `create` 效果的事件，來源記錄一建好就鎖。要先編輯再記帳，請改用 `transition` 觸發。

### 4.8 匯入

匯入（`ImportRecordsHandler`）對**是啟用事件的來源**的模組拒絕（400：「此模組有連動事件，不支援匯入」）。理由：匯入批次沒有走完整的 handler 流程，要讓它觸發事件等於重寫一遍；先 fail-closed。目標是分錄模組的匯入（期初餘額）允許，但匯入後仍會跑跨記錄驗證（匯入管線行為也掛 `RecordEffects`）。匯入的確認請求支援 `Idempotency-Key`（§3.2）。

### 4.9 外掛擴充點

`IEffectHandler`（Application 層介面）：

```csharp
public interface IEffectHandler
{
    string Name { get; }                       // 例如 "notify-webhook"，^[a-z][a-z0-9-]{1,39}$
    Task<EffectResult> ApplyAsync(EffectContext context, CancellationToken ct);
    IReadOnlyList<string> ValidateArgs(JsonElement args);   // 定義時呼叫
    // 依 args 宣告會寫哪些模組：(模組鍵, create 或 update, update 時是否會改狀態欄位)；不寫資料就回空清單。
    // 定義時用來建循環圖的邊；執行時受限寫入器只放行宣告過的組合
    IReadOnlyList<EffectWrite> DeclareWrites(JsonElement args);
}
```

`kind = "custom"` 的效果寫 `{ "handler": "<name>", "args": { } }`。`IEffectHandlerRegistry` 以 DI 收集所有實作；**目前沒有任何內建實作**。定義時 `handler` 找不到就拒絕儲存（fail-closed）；套件開啟時找不到同樣失敗。`EffectContext` 提供來源記錄的值、`OperationId`、深度，以及一個受限的寫入器（`create`／`update` 與內建效果同一條路徑，所以同樣受循環、深度、冪等約束，且同樣進寫入日誌與驗證）。不提供腳本執行、不提供任意 SQL；寫入器不收模組鍵以外的目標，所以 handler 無從繞過宣告。

內建的三種效果也實作同一個介面，測試用一個假的 handler 證明擴充點通。

## 5. 跨記錄驗證

### 5.1 宣告

資料表 `Dynamic_Check`：`Key`（全站唯一）、名稱、`ModuleId`、`Active`、`DefinitionJson`、稽核欄位。一個檢查掛在一個模組上，該模組的記錄**寫入**（新增、修改、刪除、事件效果寫入、彙總更新）時求值。

```json
{
  "groupBy": [51, 52],
  "function": "sum",
  "fieldId": 55,
  "where": { "all": [ { "field": 56, "op": "eq", "value": "opt_61" } ] },
  "assert": { "op": "gte", "limit": { "const": 0 } },
  "message": { "zh-TW": "庫存不足，不能出貨" }
}
```

意思是：以「被寫入的那筆記錄」在 `groupBy` 欄位上的值為組，把**同一模組內**符合 `where` 的未刪除記錄中，同組記錄的 `fieldId` 加總，結果必須滿足 `assert`。

| 屬性 | 說明 |
|---|---|
| `groupBy` | 本模組欄位 Id 清單（可空，空代表整個模組為一組）。每一欄只能是有索引的型別：`reference`、`enum`、`text`、整數、日期。小數、金額、公式、彙總不能當組鍵（索引是 double，相等比較不可靠，單據能力設計與負載報告 §6） |
| `function` | `sum` 或 `count` |
| `fieldId` | `sum` 要加總的欄位（整數、小數、金額），`count` 不需要 |
| `where` | 選用，規則條件格式，**不支援 `fieldRef`（欄位對欄位比較）**：SQL 聚合無法表達，定義時回 400，不是執行時才拋例外。加總只算符合 `where` 的記錄。被寫入的記錄**寫入前或寫入後任一邊符合** `where` 就求值該邊的組，兩邊都不符合才略過（理由見 §5.2） |
| `assert.op` | `gte`、`gt`、`lte`、`lt`、`eq` |
| `assert.limit` | 三擇一：`{ "const": n }`；`{ "field": id }`（被寫入記錄自己的數字欄位）；`{ "via": refFieldId, "field": id }`（被寫入記錄的參照欄位指向的那筆記錄的數字欄位） |
| `message` | 多語系錯誤訊息。可含 `{value}`、`{limit}`；**預設不含數字**，設計者自行加才會顯示（理由見 §9：加總涵蓋使用者資料範圍之外的記錄） |

情境對照：

- 進銷存味：模組 = 庫存異動，`groupBy = [品項, 倉庫]`，`sum(數量) ≥ 0`（`limit.const = 0`）。
- 人事味：模組 = 請假單，`groupBy = [假別餘額（參照）]`，`where = 狀態 = 已核准`，`sum(天數) ≤ 假別餘額.額度`（`limit.via = 假別餘額參照欄位`、`field = 額度`）。

### 5.2 求值

對本次請求寫入日誌（合併結果，§3.3）中屬於該模組的每筆記錄，看「寫入前」與「寫入後」兩個狀態（新增只有後、刪除只有前）：**狀態符合 `where`（沒有 `where` 則一律符合）才取該狀態的組鍵**，去重後逐組求值。為什麼是任一邊：同組有 +10 與 −8，把 +10 那筆改到不符合 `where`（例如狀態從已核准改成草稿）之後，這組的加總從 2 變成 −8；若只看寫入後的狀態，這筆「現在不符合 where」會被略過，違規就漏了。看寫入前的狀態才會求值這個組。兩邊都符合且組鍵相同只求值一次。

求值步驟：

1. 組鍵含空值的欄位用「為空」條件。
2. 聚合用 `DynamicQueryBuilder` 的新方法 `BuildAggregate`，與列表篩選共用同一套條件轉 SQL 的程式（相同的參數化、相同的白名單），產生
   `SELECT SUM(m.NumberValue) FROM Dynamic_Record r JOIN Dynamic_RecordIndex m ON m.RecordId = r.Id AND m.FieldId = @sum AND m.Seq = 0 WHERE r.ModuleId = @m AND r.DeleteFlag = 0 AND <組鍵條件> AND <where>`。
   查詢在**同一個交易、同一條連線**內執行，且先把變更 `SaveChanges` 刷進去，所以看得到這次請求自己的寫入。
3. **加總用索引時就算好的精確整數，不用 `SUM(double)`，也不在查詢時才放大（第二輪審查 A）。** 浮點累加會錯判：各 100 筆 +9999999999999.98 與 −9999999999999.99，再加 +0.99，真值是 −0.01，SQLite 實測 `SUM(NumberValue)` 得到 +0.0134…（符號都錯了）。上一輪的「查詢時乘 10^Scale 再 ROUND」也不夠：`999999999999.98` 在 Scale 6 放大後約 1e18，超過 2^53，`double` 的間距已大於 1，放大這一步本身就失真。所以改成**寫索引時由 `decimal` 精確算出整數存起來**：
   - `Dynamic_RecordIndex` 新增欄位 `ScaledValue INTEGER NULL`（EF migration，§11.1）。數字型別（整數、小數、金額、百分比）的索引列寫入時，`ScaledValue` = `decimal` 值 × 10^`Scale`（`Scale` 取欄位設定，整數欄位為 0），以 `decimal` 運算，必為整數（值已經過 `Normalize` 到 `Scale` 位小數）。公式欄位同樣依其 `Scale`。
   - 檢查的加總是 `SELECT SUM(m.ScaledValue) …`，結果用 `decimal` 除回 10^`Scale` 與上限比較。`SUM` 是整數運算，精確。
   - **放大後超出 `long` 範圍的值，在被檢查引用的欄位上寫入時直接 400（fail-closed）**，訊息指出欄位與原因（「此欄位被跨記錄驗證引用，數值太大無法精確加總」）；不靠 `CAST` 飽和，也不悄悄存成 NULL 讓加總少算。沒被檢查引用的欄位遇到超出範圍的值，`ScaledValue` 存 NULL（那些欄位不參與精確加總）。檢查定義儲存時回填既有記錄（§5.3），遇到超出範圍的既有值，儲存檢查回 409 並指出是哪筆記錄。
   - **溢位 fail-closed：** SQLite 的整數 `SUM` 超過 64 位元會丟 `integer overflow` 錯誤（不會回繞也不會悄悄變浮點）。捕捉這個錯誤，轉成 409（「加總超出可計算範圍」）並整筆回滾，不當成通過。
   - `NULL` 與缺值：索引列不存在代表欄位沒有值，`SUM` 自然略過；`ScaledValue` 為 NULL 的列（在被檢查引用的欄位上不應出現）會讓求值多做一次驗證查詢 `COUNT(*) WHERE ScaledValue IS NULL`，大於 0 就當成 409（索引不完整），避免少算。
4. `via` 的上限值讀取參照記錄的 `ValuesJson`（單筆讀取）。參照為空、目標記錄不存在或上限欄位為空，**視為違規**（fail-closed），訊息「找不到上限」。
5. 不符合 `assert` 就收集錯誤；全部求值完才回（一次請求把所有違規都列出），鍵為 `_record`，內容是 `message`（解析使用者語系），多筆時以去重後的訊息列出。

一次請求內最多求值 500 組，超過回 409（避免超大匯入拖垮鎖）。

### 5.3 引用的欄位一定要有索引

`RecordIndexer.ShouldIndex` 只替「可篩選、可排序、多選、參照」的欄位建索引列（`RecordIndexer.cs:10`）。檢查若引用了不可篩選也不可排序的欄位，SQL 的 `SUM` 會是 NULL、組鍵條件永遠找不到列，檢查就悄悄失效——這是 fail-open，不能接受。所以：

1. **檢查引用的每個欄位（`groupBy`、`fieldId`、`where` 用到的欄位）都必須有索引。** 儲存檢查時，欄位若尚未可篩選（`IsFilterable`）就由系統**自動打開 `IsFilterable`**（欄位版本加一、畫面提示「已自動啟用可篩選」）。欄位型別必須支援篩選（`FieldTypeCapabilities.SupportsFilter`，長文字與附件不行，定義時拒絕）。
2. **回填既有記錄。** 打開旗標的欄位用 `RecordIndexBackfill` 為模組內既有記錄補索引列。現有的 `RebuildAsync` 一次載入整個模組的全部記錄（註解寫明 POC 量小），檢查用的版本改成**分批**，並同時寫入 `ScaledValue`：依記錄 Id 每批 1000 筆，每批讀取、投影、寫入、釋放追蹤後再下一批，記憶體固定。
3. **對鎖的影響要講清楚。** 回填與「儲存檢查」是同一個交易，持有寫入鎖直到結束，這段時間所有寫入都在 `WriteGate` 排隊（上限 30 秒，逾時回 503）。每個欄位的回填成本與記錄數成正比；以負載報告的批次寫入速度（302 萬筆含索引約 90 秒，即每秒約 3 萬筆）估計，10 萬筆約數秒。因此設上限：模組記錄數超過 **20 萬筆**時儲存檢查回 409，訊息說明要在低峰時段分次處理（這個情境離小型企業的規模很遠，是安全閥）。實際耗時列入壓測量測（§15）。
4. **被引用的欄位不能移除索引，加總欄位也不能改 `Scale`。**（第二輪審查 B：舊記錄的 `ScaledValue` 是依舊 `Scale` 算的，改 `Scale` 後新舊值放大倍率不一致，加總就錯。）`UpdateField` 若會改變被檢查當加總欄位的 `Scale`，回 409 並指出是哪個檢查；要改請先刪除檢查，改完再重建（重建會回填）。 `UpdateField` 若會讓被檢查引用的欄位變成「不可篩選、不可排序、非多選非參照」，回 409 並指出是哪個檢查；欄位停用或刪除已由 §10.5 的引用檢查擋下。
5. 刪除檢查不會把欄位的 `IsFilterable` 關回去（欄位是設計者的資產，其他地方可能也用到它）。

### 5.4 範圍與限制

- 檢查掛的模組同時是被寫入與被加總的模組。「限額被調低」（例如把假別額度改小）不在請假單寫入，所以不會觸發；列為已知限制（§16）。
- 已經違規的資料：新增檢查不會回頭掃描。之後該組的任何寫入都會被擋（因為寫完仍違規）。這比「只擋變糟的寫入」嚴格，但規則簡單、可預測。設計器儲存檢查時提供「試跑」端點 `POST /checks/{key}/scan`，回報目前違規的組（至多 50 組），只回報不阻擋（§13.1）。
- 明細模組也可以掛檢查（例如單據內的合計限制），組鍵用明細的表頭參照欄位。

### 5.5 效能

每組一次索引聚合。最壞情境是熱門品項：負載報告 §4.1 在 302 萬筆下「科目＋日期」的 p95 為 627 ms（熱門科目約 45 萬筆）。小型企業的庫存異動遠低於此，但這是壓測要量的項目之一（§15）；若量測不達標，後續的做法是「結轉」——定期寫一筆期初餘額分錄，檢查改成只加總期初之後的記錄（`where` 可以表達），不需要改引擎。

## 6. 不可修改分錄

### 6.1 宣告

資料表 `Dynamic_Ledger`（一模組一列，`ModuleId` 唯一）：

```json
{ "reversalFieldId": 12, "negate": [55], "swap": [[61, 62]] }
```

| 屬性 | 說明 |
|---|---|
| `reversalFieldId` | 本模組的參照欄位，指向**本模組自己**（`lookup`、`onDelete` 為 `restrict` 或未設、`Config.ReadOnly`、非必填）。沖銷分錄在這個欄位記錄「沖銷的是哪一筆」 |
| `negate` | 沖銷時取負號的欄位：本模組或其明細模組的整數、小數、金額欄位 |
| `swap` | 沖銷時互換值的欄位對：同一模組、同型別的兩個數字欄位（例如借方與貸方） |

模組必須是啟用中的獨立模組，**不能有狀態機**（記錄建立後不能改，狀態轉移沒有意義），不能是擴充模組或明細。分錄模組的明細模組（傳票的借貸明細）自動視為分錄：隨表頭一次寫入，之後同樣不可改、不可刪。

### 6.2 語意

- **建立：** 與一般模組相同的新增流程（驗證、規則、自動編號、事件、跨記錄驗證都照走）。
- **修改、刪除：** 不允許。API 在 §2 步驟 2 就回 409（「分錄不可修改，請新增沖銷分錄」）；schema 給 `permissions.edit／delete = false`，前端不顯示按鈕；§6.4 另有後盾。明細列走表頭請求，所以同樣被擋。
- **沖銷：** 新增一筆分錄，`reversalFieldId` 指向原分錄，值由原分錄複製，`negate` 欄位取負、`swap` 欄位互換，明細列同樣複製與轉換。原分錄**不動**（不加「已沖銷」旗標，避免修改原記錄）。
- **不能重複沖銷：** 資料表 `Dynamic_LedgerReversal`，主鍵 `OriginalRecordId`（另對 `ReversalRecordId` 唯一）。沖銷新增與這列的寫入在同一個交易，主鍵衝突即回 409（「這筆分錄已經沖銷過了」）。寫入鎖已把同時的兩個沖銷請求序列化，主鍵是換資料庫之後仍成立的最後防線。
- **沖銷分錄本身不能再被沖銷**（回 409）；要重新入帳請新增一筆。
- **沖銷欄位不能直接寫**：它是 `Config.ReadOnly`，一般新增改不動；只有沖銷流程以系統填入的方式寫（同轉換的追溯欄位）。

### 6.3 沖銷的端點與權限

`POST /records/{id}/reverse`，本文可選 `values`（表頭欄位覆寫，照使用者自己的寫入權限處理，不是系統填入）。**沖銷必須精確抵銷原分錄，所以覆寫有嚴格限制，違反回 400（`values.<欄位>`）：**

1. 覆寫的欄位只能是**純說明性**型別：`text`、`textarea`、`date`、`datetime`、`time`、`boolean`、`email`、`phone`、`url`、`attachment`。數字型別（整數、小數、金額、百分比）、下拉、多選、使用者、參照、公式、彙總、自動編號一律不能覆寫：它們可能是金額、分類或歸屬，改了就不再是原分錄的鏡像。
2. 不論型別，下列欄位不能覆寫：`reversalFieldId`、`negate` 與 `swap` 的所有欄位、任何**被這個模組的檢查引用**（`groupBy`、加總欄位、`where`）或被事件的 `set`／`when` 引用的欄位。這些欄位決定「抵銷哪個組、抵銷多少」。
3. 明細列不能覆寫（請求只有表頭的 `values`），明細完全由原分錄複製再套 `negate`、`swap`。
4. 帶了 `values.qty = 0` 之類的數字欄位，因為規則 1 就是 400，不會建立沒有抵銷效果的沖銷，也不會用掉沖銷資格（失敗的請求整筆回滾，`Dynamic_LedgerReversal` 不會有列）。
5. **伺服器自我驗證：** 建好沖銷值之後、寫入之前，逐一檢查 `negate` 欄位新值 = −原值、`swap` 欄位對已互換、其餘**輸入型**數字欄位與原值相同；任何一項不符回 409（內部不一致，不應發生，當成防呆）。**公式欄位排除在相等檢查之外**（第二輪審查 F）：例如 `amount = qty × price`，`qty` 取負後 `amount` 正確地變成 −20，並不等於原值；公式欄位照公式重算，不複製也不比較。彙總、自動編號同樣不複製、不比較。

另外，複製原分錄時若使用者**看不到** `negate`、`swap`、被檢查或事件引用的欄位（欄位隱藏權限），沖銷無法精確抵銷，整個請求回 400（「你沒有權限看到沖銷所需的欄位」），而不是略過這些欄位。其他使用者看不到的欄位照原規則不複製（若因此缺必填欄位，回 400）。權限：使用者要有該模組的 **Add**（沖銷是新增）與該筆記錄的 **Read**（含資料範圍）。複製值時看不到的欄位（隱藏權限）不複製，同單據轉換——使用者拿不到的值不能透過沖銷流出，也不能被默默補成空值之後通過驗證；若因此缺必填欄位，回 400。

`GET /records/{id}/ledger` 回傳 `{ reversible, reversedBy, reverses }`，供畫面決定要不要顯示「沖銷」鈕與關聯。

### 6.4 後盾：不依賴每個 handler 都記得擋

§2 步驟 9：請求結束時看寫入日誌（整次請求的合併結果），下列兩類記錄若被改動，整筆回滾、回 409：

1. 「不是這次請求新增的」記錄屬於分錄模組（或分錄的明細模組），且被修改或軟刪除；
2. **（第二輪審查 C2）「請求開始前就有事件事實的」來源記錄**，除狀態欄位以外的值被改（包括公式欄位被重算、被連帶 `SetNull` 清空），或被軟刪除。請求開始前的判斷方式：對日誌裡出現的每筆「非本次新增」的記錄，一次查 `Dynamic_EventFact(SourceRecordId)`（索引點查），結果在步驟 8 之前快取，所以本次請求自己產生的事實不算（來源記錄在這次請求才剛記帳，這次的寫入本來就合法）。訊息說明是哪一筆已記帳的記錄擋住（記錄標題與模組名）。

涵蓋範圍：彙總重算、連帶刪除的清空與刪除（`ReferenceDeletePlanner` 的 SetNull／Cascade）、事件 `update` 效果、未來新增的任何寫入路徑。再加兩條定義時限制，讓正常流程不會撞牆：

- 分錄模組與其明細模組的**一般參照欄位**（`lookup`），`onDelete` 只能是 `restrict`（或未設）；已有其他設定時，設為分錄模組的請求被拒。**明細到表頭的參照（`relation = detail`）是例外**：`AddFieldHandler` 強制它為 `Cascade`（`AddFieldHandler.cs:51`），若一併要求 `restrict`，含明細的分錄（傳票）就永遠設不成。這個例外是安全的：連帶刪除只會在「表頭被刪除」時才規劃到明細列，而分錄表頭本身不可刪除（步驟 2 的分錄閘在刪除規劃之前就擋下），所以 Cascade 沒有機會執行；若有任何路徑繞過了閘，步驟 9 的後盾仍會把被刪除的分錄記錄擋下。測試涵蓋這兩點。
- 分錄模組不能有彙總欄位作為父記錄（彙總重算會改寫它）；分錄明細的彙總到表頭是允許的，因為同一請求內表頭與明細一起新增，表頭值在新增時已算好。公式欄位允許（只在寫入時算一次）。

### 6.5 事件的 `reverse` 效果

「出貨取消 → 庫存回補」靠它：事件在觸發時，查 `Dynamic_EventFact` 找出 `(ofEvent, ofEffect, 此來源記錄)` 新增過的所有分錄，逐一走與 `POST …/reverse` 相同的程式（系統身分、略過使用者的 Add 權限，因為是事件）；已沖銷的略過，並寫一列 `reverse` 事實（`ItemKey` = 被沖銷的分錄 Id）。重複觸發同一個取消轉移不會重複沖銷（事實唯一約束加沖銷主鍵雙重保護）。

### 6.6 已存在的定義改成分錄型

見 §10.1。

## 7. 與 `WriteGate` 的關係：夠不夠、要不要在交易內重新查詢

**結論：正確性來自「交易開始就持有 SQLite 寫入鎖」，不是來自 `WriteGate`；`WriteGate` 管的是公平與逾時。檢查必須在寫入交易內查詢，而這件事由第 2 節的管線自動滿足，不需要額外的重新查詢步驟。**

推理：

1. `EfTransactionManager` 先在 `WriteGate` 排隊，再開 EF 交易；EF 對 SQLite 開的是 `BEGIN IMMEDIATE`，**交易一開始就持有資料庫的寫入鎖**（負載報告 §4.3.1，`EfTransactionManagerTests.Begin_TakesTheWriteLockImmediately` 已驗證：EF 開出交易後，另一條連線要寫入鎖立刻失敗）。
2. handler 的所有讀取與寫入都在這個交易內。別的寫入者要等到我們提交或回滾才拿得到鎖；WAL 模式下別人的讀取看到的是我們提交前的快照，不影響我們。所以「讀餘額 → 寫入 → 再驗餘額 → 提交」之間，**沒有別的寫入者能提交**。檢查看到的就是提交時的真相，不可能兩個交易各自看到餘額 10 然後各扣 8。
3. 只靠 `WriteGate`（行程內佇列）**不夠**：它對檔案型資料庫每個檔案一個閘，但（a）多行程共用同一個檔案時閘不互通（負載報告 §4.3.1 明說「寫入鎖本身仍由 SQLite 保證，所以多行程仍然正確，只是不保證公平」），（b）記憶體資料庫沒有閘（`WriteGate.For` 回 null）。若把正確性押在 `WriteGate` 上，這兩種情況會靜默失效。這份設計**不依賴** `WriteGate` 做互斥，也**不修改**它。
4. 「寫入交易內重新查詢是否必要」：必要，但已經是現狀。檢查在交易內、寫入之後求值，查詢與寫入同連線同交易（`RecordRepository` 已用 `db.Database.CurrentTransaction`）。**不可以**把檢查搬到交易之外或用交易開始前載入的快取值。測試：直接以 `Task.WhenAll` 對同一本帳併發寫入（§14.3）。
5. 事件與串聯寫入都在同一個交易內，所以鎖持有時間變長：持鎖時間約等於一次使用者寫入加上每個效果寫入加上每組檢查的聚合查詢。吞吐上限仍是 1 除以持鎖時間；§15 的壓測要量這個數字。`WriteGate` 的排隊上限（連線字串的 `Default Timeout`，預設 30 秒）夠用的條件是：排隊人數乘以持鎖時間小於 30 秒；20 人同時、每筆 10 ms 的量級是 200 ms，餘裕很大。
6. **換資料庫時的可攜性。** 在 SQL Server 或 PostgreSQL 的讀已提交隔離下沒有「開始就持有全庫寫入鎖」，兩個交易會各自通過檢查（寫入偏斜）。屆時的做法：求值前對該組取一個鎖列——`Dynamic_CheckLock(CheckKey, GroupHash)`，以 `UPDATE … SET Counter = Counter + 1` 或 `SELECT … FOR UPDATE` 把同一組的檢查序列化。這份設計把求值前的動作抽成 `ICheckSerializer`，SQLite 的實作是不做事（已被寫入鎖序列化）；其他資料庫的實作**這次不做**，因為路線文件已決定先留 SQLite。

## 9. 失敗語意

任何一步失敗，**整個請求回滾**：來源記錄、明細、彙總、事件效果的所有記錄、事件事實、沖銷列、操作紀錄一律不留。

| 失敗 | 狀態碼 | 訊息鍵 |
|---|---|---|
| 來源自己的驗證 | 400 | 欄位鍵（既有） |
| 事件效果的目標驗證失敗（必填、型別、規則） | 400 | `_record`：「連動事件「{名稱}」失敗：{第一個錯誤}」，另附 `errors` 的完整清單 |
| 目標模組 Closed／未啟用 | 409 | 「連動事件「{名稱}」的目標模組已關閉」 |
| 事件循環、深度或總量超過 | 409 | 說明哪個上限 |
| 跨記錄驗證違規 | 400 | `_record`：檢查的 `message` |
| 分錄修改刪除 | 409 | 「分錄不可修改，請新增沖銷分錄」 |
| 重複沖銷、沖銷分錄再沖銷 | 409 | 各自的訊息 |
| 同一把 key 不同內容 | 422 | |
| 資料庫忙碌 | 503＋`Retry-After` | 既有 |

回放（`Idempotent-Replay`）永遠是原本成功的結果。

## 10. 改定義時的行為（路線風險 4）

### 10.1 把已有記錄的模組改成分錄型

`PUT /modules/{key}/ledger`：模組已有記錄時，必須在請求帶 `confirmFreeze: true`，否則回 409 並說明「這個模組已有 N 筆記錄，設為分錄後它們會立刻變成不可修改、不可刪除」。確認後既有記錄**原封不動**（不重算、不改歷程、不補沖銷欄位），只是之後不能改。UI 用確認對話框顯示筆數。

### 10.2 取消分錄型

模組**已有記錄時不允許**取消（409）；沒有記錄才能刪除分錄設定。理由：能隨時取消再重設，不可修改就沒有意義。後果：設錯就得把資料留著、或建新模組；寫在確認對話框裡。

### 10.3 分錄模組的後續設計器變更

沿用 `ClosedDataGuard` 的做法，新增 `ImmutableDataGuard`（共用同一組檢查點）：分錄模組（及其明細）已有記錄時，會**改寫既有記錄值**的設計器操作回 409：換標題欄位（重寫全部 `Title`）、新增或變更公式與彙總（重算寫回）、刪除仍有值的欄位或區塊。不改寫記錄值的操作照常放行：新增欄位（舊記錄沒有值）、改標籤、改選項、停用欄位、權限、規則、檢視。這保證「已過帳的資料不隨定義改變」。

### 10.4 已固定的記錄不隨定義變更重算

路線風險 4 的另一半不是分錄而是單據：單據過帳後，值要固定。**由定義變更觸發的整批重算**——`FormulaRecalc`（`FormulaRecalc.cs:16` 對模組內每筆未刪除記錄重算公式）、`RollupRecalc.RecalculateModuleAsync`、`RollupRecalc.RecalculateForSourceModuleAsync`——一律跳過下列「已固定」的記錄，它們保留原值、不換 `RowVersion`、不重建索引：

1. 處於狀態機唯讀狀態的記錄；
2. **有事件事實的來源記錄**（`Dynamic_EventFact` 有它的 `create` 或 `reverse` 事實），不論模組有沒有狀態機。沒有狀態機的已記帳來源若被重算，來源與已寫入的帳務會失配，這正是事實鎖（§4.7）要防的；
3. 已有事實的記錄，**公式欄位也不再重算**（單筆寫入與狀態轉移同理，§4.7），保留記帳當時的值；
4. 分錄模組的記錄不會走到這裡（§10.3 在入口就擋掉會重寫的設計器操作）。

做法：重算前一次查詢「這個模組裡有事實的來源記錄 Id 集合」（`Dynamic_EventFact.SourceRecordId` 配 `Dynamic_Record.ModuleId`），與狀態機唯讀判斷一起過濾。子記錄寫入觸發的單筆彙總重算不受影響，那是資料變動而不是定義變動。測試：改公式後，唯讀狀態的單據與沒有狀態機但有事實的來源值不變，草稿單據值更新。

### 10.5 事件與檢查本身的變更

- **只影響之後的寫入**，不回頭補做：新增事件不會對既有單據補記帳；改效果的 `code` 等於新效果，對已經觸發過的來源會再觸發一次（因為唯一鍵不同）——UI 在修改既有效果的 `code` 時禁用輸入框，只能新增或刪除效果。
- 刪除事件不刪事實（事實用鍵字串，沒有外鍵）；刪除後用同一個 `Key` 重建，會繼承舊事實的冪等紀錄：舊來源不會重新記帳，這是預期的。
- 新增檢查不回頭掃描（§5.4）。
- 被事件、檢查、分錄設定引用的欄位，**不能刪除或停用**（409，訊息指出被哪個定義使用），與狀態機的狀態欄位、轉換的追溯欄位同一套檢查點。被引用的模組不能停用。刪除事件或檢查後才能刪欄位。
- 應用程式關閉（Closed）後：事件與檢查不執行（資料唯讀，沒有寫入）；若開著的來源模組的效果指向 Closed 的目標，來源寫入整個失敗（§9），訊息明確。

## 12. 序列化進應用程式套件

套件格式 **3 提高到 4**（`CurrentFormatVersion = 4`，`MinFormatVersion` 仍為 2）。理由遵循套件規格 §4.9：舊讀取器讀到新檔案可能漏掉控管，必須提高版本；格式 3 的檔案 `events` 非空仍整份拒絕（現況不變），新增的頂層 `checks`、`ledgers` 在 3 以下是未知屬性，同樣拒絕。格式 4 才收這三個 section，且**不再保留 `events` 為空陣列限制**。

```json
{
  "events": [ {
    "code": "shipPost", "name": { "zh-TW": "出貨過帳" }, "active": true, "source": "ship",
    "trigger": { "on": "transition", "from": ["draft"], "to": "shipped" },
    "when": null,
    "effects": [
      { "code": "post", "kind": "create", "target": "stockMove", "each": "shipLine",
        "set": [
          { "to": "stockMove.item", "from": { "side": "line", "field": "shipLine.item" } },
          { "to": "stockMove.qty",  "formula": { "side": "line", "expr": "-{qty}" } },
          { "to": "stockMove.kind", "const": "opt_out" } ] } ] } ],
  "checks": [ {
    "code": "noNegativeStock", "name": { "zh-TW": "庫存不可為負" }, "active": true, "module": "stockMove",
    "groupBy": ["stockMove.item", "stockMove.warehouse"], "function": "sum", "field": "stockMove.qty",
    "where": null, "assert": { "op": "gte", "limit": { "const": 0 } },
    "message": { "zh-TW": "庫存不足，不能出貨" } } ],
  "ledgers": [ {
    "module": "stockMove", "reversalField": "stockMove.reverses",
    "negate": ["stockMove.qty"], "swap": [] } ]
}
```

引用規則沿用套件規格 §4.7：欄位用限定欄位名、選項值用 `opt_<選項代號>`、狀態用選項代號、模組用模組代號；`when`、`where` 內條件的欄位引用同規則條件的代號寫法。`event.code`／`check.code` 就是資料庫的 `Key`（全站唯一，慣例以應用程式 id 當前綴）。

要改的程式：

- `AppPackageData` 加 `Events`、`Checks`、`Ledgers` 的 record；`UnsupportedSections()` 對格式 4 不再把 `events` 列為不支援；格式小於 4 且這三者非空整份拒絕。
- `AppPackageValidator` 加 V4 引用層：模組與欄位在套件內、選項代號存在、狀態機存在、群組不涉及；定義內的循環檢查在純函式層就做（套件內事件圖），資料庫已有事件的合併檢查在開啟時由 `SaveEventRequest` 負責。
- `AppFlowInstaller` 安裝順序：狀態機 → 分錄 → 事件 → 檢查（事件的 `reverse` 需要分錄，狀態轉移需要狀態機）。欄位被使用者取消勾選時，引用到它的事件、檢查、分錄**整個略過並警告**（同轉換）。
- `AppExporter` 匯出三者；`AppPackageUpgrader.FromTemplate` 用 `CurrentFormatVersion`，不需其他改動。
- `apps/app.schema.json` 加頂層三個陣列。
- 空系統：不開任何應用程式時，三張定義表為空、三個管線行為每次寫入各做一次對空表的查詢（合併為一次 `DefinitionLookup`），平台任何功能不依賴它們存在。

## 14. 測試清單

原則：每項先寫失敗測試再實作；每個能力兩個不相干情境（進銷存味／人事味），模組與欄位都在測試內自己定義；被測程式沒有業務名詞。

### 14.1 單元（Domain、Application）

- 事件循環圖：無環放行；A→B→A、自我指向、經 `transition` 的間接環都拒絕並列出路徑；`custom` 效果依宣告建邊（宣告空清單的 handler 不被拒、宣告的環被拒、宣告以外的寫入在執行時失敗）。
- 事件定義驗證：每條 §4.3 規則一個案例。
- 觸發判定：`create`／`update`（`watch`）／`transition`（`fromStates`）／`when`；新增時的起始狀態不算轉移；值沒有實際變動的修改不觸發。
- 寫入日誌合併：新增後修改、多次修改、彙總靜默。
- 檢查：`where` 前後任一邊符合就求值（+10、−8 同組，把 +10 改成不符合 `where`，違規被擋；兩邊都不符合才略過）；索引時精確整數加總（各 100 筆 +9999999999999.98 與 −9999999999999.99 直接灌入資料庫，再以 API 寫入 +0.99，真值 −0.01，被擋；`double` 累加會算成 +0.01）；**高小數位大數**（Scale 6 的 `999999999999.98` 放大後超過 2^53：加總精確、不被 `double` 失真）；被檢查引用的欄位寫入時放大後超出 `long` 的值回 400（`ScaledValue` 不飽和、不存 NULL）；回填遇到超範圍既有值時儲存檢查回 409；整數 `SUM` 溢位（灌入超過 9.2e18 的整數加總）轉成 409 並回滾；被檢查引用的加總欄位改 `Scale` 回 409；檢查的 `where` 含 `fieldRef` 於定義時 400；組鍵取前後兩個、去重；空值組；`sum`／`count`；`gte`／`gt`／`lte`／`lt`／`eq`；`const`／`field`／`via`；`via` 缺值 fail-closed；四捨五入到 Scale；訊息預設不含數字。
- 分錄定義驗證（含明細到表頭的 Cascade 參照例外、一般參照必須 restrict）；沖銷計算（`negate`、`swap`、明細列；**公式欄位**如 `amount = qty × price` 在 `qty` 取負後 `amount` 為 −20，自我驗證不誤判、不複製）；沖銷覆寫規則的每一條（數字欄位、下拉、`negate`／`swap`／沖銷欄位、被檢查引用的欄位、明細都被拒；說明性欄位放行；隱藏了必要欄位時 400）。
- 引用欄位索引：儲存檢查自動打開 `IsFilterable` 並分批回填（回填後 `SUM` 與手算一致、既有記錄的組鍵可查到）；不支援篩選的型別被拒；移除被引用欄位的索引被拒；超過記錄數上限回 409。
- 寫入日誌：跨輪不合併（A 新增後被另一事件改狀態，`transition` 事件會觸發）；一輪內合併；整次請求的合併結果供驗證與後盾使用。
- 已記帳來源的後門：有事實的記錄，單筆寫入、狀態轉移、定義變更都不重算公式（值保留）；寫入後盾——請求開始前就有事實的來源記錄，除狀態欄位外的值被連帶 `SetNull` 清空、被連帶刪除、被公式重算，都整筆回滾 409 並指出是哪筆；本次請求才剛記帳的來源不誤擋；彙總欄位仍隨子記錄更新；事件 `from`／`formula` 引用彙總欄位或依賴彙總的公式欄位於定義時 400。
- `DynamicQueryBuilder` 對數值公式欄位的比較（見 §16.1 第 18 條）：清單篩選與檢查一起受惠。
- 冪等：雜湊相同回放、不同 422、失敗不留紀錄、7 天清除。

### 14.2 整合（WebAPI，檔案型 SQLite 的 `TestApp`）

**事件**
- 情境 A：出貨單轉「已出貨」，每列明細產生一筆庫存異動，擁有者是來源擁有者；轉「已取消」時 `reverse` 效果沖銷；重複轉移不重複記帳（事實唯一）；記帳後來源除狀態外不能改、不能刪。
- 情境 B：請假核准時假別餘額記錄的日期被設為今天；沒有目標權限的使用者也能觸發；`via` 為空略過。
- 權限：欄位唯讀與隱藏不擋效果寫入；沒列在 `set` 的欄位使用者輸入進不來；不允許的狀態轉移使整筆失敗；目標 Closed 使整筆失敗且來源不留痕。
- 失敗回滾：目標驗證失敗時，來源記錄、事實、操作紀錄都不存在。
- 循環：定義時擋；繞過定義檢查直接寫資料庫的環在執行時被深度或造訪集合擋下。
- 匯入到事件來源模組被拒。
- 擴充點：註冊假的 `IEffectHandler`，`custom` 效果執行；未註冊的 handler 儲存被拒。

**冪等**
- 同一把 key 重送新增：一筆記錄、一組異動、第二次回放且標頭正確。
- 匯入：同一把 key 重送同一份檔案只生效一次；同 key 換檔案 422。
- 同一把 key 同時送兩次（`Task.WhenAll`）：一筆記錄。
- 同 key 不同內容 422；不同使用者同 key 互不影響。

**跨記錄驗證**
- 情境 A：出貨使餘額為負被拒（400，`_record` 為檢查訊息），整筆回滾，包含事件新增的異動。
- 情境 B：已核准天數超過額度被拒；改狀態離開「已核准」可釋放；刪除請假單後餘額回復。
- 修改把記錄從 A 組移到 B 組，兩組都被檢查。
- 匯入期初餘額後仍會跑檢查。

**分錄**
- 情境 A：庫存異動不能 `PUT`、`DELETE`（409）；沖銷產生負號分錄、連回原分錄；重複沖銷 409；沖銷分錄不能再沖銷。
- 情境 B：傳票含借貸明細，沖銷借貸互換、明細列一併複製；表頭或明細都不能改。
- 後盾：以事件 `update` 效果、連帶刪除、彙總重算想改分錄，整筆回滾（用繞過 handler 閘的測試設定觸發）。
- 設定：已有記錄時啟用需要 `confirmFreeze`；已有記錄不能取消；已有記錄時改公式、換標題欄位被擋，新增欄位放行。

**定義變更**
- 改公式後，唯讀狀態的單據值不變（§10.4）；沒有狀態機、有事件事實的來源值也不變。
- 事實鎖不依賴定義：刪掉模組最後一個事件（或停用）後，已記帳的來源仍不能改、不能刪。
- 含明細的分錄（傳票）可設定；表頭刪除被分錄閘擋下，Cascade 不會執行。
- `GET /records/{id}/effects`：標題欄位對使用者隱藏時目標標題為空；沒有目標模組 Read 的不回傳。
- 被事件、檢查、分錄引用的欄位不能刪或停用。

### 14.3 併發（`Task.WhenAll`、檔案型 SQLite）

- **同一本帳：** 初始餘額 100，50 個請求同時寫入 −3（一半經事件、一半直接寫異動）：恰好 33 筆成功、17 筆 400、無 500、最終餘額 1、沒有任何時間點為負。
- **重送：** 20 個帶同一把 key 的出貨請求同時送出：一張出貨單、一組異動。
- **同時沖銷：** 10 個請求同時沖銷同一筆分錄：一個成功、其餘 409。
- 兩個互相獨立的組同時寫入不互相阻擋結果的正確性。

### 14.4 套件

- 引用被隱藏來源欄位且無 `allowHiddenSource` 的事件：儲存、套件匯入、開啟應用程式皆 400；有旗標則通過；事後把被引用欄位設為隱藏的欄位權限儲存被拒（400，列出事件與效果）。
- 格式 4 往返（匯出再匯入逐項相同）；格式 3 含 `checks`／`ledgers` 被拒；格式 3 含非空 `events` 仍被拒；事件引用被取消勾選的欄位時略過並警告；與資料庫既有事件合併後成環時開啟失敗並整批回滾。
- 套件範例檔放進測試資料（情境 A 與 B 各一份）。

### 14.5 鐵則與空系統

- **無業務名詞掃描：** 測試掃描 `Application/Dynamic/{EventService,CheckService,LedgerService}` 與新增的 Domain 檔案，不得出現詞表中的字串（庫存、工令、傳票、出貨、報工、stock、inventory、voucher、shipment 等；詞表放在測試內）。
- **空系統：** 全新資料庫、沒開任何應用程式，建立一個臨時模組並新增、修改、刪除記錄、匯入，三個管線行為不影響結果；三組端點回空清單。

### 14.6 前端

- 單元：三個分頁元件、事件對應表、冪等 key 產生與重送沿用、`frozenByEffects`／分錄權限旗標隱藏按鈕、沖銷確認對話框。
- 型別檢查、建置、既有的顏色掃描測試。
- 實機（§15）。

## 16. 我代為決定的事、未解與風險

### 16.1 我代為決定的事（可推翻）

1. **事件只做 `create`、`update`（設值）、`reverse`、`custom`，不做累加。** 理由 §1；錯了的代價：想要「已完工量 += 報工量」的人要改用彙總欄位（本來就比較對）。
2. **事件效果用系統身分寫入，複製來源值不看使用者欄位可見性。** 這是事件的存在理由。**使用者已裁決（2026-11-08）：引用被隱藏的來源欄位時，定義時預設擋下，需在該對應項加 `allowHiddenSource` 明確允許**；欄位事後才被隱藏時，儲存權限被拒絕（§4.2）；套件匯入同樣檢查。
3. **來源記錄一旦產生 `create`／`reverse` 事實就鎖住（只能動狀態）。** 錯了的代價：用 `create` 觸發的設計無法事後編輯來源，需要改用 `transition` 觸發。
4. **同一事件對同一來源的 `create` 效果最多一次（唯一約束）。**
5. **循環判定是模組層級、保守的；`custom` 效果依 handler 的宣告建邊，宣告以外的寫入在執行時失敗。**
6. **彙總重算不觸發事件；刪除不觸發事件；來源不能是明細；匯入到事件來源模組被拒。**
7. **驗證在事件與彙總之後、提交之前，用寫入後的狀態求值，並且對已違規的資料採嚴格語意（寫完仍違規就擋）。**
8. **檢查的加總是放大成整數的精確 SQL 加總（`SUM(CAST(ROUND(值 × 10^Scale) AS INTEGER))`），整數溢位當成失敗回滾；組鍵限整數、日期、文字、下拉、參照。**
9. **分錄的沖銷由專用端點產生，沖銷欄位唯讀；沖銷需要 Add 而不是新權限軸；原分錄不加已沖銷旗標，重複沖銷的防線是主鍵。**
10. **已有記錄的模組能設為分錄（需確認）。** 取消設定：**使用者已裁決（2026-11-08）有記錄後不允許取消**（沒有任何記錄時可以取消，因為沒有東西需要保護）。
11. **冪等紀錄保留 7 天；匯入的確認請求也支援。`Idempotency-Key` 維持選填，伺服器不強制——使用者已裁決（2026-11-08）**；自家前端一律帶，效果層唯一約束是最後防線。
12. **檢查引用的欄位由系統自動打開「可篩選」並分批回填索引，模組記錄數超過 20 萬筆時拒絕儲存。** 錯了的代價：設計者的欄位多了一個旗標；超過上限的大模組要先分次處理。
13. **事件分輪處理，日誌跨輪不合併；驗證與分錄後盾看整次請求的合併結果。**
14. **沖銷的 `values` 只能覆寫說明性欄位，看不到必要欄位就整個拒絕。**
15. **套件格式提高到 4，事件、檢查、分錄只能指向同一份套件的模組。**
16. **（第二輪審查 A）檢查的加總欄位在 `Dynamic_RecordIndex` 新增 `ScaledValue`，寫索引時由 `decimal` 精確算出；超出 `long` 的值在被引用欄位上直接 400。** 錯了的代價：多一個索引欄位與一次回填；被檢查引用的欄位數值上限變成約 9.2e18 除以 10^Scale。
17. **（第二輪審查 B、C）被檢查引用的加總欄位不能改 `Scale`；已記帳的來源不重算公式、寫入後盾擴大到已記帳的來源；事件不得引用彙總（或依賴彙總的公式）。** 錯了的代價：改 Scale 要先刪檢查；已記帳單據上的公式值不隨輸入或參照改變（本來也不該變）。
18. **（第二輪審查 D）`DynamicQueryBuilder` 的 `Column()` 對數值公式欄位的處理，若確認是既有 bug，在 builder 修，獨立 commit。**

### 16.2 使用者裁決與待決

使用者已於 2026-11-08 裁決三項：

1. **來源欄位可見性：預設擋下，需明確允許**（§4.2、§16.1 第 2 條）。
2. **`Idempotency-Key` 不強制，維持選填**（§16.1 第 11 條）。
3. **分錄型有記錄後不允許取消**（§16.1 第 10 條）。

仍待使用者決定：是否需要一個「作廢整個分錄模組資料」的管理員流程（目前沒有，分錄只能沖銷）。

### 16.3 未解與已知限制

1. **限額被調低不觸發檢查**（§5.4）：需要「監看另一個模組」的宣告，列後續。
2. **新增檢查不回頭掃描**，只有試跑端點報告。
3. **其他資料庫的寫入偏斜**（§7 第 6 點）：`ICheckSerializer` 的非 SQLite 實作沒做。
4. **熱門組的聚合耗時**（§5.5）：壓測量測；備案是結轉。
5. **事件事實不含 `update` 效果**，因此 `update` 效果沒有「這筆來源改過哪裡」的追溯，只有歷程表。
6. **匯入到事件來源模組被拒**，批次匯入單據要走多筆新增。
7. **事件回應不含事件效果對來源本身的改動**：效果若修改了來源記錄自己（目標模組與來源相同，且不構成環），回應內容是效果之前的值，畫面需要重新讀取。
8. **操作紀錄回放只保證結果相同，不重新檢查使用者權限**；權限在這七天內被收回，仍會回放當初的成功結果。
