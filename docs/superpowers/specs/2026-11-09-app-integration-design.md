# 階段 2 後續（s2c）設計：應用程式整合層（可選相依）與 s2b 留下的通用能力缺口

> 2026-11-09｜路線階段 2 的收尾，排在階段 3（會計）之前｜前置：[路線](2026-11-06-erp-roadmap-design.md)、[進銷存與 MES](2026-11-08-inventory-mes-design.md)（§2、§9、§15）、[應用程式套件](2026-11-06-app-package-design.md)、[事件、檢查、分錄](2026-11-08-events-ledger-design.md)、[單據能力](2026-11-06-document-flow-design.md)
> 標「（我的判斷）」的是我代為決定、可以改的，彙整在 §13。使用者裁決的事在 §14。**第一輪審查（9 必修、1 建議）的處置在 §16，第二輪（5 必修、2 建議）在 §17，正文已依它們修訂。**這份文件寫決定與理由，細節以程式與測試為準。

## 1. 問題與情境

s2b 做完後，CRM、MES 模具廠、進銷存三個內建套件彼此完全獨立。這是刻意的：鐵則要求每個應用程式能單獨開關，套件格式也從頭到尾保證這一點（跨應用程式只能在模組層級引用，事件與檢查只能指向同一份套件的模組）。

但階段 3 到 5 已經排定的流程都跨應用程式：發票過帳產生傳票（進銷存或 CRM → 會計）、費用報支核准進傳票（HRM → 會計）、全部開啟時貫穿流程跑通。這些都是同一個需求：**兩個應用程式都開著的時候，其中一邊的動作要連動另一邊；只開一邊的時候，這邊照常用，不報錯、不留殘缺。**

現在做不到的原因有三個，這份設計逐一補上：

1. 套件沒有地方宣告「若另一個應用程式存在則啟用這些連動」。`requires.apps` 是硬相依，缺了就開不起來。
2. 開啟後，欄位與選項的**套件代號沒有存進資料庫**（`TemplateIdMap` 只活在那次開啟的記憶體，套件規格 §7.4）。後開的那一邊無法把代號翻成對方的 Id，連動就沒辦法在「對方先開、我後開」時安裝。
3. 關閉其中一個應用程式時，連動事件的目標模組變成 Closed，事件設計 §4.2 規定整個請求回 409：關掉進銷存會讓 MES 的出貨全部寫不進去。

s2b 另外留下四個待辦（§9 缺口 B、E、F，以及 §2.4、§15 的客戶主檔與兩套訂單），這份設計一起處理。四個項目各自做或不做的理由在 §11。

**不做：** MRP、排程、成本計價、多層簽核、對外 Webhook、腳本執行環境、執行期 DDL。

## 2. 選定的方案與為什麼

### 2.1 整合是套件的一個新 section，由「擁有者」宣告

套件格式 4 提高到 **5**，新增頂層 `integrations[]`。每個整合有：

- **擁有者**：宣告它的那份套件。整合只能**新增欄位到擁有者自己的模組**，以及新增事件與檢查（來源或被檢查的模組是擁有者的）。
- **夥伴**：`with[]` 列出的其他應用程式與用到的模組。夥伴的模組只能被**引用**（參照欄位的目標、事件效果的目標、事件或檢查讀取的欄位），整合**不會改夥伴的任何結構**。

理由：夥伴因此完全不需要知道有人整合它，永遠能獨立開關；擁有者要關、要刪，整合的東西都在擁有者這邊，清理範圍明確。

為什麼不另做「橋接套件」（一個只有整合、硬相依兩邊的第三個應用程式）：橋接套件靠既有的 `requires` 與連帶關閉就能做，但它要求夥伴先開才能開（不是「沒開就靜默略過」），而且關閉其中一個會連帶關掉橋接，整合的資料與欄位就跟著唯讀。使用者要的是前者的語意，所以選 section 方案。

### 2.2 補上缺的那塊：開啟時把代號對照存進資料庫

新增兩張關聯表，在開啟應用程式時把 `TemplateIdMap` 的 `FieldIds`、`OptionIds` 存下來（模組代號對照本來就在 `Dynamic_AppModule`）。後開的一邊就能用 `應用程式 id + 模組代號 + 欄位代號` 找到對方當下實際的 Id。

這是套件規格 §7.4 當時評估過的缺口。§7.4 擔心的是「在 `Dynamic_Field` 加代號欄位，並讓客戶改欄位時維持代號」；改用**旁表加外鍵**就沒有這個問題：客戶怎麼改欄位名稱、標籤都不影響（靠 Id），客戶刪掉欄位時外鍵 cascade 讓對照列消失，整合會偵測到「對照缺失」而不安裝，不會指到別的東西。核心的 `Field`、`FieldOption` 實體不動。

### 2.3 一個冪等的「調和」函式決定所有狀態

不為「A 先開、B 後開」「B 先開、A 後開」「關閉」「重開」各寫一條路徑。只有一個函式 `IntegrationReconciler.ReconcileAsync(受影響的應用程式)`：對每個整合，只看**當下**的條件（是否啟用、是否已安裝、擁有者與夥伴開或關）算出目標狀態，再把現況推到目標。開啟、關閉、重新開啟、重試、啟用開關都只是呼叫它。結果不依賴歷史（先關誰、關過幾次），測試只需要驗證「同一組條件不論怎麼走到，結果與行為相同」。

**整合是一個不可分割的單位（第一輪審查原則）：** 全部項目（欄位、事件、檢查）一起安裝、一起停用、一起恢復；任何一項缺失或失敗，整個整合 `Blocked`，全部事件與檢查都不執行。不存在「一部分連動」的狀態。

## 3. 格式

### 3.1 頂層與整合

`formatVersion` 提高到 **5**（`CurrentFormatVersion = 5`，`MinFormatVersion` 仍為 2）。格式 4 以下的檔案出現非空 `integrations`，或任何欄位設定了 `config.refGuard`（§9），整份拒絕：舊讀取器靜默略過整合或守衛，會讓客戶以為有連動、有控管卻沒有（fail-closed，同事件設計 §12 提高版本的理由）。既有三個內建套件的 `formatVersion` 不變（4），只有 MES 因為用到新功能而升到 5。

```json
"integrations": [ {
  "code": "stockOut",
  "name": { "zh-TW": "出貨扣庫存", "en-US": "Shipments deduct stock" },
  "with": [ { "id": "inventory", "modules": ["item", "warehouse", "move"] } ],
  "onPartnerClosed": "skip",
  "fields": [
    { "module": "shipment", "block": "main", "code": "stockItem", "type": "reference",
      "label": { "zh-TW": "庫存品項" },
      "config": { "refTarget": { "kind": "module", "key": "item", "app": "inventory" }, "isFilterable": true } },
    { "module": "shipment", "block": "main", "code": "stockWarehouse", "type": "reference",
      "label": { "zh-TW": "出庫倉" },
      "config": { "refTarget": { "kind": "module", "key": "warehouse", "app": "inventory" } } }
  ],
  "events": [
    { "code": "mes-stock-out", "name": { "zh-TW": "出貨過帳扣庫存" }, "active": true, "source": "shipment",
      "trigger": { "on": "transition", "from": ["draft"], "to": "shipped" },
      "when": null,
      "effects": [ { "code": "post", "kind": "create", "target": "inventory/move",
        "set": [
          { "to": "inventory/move.item", "from": { "side": "header", "field": "shipment.stockItem" } },
          { "to": "inventory/move.warehouse", "from": { "side": "header", "field": "shipment.stockWarehouse" } },
          { "to": "inventory/move.qty", "formula": { "side": "header", "expr": "-{shipment.qty}" } },
          { "to": "inventory/move.kind", "const": "opt_out" },
          { "to": "inventory/move.moveDate", "const": "today" },
          { "to": "inventory/move.docNo", "from": { "side": "header", "field": "shipment.no" } } ] } ] },
    { "code": "mes-stock-out-cancel", "name": { "zh-TW": "出貨取消沖銷庫存" }, "active": true, "source": "shipment",
      "trigger": { "on": "transition", "from": ["shipped"], "to": "cancelled" }, "when": null,
      "effects": [ { "code": "undo", "kind": "reverse", "target": "inventory/move",
        "ofEvent": "mes-stock-out", "ofEffect": "post" } ] }
  ],
  "checks": [
    { "code": "mes-stock-item-required", "name": { "zh-TW": "出貨必須指定庫存品項" }, "active": true, "module": "shipment",
      "groupBy": ["shipment.no"], "function": "count", "field": null,
      "where": { "all": [ { "field": "shipment.status", "op": "eq", "value": "opt_shipped" },
                          { "field": "shipment.stockItem", "op": "isEmpty" } ] },
      "assert": { "op": "lte", "limit": { "const": 0 } },
      "message": { "zh-TW": "整合啟用中，已出貨的出貨單必須指定庫存品項" } }
  ]
} ]
```

| 屬性 | 說明 |
|---|---|
| `code` | 整合在擁有者套件內的代號，`^[a-z][a-zA-Z0-9_]{0,39}$`。資料庫主鍵是（應用程式, 代號） |
| `with[]` | 夥伴：`id` 是應用程式 id，`modules` 是用到的夥伴模組代號（跟 `requires.apps` 同形，也是它的對帳依據）。至少 1 個、至多 5 個夥伴 |
| `onPartnerClosed` | `skip`（預設）或 `block`，見 §5.3 |
| `fields[]` | 新增到**擁有者**模組的欄位：`module`（擁有者模組代號）、`block`（該模組既有區塊代號，欄位附加在區塊尾端；區塊代號靠 `Dynamic_AppBlock` 解析，§4）、`code`、`type`、`label`、`config`（就是模組欄位的 `config`，同樣做未知鍵檢查）。欄位代號不得與該模組既有欄位重複。**不得是必填**（原因見 §5.2） |
| `events[]`、`checks[]` | 就是格式 4 的 `AppEvent`、`AppCheck`，只多了「夥伴符號」的寫法（下表） |

**夥伴符號的寫法：** 擁有者自己的模組與欄位照舊（`shipment`、`shipment.qty`）；夥伴的以 `<應用程式 id>/` 開頭：模組 `inventory/move`、欄位 `inventory/move.qty`、選項 `inventory/move.out`。選項值常數仍寫 `opt_out`，由目標欄位所在的模組解析。`/` 不在模組代號與欄位代號的合法字元裡，所以不會與既有符號混淆。

**一個整合內的限制：**

- `fields` 只能加在擁有者的模組。夥伴模組的 `fields`、`views`、`rules` 都不能動。
- 事件 `source`、檢查 `module` 必須是擁有者的模組。夥伴的模組不能被掛上別人的事件；夥伴若要連動回擁有者，由夥伴自己的套件宣告另一個整合。
- 事件與檢查只能引用：擁有者的欄位（套件原有的，加上**本整合**新增的）、`with` 列出的夥伴模組與其欄位。不能引用別的整合新增的欄位。
- 不收：工作流程、轉換、分錄、報表、列印範本、儀表板。理由見 §11 項目 3。
- `events[].code`、`checks[].code` 與一般事件、檢查共用同一個全站唯一鍵空間，慣例以擁有者的前綴開頭。

### 3.2 `config.refGuard`（缺口 F，§9）

```json
"config": { "refTarget": { "kind": "module", "key": "workorder" },
            "refGuard": { "field": "workorder.status", "in": ["done"] } }
```

### 3.3 套件驗證（新增的層）

沿用四層。新增：

- **結構層：** 格式 5 才收 `integrations` 與 `refGuard`；`onPartnerClosed` 列舉；`with` 的 id 格式、不得是自己；整合代號不重複；欄位 `config` 的未知鍵檢查照舊（`refTarget.app` 此時必須出現在 `with`）。
- **引用層：** 擁有者的符號對套件自己的模組檢查；夥伴符號檢查前綴是否在 `with`、模組是否在該項的 `modules`。**欄位層級**能否解析，取決於夥伴套件是否已知：內建套件在 `AppCatalog` 啟動時互相對帳（夥伴套件在目錄裡，欄位與選項代號存不存在都查），對不上就拒絕啟動；匯入的套件夥伴可能未知，只檢查前綴與模組，欄位層級延後到安裝時。
- **目錄層（新增）：** `AppCatalog` 載入完成後，把所有內建套件的事件加上所有整合的事件放進同一張模組層級的事件圖，找循環（§8.1）。

## 4. 資料模型（一次 migration：`AppIntegrations`）

只走 EF migration，沒有執行期 DDL。

| 異動 | 內容 |
|---|---|
| 新表 `Dynamic_AppField` | `AppId`、`Name`（`<模組代號>.<欄位代號>`）、`FieldId`；主鍵 (`AppId`, `Name`)；`FieldId` 外鍵到 `Dynamic_Field`，cascade |
| 新表 `Dynamic_AppOption` | `AppId`、`Name`（`<模組代號>.<選項代號>`）、`OptionId`；主鍵 (`AppId`, `Name`)；外鍵到選項表，cascade |
| 新表 `Dynamic_AppBlock` | `AppId`、`Name`（`<模組代號>.<區塊代號>`）、`BlockId`；主鍵 (`AppId`, `Name`)；外鍵到區塊表，cascade。擁有者先開、夥伴後開時，整合要把欄位加進擁有者既有的區塊，沒有這張表就找不到（審查必修 8） |
| 新表 `Dynamic_AppIntegration` | `AppId`（擁有者，cascade）、`Code`、`Enabled`、`Installed`、`Status`、`Reason`、`ItemsJson`；主鍵 (`AppId`, `Code`) |
| `Dynamic_App` 新欄位 | `IntegrationsJson`（可空）：開啟當時 `integrations` 的原文副本。調和靠它，不靠目錄，所以目錄換版、套件被移除，已開啟的應用程式行為不變 |

`Installed` 只有在整個整合（所有欄位、事件、檢查）都建好時才為真，是調和函式推導狀態的輸入之一。`ItemsJson`：`{ "fields": [ {module, code, fieldId} ], "events": [key], "checks": [key], "suspendedActive": { "events": [key], "checks": [key] } }`。`suspendedActive` 記停用當下哪些事件、檢查原本是啟用的，恢復時只還原這些（客戶自己停用的不被我們打開）。

開啟時（`AppOpener`）在 `Dynamic_App` 寫入的同一個交易裡寫三張對照表（來源是實例化回傳的 `TemplateIdMap` 的 `FieldIds`、`OptionIds`、`BlockIds`；模組代號對照本來就在 `Dynamic_AppModule`）。

**對照表同時決定匯出的代號：** 匯出時欄位、區塊、選項的代號改用這三張表的 `Name`（沒有對照列的，例如開啟後客戶新增的欄位，才退回 `f_<id>`／`b_<id>`／`o_<id>`，並避開撞名）。這樣匯出的套件**保留開啟時的代號**，整合宣告裡的符號和匯出的模組是同一套，匯入後直接可用（§5.6）。

**舊資料庫：** 本設計上線前開啟的應用程式沒有對照列，欄位代號當時沒存，無法回補。它們當夥伴時，整合的狀態是 `Blocked`，原因 `unbound`（「這個應用程式是在整合功能之前開啟的，缺少欄位對照，請重建」）。模組層級的引用不受影響。Demo 資料庫每次部署重建，這不影響 Demo；真實客戶上線前路線已要求重新決定升級策略（路線「套件更新入口」），到時一起處理。

## 5. 行為

### 5.1 整合的狀態

狀態**只由當下的條件推導，不依賴歷史**：先關誰、關過幾次、是不是剛重開，都不影響結果。輸入有五個：`enabled`、`installed`（整個整合是否已完整安裝）、擁有者是否 Open、夥伴是否都在（全部 Open，且用到的模組都 Active，下稱「夥伴在」）、`onPartnerClosed`。

| 狀態 | 意義 | 事件與檢查 |
|---|---|---|
| `Disabled` | `enabled = false`（匯入套件的預設） | 全部停用 |
| `Waiting` | 已啟用、尚未安裝，擁有者或夥伴還沒就緒 | 沒有 |
| `Active` | 已安裝，擁有者與夥伴都在，完整性檢查通過 | 全部啟用 |
| `Suspended` | 已安裝，擁有者關閉；或夥伴不在且 `skip` | 全部停用 |
| `Held` | 已安裝，擁有者 Open、夥伴不在且 `block` | 全部啟用；來源寫入因目標已關閉被擋（§5.3） |
| `Blocked` | 條件齊了卻裝不起來，或完整性檢查失敗；`Reason` 說明 | 全部停用 |

| enabled | installed | 擁有者 | 夥伴 | 目標狀態 |
|---|---|---|---|---|
| 否 | 任 | 任 | 任 | `Disabled`（已安裝的項目全部停用） |
| 是 | 否 | Open | 在 | 安裝（§5.4）：成功 `Active`；失敗 `Blocked`，整個整合回滾，`installed` 仍為否 |
| 是 | 否 | 其他 | 其他 | `Waiting` |
| 是 | 是 | Open | 在 | 完整性檢查通過 `Active`；不通過 `Blocked`（全部停用） |
| 是 | 是 | Open | 不在 | `skip`：`Suspended`；`block`：`Held` |
| 是 | 是 | Closed | 任 | `Suspended` |

「其他」指擁有者或夥伴至少有一項不滿足。從任何狀態出發，只要條件相同，終點相同；`enabled` 從否變是就是重新進入這張表（進 `Waiting`，或直接安裝／恢復），從是變否就是進 `Disabled`。

**完整性檢查**（每次進到 `Active` 前都做，缺一即整個 `Blocked`）：

- 整合建立的欄位都還在，且 `Status = Active`、型別與參照目標沒被改。
- 事件、檢查都還在，且啟用旗標與宣告相符。**單獨停用整合裡的某個事件或檢查不被允許：** 只要有一項被停用，整個整合 `Blocked`，不做部分恢復（第二輪必修 4）。
- 解析用的對照（夥伴與擁有者的欄位、選項、區塊）都解析得到，且欄位為啟用狀態。選項要屬於該欄位。

**恢復是整組動作：** `Suspended`、`Blocked`、`Disabled` 回到 `Active` 時，全部事件與檢查在**同一個 savepoint**內一起重新啟用並走完整驗證（含循環判定）；任何一項失敗，整組回滾、保持原狀態並標 `Blocked`。**停用同樣整組**：停用時全部事件與檢查一起停用，不存在只停一半。

### 5.2 欄位不得必填

整合新增的欄位在夥伴關閉後仍留在擁有者的表單上，而目標在夥伴的參照欄位無法再選值（目標模組 Closed，套件規格 §6.3）。若欄位必填，夥伴一關，擁有者的表單就存不了：獨立性被破壞。所以整合欄位一律不必填；「啟用中就必須有值」靠事件本身：夥伴模組的必填欄位在事件 `create` 時缺值，事件整筆失敗並指出原因（事件啟用中才有這道檢查，停用後自然不擋）。整合 `Active` 時「已出貨就必須有品項」靠整合自己的檢查（上面範例的 `mes-stock-item-required`，用既有的跨記錄驗證，不需要新能力）；整合不是 `Active` 時檢查隨整組停用，欄位可以留空。

### 5.3 夥伴不在時：`skip` 與 `block`

事件設計 §4.2 規定目標模組 Closed 時整個請求回 409。對可選相依來說，兩種預期都合理，所以由整合宣告。**判定只看當下狀態（§5.1 的表），與誰先關、關過幾次無關。** 這次只要格式與行為兩種都支援，帳務類整合用哪一種留到階段 3 設計。

- **`skip`（預設，符合「沒開就靜默略過」）：** 已安裝的整合在夥伴不在時 `Suspended`，事件與檢查停用，擁有者的操作照常，不連動。代價：不在期間產生的來源記錄**不會**在夥伴重新開啟後補入（事件不回補，事件設計 §16.3）。**但已經連動過的記錄不能就此遺失反向效果，見 §5.8。** 調和函式在回應 `warnings` 回報「整合 X 已暫停，期間的來源記錄不會補入」。
- **`block`：** 已安裝的整合在擁有者 Open、夥伴不在時 `Held`：事件與檢查維持啟用，擁有者寫入來源模組會因目標已關閉被擋（409，訊息指出連動目標已關閉）。適合帳務類：寧可不能過帳，也不要帳少一邊。

不論哪一種，擁有者 Closed 時都是 `Suspended`：擁有者的來源模組已唯讀，事件不會觸發。擁有者重開而夥伴仍不在，`skip` 維持 `Suspended`，`block` 變 `Held`。

### 5.4 安裝與恢復（以整個整合為單位）

在調和函式內，對一個整合，**所有步驟在同一個 SQLite savepoint 內**（EF Core 的 `CreateSavepoint`／`RollbackToSavepoint`）：

1. **解析對照。** 夥伴符號用 `Dynamic_AppModule`／`Dynamic_AppField`／`Dynamic_AppOption`／`Dynamic_AppBlock` 與夥伴 Open 的模組解析成 Id，組成一份合併的 `TemplateIdMap`（夥伴的鍵加 `<id>/` 前綴，擁有者的不加）。任何一個解析不到、欄位非 Active、選項不屬於該欄位 → 不寫任何東西，直接 `Blocked`（`unbound`，列出缺的符號）。
2. **逐項建立或沿用（冪等）。** 對 `fields[]`、`events[]`、`checks[]` 的每一項，依代號判斷：
   - 不存在 → 用既有的 `AddFieldRequest`、`CreateEventRequest`、`CreateCheckRequest` 建立（驗證照跑，含循環與隱藏來源檢查）。代號翻成 Id 的邏輯重用 `AppEffectsCodec`（它收的是 lambda，不綁定資料來源）。
   - 已存在、是本整合 `ItemsJson` 登記的、且定義與這次宣告翻出來的定義**相同**（正規化後比對）→ 視為既有，沿用，不報代號衝突。
   - 已存在但定義不同（客戶改過）→ `Blocked`（`itemConflict`），不覆寫客戶的修改。
   - 已存在但不是本整合登記的（別人的事件占了這個鍵）→ `Blocked`（`codeConflict`）。
3. **記帳。** 全部成功才寫 `ItemsJson`、`Installed = 是`、狀態 `Active`。

**失敗隔離：** 任何一步失敗就回滾到 savepoint、清除 change tracker、記 `Blocked` 與原因（這一筆記帳寫在 savepoint 之外），**不讓失敗往外傳**：夥伴開啟不應該因為擁有者的整合有問題而失敗。savepoint 在外層請求交易裡，所以呼叫端（`AppOpener`）必須在自己的 `SaveChanges` 之後才調和，清 change tracker 才不會丟掉未存的東西。

**只用 savepoint，沒有備案（主控裁決）。** 若實作時發現 SQLite 上的 savepoint 做不到（交易模型不支援、回滾後 change tracker 無法恢復一致），**停下來回報主控**，不改用「每個整合各自一個交易」，因為那會留下「應用程式已開、整合只裝一半」的空窗。

**retry**（`POST .../retry`）就是用同一套邏輯重新跑一遍：缺的補建、相同的沿用、不同的 `Blocked`。可重複呼叫，結果相同。

**`itemConflict` 的恢復路徑（管理員）：** (1) 看整合的 `reason`，知道是哪個項目；(2) 在設計器把該項目**還原成宣告的定義**，不要刪除重建（欄位尤其不能刪：整合欄位上有資料，刪除會被安全刪除擋下，也會讓既有的 `FieldId` 與事件事實對不上，所以一律保留原 `FieldId`，只改回設定）；(3) 呼叫 retry，定義相同則沿用，整個整合恢復 `Active`。不提供「用宣告覆寫」的捷徑，避免靜默蓋掉客戶的修改。

### 5.5 行為表：開啟、關閉、重新開啟、匯出匯入

以擁有者 MES（M）、夥伴進銷存（I）為例；整合 `stockOut` 為 `skip`，啟用。

| 操作 | 結果 |
|---|---|
| 只開 M | 整合 `Waiting`；M 的出貨單沒有「庫存品項」「出庫倉」兩個欄位；出貨不連動 |
| 只開 I | 無整合（I 不知道有整合）；I 完全不受影響 |
| M 先開、I 後開 | 開 I 的交易結束時調和 → `Active`，欄位與事件此時才建立 |
| I 先開、M 後開 | 開 M 的交易結束時調和 → `Active` |
| 關閉 I | 不被擋（整合新增的參照欄位不算依賴，§6.1）。整合 → `Suspended`；M 的出貨照常；I 的庫存異動仍可查。**M 裡已扣庫存的出貨單，取消會被擋（§5.8）** |
| 關閉 M | 整合 → `Suspended`；M 唯讀；I 不受影響 |
| 重新開啟其中一個 | 另一邊也在時 → `Active`，整組一起恢復；之前停用期間的出貨不補入 |
| 兩個都關，再依任意順序重開 | 最後一個重開時才 `Active` |
| 匯出 M | `modules[]` 不含整合欄位、`events[]`／`checks[]` 不含整合事件與檢查，`integrations[]` 輸出開啟時存的宣告；代號保留開啟時的（§5.6） |
| 匯入 M 套件到空資料庫、開啟 | 與直接開 M 相同；匯入的整合預設 `Disabled`，啟用後依 §5.1 進 `Waiting` 或安裝 |
| 停用整合（`enabled = false`） | `Disabled`；已安裝的項目全部停用；行為同 `Suspended`，也適用 §5.8 |
| 刪除 I | 整合 `Active`、`Held`、`Suspended` 時被擋（整合欄位是真的參照，刪除檢查看得到）；要先移除整合（§5.7） |
| 刪除 M | 整合隨 M 一起刪除（欄位在 M 的模組裡，事件與檢查依事件設計的刪除規則隨來源模組一起清） |

資料一律不刪：整合欄位上的值、已產生的庫存異動都留著，兩邊關閉後仍可查閱。

### 5.6 匯出與匯入的符號空間

`AppExporter` 目前從資料庫重建 `modules[]`、`events[]`、`checks[]`。現行 `TemplateExporter` 把欄位代號換成 `Field.Key`（`f_<id>`）、區塊 `b_<id>`、選項 `o_<id>`，也就是**不保留原始代號**。若整合宣告原樣輸出（用 `shipment.qty`），匯入後模組裡的欄位卻叫 `f_123`，整合就解析不到。這是審查必修 7。

**二擇一，我選保留代號（甲）：**

- **甲（採用）：** 匯出時欄位、區塊、選項的代號改用 §4 的三張對照表（`TemplateExporter` 的 `Code()`、`b_`、`o_` 三處改成可注入的代號提供者；沒有對照列的才退回舊格式）。整合宣告、夥伴符號（`inventory/move.qty`）和匯出的模組是同一套代號，匯入後不必改寫。夥伴自己匯出時同樣保留代號，所以兩份匯出的套件互相引用仍成立。好處：匯出的檔案可讀（`shipment.qty` 比 `f_123` 好讀），多次匯出匯入代號穩定。
- **乙（不採用）：** 沿用 `f_`／`b_`／`o_`，匯出時把整合宣告裡的符號改寫成同一套。要重寫宣告內所有嵌套位置（`set`、`when`、`formula`、`ofEvent` 等），等於再做一個反向編碼器，而且夥伴符號要連夥伴的匯出一起改寫，跨檔案無法保證。

匯出時另外：用 `ItemsJson` 把整合建立的欄位、事件、檢查**排除**（不進一般 section）；`integrations[]` 輸出存下來的 `IntegrationsJson`。代價：客戶事後在設計器改了整合事件，匯出不反映，匯出的是「開啟當時的宣告」（§13）。

**保留代號與 `f_<id>` 撞名（第二輪建議 7）：** 回退代號 `f_<id>` 可能與某個欄位保留下來的原始代號相同（例如另一個欄位原始代號恰好叫 `f_123`）。匯出時每個模組只有**一份**避撞對照：先登記所有有對照列的原始代號，再替沒有對照列的欄位配回退代號，撞到就加 `_2`、`_3`；欄位定義、規則、事件、檢查、整合宣告、報表等所有引用都用這同一份對照解析，不各自推算。測試：原始代號恰為 `f_123` 的欄位往返。

**往返測試（必做）：** 在庫 A 兩個應用程式都開、整合 Active；分別匯出兩個套件；匯入空庫 B；兩種開啟順序各一遍；整合都要 `Active`，且出貨扣庫存行為與庫 A 相同。

### 5.7 其他

- **重試與啟用開關：** `POST /api/v3/dynamic/apps/{key}/integrations/{code}/retry`（§5.4 的冪等邏輯）、`PUT .../integrations/{code}` body `{ "enabled": bool }`（轉移見 §5.1）。權限同開啟（設計器 Edit 加系統管理員）。
- **移除整合**不另做；先用停用（`enabled = false`）。真要刪欄位與事件，走設計器既有的刪除，下次調和的完整性檢查會標 `Blocked: itemMissing`，不會偷偷重建（客戶刪了就是刪了），要重建用 retry。
- **回應：** `AppResponse` 新增 `integrations[]`（`code`、`name`、`with`、`enabled`、`status`、`reason`）；`OpenPreview` 新增 `integrations[]`（會安裝、等待、或阻擋，以及「這個整合會寫入哪些夥伴模組」的清單，給管理員決定要不要啟用）。目前前端沒有應用程式管理頁（階段 5 才做），所以這次只有 API，不加畫面。

### 5.8 整合入口守衛（第二輪核心；涵蓋第一輪必修 1 與 4）

問題有兩類，同一個根因：事件選取是看「目前仍存在且啟用的事件」，所以整合一旦缺項、被停用或暫停，該連動的操作就在不被察覺的情況下略過。

- 反向：出貨過帳扣了庫存，之後進銷存關閉（或有人刪掉取消事件），取消那張出貨，單據變已取消、庫存不回補，之後也補不回來。
- 正向：整合欄位被停用，新出貨轉 `shipped` 沒扣庫存，使用者以為連動著。

**守衛：** 在擁有者這一側、**選取事件之前**（`RecordEffects` 管線、事件階段之前），對每個 `installed` 的整合，依**保存的整合宣告（`IntegrationsJson`）**，不是當下還存在的事件定義，算出這次寫入會不會觸發它的任何項目：

- **正向項目：** 宣告裡 `trigger` 符合這次寫入（`create`、`update` 的 `watch`、`transition` 的 `from`／`to`）的非 `reverse` 效果事件，以及掛在這個模組上的檢查所依賴的寫入。守衛只看 `trigger`，不看 `when`：被擋時欄位可能已經壞了，無法可靠求值，寧可多擋。
- **反向項目：** 宣告裡 `trigger` 符合、有 `reverse` 效果，而它的（`ofEvent`、`ofEffect`）在這筆來源記錄上有未沖銷的事件事實。

會觸發時，依整合**當下推導的狀態**（§5.1 的表；狀態在守衛內重新算，不信任儲存的 `Status`）處理：

| 整合狀態 | 正向操作（如轉 `shipped`） | 反向操作（如取消已連動記錄） |
|---|---|---|
| `Active` | 照常 | 照常 |
| `Suspended`（`skip`、夥伴未開，或擁有者關閉） | 允許，不連動（各自獨立的設計原意） | **409**，提示先重開夥伴應用程式 |
| `Held`（`block`、任一夥伴未開） | **409** | **409** |
| `Blocked`（完整性失敗：缺項、停用、衝突、對照缺失） | **409**，提示管理員修復整合 | **409** |
| `Disabled`（`enabled = false`） | 允許，不連動 | 記錄若有連動事實 → **409** |

- **`Active` 也要做輕量完整性檢查：** 守衛對會被觸發的整合，用項目鍵查一次：整合欄位、事件、檢查都在、為啟用、夥伴符號解析得到。不通過就當 `Blocked` 處理（上表）。這解決「兩次調和之間有人停用欄位或事件，儲存的狀態還寫著 `Active`」。守衛擋下的請求會整筆回滾，不寫狀態；下一次調和才把 `Blocked` 寫進去。
- **`Held` 以整合的全部夥伴判斷**（第二輪必修 5）：任一夥伴未開就是 `Held`，守衛擋下整個整合的操作，不看這次效果實際會寫哪個夥伴。
- **訊息：** 指出整合名稱與原因（夥伴未開、整合被阻擋、缺哪個項目）與該怎麼做。
- **改選與刪除：** 事件事實鎖（事件設計 §4.7）本來就不允許有事實的來源記錄改非狀態欄位或刪除，不論事件是否啟用，已被擋，補測試確認。
- **位置與純度：** 守衛是通用的 `RecordEffects` 步驟，核心程式不出現業務名詞；它只讀 `Dynamic_AppIntegration` 與事件事實。**沒有 installed 的整合時零成本**（先查是否有任何 installed 的整合，快取於請求）。

### 5.9 整合事件在執行期 fail closed

入口守衛之後，整合事件（`ItemsJson.events` 登記的）真正執行時若遇到下列情況，仍擋下這次寫入（409，訊息指出整合、事件與缺的符號），不當成「條件不成立」而略過：`when` 引用的欄位已停用或不存在、`set` 的來源或目標欄位已停用或不存在、選項不屬於該欄位、目標模組不可寫入。這是守衛之外的第二道。若現行事件對「條件引用已停用欄位」已是失敗，只補測試；若是靜默略過，只對整合事件改成失敗（一般事件的行為不動，避免影響既有）。

## 6. 對既有行為的改動

### 6.1 相依判定要排除整合欄位（關閉時）

`AppDependencyChecker.DependentsOfAsync` 現在會把「成員模組有 Active 的參照欄位指向 A」當成依賴。整合新增的參照欄位指向夥伴，若照算，關閉進銷存就得連帶關閉 MES，可選相依就不是可選。改成：判定依賴時排除 `ItemsJson` 登記的整合欄位。**刪除時不排除**（欄位是真的參照，§5.5）。這是關閉與刪除共用函式，加一個參數 `forClose`。

### 6.2 `AppOpener`、關閉、重新開啟、刪除

- `AppOpener`：寫 `Dynamic_AppField`／`Dynamic_AppOption`／`Dynamic_AppBlock`、`IntegrationsJson`；`SaveChanges` 之後呼叫調和（受影響的應用程式 = 剛開的這一個）；調和的警告併入回應。
- `CloseAppHandler`、`ReopenAppHandler`：關閉時先調和（停用事件）再把模組改 Closed，避免中間狀態；重開時先把模組還原 Active 再調和（重新啟用事件，因為事件驗證要求來源可寫），兩者都是整組動作（§5.1）。關閉後已連動記錄的取消由 §5.8 的守衛擋下。
- `DeleteApp`：先看整合（§5.5）。
- 範圍：「受影響的應用程式」= 本身，加上宣告了它當夥伴的、以及它宣告的夥伴。

## 7. 權限

- **安裝、停用、恢復、重試整合，只發生在開啟、關閉、重新開啟、retry、啟用開關**，這些都要設計器對應動作加系統管理員（`ISystemAdminRequest`），沒有新權限。
- **整合事件一律以系統身分執行**（事件設計 §4.2）。**觸發權限就是擁有者那個操作本身的權限**：例如誰能把出貨單轉為已出貨（狀態機轉移的群組與模組的編輯權限），誰就能觸發扣庫存；整合不另加、不放寬、也不收緊。整合只對夥伴寫入帳務類資料（事件 `create`／`reverse` 的分錄），**不給操作者讀取夥伴資料的能力**。
- **品項參照欄位的挑選**仍需要使用者對進銷存品項模組有 Read（`records/light` 既有的檢查，選單的資料來源）。沒有 Read 的使用者選不了品項；整合 `Active` 時，品項為空的 `shipped` 會被整合的檢查擋下（400，§5.2），所以不會漏扣，只是這個人出不了貨，要請管理員給他進銷存的讀取權限。**夥伴模組的讀取權限需由管理員授予擁有者的操作角色**（整合不會替任何人授權，見下）。Demo 讓出貨的帳號（生管、業務）屬於「進銷存查詢組」，對應進銷存套件只讀品項與倉庫的 `viewer` 群組；不加入倉管組，因為倉管能過帳調整單，權限過大。
- **整合不替任何群組授權，也不改任何群組的權限。**
- 事件效果是系統身分寫入，跨應用程式後變成「M 的人能讓 I 的帳變動」。緩解：
  - 預覽顯示每個整合會寫入哪些夥伴模組，管理員開啟時看得到。
  - **匯入的套件，整合預設 `Disabled`**，必須管理員逐一啟用（內建套件預設啟用）。理由：匯入套件的作者能宣告「夥伴 = 任何已開啟的應用程式」，沒有這道，之後開夥伴時會靜默安裝一個管理員從沒看過的寫入路徑。
  - 啟用開關只改狀態，不改定義。
- 隱藏來源檢查（`allowHiddenSource`）照事件設計 §4.2，整合事件不例外。

## 8. 循環判定

事件圖本來就是「所有啟用中的事件」的全域圖（`EventValidator.FindCycleAsync`），不限制在同一份套件，所以**執行期與安裝時的檢查已經是跨套件的**：整合事件安裝時走 `CreateEventRequest`，環一律拒絕，整合變 `Blocked`（原因列出環上的事件鍵）。重新啟用同樣走驗證。

### 8.1 新增：目錄層的靜態檢查

兩個整合各自無環，但合起來有環（M→I 一個、I→M 一個，各在不同套件），要到第二個安裝時才被擋，這時另一個應用程式的使用者會看到整合神祕地沒裝。對內建套件，`AppCatalog` 載入時把所有內建套件的事件（含整合事件）放進一張模組層級的圖，找環，有環拒絕啟動。匯入的套件只能在安裝時擋。

### 8.2 停用事件不留邊

停用中的事件不進圖（現有行為）。`Suspended` 的整合因此不會讓圖多出邊；重新啟用時才重新檢查，這時若別的整合在中間補了一條邊形成環，重新啟用失敗 → `Blocked`。

## 9. 缺口 F：參照目標狀態守衛

**能力：** 參照欄位可設定 `refGuard`：目標記錄的某個狀態欄位必須屬於指定狀態，才能在建立或改選時填入。

```json
"refGuard": { "field": "workorder.status", "in": ["done"] }
```

DB 內是 `FieldConfig.RefGuard { FieldId, OptionIds[] }`（`FieldConfig` 是 JSON，不需要 schema migration）。

- **執行：** `ReferenceValidator` 本來就只對「有變動」的參照驗證。在取得合法鍵集合時，多一道：目標記錄的 `FieldId` 欄位值（讀 `RecordIndex`；欄位必須是可篩選的選項欄位，定義時驗證）必須在 `OptionIds` 裡，否則該鍵不在合法集合，沿用既有的「找不到」錯誤路徑，訊息改成「目標記錄的狀態不符，不能選」。
- **定義時驗證：** 只能設在 `module` 目標的參照欄位；`FieldId` 屬於目標模組、是下拉；`OptionIds` 屬於該下拉。
- **挑選清單：** `records/light` 新增選用參數 `forField`，帶了就套同一個守衛過濾，使用者只看得到可選的記錄。做不到時只剩提交時的錯誤訊息，列為可降級。
- **兩個以上不相干情境（鐵則）：** MES 出貨單只能選已完工的工令；進銷存出貨單只能掛已確認的採購單；階段 3 的付款單只能掛已過帳的發票；保養紀錄只能掛使用中的模具。
- **範圍外：** 守衛只擋「建立與改選」，不擋之後目標的狀態變化。目標之後離開允許的狀態，已存在的參照不受影響；要擋住離開，用 s2b 已有的重開守衛這類規則（MES 工令的 `liveShipments`）。這與現有所有參照驗證「只看有變動的」一致。
- 套件格式：`config.refGuard` 的 `field` 是限定欄位名（必須是目標模組的），`in` 是該欄位的選項代號。允許的 `config` 鍵清單加入 `refGuard`（格式 5）。

## 10. Demo 整合：MES 出貨扣進銷存庫存

### 10.1 為什麼選這個

三個候選都看過：

| 候選 | 評估 |
|---|---|
| MES 出貨 → 進銷存庫存 | **選它。** 用到整合的全部形狀（欄位、事件、沖銷、夥伴的檢查），而且夥伴的 `inv-no-negative-stock` 檢查是現成的守衛：MES 出貨超過庫存會被擋，不需要寫任何新規則，示範效果最直接。不改 MES 與進銷存既有的模組、事件、檢查 |
| CRM 訂單 → MES 訂單或工令 | 要先解決客戶對應（§11 項目 3）：MES 訂單的客戶是外部實體 `sales.customer`，CRM 的是動態模組，兩邊型別不同，不能複製。另外還需要整合新增轉換與追溯欄位（§11 項目 3）。這次不做 |
| CRM 客戶與 MES／進銷存客戶對應 | 只是對應欄位，沒有流程可示範；沒有主檔決定之前（§14）做了也只是多一個沒人維護的欄位 |

### 10.2 品項兩邊各一份：怎麼對應，代價

**決定：不同步品項主檔。MES 的出貨單在出貨時直接選進銷存的品項與出庫倉**（整合新增的兩個欄位）。品項對應就是使用者每次出貨時選一次。

- 為什麼不做自動對應：MES 的品號是文字（工令一張一品項，`itemNo` 文字），進銷存的品項是記錄。自動對應要嘛以品號比對（兩邊品號規則不同，比對失敗只能默默略過）、要嘛在工令加品項對照欄位並改寫既有的 `workOrder` 參照欄位的帶值設定（要修改既有欄位的設定，超出整合「只加不改」的範圍）。
- 代價：出貨單要多選兩個欄位；選錯品項就扣錯品項（取消出貨可沖銷）。整合 `Active` 時，**已出貨就必須選庫存品項**（第二輪必修 3，整合自己的檢查擋下）。模具廠若有不入庫的成品，整合啟用期間無法出貨；要嘛為它建一個庫存品項（入帳 0 的成品也行，但庫存不足會被擋，所以要先盤點入帳），要嘛停用整合（`enabled = false`，此時出貨不連動）。這是為了避免「沒有任何提示就漏扣」而付的代價。
- 進階做法留作後續：整合支援「修補既有欄位的設定」（`patches`），讓工令記一次庫存品項、出貨自動帶。需求出現再做。

### 10.3 Demo 資料

- 進銷存新增 3 個成品品項（模具成品，`category = finished`）與 1 個成品倉；用盤點調整單（原因：期初）入帳，量足夠 Demo 的出貨用。
- MES 已出貨的出貨單，在兩個應用程式都開時一律指定庫存品項與出庫倉並出貨，扣庫存（庫存量要夠）；其中 1 張之後取消（沖銷）。
- **缺口 F 的情境：** Demo 產生器在出貨之前先由生管把工令推進 `done`（原本靠出貨事件順便結案，已取代，§11 項目 2）。被擋的情境（業務對未完工工令建立出貨單）不留紀錄，由整合測試涵蓋。
- Demo 開啟順序不影響結果（兩種順序都有測試）。Demo 產生器取整合欄位 Id 的來源是 `ItemsJson`，不是欄位代號對照。
- 示範帳號：生管與業務帳號加入「進銷存查詢組」（進銷存套件的 `viewer` 群組，只讀品項與倉庫，選庫存品項與出庫倉需要的 Read）。**群組名稱不得與任何套件開啟時以 `create` 模式新建的群組同名**（會 400「已有同名的群組」），沿用既有的「…組」命名，並在 `DemoStructure` 測試守住。
- 儀表板「庫存」那張不變；「各工令出貨」報表仍以 MES 數據為主。庫存餘額報表因出貨而減少，是這個整合在畫面上最直接的證據。
- 資料量與日期是我估的，實作時可微調，以「看得到跨月、有一張被擋的（由整合測試涵蓋）、庫存餘額報表有變化」為目標。

### 項目 1：缺口 B 可選相依 — 做

### 項目 2：缺口 F 參照目標狀態守衛 — 做（小）

§9。並**取代** s2b 的 `mes-shipment-close-wo`、`mes-shipment-repoint-wo` 兩個事件：

- 原做法的目的是「出貨單建立時工令必須完工」，用事件把工令寫成 done 來近似。有 F 之後直接宣告 `workOrder` 的 `refGuard`（`workorder.status` 屬於 `done`），事件刪除。
- **改善：** 原做法在出貨單建立時由事件（系統身分，不看群組）把工令推進 done，等於業務身分的人能繞過工令狀態機只有生管能 `running → done` 的限制。改後業務不能替生管結案，權限邊界回到狀態機宣告的樣子。
- **代價（行為改變）：**
  1. 工令是 `running` 且完工量已達標時，過去出貨會順便結案；現在要生管先把工令推到 `done` 才能出貨，多一步。
  2. 過去 `shortClose` 的工令也靠出貨結案；現在一樣要生管推進。
  3. 既有測試與 Demo 中「對 running 的工令直接出貨」的步驟要改成先推進 `done`（§12.2 列出）。
  4. `done` 規則（完工量 ≥ 工令數量或勾短交結案）與重開守衛（`liveShipments`）不變。
  5. 主控已接受這項行為改變（第一輪裁決）；記入已知限制（§15）與 Demo 情境（§10.3）。
- 若實作時發現 `RecordIndex` 取狀態值有阻礙，F 退回只做提交時驗證不做挑選過濾，取代事件的部分不退（取代的是事件，與挑選清單無關）。F 本身做不出來就不取代，兩個事件保留，寫進結果檔。

### 項目 3：客戶主檔與兩套訂單 — 只寫決定，不做

**決定（主控已依使用者授權裁決，§14）：** CRM 與 MES 兩套客戶、兩套訂單、進銷存自己的客戶，**都維持各自一份，不合併、不指定誰為主**；本次不做它們之間的自動橋接。

- **為什麼能用這次的能力解決一部分，卻不做：** 「CRM 訂單產生 MES 訂單」需要整合能新增轉換與追溯欄位（本設計沒收轉換，見下）；更根本的是客戶：MES 的客戶是外部實體 `sales.customer`（在 POC 是模擬提供者），CRM 的是動態模組，型別不同，轉換無法複製，只能讓使用者在 MES 訂單上重選。整合只能把問題從「完全不連動」變成「連動一半」，而客戶主檔以誰為準是產品方向，不由我決定。
- **整合為什麼沒收轉換：** 轉換需要追溯欄位（擁有者模組新增參照欄位到夥伴）、剩餘量鎖與狀態機互動，驗證面比事件大。這次的整合只收有明確 Demo 的欄位、事件、檢查。收轉換是同一個 section 加一個陣列，格式向前相容，需求出現再加。
- **現況與使用者感受：** 兩個應用程式都開時，使用者看到兩組選單、兩份客戶、兩套報價與訂單。這是 s2b 已接受的狀態（進銷存設計 §2.4）。
- **後續選項（§14 已裁決：各自一份，階段 3 再定）：** (a) 維持各自一份，階段 3 的會計用「往來對象」另外建主檔，各應用程式的客戶對應過去；(b) 讓動態模組能擔任實體提供者（`sales.customer` 背後是 CRM 的客戶模組），CRM 開啟時自動成為 MES 的客戶主檔；(c) 整合新增對應欄位。我傾向 (a) 與 (c) 並用，(b) 動到核心「實體」的定義，工作量最大。

### 項目 4：缺口 E 逐列轉換 — 不做，只寫設計

**形狀：** 轉換定義新增 `mode: "perLine"`：選擇來源明細的若干列，**每一列各產生一張目標單據**（目標表頭，數量與品項由該列複製），剩餘量按來源列計。與現有的「含明細部分轉換」（選若干列、產生**一張**目標表頭與其明細）並列。

**需要的改動：** 轉換定義與驗證（來源明細列 → 目標表頭的欄位對應，`header.copy` 要能引用來源列的欄位）、`ConversionExecutor`（迴圈建立多張單據，每張走完整寫入流程與事件）、互斥鎖（對來源列而不是來源表頭上鎖，現在鎖在表頭）、剩餘量表（現在以（轉換, 來源列）計，可重用）、前端轉換對話框（多選列、顯示將產生幾張）、追溯（目標表頭記來源列 Id，不是來源表頭）。

**為什麼不做：** 估計超過這次工作量的三分之一。整合（§3 到 §8）加 F（§9）已是主要工作；E 要新的轉換型別、執行器、鎖與前端，且目前只有「訂單明細逐列排工令」一個明確情境，MES 現在用「工令以參照選訂單」的替代做法可運作。另外兩個情境（銷售訂單明細各出一張出貨單、採購單明細各開一張請購）沒有任何應用程式在排程內，不符「至少兩個不相干情境」的立項門檻。等階段 5 或第二個情境出現再做。

### 12.3 測試清單

**單元（Application、Domain）**
- 整合格式驗證：版本門檻、未知鍵、`with` 對帳、夥伴符號前綴、欄位不得必填、事件來源必須是擁有者模組、不得引用別的整合的欄位、事件代號撞名。
- 目錄層：內建套件欄位層級對帳（故意弄錯一個夥伴欄位代號得到啟動錯誤）；跨套件事件循環（兩個套件各一個整合形成環）拒絕啟動。
- 調和函式的狀態表（§5.1）逐格：每個「現況 × ready」組合。
- 合併 `TemplateIdMap` 的前綴解析。
- `refGuard`：定義驗證（非參照、非 module 目標、欄位非目標模組的、選項非該欄位的）；執行（建立、改選、值沒變不驗、目標在允許狀態、目標在不允許狀態、目標不可見）。
- `DependentsOf(forClose)`：整合欄位不算依賴；刪除時算。

**整合（WebAPI，檔案型 SQLite）— 兩個應用程式（MES、進銷存）**
- **四種組合：** 都不開／只開 MES／只開進銷存／都開，各自斷言：整合狀態、MES 出貨單有無整合欄位、出貨是否扣庫存、庫存餘額。
- **兩種順序：** MES 先、進銷存先，最後狀態完全相同（欄位、事件、檢查的集合與 Id 無關的內容相等）。
- **連動正確：** 出貨過帳 → 庫存減少、`docNo` 為出貨單號；取消 → 沖銷；不選品項 → 不連動；庫存不足 → 出貨 409、訊息指出庫存不足，出貨單仍是草稿；選品項沒選倉庫 → 失敗並指出必填。
- **關閉其中一個再重開：** 關進銷存 → 整合 Suspended、關閉不被擋、MES 出貨成功但不扣庫存、庫存異動與出貨單仍可查閱；重開進銷存 → Active，新出貨扣庫存，停用期間的出貨沒有補入；關 MES 再重開同理。
- **兩個都關再依兩種順序重開。**
- **`block` 模式（測試用套件）：** 夥伴關閉後擁有者寫入來源 409；重開後恢復。
- **匯出匯入：** 匯出 MES → 不含整合欄位／事件、含 `integrations`；匯入到空資料庫、開啟 → Waiting、匯入的整合預設 Disabled、啟用後開進銷存 → Active；匯出再匯入 MES 的內建版與匯入版行為相同。
- **失敗隔離：** 整合內第二個事件故意錯 → 整合 Blocked，沒有殘留欄位、事件，夥伴與擁有者的開啟都成功。
- **整組不可分割（必修 3、6）：** 整合已 Active 後刪掉其中一個事件 → 調和 Blocked、**全部**事件與檢查停用（出貨不再連動，也不會只剩一半）；恢復時第二個事件驗證失敗（製造循環）→ 整組回滾、仍 Blocked、第一個事件沒被打開。
- **retry 冪等（必修 6）：** 對 Active 的整合 retry 兩次 → 無重複、無代號衝突；刪掉一個事件後 retry → 補建；客戶改過事件定義後 retry → `Blocked: itemConflict`，不覆寫；別的應用程式占用同代號 → `Blocked: codeConflict`。
- **反向效果不遺失（必修 1）：** 出貨過帳扣庫存 → 關閉進銷存 → 取消該出貨 → 409，單據仍是已出貨；重開進銷存 → 取消成功 → 庫存回補。改選庫存品項、刪除該出貨在關閉期間同樣被擋（事實鎖）。停用整合（`enabled = false`）後取消也 409；`Blocked` 後亦同。
- **`block` 與歷史無關（必修 2）：** 測試用套件（`block`）：(甲) 先關夥伴、再關擁有者、再開擁有者；(乙) 先關擁有者、再關夥伴、再開擁有者；(丙) 夥伴關、擁有者不動。三者最終都是 `Held`，擁有者寫入來源 409；重開夥伴 → `Active`。`skip` 同樣三條路徑終點都是 `Suspended`。
- **停用欄位（必修 4）：** 停用整合欄位 `stockItem` → 兩次調和之間，出貨過帳 409（fail closed）而不是靜默不扣；調和後整合 `Blocked`、事件全停用。停用夥伴的 `inv-move.qty`、`inv-move.item` 同樣；選項被停用／不屬於該欄位同樣。
- **enabled 轉移（必修 9）：** 匯入的整合 `Disabled` → 啟用且夥伴不在 → `Waiting`；啟用且夥伴在 → 直接 `Active`；`Active` → 停用 → `Disabled`，事件全停用，取消已連動出貨 409。
- **入口守衛（第二輪）：** 對照 §5.8 的表逐格：`Active`／`Suspended`／`Held`／`Blocked`／`Disabled` × 正向（新出貨轉 `shipped`）、反向（取消已連動出貨）共 10 格，各一個測試。另外：刪掉取消事件 → 取消已扣庫存的出貨 → 409；停用 `stockItem` → 新出貨轉 `shipped` → 409；單獨停用整合裡的某個事件 → 守衛視為 `Blocked`、下次調和整個整合 `Blocked`，不部分恢復。
- **多夥伴（第二輪必修 5）：** 測試用套件宣告兩個夥伴，只有一個關閉 → `Held`，整合的操作全擋，不看實際寫哪個夥伴。
- **品項為空（第二輪必修 3）：** 整合 `Active`，品項為空轉 `shipped` → 400（檢查訊息）；沒有進銷存 Read 的使用者選不了品項、出不了貨；整合 `Suspended`／`Disabled` 時品項為空可以出貨（不連動）。
- **`itemConflict` 恢復（第二輪建議 6）：** 客戶改了整合事件 → retry `Blocked: itemConflict`；管理員還原成宣告的定義（保留 `FieldId`，欄位值不變）→ retry → `Active`。
- **匯出匯入往返（必修 7、8，第二輪建議 7）：** 見 §5.6，另加「原始代號恰為 `f_123`」的往返。另加：擁有者先開、夥伴後開時，整合欄位正確加進原區塊（`Dynamic_AppBlock`）；匯出的套件保留代號（`shipment.qty`，非 `f_123`）。
- **對照缺失：** 以舊版（沒有對照列）夥伴與刪掉夥伴欄位兩種情況 → Blocked `unbound`，retry 在修復後成功。
- **冪等：** 連續調和兩次不產生重複。
- **權限：** 非管理員不能 retry、不能開關整合；使用者沒有進銷存 Read 時挑品項看不到，存檔成功、不連動；管理員仍是唯一能安裝的人。
- **客戶刪掉整合事件：** 下次調和 Blocked `itemMissing`，不重建；retry 重建。
- **F 取代：** 業務對 running 的工令建立出貨單 400；生管推進 done 後成功；改選到未完工工令 400；`done → running` 重開守衛仍有效。

## 15. 風險與已知限制

1. 事件不回補：整合停用期間（夥伴關閉）產生的來源記錄、整合安裝之前已存在的來源記錄，都不會連動（事件設計 §16.3）。`block` 模式能避免前者。
2. 整合欄位在整合停用後仍留在表單上，使用者可能誤以為還在連動。Suspended 的狀態只能從 API 看到，要等階段 5 的應用程式頁面才有畫面。
3. 匯出不反映客戶對整合事件的修改（§5.6）。
4. 沒有「移除整合」功能；要移除只能停用，再用設計器逐項刪除。
5. 舊資料庫的夥伴整合不可用（§4）。
6. 整合讓「擁有者的使用者能經事件寫夥伴的帳」（§7），靠預覽與匯入預設停用緩解，沒有再細的授權。沒有進銷存 Read 的使用者選不了庫存品項，整合 `Active` 時他出不了貨（被檢查擋下並有訊息），不會漏扣。
7. th、vi 為機器翻譯，待母語者校對。
8. `refGuard` 只擋建立與改選，不擋目標之後離開允許狀態（§9）。
9. **缺口 F 取代出貨事件後，業務不能再靠出貨替生管結案**（主控已接受）：工令要先由生管推進 `done` 才能建立出貨單；原本「running 且完工量達標時出貨順便結案」的便利沒有了。
10. 夥伴關閉期間（`skip`）已連動的記錄不能取消、改選、刪除（§5.8），要先重開夥伴；整合被阻擋（`Blocked`、`Held`）時，連正向操作也被擋。這是為了不讓兩邊對不上而付的代價。
11. 夥伴的設計者停用、改動被整合引用的欄位，會讓擁有者的出貨失敗（§5.9）：fail closed 的另一面，訊息指出是哪個整合與符號。
