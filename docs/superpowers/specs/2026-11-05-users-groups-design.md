# 使用者與群組管理 設計文件

> 2026-11-05｜上位文件：[動態模組與自訂欄位 設計文件](2026-11-03-dynamic-modules-design.md)；相關：[Demo 資料 設計文件](2026-11-05-demo-data-design.md)
> 標「（我的判斷）」的是我代為決定、可以改的；其餘是使用者已拍板的決策。

## 1. 意圖

這套系統要成為獨立產品，每家客戶各裝一套。現在有兩個擋住產品化的缺口：

- **沒有真正的登入。** 前端用右上角下拉選單切換身分，後端只看 `X-User` 標頭，任何人都能冒用別人，包括系統管理員。
- **使用者和群組寫死在程式裡。** 客戶沒辦法自己加人、開群組，全新安裝還會看到「業務一」這類示範帳號。

做完之後，客戶拿到全新系統，用一個管理員帳號登入，自己建立群組和員工帳號，再用現有的模組權限畫面授權。

## 3. 目標、非目標、反目標

**目標**

1. 全新安裝只有一個管理員，沒有任何示範資料。
2. 管理員可以在畫面上管理使用者和群組，重開站台後設定不變。
3. 冒用身分的路徑消失：正式環境送 `X-User` 不再有任何效果。
4. Demo 站照樣能示範權限差異，`docs/demo.md` 跟著更新。

**非目標**

- AD、LDAP、SSO、雙因素驗證、自助註冊、寄信重設密碼。
- 列表的使用者欄位改顯示名稱（已在路線圖，main 既有行為）。
- 使用者和群組異動的稽核紀錄畫面；登入成功、失敗、鎖定只寫 log（我的判斷）。
- 多資料庫支援。但不寫 SQLite 專屬語法，避免日後多一筆帳。
- 匯入使用者（Excel）。

**反目標**

- 正式站存在任何不驗密碼就能登入的路徑。
- 管理員把自己或所有人鎖在系統外，只能改資料庫救回。
- 舊記錄因為員工離職，顯示不出是誰建立的。

## 4. 登入

### 行為

- 帳號加密碼登入。帳號即既有的 `UserId`，建立後不可改，因為記錄、歷程、檢視都用它關聯。
- 帳號一律存小寫，登入時不分大小寫；格式 `^[a-z0-9._-]{2,50}$`（我的判斷）。
- 密碼至少 8 碼，沒有其他組成規則（我的判斷）。
- 連續輸錯 5 次鎖定 15 分鐘，成功登入後歸零（我的判斷）。管理員重設密碼時一併解鎖。
- 帳號不存在、密碼錯、已停用、已鎖定，對外都回同一則 401 訊息，「帳號或密碼錯誤，或帳號暫時無法登入」，避免探測帳號。log 記真實原因。
- 第一次登入和管理員重設後必須改密碼（`MustChangePassword`）。這段期間伺服器端擋住 `/auth/*` 以外的所有 API，回 403 並帶可辨識的錯誤碼，前端導到改密碼頁。只靠前端導頁不算數。
- 使用者可以自己改密碼，要輸入舊密碼。新密碼不可與舊密碼相同。
- 忘記密碼由管理員重設；系統不寄信，因為每家客戶不一定有郵件伺服器。

### 機制

- 用 ASP.NET Core 內建的 cookie 驗證，不引入第三方套件。cookie 為 `HttpOnly`、`SameSite=Lax`，HTTPS 請求才加 `Secure`。8 小時滑動逾期，關閉瀏覽器失效（我的判斷）。
- 站台在反向代理後面（Render）時要處理 `X-Forwarded-Proto`，否則 `Secure` 不會生效。
- 密碼用框架內建的 `PasswordHasher`（PBKDF2）存雜湊。
- `AppUser` 新增 `SecurityStamp`，寫進 cookie。每個請求比對資料庫的 stamp 與 `IsActive`，所以停用、重設密碼、改密碼會讓該使用者其他 session 在下一個請求立刻失效。自己改密碼的當前 session 重發 cookie，不用重新登入。
- 這表示每個請求多一次依主鍵的查詢，可接受。
- DataProtection 金鑰存在資料庫同一個目錄，重開站台後登入狀態不失效（我的判斷）。Render 沒有永久磁碟，重新部署後要重新登入，連資料都一起清空，不是問題。

### 要拿掉的東西

- `HeaderCurrentUser`：改由 cookie 的 claim 提供 `ICurrentUser`。`ActingScope` 的裝飾器不動，Demo 產生器照舊運作。
- `IdentityMiddleware` 對 `GET /users` 的匿名例外：`/users` 回傳全部帳號，登入後才能取得。匿名只能呼叫 `/auth/login`、`/auth/options`、`/auth/demo-login`、`/api/health`。
- `DbKnownUsers`：它在程序存活期間只載入一次使用者清單，新增的使用者會被當成不存在，必須移除。
- 前端 `use-identity-store` 的 localStorage、`X-User` 攔截器、右上角下拉選單。

### API

`/api/v3/dynamic/auth` 底下：

| 方法 | 路徑 | 說明 |
|---|---|---|
| GET | `/options` | 匿名。回 Demo 登入是否開啟與可用帳號 |
| POST | `/login` | 匿名 |
| POST | `/demo-login` | 匿名。僅 Demo 模式，否則 404 |
| POST | `/logout` | |
| POST | `/change-password` | |

既有的 `GET /me` 繼續當「目前使用者」，加上 `mustChangePassword`。

### 前端

- `/login` 和 `/change-password` 兩頁，不套用主版面。其餘路由未登入時導到 `/login?redirect=…`，`redirect` 只接受站內路徑。
- 任何 API 回 401 就導回登入頁。
- 右上角改成：目前使用者名稱、改密碼、登出。
- 登出和換人時清空 TanStack Query 快取，避免下一位使用者看到上一位的資料。
- 新畫面都要有 zh-TW、en-US、th、vi 四語系。

## 5. 使用者管理

系統管理 → 使用者，只有系統管理員看得到，API 也由伺服器端檢查 `IsSystemAdmin`，否則 403。可以設多位系統管理員。

欄位：帳號、姓名、群組（可多個）、狀態（啟用／停用）、系統管理員。

- **新增：** 填帳號、姓名、初始密碼、群組，下次登入必須改密碼。帳號重複回錯誤訊息。
- **編輯：** 姓名、群組、系統管理員。帳號不可改。
- **重設密碼：** 管理員輸入新的臨時密碼（我的判斷，不自動產生，與新增一致）。同時解鎖、要求改密碼、使既有 session 失效。
- **停用／啟用：** 不提供刪除。停用後不能登入、既有 session 立刻失效，也不再出現在使用者欄位的下拉選項和權限畫面的挑選清單；舊記錄、歷程的顯示不受影響。
- **防呆：** 不能停用或取消最後一位啟用中的系統管理員；不能停用自己（我的判斷）。兩者都由伺服器端擋。

`GET /users` 預設只回啟用中的使用者，所有現有呼叫端照舊；管理頁呼叫另一個支援 `includeInactive` 且限管理員的端點（我的判斷）。歷程、匯出用的 `ListUsersAsync` 維持回傳全部，名稱才解析得出來。匯入的使用者欄位比對只接受啟用中的帳號（我的判斷）。

## 6. 群組管理

系統管理 → 群組，權限同上。欄位：名稱、成員數。

- **新增：** 只填名稱，內部 `Key` 由系統產生（`g-` 加短亂碼）且不可改（我的判斷）。
- **改名：** 顯示名稱沿用 `NameI18n`，畫面只編輯目前語系（我的判斷）。其他語系沒填就用既有 fallback。
- **成員：** 可從群組這邊維護，也可從使用者那邊維護，資料同一份。
- **權限：** 不在這裡設定，沿用模組權限畫面。使用者不屬於任何群組時沒有任何模組權限，維持現有 fail-closed 行為。
- **刪除：** 先呼叫影響查詢，對話框列出成員數、有授權的模組、欄位例外和資料範圍的數量。
  - 有欄位選項範圍（`FieldOptionScope`）還指定這個群組就擋下，列出是哪些模組的哪些選項。原因是選項範圍移除後，該選項可能變成所有人都能選，等於放寬權限。
  - 其他情況確認後一起刪除成員對應、模組授權（`GroupProgramPrivilege`）、欄位例外（`FieldPermission`）、資料範圍（`ModuleDataScope`），同一個交易。這些表目前沒有 FK cascade，要明確刪。
  - **注意：** 刪除帶「隱藏」或「唯讀」欄位例外的群組也可能放寬權限。對話框要明講「成員會失去這個群組的授權與限制」，不擋（我的判斷）。

`templates/*.json` 用群組 `Key` 指定權限建議。全新安裝沒有這些群組時，`TemplateInstantiator` 已經是略過並回傳警告，這個行為正確，不用改，只要加測試鎖住。

## 7. 第一次安裝與種子資料

`SeedData.EnsureSeededAsync` 拆成兩塊：

- **核心種子**（每次啟動都跑，只補缺）：`DYN00000` 程式、管理員引導（見下）、既有的資料修復步驟。
- **示範人員與示範實體**：`Users`、`Groups`、`Molds`、`Customers` 從核心種子移出。模具和客戶基於同樣理由一起移，正式客戶不該看到虛構的客戶（我的判斷）。

**管理員引導：** 資料庫裡沒有任何「啟用中且已設密碼的系統管理員」時：

1. 建立或更新帳號 `admin`（姓名「系統管理員」、`IsSystemAdmin`、`MustChangePassword`）。
2. 密碼取環境變數 `Auth__InitialAdminPassword`；沒設就產生隨機密碼，在啟動 log 以 Warning 印出一次。
3. 之後每次啟動，只要條件不成立就什麼都不做，環境變數改了也不會覆寫。

現有程式每次啟動都強制 `admin.IsSystemAdmin = true`、補回群組成員，這兩段要移除，否則管理員的操作重開後會被蓋掉。`firstUpgrade` 的舊資料授權邏輯一併移除：POC 階段沒有要保留的舊資料庫（我的判斷）。

**既有的資料庫：** 本機舊 `poc.db` 裡的使用者會留著但沒有密碼。`admin` 會走引導流程，其他人由 admin 重設密碼，或直接刪庫重建。沒有密碼的帳號無法登入。

## 8. Demo 資料與 Demo 登入

### 產生器

- 產生器在交易開頭建立示範使用者、群組、模具、客戶，產生失敗時一起回滾。
- 這些使用者標記 `IsDemoAccount = true`，密碼雜湊留空，所以不能用密碼登入，只能走一鍵登入。
- Preflight 增加衝突檢查：示範使用者帳號、群組 `Key`、模具、客戶編號已存在就列入衝突，整批不做，與現有規則一致。
- 確定性（同 seed 同結果）的既有測試要繼續通過。
- 測試需要的示範人員由同一段程式碼提供（例如 `DemoPeople.EnsureAsync`），避免在測試裡再維護一份清單。

### Demo 模式

- 環境變數 `Demo__LoginEnabled=true`，寫進 `render.yaml`，預設關閉。開啟時啟動 log 印 Warning。
- 登入頁多列帳號清單，點一下就以該身分登入，換人要先登出。
- 可一鍵登入的帳號是 `IsDemoAccount = true` 的使用者，加上 `admin`。Demo 站要能展示系統管理功能，所以包含 admin。
- 一鍵登入不要求改密碼。
- 站台剛啟動、Demo 資料還在產生時，清單只有 admin，並顯示「Demo 資料產生中」。
- Demo 站是公開的，訪客可能改掉資料或停用帳號，重新部署或休眠後資料會回到初始狀態，這點照舊接受。一鍵登入不受 admin 的密碼被改影響。

`DemoDataController` 的權限不變。`docs/demo.md`、`docs/manual.md`、README 跟著更新：切換身分改成登出再點帳號，手冊新增使用者、群組、第一次安裝三節。

## 9. 資料模型

`AppUser` 新增欄位，走 EF migration：

| 欄位 | 型別 | 預設 |
|---|---|---|
| `PasswordHash` | string? | null |
| `MustChangePassword` | bool | false |
| `IsActive` | bool | true |
| `IsDemoAccount` | bool | false |
| `FailedLoginCount` | int | 0 |
| `LockedUntil` | DateTimeOffset? | null |
| `SecurityStamp` | string | 新值 |

`PermissionGroup`、`UserGroupMapping` 不用動。鎖定時間的判斷用真實時間，不走 `IBusinessTime`，因為它會被 `ActingScope` 模擬。

## 10. 測試策略

- 既有 WebAPI 測試約 164 個透過 `TestApp.AsUser` 帶 `X-User`。不逐一改寫：`TestApp` 預設註冊測試專用的驗證 scheme 讀 `X-User`，這段程式碼只存在測試專案。
- 另外提供走真實 cookie 驗證的 `TestApp` 模式，新的驗收測試都用它。必須有一個測試證明：真實設定下送 `X-User` 不帶 cookie 回 401。
- ApplicationTests 有多處呼叫 `SeedData.EnsureSeededAsync` 後直接用 `sales01` 等帳號，改成同時呼叫示範人員的種子。
- 其餘要有測試的行為：鎖定與解鎖、`MustChangePassword` 的伺服器端阻擋、停用與重設後舊 session 失效、最後一位管理員防呆、群組刪除的擋下與連帶清除、重開後成員不被補回、引導不覆寫既有密碼、Demo 登入關閉時 404、一鍵登入拒絕非 Demo 帳號。
- 實機走查：全新資料庫走完「引導 → 改密碼 → 建群組 → 建使用者 → 授權 → 新使用者登入」，以及 Demo 模式的一鍵登入。
