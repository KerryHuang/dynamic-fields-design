## 1. 目的

使用者 2026-11-11 指示：「所有的規則都要是能設定的，不要用程式寫死的方式……也要檢查現有程式是不是有寫死規則的地方」。

範圍已釐清（使用者裁決）：

- **業務政策**要可設定：數量上限、預設值、天數與時間規則、通知對象、特定模組或應用程式代碼的特例分支。
- **完整性守衛、安全檢查、技術限制**可以寫死，但要列清單給使用者看過（§10）。
- **畫面呈現方式**（按鈕隱藏或灰色、頁籤排列）不算規則。

2026-11-11 盤點 poc 程式，找到 24 類寫死的業務政策（§4 的 A1–A24）、27 類建議維持寫死的平台不變式（§10）。

## 2. 目標、不做、反目標

**目標**

- 每個業務政策都有一個登記項：代碼、型別、出廠預設值、可設定範圍、適用層級。程式只從這份登記讀值，不再各處寫常數。
- 系統管理員在一個獨立的「政策設定」頁（系統管理 → 政策設定）集中調整全系統預設值。政策頁是獨立頁，不是系統設定頁的分頁（使用者 2026-11-12 確認）。
- 模組設計者可以在模組設計頁覆寫「可模組覆寫」的政策（使用者裁決）。
- 前端一律從 API 取得生效值，不另存一份（AGENTS.md 鐵則 2）。
- 上線當下行為完全不變：出廠預設值等於目前寫死的值。

**不做（這一輪）**

- 不做設定變更歷程與還原（§12 判斷 8，列為 💡）。
- 應用程式套件不帶模組政策覆寫（§12 判斷 6，列為 💡）。
- 不做依群組、依使用者的政策層級。
- 密碼政策、登入閒置逾時不在這一輪（§10 B18、B19 已註明之後可升級）。

**反目標**

- 不准出現「設定存在，但某段程式仍讀自己的常數」：同一政策只有一個讀值入口。
- 不准讓管理員把值設到會拖垮伺服器的程度：每個政策有寫死的技術上下限（§3.3）。
- 改嚴不准讓既有資料突然不能存檔（§3.5）。

## 3. 規則

### 3.1 層級與查值（使用者裁決）

- 兩層：**全系統預設**、**模組覆寫**。
- 查值順序：該模組有覆寫用覆寫 → 否則用全系統值 → 管理員沒設過就用出廠預設值。
- 每個政策宣告自己的範圍（主控判斷）：
  - `system`：只有全系統一個值，例如時區、預設語系、通知保留天數、組織層數。
  - `module`：全系統預設＋可模組覆寫，例如附件上限、明細列上限、任務規則數。
- 模組覆寫可以比全系統值寬或嚴，只受技術上下限約束（使用者裁決 2026-11-11）。全系統值是預設，不是天花板；管理員調全系統值不影響已存在的覆寫。
- 跟特定模組無關的地方（例如全系統的通知清理）查值時不帶模組，只取全系統值。

### 3.2 誰能改（使用者裁決）

| 層級 | 誰能改 | 在哪改 |
|---|---|---|
| 全系統預設 | 系統管理員 | 獨立頁「政策設定」（系統管理 → 政策設定；使用者 2026-11-12 確認，不是系統設定頁的分頁） |
| 模組覆寫 | 有設計權的人（沿用現有設計權限的 Edit；目前沒有單一模組的設計權，不另做） | 模組設計頁的「政策」分頁 |

- 其他人只能透過生效值 API 讀到結果，看不到誰設了什麼。
- 由應用程式管理的模組，覆寫一樣可以改（主控判斷，同 2026-11-10 裁決「app 帶來的任務規則可改可刪」）。

### 3.3 範圍與型別

- 型別：整數、布林、單選代碼、使用者或群組（收件人）、時區、語系清單。
- 整數政策都有寫死的技術下限與上限（主控判斷），是保護伺服器的技術限制，列進 §10 的「技術上下限」。
  - 例：匯入筆數可設 1–10000，出廠 1000。
- 存檔時超出範圍就擋下，訊息寫出允許範圍。

### 3.4 出廠預設值

等於目前程式寫死的值（§4 表格的「出廠」欄）。部署後沒人改設定時，行為與現在完全相同；既有測試不用改預期值。

附件（A20）目前可由部署設定檔 `Attachments` 節改單檔大小、每欄檔數、白名單（主控判斷）：

- 設定檔有寫的值就當作該環境的出廠值，蓋過程式內的出廠值，所以已部署環境上線後行為也不變。
- 管理員在畫面設過就以畫面為準。
- 設定檔的值也要在技術上下限內，超出就啟動時記 Warning 並夾到上下限。

### 3.4.1 任務通知收件人（A13）的形狀

- 每種任務事件各一個值，值是「收件角色」的組合（主控判斷）。
- 角色有兩種：負責人、建立者。指派與提到的收件人固定是被指派、被提到的那個人，不開放設定。
- 一律排除觸發事件的本人；留言時已被 @ 到的人不重複收「新留言」，沿用現行規則。
- 出廠值：

| 事件 | 收件角色 |
|---|---|
| 留言 | 負責人＋建立者 |
| 完成 | 建立者 |
| 取消 | 建立者 |

- 型別多一種「角色組合」，畫面是一排勾選框。

### 3.5 改嚴只管之後的新增（使用者裁決）

- 把上限調低時，既有資料保留不動，照常可看、可改其他欄位。
- 只有「再新增一筆」時用新上限擋下。
  - 例：一則留言已有 5 個附件，上限改成 3 之後不能再加第 6 個，也不能再加第 4 個；刪到剩 2 個之後才能再加 1 個。
  - 例：模組已有 20 條任務規則，上限改成 10 後仍可編輯既有規則，不能再新增。
- 編輯一筆既有資料時，不因它本來就超標而擋存檔；只有這次編輯**增加**數量才檢查。

非數量類的政策改了之後（主控判斷，同樣只管之後）：

- 副檔名白名單縮小：既有檔案照常可下載，只擋新上傳。
- 必填語系增加（政策「必填的多語文字要有哪些語系」，管所有必填多語文字，不只名稱）：只在新增記錄，或編輯時改到該多語文字欄位才檢查；只改其他欄位不擋。
- 營運時區改變（使用者 2026-11-12 確認）：只保證**記錄的日期時間欄位**保持原本的絕對時間、不重算；系統自記的時間（建立、修改、通知、歷程、簽核時間）不換算，沿用當時存的時刻。之後的顯示、前端「今天」（改用營運時區算）與報表的日期切點照新時區算。p3 的確認框要寫明：「改時區會讓今天、逾期、報表日期切點跟著變；記錄的日期時間欄位保持原本的絕對時間，系統自記的時間不換算」。
- 收件人或備援對象改變：只影響之後產生的通知與待簽，已送出的不動。

### 3.6 前端取用

- 前端從生效值 API 拿到該模組的生效值，用來顯示上限、灰掉新增按鈕、設預設值。
- 後端永遠再驗一次；前端顯示只是提示。

### 3.7 p2、p3 政策細則（使用者 2026-11-12 確認）

**p2**

- **A25 每列欄數**：區塊每列欄數上限是 S 政策，技術上限 4。調低上限後，既有區塊照原欄數顯示，只限制之後的設定；開啟套件時，區塊欄數超過上限就自動夾到上限，不報錯。
- **A19**：只有「名稱」欄位可以關；「基本資料」區塊一律建，因為模組至少要有一個區塊是完整性守衛，不是政策。
- **A16**：六種數量上限只在套件匯入或開啟時檢查，不影響既有模組的編輯；政策頁的說明要寫明這一點。
- **A22**：政策管「每來源模組事件數」，出廠 20。
- **A24**：報表「近 N 天」的上限只能調低，不能超過 3650。

**p3**

- **A17 時區**：存固定 UTC 偏移（例如 +08:00），不支援日光節約時間。改時區時的行為見 §3.5。前端「今天」改用營運時區算；改時區後，前端約每 60 秒重新取一次生效值，發現時區變了就提示使用者並重新整理頁面。
- **A18 語系**：「必填的多語文字要有哪些語系」管所有必填多語文字（政策原稱「名稱必填語系」）。預設語系、啟用語系、必填語系三個政策存檔時互相檢查：預設語系必須在啟用語系內、必填語系必須是啟用語系的子集。停用某語系後，語系選單與輸入框不再列出它，已存的該語系文字保留不刪。應用程式套件仍然要求繁中（zh-TW）。

## 5. 資料

- 全系統值：沿用既有的 `Dynamic_SystemSetting` 鍵值表，鍵為 `policy.<代碼>`（主控判斷）。沒有這筆就用出廠值。
- 模組覆寫：新增一張表 `Dynamic_ModulePolicy`，欄位為模組、政策代碼、值、最後修改者、最後修改時間；主鍵為模組＋政策代碼。整段只加這一個 migration。
- 值一律存字串，由登記項的型別解析；解析失敗視為沒設，用上一層的值並記 Warning（主控判斷），不讓壞值擋住整個系統。
- 模組刪除時，連同它的覆寫一起刪。

## 6. 讀值入口

- Domain 定義政策登記（代碼、型別、出廠值、上下限、範圍）。這是唯一寫出廠值的地方。
- Application 提供一個讀值服務：給政策代碼與（可選的）模組，回傳生效值；同一個 request 內快取。
- 現有各處常數（§4 檔案位置見盤點）改成呼叫讀值服務。Domain 的純函式需要上限時，由呼叫端把值傳進去，不讓 Domain 碰 IO。

## 7. API

（主控判斷，實作可調整命名）

| 方法 | 路徑 | 權限 | 用途 |
|---|---|---|---|
| GET | `/api/system/policies` | 系統管理員 | 全部政策：登記資訊、全系統值、出廠值 |
| PUT | `/api/system/policies/{code}` | 系統管理員 | 設全系統值；傳 null 表示回到出廠值 |
| GET | `/api/modules/{key}/policies` | 該模組設計權 | 可覆寫的政策：全系統值、覆寫值 |
| PUT | `/api/modules/{key}/policies/{code}` | 該模組設計權 | 設覆寫值；null 表示取消覆寫 |
| GET | `/api/policies/effective?module={key}` | 登入者 | 生效值（不含誰設的），給畫面用 |

- 設定 `system` 範圍的政策做模組覆寫，一律回 400。
- 寫入都走 `ITransactionalRequest`。

## 8. 畫面

- **系統管理 → 政策設定**（獨立頁，使用者 2026-11-12 確認）：依類別分組（任務、通知、附件、簽核、設計上限、匯入、事件、報表、地區與語系）。
  - 每列顯示政策名稱、說明、目前值、出廠值、允許範圍。
  - 改過的值旁邊有「恢復出廠值」。
- **模組設計 → 政策**：只列 `module` 範圍的政策。每列顯示全系統值，以及「沿用全系統」或「覆寫為 ___」。
- 存檔失敗時顯示允許範圍。四語文案，四種寬度不橫捲。

## 10. 可寫死清單

以下維持寫死。理由分三類：資料完整性、安全、技術限制。三類都已由使用者 2026-11-12 確認；其中補盤的 B28–B34 也確認維持寫死。

**資料完整性**

- 有唯讀或已記帳記錄時，不能改標題樣板（B1）。
- 由應用程式管理的模組不能單獨開關（B2）。
- 分錄只能沖銷，沖銷單不可再沖銷（B3）。
- 被引用的主檔不能刪；未關閉的應用程式不能刪（B4）。
- 規則產生的任務不能刪（B6）。
- 不能停用最後一位系統管理員（B21）。
- 事件不得循環；流程形狀只能是 sequence（B27）。
- 被任務規則引用的欄位不能停用（2026-11-11 裁決）。
- A9：開啟應用程式時自動打開任務；應用程式關閉時，它的規則不執行。
- 檢查的加總溢位超出 64 位元時擋寫入（B30，fail-closed）。
- 轉單互斥：兩人同時轉單，後到者回 409，不會超轉（B32）。
- 明細模組的權限沿用表頭模組（B33）。
- 整合狀態由開關、安裝、擁有者與夥伴是否開啟推導；含沖銷效果的整合有守衛（B34）。

**安全**

- 附件危險副檔名黑名單（A20，計畫判斷 14）：html、htm、xhtml、svg、js、mjs、exe、msi、bat、cmd、com、scr、ps1、sh、jar、vbs、dll、app、dmg、php、asp、aspx、jsp。白名單從「只有維運能改的設定檔」移到「系統管理員能在畫面改」，可改的人變多，所以含這些副檔名的值一律不合法：畫面存檔回 400 並列出被拒項目，部署設定檔的項目丟掉並記 Warning，上傳時再擋一次。出廠白名單本來就不含它們；要收這類檔案要改程式，不是改設定。
- 登入失敗降速、鎖定次數、輸入截斷（B16、B17）。
- 密碼最少 8 字（B18；客戶要自訂密碼政策時再升級成政策）。
- 登入 cookie 滑動 8 小時（B19；閒置逾時之後可考慮設定化）。
- 管理 API 的權限檢查（B22）。
- 列印範本的 HTML 標籤白名單（B14）。
- CSV 公式注入跳脫（B15）。
- 內建 admin 帳號（B25）。

**技術限制**

- 代碼格式（B7；檢查與轉換代碼同型，B28）、共用主檔前綴 `master-`（B26）。
- 檢查的聚合函式清單（B29）、索引回填每批 1000 筆（B31）。
- 簽核動作的內部常數、SQLite 寫入鎖逾時（補盤附註；寫入鎖在 PostgreSQL 下停用）。
- 文字長度：標題 200、說明 4000、留言 4000（B8）。
- 樣板、流水號、公式、條件的長度與深度（B9、B10）。
- 查詢：排序 3 欄、關鍵字 100 字、檢視欄位 50、分頁 50（B11、B12）。
- 刪除串聯深度 5（B5）。
- 套件大小 1MB、JSON 深度 32、格式版本範圍（B13）。
- 應用程式套件的 14 個數量上限（事件 100、檢查 100、轉換 50、報表 50、列印範本 100、欄位權限與選項範圍各 2000 等）與連動事件每套件總數 100：列為技術限制，維持寫死（使用者 2026-11-12 裁決）。
- 帳號格式、名稱長度（B20）。
- 提及候選 20 人、`@{id}` 語法（B23）。
- 圖表種類、時間桶、聚合函式（B24）：這些是平台功能清單，不是政策。
- 各政策的技術上下限（§3.3），只寫在 `PolicyCatalog`。p1a 已登記：
  - 每模組任務規則數 1–100（A1，出廠 20）。
  - 每條規則的任務數 1–50（A1，出廠 20）。
  - 套件內任務規則總數 1–500（A2，出廠 50；套件本身另受 1MB 限制）。

  p1c 已登記：
  - 到期前提醒天數 1–30（A6，出廠 1）。
  - 通知保留天數 1–3650（A14，出廠 90）。
  - 一週起始日：星期一到星期日七選一（A7，出廠星期一）。
  - 通知收件角色：只有負責人、建立者兩種選項（A13）；開放的事件只有留言、完成、取消三種，指派、提到、到期提醒的收件人固定（到期提醒為負責人）。

  p1d 已登記：
  - 附件單檔大小 1–52428800 位元組（A20，出廠 10485760）。
  - 每個附件欄位的檔案數 1–100（A20，出廠 20）。
  - 副檔名白名單 1–40 個，每個 `^[a-z0-9]{1,10}$`（A20，出廠 pdf、png、jpg、jpeg、webp、txt、csv、docx、xlsx、pptx；只能全系統設定）。
  - 每則任務留言的附件數 1–10（A20，出廠 5）。

- 格式不跟政策走：ISO 8601 週分桶鍵（如 `2026-W45`）維持寫死；A7 只決定「本週、上週、近 N 週」區間從哪天算起。

**可寫死清單（a2d 新增）**

資料完整性：

- 鎖定規則本身：哪些狀態、哪些欄位鎖、附件全鎖、以「請求開始前的狀態」判斷、解鎖只放行事件效果。
- 定義守衛：有進行中實例時，拒絕改寫值的定義，並保護轉移與狀態。
- 有記錄停留在鎖定狀態時，存狀態機不能把那些狀態變成不鎖定（裁決 8）。
- 有記錄停留在鎖定狀態、而且欄位在鎖定集合中有值時，不能刪除欄位或區塊（裁決 10）。
- 已記帳的單據不能增減附件（裁決 6）。
- 被收件人政策引用的群組不能刪。

安全：

- 系統身分略過轉移群組與簽核入口：平台不變式。
- 異常通知對象解析為空時，改送全部系統管理員。

技術限制：

- 收件人政策 1 到 20 項。
- 意見字數不超過 1000（資料庫欄位長度）。
- 主管層數技術上限 10，執行期主管鏈也只用這個上限。
- 期限時數不超過 8760。
- 每關人數技術上限 50（整關合計，來源加頂替的備援、去重後）；固定名單的關卡與任何頂替的備援，執行期只用這個上限（不受當下的每關上限管）。
- 刪群組的收件人守衛只檢查系統值與模組覆寫，部署設定檔層的出廠值不檢查。

## 11. ERP 對照

- 主流 ERP 都有集中的「系統參數」，加上依公司或模組的覆寫：
  - Odoo：設定頁加各模組設定；
  - SAP：customizing 依 company code；
  - 鼎新、正航：系統參數加模組參數。
- 本設計對應「系統參數＋模組參數」兩層，不做公司層：目前是單一公司。
- 主流 ERP 的參數也多半只影響之後的新單據，與 §3.5 一致。

## 12. 主控判斷彙整（可推翻）

1. 每個政策宣告範圍（只限全系統／可模組覆寫）。時區、語系、保留天數、組織層數、設計上限只限全系統。
2. 整數政策有寫死的技術上下限，管理員只能在範圍內調整。
3. 全系統值存既有的 `Dynamic_SystemSetting`；模組覆寫另開一張表。
4. 壞值（解析失敗）退回上一層的值並記 Warning，不擋系統。
5. 由應用程式管理的模組也能改覆寫。
6. 套件不帶政策覆寫（💡）。
7. A2 套件規則總數保留為獨立政策（出廠 50），維持上線行為不變；原本打算改沿用 A1，但那會讓原本被拒的套件變成可開啟。
8. 不做設定變更歷程，只在覆寫表記最後修改者與時間（💡）。
9. A7 逾期定義、A8 頁籤、A9 開關一致性不設定化，列進 §10。

### 實作期間的判斷（p1 計畫，可推翻）

以下是實作計畫自己決定、設計沒寫清楚的地方。完整理由與代價見 p1 實作計畫；p1a、p1b、p1c、p1d 已照做。

- 計畫判斷 2：API 沿用既有前綴 `api/v3/dynamic`（`system/policies`、`modules/{key}/policies`、`policies/effective`）。
- 計畫判斷 3：共用主檔模組的覆寫除了設計權 Edit，還要系統管理員，比照其他設計器寫入。
- 計畫判斷 4：生效值 API 只要求登入，不檢查模組讀取權；不存在的模組回 404。
- 計畫判斷 5（**使用者 2026-11-12 確認**）：政策設定做成獨立頁 `/system/policies`，選單名「政策設定」，排在「外觀預設」之後。使用者 2026-11-11 裁決的字面是「系統設定頁的政策分頁」，但 repo 沒有叫「系統設定」的頁面，系統管理是一組獨立頁；使用者 2026-11-12 確認政策頁就是獨立頁（系統管理 → 政策設定），不是系統設定頁的分頁。
- 計畫判斷 12：A2 是獨立的全系統政策，在匯入與開啟套件時檢查，不放在啟動時也會跑的靜態套件驗證。
- 計畫判斷 13：附件單檔大小以位元組存、畫面也以位元組編輯，旁邊附 MB 換算提示（部署設定檔本來就是位元組）。
- 計畫判斷 14：副檔名黑名單寫死（見 §10 安全類）。
- 計畫判斷 15：`AttachmentSettings` 縮成部署設定（路徑、上傳開關、原因）；`GET attachments/settings` 回應形狀不變，三個上限改回全系統值，需要模組值的畫面（任務留言輸入框）改讀生效值 API。
- 計畫判斷 16：上傳 filter 的順序改成「上傳開關 → 資格檢查（回傳該模組上限）→ 主體大小」；代價是 Content-Length 超大又沒權限的請求回 403／404 而不是 413。
- 計畫判斷 20：模組設計頁的「政策」分頁對明細模組隱藏。p1 的模組政策（任務規則、附件、提醒）對明細模組都無效；p2 的 A23 明細列上限是給明細模組的，到時要改條件。
- 計畫判斷 22（含 p1b 偏離 2）：前端不留上限的預設值，生效值載入前，受上限控制的「新增」鈕一律停用；p1b 進一步連任務規則的「編輯」鈕也停用、編輯對話框不掛載（對話框驗證需要 `maxTasks`）。代價：生效值 API 失敗時（頁面顯示載入失敗），既有規則也不能編輯，只剩停用與刪除。
- 計畫判斷 23：套件裡每條規則的任務數用 A1 的全系統值檢查（匯入與開啟時）；開啟建立規則時再依模組生效值檢查一次。
