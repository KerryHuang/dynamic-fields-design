## 1. 意圖與原因

簽核第一版（簽核設計，a1–a4b、a6 已上線）做的是「條件式依序關卡」：一條流程是一串關卡，每關可以有條件、不成立就跳過。這個形狀好驗證、好在手機上編輯，但有三個缺口：

1. **看不到全貌。** 設計者在對話框裡看到的是一串卡片，條件與跳過要逐張點開才知道；送簽人與簽核人在單據頁只看到文字時間軸，看不出「接下來還有哪幾關、為什麼走這條」。
2. **不能並行。** 「法務與財務同時看合約」只能用一關會簽、兩個群組近似（簽核設計 §16.1），兩邊各自要多關、或任一邊核准就夠的情況表達不了。
3. **不能分路。** 依金額走不同的人，只能靠「多個流程依優先序比對」或「關卡條件跳過」湊出來；路線一多，設計者自己都很難確定某張單會走哪條。

市場上的商用 BPM 都以流程圖解決這三件事：畫布上拖拉節點、連線，條件分支與並行分支直接畫出來，單據頁用同一張圖標示走到哪裡。使用者要求 Formwright 對標這個基本盤（§4 第 1 條）。

這份設計在第一版的地基上加「圖」：簽核仍然掛在狀態機的轉移上、流程仍然依優先序比對、版本與快照、重新比對、鎖定、權限都沿用；改的是一條流程內部的形狀，從「關卡串列」變成「節點與連線」。

## 2. 目標、非目標、反目標

**目標**

- 流程定義支援 `shape: graph`：節點（開始、簽核、條件、分支、匯合、結束、通知）與連線。
- 執行引擎依圖推進：條件分路、並行分支、兩種匯合、分支取消、退回、重新比對。
- 一個設計器：拖拉式流程圖設計器，取代現有的「關卡」卡片編輯；舊流程自動轉成直線圖。
- 單據頁用唯讀流程圖標示進度，保留文字時間軸。
- 通知節點：流程走到時發站內通知，內容可帶欄位值，不擋流程。
- 為「一條流程套多張單據」（流程範本＋欄位槽位）預留介面，細節另寫設計（§16）。
- 四種寬度可用：手機看圖與改節點屬性，平板以上完整編輯。

**非目標（這一版不做）**

- 迴圈（流程圖必須無環，§8.11）。
- 連線即按鈕：簽核節點只有核准、退回兩個動作，不讓設計者在節點上定義「同意 A／同意 B」等自訂結果（§4 第 9 條）。
- 節點層級的欄位權限（某節點的簽核人看得到、改得到哪些欄位）：第一版不做，簽核中單據維持唯讀，只保留既有的「可編輯欄位隨同意送出」（§4 第 10 條）。
- 通知節點發 Email、推播或對外 webhook：只發站內通知（§4 第 11 條）。
- 子流程、呼叫另一條流程、計時器節點、自動核准節點、指令碼節點。
- 流程範本與槽位對應的實作（§16 只寫方向）。
- 改寫第一版的動作語意（轉交、後加簽、代理、改派、終止的規則照簽核設計，只補並行情境下的定義）。

**反目標（絕對不能發生）**

- 圖形化讓單據少簽：任何結構錯誤、條件無法判斷、分支狀態不一致，一律落在「不放行」（fail closed），與簽核設計 §1.4 相同。
- 同一件事有兩個設計器：舊的卡片關卡編輯在流程圖設計器上線時移除（§4 第 6 條）。
- 進行中的單據因為升級而改走新定義：進行中實例照它的流程快照跑完。
- 前端驗證取代後端：設計器的即時檢查只是提示，發布時後端完整重驗。
- 業務政策寫死：分支數、節點數等上限走政策設定；能寫死的只有 §15 列出的完整性、安全、技術限制。

## 3. 限制

- **沿用簽核設計的全部約束**：簽核掛在狀態機轉移、流程掛在目標狀態並依優先序比對（§5.2）、流程快照與版本（§4.4）、每次同意重新比對（§5.5）、找不到人的備援（§6.5）、可編輯欄位不得影響條件（§9.2）、簽核鎖定依狀態判斷（§9.3）、每個動作一個交易（§8.1）。流程圖只改「一條流程內部的形狀」。
- **核心不寫 ERP 名詞**：節點型別是平台機制，不出現請假、採購這類詞。
- **空系統是合法起點**：流程圖、通知節點只依賴核心的狀態機、組織、群組與站內通知，不開任何應用程式也能用。應用程式關閉（模組 `Closed`）時照簽核設計 §8.6：所有簽核動作回 409、進行中實例保留，進度圖照常可看；重新開啟後從原位置繼續。由應用程式帶來的流程（a5 之後）開啟後屬於客戶，可在流程圖設計器改。
- **不做執行期 DDL**：新欄位只走 EF migration。
- **SQLite 與 PostgreSQL 都要能跑**：pg0 合併後的段要兩種資料庫都驗；並發正確性不能只靠 SQLite 的全庫寫入鎖。
- **前端技術棧**：Vue 3、Quasar、TanStack Query；新增的圖形函式庫要能放 Quasar 元件在節點裡、支援觸控、授權相容開源發行。
- **公開 repo**：文件與程式不出現公司名、商用 BPM 品牌名、個人路徑。
- **四種寬度**：手機 390、平板 820、筆電 1366、桌機 1920，頁面不得橫向捲動；畫布在自己的區塊內平移縮放，不算頁面捲動。斷點沿用 Quasar：小於 600 為手機、小於 1024 為平板（簽核設計 §20.4 第 31 條）。

## 4. 使用者已決定的部分（使用者決定）

以下 11 條使用者 2026-11-13 已拍板，本文照寫，不再討論：

1. 目標對標商用 BPM：流程圖顯示、拖拉式設計、一條流程套用多張單據，三項都要。
2. 「一條流程套多張單據」是讓不同單據共用同一條路線；做法是流程範本加欄位槽位對應（slot mapping），排在流程圖設計器之後。本文件只寫方向與介面預留（§16）。
3. 先做流程圖設計器。
4. 第一版節點：開始、簽核、條件、分支（並行拆開）、匯合、結束、通知。
5. 匯合支援「全部到齊」與「任一到齊」；任一到齊時其他分支自動取消；任何分支被退回，整張單退回。
6. 舊的順序關卡流程自動轉成直線圖，只留流程圖設計器一個設計器；進行中的單據照舊版定義跑完。
7. 手機（390 寬）只能看圖與改節點屬性（例如簽核人），不能新增節點或拉線；平板以上完整編輯。
8. 第一版就在單據頁用唯讀流程圖標示進度（已過、進行中、被退回上色），保留既有文字紀錄。
9. 簽核節點固定「核准／退回」兩個動作，分支一律靠條件節點依欄位決定；不做「連線即按鈕」。
10. 節點層級欄位權限第一版不做，列後續；簽核中單據維持唯讀。
11. 通知節點只發站內通知；對象可選使用者、角色、申請人、申請人主管；內容範本可帶欄位值。通知節點不擋流程。

第 9 條的解讀：「核准／退回」指簽核節點的**結果**只有這兩種，所以簽核節點只有一條出線（核准往下走），退回不畫線，照簽核設計 §7.3 處理（退回發起人或退回上一關，§8.4）。轉交、後加簽、撤回、代理、改派、終止這些「不產生結果」的動作照舊存在。

第 11 條的「角色」：Formwright 沒有獨立的角色實體，權限以群組為單位（使用者與群組設計），所以「角色」對應**群組**。

## 5. ERP 對照

主流 ERP 與商用 BPM 的簽核設計器有共通的節點集合：開始、結束、人工審核（會簽、或簽、依序）、條件分支（排他閘道）、並行分支（並行閘道）與匯合、抄送或知會。差異在兩處：一是審核結果是否可以自訂成多條出線（「連線即按鈕」），二是是否允許退回到任意節點與迴圈。

| ERP 情境 | 典型路線 | Formwright 流程圖 |
|---|---|---|
| 合約審閱 | 業務主管與法務同時看，都同意才生效 | 分支 → 兩個簽核節點 → 匯合（全部到齊） |
| 費用報支 | 部門主管或專案經理任一方核准即可，各自可能有兩層 | 分支 → 兩條各含多個簽核節點 → 匯合（任一到齊） |
| 採購單 | 一萬以下免簽、十萬以下採購主管、以上加總經理 | 條件節點三條出線，最低一級接結束 |
| 請假 | 主管核准後知會人事 | 簽核 → 通知（群組「人事」）→ 結束 |
| 付款申請 | 會計 → 主管 → 出納 | 直線三個簽核節點（舊流程轉換後就是這個形狀） |
| 製程變更 | 品保、生產、採購同時會簽，再由廠長核定 | 分支三條 → 匯合（全部到齊）→ 簽核（廠長） |
| 單據作廢 | 已核准的單作廢須主管同意，並知會財務 | 簽核 → 通知 → 結束，掛在「已核准 → 已取消」 |

取捨：

- **不做「連線即按鈕」**（使用者決定）：結果自訂會讓「這張單到底算核准還是退回」由圖決定，鎖定、狀態轉移、事件都要跟著變；分路改由條件節點依欄位決定，判斷依據寫在單據上、看得見也鎖得住。
- **不做迴圈**（U2）：ERP 的「退回重改」用退回發起人或退回上一關表達，不需要畫回頭線。
- **抄送**：簽核設計把抄送列在第二版候選；通知節點涵蓋「流程走到某處時知會某人」，這是 ERP 抄送最常見的用法。「抄送人可以看單據」的臨時讀取權不在範圍內（§12.5）。
- **多個流程依優先序比對保留**：ERP 慣例的「依金額選不同簽核策略」在流程圖裡可以用條件節點表達，也可以照舊用多個流程；兩者並存，設計器不強迫合併（§6.3）。

## 6. 概念與名詞

### 6.1 名詞

| 名詞 | 意思 |
|---|---|
| 節點（node） | 圖上的一個步驟，有型別與屬性 |
| 連線（edge） | 兩個節點之間的有向線 |
| 執行線（token） | 實例中一條正在推進的路徑；並行分支會同時有多條 |
| 分支段（branch） | 從分支節點的一條出線到對應匯合節點之間的範圍 |
| 並行區（parallel region） | 一個分支節點到它配對的匯合節點之間的全部節點 |
| 節點實例（node run） | 實例中某個節點實際被走到的一筆紀錄；沿用 `Dynamic_ApprovalStageRun` |

### 6.2 節點型別

| 型別 | `kind` | 停留 | 入線 | 出線 |
|---|---|---|---|---|
| 開始 | `start` | 否 | 0 | 1 |
| 簽核 | `approval` | 是，等任務 | 1 以上 | 1 |
| 條件 | `condition` | 否 | 1 以上 | 2 以上，恰一條預設 |
| 分支 | `fork` | 否 | 1 以上 | 2 以上 |
| 匯合 | `join` | 是，等分支 | 2 以上 | 1 |
| 結束 | `end` | 否 | 1 以上 | 0 |
| 通知 | `notify` | 否 | 1 以上 | 1 |

「入線 1 以上」代表允許**互斥路徑**（條件節點的不同出線）在同一個節點會合，不必另放匯合節點；並行分支的會合一律要用匯合節點（§9 G7）（技術類，主控決定，J1）。

### 6.3 與第一版的關係

- 流程表、版本表、實例、任務、歷程、代理都沿用；一條流程有一個 `DefinitionJson`，`shape` 決定內部形狀。
- 流程層的屬性（啟動條件 `when`、退回狀態 `rejectTo`、備援簽核人 `fallbackApprovers`、目標狀態、優先序）照舊在流程層，不搬進圖裡。啟動條件決定「這條流程接不接這張單」，條件節點決定「接了之後走哪條路」。
- 簽核節點的屬性就是第一版關卡的屬性（簽核人來源、會簽或簽、可編輯欄位、逾期時數、找不到人時），加上「略過條件」（§7.3）。

## 7. 資料模型

### 7.1 `DefinitionJson` 的 graph 格式草案

```json
{
  "shape": "graph",
  "when": { "all": [ { "field": 21, "op": "gte", "value": 10000 } ] },
  "rejectTo": 11,
  "fallbackApprovers": { "source": "group", "groupIds": [7] },
  "nodes": [
    { "id": "start", "kind": "start" },
    { "id": "mgr", "kind": "approval", "name": { "zh-TW": "直屬主管" },
      "when": null, "approvers": { "source": "manager", "level": 1 }, "mode": "any",
      "editableFields": [], "dueHours": 24, "onEmpty": "fallback" },
    { "id": "amount", "kind": "condition", "name": { "zh-TW": "金額分級" } },
    { "id": "split", "kind": "fork", "name": { "zh-TW": "法務與財務" } },
    { "id": "legal", "kind": "approval", "name": { "zh-TW": "法務" },
      "when": null, "approvers": { "source": "group", "groupIds": [5] }, "mode": "any",
      "editableFields": [], "dueHours": 48, "onEmpty": "fallback" },
    { "id": "fin", "kind": "approval", "name": { "zh-TW": "財務" },
      "when": null, "approvers": { "source": "group", "groupIds": [6] }, "mode": "any",
      "editableFields": [31], "dueHours": 48, "onEmpty": "fallback" },
    { "id": "merge", "kind": "join", "forkId": "split", "mode": "all" },
    { "id": "tell-hr", "kind": "notify", "name": { "zh-TW": "知會人事" },
      "recipients": [ { "kind": "group", "groupIds": [9] }, { "kind": "initiator" } ],
      "template": { "title": { "zh-TW": "{title} 已過主管核准" },
                    "body": { "zh-TW": "申請金額 {f:21}，請備查。" } } },
    { "id": "end", "kind": "end" }
  ],
  "edges": [
    { "id": "e1", "from": "start", "to": "mgr" },
    { "id": "e2", "from": "mgr", "to": "amount" },
    { "id": "e3", "from": "amount", "to": "split", "order": 1, "label": { "zh-TW": "十萬以上" },
      "when": { "all": [ { "field": 21, "op": "gte", "value": 100000 } ] } },
    { "id": "e4", "from": "amount", "to": "tell-hr", "default": true, "label": { "zh-TW": "其他" } },
    { "id": "e5", "from": "split", "to": "legal" },
    { "id": "e6", "from": "split", "to": "fin" },
    { "id": "e7", "from": "legal", "to": "merge" },
    { "id": "e8", "from": "fin", "to": "merge" },
    { "id": "e9", "from": "merge", "to": "tell-hr" },
    { "id": "e10", "from": "tell-hr", "to": "end" }
  ]
}
```

頂層屬性：

- `shape`：`sequence` 或 `graph`。`graph` 時有 `nodes`、`edges`，沒有 `stages`；`sequence` 時反之。
- `when`、`rejectTo`、`fallbackApprovers`：與第一版相同。

### 7.2 節點屬性

共同屬性：`id`（流程內唯一，`^[a-z][a-z0-9-]{0,39}$`，與第一版關卡代號同格式，轉換時直接沿用）、`kind`、`name`（多語系；開始與結束可省略，畫面用固定文字）。

- **`approval`**：`when`、`approvers`、`mode`、`editableFields`、`dueHours`、`onEmpty`，語意與驗證同第一版關卡（簽核設計 §4.3、§6、§9.2）。
- **`condition`**：只有共同屬性；分路條件放在出線上（§7.4）。
- **`fork`**：只有共同屬性。
- **`join`**：`forkId`（配對的分支節點）、`mode`：`all`（全部到齊）或 `any`（任一到齊）。新放的匯合節點預設 `all`（較嚴格的一邊，列 §15）。
- **`notify`**：`recipients`（1 到 20 項，見 §12.1）、`template.title`、`template.body`（多語系範本，見 §12.2）。
- **`start`、`end`**：只有共同屬性。

`forkId` 明寫而不是由圖推導（技術類，主控決定，J2）：推導本身就是驗證的一部分，明寫讓驗證器檢查「設計者以為的配對」與「圖的結構」一致，執行引擎也不必每次重算配對。設計器在拉出匯合節點時自動填入。

### 7.3 簽核節點的「略過條件」

簽核節點保留第一版關卡的 `when`：不成立就略過這個節點、直接沿出線往下走，記一筆 `skip`（`SkipReason = condition`）。設計器在節點上顯示「有略過條件」標記（U1，使用者裁決 2026-11-13）。

理由：第一版的關卡條件要原樣轉成直線圖（§4 第 6 條）。若把每個關卡條件都改寫成一個條件節點加兩條線，舊流程會變成一串菱形，不是「直線圖」，設計者也認不出自己原本的流程。代價是「要不要走這個節點」有兩種畫法（略過條件、條件節點），設計器的屬性面板會註明「要依欄位走不同的人，請用條件節點」。

### 7.4 連線屬性

- 共同：`id`（流程內唯一，同節點代號格式）、`from`、`to`、`label`（選填多語系，畫在線上）。
- 只限條件節點的出線：`when`（核心既有的規則條件語法）、`order`（比對順序，正整數，同一個條件節點內唯一）、`default`（恰好一條為 `true`，沒有 `when`、不參與排序）。

分路條件放在線上而不是條件節點內（技術類，主控決定，J3）：畫面上條件就寫在它控制的那條線旁，設計者一眼看得出「這條線什麼時候走」；刪線時條件跟著消失，不會留下指向不存在出線的孤兒條件。

### 7.5 版面資訊不進定義

節點座標與畫布視角存在版本表的新欄位 `LayoutJson`，不放進 `DefinitionJson`（技術類，主控決定，J4）：

- 版本一經使用就不可變（簽核設計 §4.4）。若座標在定義裡，被用過的流程只是挪一下節點也要開新版本，進行中實例的數量提示會一直跳。
- `LayoutJson` 是非語意資料：可以原地改寫、不參與「定義有沒有變」的比對（`ApprovalDefinitionJson.SameAs`）、不進流程快照、不影響執行。
- 單據頁進度圖依實例綁定的 `FlowVersionId` 讀它；沒有就由前端自動排版（舊流程轉換、套件匯入、手動清掉都會沒有）。

### 7.6 資料表變更

一次 EF migration `ApprovalGraph`，全部是可為空或有預設值的新欄位，不改既有資料：

| 資料表 | 變更 |
|---|---|
| `Dynamic_ApprovalFlowVersion` | 加 `LayoutJson` |
| `Dynamic_ApprovalFlow` | 加 `DraftJson`（只含定義與版面，§10.8）、`DraftUpdatedBy`、`DraftUpdatedTime` |
| `Dynamic_ApprovalStageRun` | 加 `NodeKind`、`InEdgeId`、`CloseReason`；`BranchKey` 放寬到 256 |
| `Dynamic_Notification` | 加 `DataJson` |

`Dynamic_ApprovalStageRun` 已預留 `NodeId`、`BranchKey`（第一版不寫入，程式與設計 §16.2 一致）。graph 實例開始寫入：

- **每個被走到的節點都寫一列**（技術類，主控決定，J5），不只簽核節點。條件、分支、通知、結束是瞬間通過的節點，狀態直接是 `passed`；匯合節點在等分支時是 `waiting`。理由：進度圖要知道每個節點走過沒有、每條線走過沒有，從同一張表讀最直接；歷程也看得到「條件節點走了哪條線」。
- `NodeId`：節點代號。簽核節點的 `StageCode` 也寫節點代號，讓既有以 `StageCode` 查定義、查發起人自選（`Picks`）的程式繼續成立。
- `NodeKind`：節點型別；sequence 實例為 null。
- `InEdgeId`：執行線是從哪條線進來的；進度圖據此標出走過的線。
- `BranchKey`：執行線所在的分支段，格式是從外到內、每層分支節點出線代號以 `/` 串接（例如 `e3/e9`），根段為空字串。分支巢狀上限 5 層、代號上限 40 字，所以放寬到 256。
- `Status` 增加 `passed`、`waiting`；被「任一到齊」取消的分支，節點實例改 `closed`，`CloseReason = branchCancelled`；整張單結束時一併關閉的，`CloseReason = instanceEnded`。

程式現有的 `ApprovalStageStatus.Queued`（後加簽排隊用）不在簽核設計 §4.3 的狀態清單裡，屬於文件落後；本設計照程式，`queued` 保留。

### 7.7 版本與舊版相容

- `shape` 是定義的分派鍵：讀到 `sequence` 走第一版路徑，讀到 `graph` 走圖引擎。兩種形狀的流程版本、快照可以同時存在於同一個資料庫。
- **進行中的實例照舊版定義跑完**（使用者決定）：實例只讀自己流程快照裡的定義（簽核設計 §4.4），快照裡是 `sequence` 就一路用第一版引擎，包含重新比對後重來的新實例（新實例沿用舊快照）。
- 新送出的單：流程目前版本是什麼形狀就用什麼形狀。§13 的批次轉換做完後，所有目前版本都是 `graph`，第一版引擎只剩進行中實例在用。
- 鎖定欄位（簽核設計 §9.3）取「所有流程、各版本」的聯集，兩種形狀都要讀：`FieldClosure.DirectFields` 對 `graph` 收集流程啟動條件、簽核節點的略過條件與 `userField`、條件節點出線的 `when`、可編輯欄位。通知範本引用的欄位不影響路線，**不**納入鎖定與閉包。
- 「被用過」的定義、改版規則、刪除與停用規則全部照第一版。

### 7.8 sequence → graph 轉換規則

轉換是純函式（Domain），無損、可重複執行、結果穩定：

1. 建 `start`（代號 `start`）與 `end`（代號 `end`）。若某個關卡代號剛好是 `start` 或 `end`，開始、結束節點改用 `start-0`、`end-0`，依此遞增到不衝突為止。
2. 每個關卡依原順序轉成一個 `approval` 節點：`id = code`，`name`、`when`、`approvers`、`mode`、`editableFields`、`dueHours`、`onEmpty` 原樣搬過去（含開啟套件時寫入的 `UnmatchedGroups`、`CandidatesUnmatched`）。
3. 依序連線：`start → 第 1 關 → … → 最後一關 → end`，連線代號 `e1`、`e2`… 依序編號。
4. 頂層 `when`、`rejectTo`、`fallbackApprovers` 原樣保留，`shape` 改 `graph`。
5. 不產生 `LayoutJson`，由前端自動排版成由上而下的直線。

等價性：直線圖上，「下一關」「被條件跳過的關卡」「最近一個已同意的關卡」「後加簽插在目前關卡之後」與第一版完全一一對應，所以新送出的單在轉換前後走的路、找的人、重新比對的結果都相同。這是 §14 的必測項（同一組情境跑兩種形狀，結果逐筆相同）。

轉換的觸發點：設計器打開 `sequence` 流程時（後端回傳轉換後的圖，§10.7）、§13 的批次轉換、匯入或開啟舊格式套件時。

## 8. 執行語意

### 8.1 推進模型

一個 graph 實例同時可以有多條執行線。執行線只會停在兩種地方：**進行中的簽核節點**（節點實例 `active`，等任務）與**等待中的匯合節點**（`waiting`，等其他分支）。其他節點都是瞬間通過，在同一個交易內一路走完。

所以實例的「目前位置」不必另存，就是所有 `active` 與 `waiting` 的節點實例；`CurrentStageRunId` 繼續當快取，graph 實例填 `Seq` 最小的那個 `active` 節點實例（沒有就 null）。程式中所有讀 `CurrentStageRunId` 當作「唯一目前關卡」的地方（目前約 14 處）都要改成讀 `active` 節點實例的集合，這是 fg2 的主要改動面。

### 8.2 推進演算法

「從某節點沿某條線往下走」（`Advance(edge, branchKey)`），在同一個交易內：

1. 依 `edge.to` 取得目標節點，寫一列節點實例（`InEdgeId = edge.id`、`BranchKey`、`Seq` 遞增）。
2. 依型別處理：
   - **`approval`**：先求略過條件；不成立寫 `skipped`（`condition`），沿出線繼續。成立就照第一版解析簽核人（簽核設計 §6）：整關為空且 `onEmpty = skip` 寫 `skipped`（`empty`）並繼續；解析失敗回 409、整筆回滾；否則建任務、`active`，這條執行線停住。
   - **`condition`**：依 `order` 由小到大求出線的 `when`，取第一條成立的；都不成立走預設線。寫 `passed`，沿選中的線繼續。
   - **`fork`**：寫 `passed`，依出線在定義中的順序，每條出線各開一條執行線，`BranchKey` 加上該出線代號，逐一推進。
   - **`join`**：見 §8.3。
   - **`notify`**：解析收件人、套範本、寫通知（§12），寫 `passed`，沿出線繼續。通知相關的任何問題都不讓這一步失敗（§12.4）。
   - **`end`**：寫 `passed`。結構驗證保證走到結束時沒有其他執行線（§9 G8），所以實例核准，照第一版執行轉移（簽核設計 §8.2 的 `CompleteAsync`：事件、分錄、檢查同一交易）。
3. 推進途中任一步失敗，整個動作回滾（與第一版的「推進中的失敗」相同，簽核設計 §6.5 末段）。

送出時從 `start` 的出線開始推進；簽核節點完成（或簽任一人同意、會簽全部席位滿足）後，沿它的出線推進。

逐條處理分支出線的順序固定為定義中的順序（技術類，主控決定，J6），讓同一份定義、同一組資料永遠得到相同的節點實例順序，測試可重現。

### 8.3 並行分支與兩種匯合

執行線到達匯合節點時：

- 這個匯合節點在本實例中第一次被到達（同一個並行區、同一輪），建一列 `waiting` 的節點實例，記下已到達的分支。
- **全部到齊（`all`）**：配對的分支節點所開出的每一條分支都到達後，匯合節點改 `passed`，以分支節點所在的 `BranchKey`（外層）沿出線繼續。分支內走了哪條路、有沒有經過簽核節點都不影響「到達」的判斷。
- **任一到齊（`any`）**：第一條到達的分支讓匯合節點立刻 `passed` 並繼續；同一個並行區內其他分支**自動取消**（使用者決定）：
  - 其他分支上所有 `active`、`waiting`、`queued` 的節點實例改 `closed`（`CloseReason = branchCancelled`），巢狀在裡面的分支一併取消。
  - 這些節點上 `open` 的任務改 `closed`，失去臨時讀取權（簽核設計 §10.1）。
  - 歷程記一筆 `branch-cancelled`，說明「分支「{名稱}」已完成，其他分支自動取消」。
  - 被取消任務的負責人不另發通知；簽核中心與詳情頁對已關閉任務顯示「其他分支已完成，不需處理」（U5，使用者裁決 2026-11-13）。與或簽「已由他人處理」的做法一致，避免一張單一次發出好幾則「不用簽了」。
- 送出當下某條分支就已經能到達匯合（分支內沒有簽核節點、或略過條件都不成立），任一到齊會立刻通過、取消其他分支。這是語意的直接結果；設計器在發布時對「任一到齊的並行區裡有分支可能不經簽核就到達」顯示**警告**，不擋發布（U13，使用者裁決 2026-11-13）。

### 8.4 退回

- **退回發起人**：任何分支上的任何簽核節點退回發起人，**整張單退回**（使用者決定）。實例 `rejected`，所有執行線關閉（`CloseReason = instanceEnded`），其他分支已經核准的結果作廢但保留在歷程；記錄照第一版轉到 `rejectTo`（簽核設計 §7.3、§8.3）。
- **退回上一關**（U3，使用者裁決 2026-11-13）：退到**同一分支段內**、這條執行線上最近一個已核准的簽核節點，重新啟動它（新節點實例、重新解析簽核人），從那裡往下重新推進（途中的條件重新求值）。
  - 「同一分支段」是指 `BranchKey` 相同，而且在最近一次進入這個分支段（分支節點或匯合節點）之後。
  - 分支內第一個簽核節點、匯合後第一個簽核節點，沒有「上一關」，只能退回發起人；畫面上「退回上一關」停用並說明原因。
  - 不做「退回到分叉之前」：那會讓其他正在簽的分支同時作廢重跑，簽核人在自己的分支按退回卻影響別人，代價大、語意難懂；真要整條重來就退回發起人。
  - 被略過的簽核節點不算上一關（同第一版）。
  - 並行區外（根段）的行為與第一版完全相同。

### 8.5 撤回

發起人在**所有進行中的簽核節點都還沒有任何人同意或退回**時可以撤回（U4，使用者裁決 2026-11-13）。這是第一版「目前關卡還沒有任何人動作」（簽核設計 §7.4）在多條執行線時的延伸，兩者等價：只看目前 `active` 的簽核節點。

- 已經通過的前面節點（含分支內前一關已核准）不影響撤回資格，與第一版「已經通過的前面關卡不影響撤回資格」相同。
- 某條分支已經到達「全部到齊」匯合、停在 `waiting` 等其他分支，這條分支不影響撤回資格；它已經沒有進行中的簽核節點。
- 被「任一到齊」取消掉的分支不列入判斷。
- 撤回後實例 `withdrawn`，所有執行線關閉（`CloseReason = instanceEnded`），記錄狀態不動，同第一版。

### 8.6 終止與其他動作

- **終止**（簽核管理員）：實例 `cancelled`，所有執行線關閉，同第一版。
- **轉交、改派、代理**：以任務為單位，與分支無關，照第一版。同一節點內「一人一票」的限制照舊；同一人在兩條並行分支各有一個任務是合法的，各簽各的（延續第一版「同一人連續出現在兩關不自動略過」）。
- **後加簽**：加簽節點實例排在目前節點完成之後、沿出線推進之前，`BranchKey` 與目前節點相同；加簽完成後才沿出線繼續。加簽總數上限照第一版（一個實例至多 5 個）。
- **逾期提醒**：以簽核節點為單位，照第一版。

### 8.7 重新比對（每次同意）

第一版的規則（簽核設計 §5.5）不變：每次同意在推進之前，用當下的記錄值、只看流程快照，重新算這張單「應走的路線」，不同就這次同意不計入、從頭重來。graph 的「路線」定義為（技術類，主控決定，J7）：

1. 流程與版本：同第一版。
2. 已經 `skipped`（`condition`）的簽核節點，略過條件重算後變成立，算路線不同（同第一版，「多簽不算少簽」：已核准節點的條件變不成立，不算不同）。
3. **已經通過的條件節點**，用當下的值重算後選中的出線**不同**，算路線不同。不分哪條比較嚴：條件節點的出線之間沒有一般性的嚴格順序，有疑慮就重簽（簽核設計 §21 總原則）。
4. 被「任一到齊」取消的分支上的節點不參與比較（那些分支已經不是這張單的路線）。

代價：簽核中靜默變動的欄位（跨模組彙總、時間條件）若剛好跨過條件節點的門檻，即使改走的那條路比較寬鬆，也會整張重簽。可編輯欄位不得影響任何條件（§9 G11），所以簽核人自己改的值不會觸發這種重來。列 §18 已知限制。

### 8.8 條件節點沒有符合路徑

- **結構上不會發生**：每個條件節點必須恰有一條預設線（§9 G6），條件都不成立就走預設線。
- **條件無法判斷**（引用的欄位或選項已不在）：照第一版主控裁決（簽核設計 §20.4 第 16 條），不當成立也不當不成立，動作回 409、整筆回滾，並登記異常通知給異常通知對象（政策 A11）。不可以退回走預設線：預設線常常是「小額直接通過」。
- **定義缺預設線**（例如繞過驗證的資料）：執行時再驗不過，回 409 並通知管理員（同簽核設計 §5.2 末段的執行期再驗）。

簽核節點的略過條件無法判斷時照第一版：視為成立、不略過（寧可多簽一關）。

### 8.9 送出前預覽與發起人自選

- 預覽沿用第一版的揭露規則（簽核設計 §5.4）：只回節點名稱與目前解析到的簽核人，不回條件內容與略過理由。graph 的預覽多回「預計路徑」：依送出當下的值，標出預計會走到的節點與線；引用了發起人看不到的欄位的條件節點，它之後的路徑標「依條件決定」，不標選哪條。
- 發起人自選（`initiatorPick`）：送出時要求**定義中所有**自選簽核節點都選好人，不論預計會不會走到，與第一版要求所有自選關卡一致（技術類，主控決定，J8）。理由：退回上一關或資料變動可能讓路線改變，到時發起人不在場；而只問預計路徑上的節點，等於向發起人透露了條件的結果。

### 8.10 匯合與通知的冪等

同一個交易內同一個節點可能被到達多次（兩條互斥路徑會合處不會，但「全部到齊」的匯合會被每條分支到達一次）。匯合節點以「本實例、本並行區這一輪」唯一一列 `waiting` 實例為準，重複到達只更新已到達的分支清單。退回上一關讓分支段重跑時，該分支已到達的紀錄撤回，等它再次到達。

### 8.11 迴圈

不允許（U2，使用者裁決 2026-11-13）。流程圖必須是有向無環圖，發布時驗證（§9 G5）。

理由：無環保證每張單一定會在有限步內結束，驗證器能完整檢查所有路徑（每條路徑都有預設、都到得了結束、並行區配對正確）；「改了再送」的需求已由退回發起人、退回上一關涵蓋。允許迴圈就必須再加「最多繞幾圈」的上限與「繞回來時前面的核准算不算數」的規則，商用 BPM 常見的「退回到任意節點」也會讓鎖定與重新比對的推理變得不可驗證。

### 8.12 通知節點的推進

通知節點不擋流程（使用者決定）：它在推進途中寫通知、立刻沿出線繼續。重新比對後從頭重來、或退回上一關讓路徑重跑時，再次經過通知節點**會再發一次**；觸發這次推進的人若在收件人裡，照樣收到（U10，使用者裁決 2026-11-13）。理由：通知內容帶的是當下的欄位值，重跑時值可能已經不同；收件人是設計者明確指定的，系統不替他過濾。

### 8.13 併發

第一版的動作請求帶**實例**的 `rowVersion`（簽核設計 §8.4），或簽兩人同時同意時後到者 409。並行分支下，法務同意會換掉實例的 `rowVersion`，財務手上的畫面就過期了，財務按同意會收到不該有的 409；兩條分支同時抵達「全部到齊」匯合時，若各自只看到自己到了，兩邊都不會推進。改成**同一張單的動作逐筆處理**（技術類，主控決定，J18，取代初稿的 J9）：

- **以實例為單位序列化**：graph 實例的每個動作在交易一開始，先對實例列做條件更新（`WHERE Id = … AND RowVersion = 讀到的值` 換新值）取得這張單的處理權。條件更新失敗代表同一張單剛有別的動作提交，後端在伺服器內重新讀取、自動重試，次數上限是技術限制（§15）；重試用完才回 409「單據正忙，請稍後再試」。只鎖單一實例，不是全庫鎖。
- **分支上的同意不比對畫面的實例 `rowVersion`**：同意、退回、轉交、後加簽只要求「自己的任務仍是 `open`」，任務是否 `open` 在取得處理權之後才判斷。所以法務先同意、財務後同意，財務不會因為畫面舊而收到 409。
- **同一節點的競爭照舊 409**：或簽兩人同時同意，後取得處理權的那個發現任務已經 `closed`，回 409「這一關已由他人處理」。分支被「任一到齊」取消、或整張單已被退回時，晚到的動作同樣在取得處理權後發現任務已關閉，訊息依 `CloseReason` 說明「其他分支已完成」或「單據已退回」。
- **匯合判斷在處理權內做**：到達匯合、檢查是否到齊、推進，都在同一個序列化區段內完成，兩條分支同時抵達時一定有一個看得到另一個已到達，不會兩邊都不推進。
- **實例層動作仍比對畫面的版本**：撤回、終止這類以整張單為對象的動作，帶畫面讀到的實例 `rowVersion`；讀取之後有任何分支動作過（版本已變），回 409「單據已有變動，請重新整理」，不自動重試。理由：撤回資格（§8.5）取決於當下各分支的狀態，發起人看到的畫面過期就不該替他決定。
- 不需要節點實例層的 `RowVersion`，§7.6 的資料表變更因此不加這個欄位。
- 正確性不依賴 SQLite 的全庫寫入鎖：SQLite 與 PostgreSQL 都靠實例列的條件更新；兩種資料庫都要有並發測試（§14）。
- `sequence` 實例維持第一版的實例層 `rowVersion` 比對，不改。

### 8.14 可編輯欄位在並行區

兩條並行分支的簽核人若都能改同一個欄位，後寫的人會蓋掉前一個人的值，而前一個人以為自己的數字已經生效。所以**同一個並行區內不同分支的簽核節點，可編輯欄位不得重疊**（§9 G12）。其他限制照第一版（簽核設計 §9.2）。

## 9. 發布前驗證規則

規則在發布（或沒有草稿機制時的存檔）時由後端完整檢查，錯誤鍵以代號定位：`nodes.{id}.{屬性}`、`edges.{id}.{屬性}`、`graph`（整體結構），讓設計器能把錯誤標在對應的節點或線上（技術類，主控決定，J10）。前端以同一組規則即時提示，規則的判斷案例放在 `poc/shared/approval-graph-cases.json`，前後端測試都跑（沿用 `rule-cases.json` 的做法）。

- **G1 節點與線的基本形狀**：代號格式與唯一性；`kind` 在列舉內；每條線的 `from`、`to` 指向存在的節點；沒有自己連自己；同一對節點之間沒有重複的線。
- **G2 開始與結束**：恰一個開始節點；至少一個結束節點；各型別的入線、出線數量符合 §6.2。
- **G3 可達**：每個節點都能從開始到達。
- **G4 可結束**：每個節點都能到達某個結束節點，沒有死路。
- **G5 無環**：圖是有向無環圖（§8.11）。
- **G6 條件節點**：出線至少 2 條；恰一條預設線；其餘每條都有合法的 `when`（核心條件語法、引用存在且啟用中的欄位）與同節點內唯一的 `order`；預設線不得有 `when`。非條件節點的出線不得有 `when`、`order`、`default`。
- **G7 分支與匯合配對**：每個分支節點恰有一個匯合節點以 `forkId` 指向它，反之亦然；並行區是單一入口、單一出口：從分支節點出發的每條路徑都必須先經過配對的匯合節點才能到結束，匯合節點的每條入線都來自自己的並行區內，並行區內的節點不能有線連到區外（匯合節點的出線除外）、區外的線也不能連進區內（分支節點的入線除外）。並行區可以巢狀，必須完整包含，不能交錯。
- **G8 結束不在並行區內**：任何結束節點都不能位於並行區內（否則一條分支結束時其他分支還在跑，語意不明）。
- **G9 簽核節點**：屬性驗證同第一版關卡（簽核設計 §4.3、§6.1、§9.2；`ApprovalDefinitionValidator` 的既有規則逐條沿用）。
- **G10 通知節點**：收件人 1 到 20 項、每項的參數合法（使用者啟用中、群組存在、主管層級在政策上限內）；範本語法正確、引用的欄位存在（§12.2）。
- **G11 可編輯欄位不影響條件**：可編輯欄位不得被同一目標狀態上任何流程的啟動條件、簽核節點略過條件、條件節點出線條件、`userField` 來源直接或間接引用；閉包規則同第一版（簽核設計 §9.2）。
- **G12 並行區內可編輯欄位不重疊**（§8.14）。
- **G13 數量上限**：簽核節點數不超過政策「簽核節點數」（沿用 `approval.maxStages`，§15）；每個分支節點的出線數不超過政策「每個分支的分支數」；節點總數、線總數、分支巢狀層數不超過技術上限（§15）。
- **G14 入口約束照舊**：簽核設計 §5.2 的入口一致性、鎖定、`rejectTo` 等跨流程約束，在儲存狀態機、發布流程、改目標狀態時照樣重算。

警告（顯示但不擋發布）：

- **W1**：任一到齊的並行區中，有分支可能不經任何簽核節點就到達匯合（§8.3，U13）。
- **W2**：條件節點的預設線直接接結束、而且沒有經過任何簽核節點（常見於「小額免簽」，提醒設計者確認是刻意的）。
- **W3**：簽核節點同時有略過條件、又位於條件節點的某條出線上（兩種分路畫法混用，提醒設計者檢查）。

版面資訊（`LayoutJson`）不驗證語意，只檢查格式、大小與節點代號都存在；多出來的座標直接丟掉。

## 10. 前端設計器

### 10.1 流程圖函式庫（技術類，主控決定，J11）

評估四個方向：

| 方向 | 與 Vue 3 整合 | 節點放 Quasar 元件 | 觸控 | 授權 |
|---|---|---|---|---|
| Vue Flow | 原生 Vue 3 元件 | 可以，節點就是 Vue 元件 | 平移、縮放、拖曳 | MIT |
| 框架無關的圖形編輯引擎（附 Vue 包裝） | 要透過包裝層 | 要另外掛載，事件與響應式要自己橋接 | 依引擎 | 多為 MIT，部分進階功能收費 |
| 流程圖專用開源引擎（自帶節點樣式與流程標準記號外掛） | 要透過包裝層 | 受限於引擎的節點模型 | 依引擎 | 開源 |
| 自刻 SVG 畫布 | 完全自主 | 可以 | 全部自己做 | — |

**建議 Vue Flow。** 理由：

- 節點是 Vue 元件，簽核節點裡的簽核人摘要、徽章、驗證錯誤可以直接用 Quasar 元件與既有的 i18n、語意色彩 token，不必在兩套元件模型之間搬資料。
- 狀態是 Vue 的響應式資料，與 TanStack Query、設計器既有的草稿與伺服器狀態分離做法（簽核設計 §20.4 第 45 條）相容。
- 同一個函式庫可以用唯讀模式做單據頁進度圖（§11），不必再引入第二套。
- 授權寬鬆，核心功能（平移縮放、拖拉、連線、小地圖、控制列）都在開源範圍。

風險與對策：

- **觸控連線**：拖曳把手連線在觸控上不好用。平板改用「點出發點、再點目標」的連線模式，以及在線上的「＋」插入節點（§10.5）；實作第一步先在 820 寬的觸控裝置上做技術驗證，不行再退回只用「＋」插入（⚠️ 未驗證）。
- **體積**：只在設計器頁與詳情頁的進度圖動態載入，不進主包；實作時量測 build 體積增加量並寫進該段的回報。
- **版本**：鎖定確切版本，不用範圍版本。

自動排版不引入圖形排版函式庫（技術類，主控決定，J12）：發布規則保證圖是「並行區正確巢狀」的無環圖，用遞迴的分層排版（主幹由上而下、分支段左右展開、匯合置中）就足夠，邏輯放在前端 `domain`，可單元測試。實作者若發現品質不足，再評估現成函式庫。

### 10.2 頁面與進入點

- 模組設計頁的「簽核流程」分頁（a4a）保留：依目標狀態分組的流程卡片、啟停、優先序、刪除。
- 點流程卡片的「編輯」或「新增流程」，進入**全螢幕的流程圖設計頁**（獨立路由，帶模組代號與流程代號），取代原本流程編輯對話框的「關卡」段（技術類，主控決定，J13）。畫布需要整個視窗，對話框裡放不下。
- 設計頁三個區域：上方工具列、左側節點面板、中間畫布、右側屬性面板。原對話框的「基本」（名稱、目標狀態、啟動條件、退回狀態、備援）移到屬性面板：點畫布空白處就顯示流程層屬性。「試算」移到工具列，結果疊在畫布上。

### 10.3 畫布與節點面板

- **節點面板**：七種節點的圖示與名稱（開始節點固定一個，不在面板裡）。從面板拖到畫布放置；拖到線上就插在那條線中間。
- **拉線**：從節點的出線把手拖到另一個節點的入線把手；不合法的連線（例如連到開始、從結束拉出、簽核節點第二條出線）在拖曳時就不給放。
- **線上「＋」**：滑鼠移到線上（觸控時選取線）出現「＋」，點了選節點型別，直接插入。這是觸控裝置上新增節點的主要方式。
- **分支節點**：新放一個分支節點時，自動帶出配對的匯合節點與兩條空分支，避免設計者畫出不配對的分支。刪除分支節點時一併詢問是否刪除配對的匯合。
- **選取與刪除**：點選節點或線；Delete 鍵或工具列刪除。開始節點不能刪。
- **復原、重做**：前端操作歷史，至少保留最近 50 步（畫面行為，不屬於政策）。
- **工具列**：復原、重做、整理排版、縮放到全圖、驗證、試算、儲存草稿、發布（後兩者依 U6 而定）。
- **驗證標示**：有錯的節點或線加紅框與錯誤數徽章；工具列「驗證」展開錯誤清單，點一項就把畫布移到那個節點並打開屬性面板。警告用黃色。
- **節點外觀**：用語意色彩 token 區分型別，不靠顏色單獨傳達（另有圖示與文字）；簽核節點顯示名稱、簽核人來源摘要、會簽或簽、有略過條件的標記；條件出線顯示 `label`，沒有 `label` 時顯示條件摘要。
- **小地圖**：桌機與筆電預設顯示，平板預設收起。

### 10.4 屬性面板

依選取的對象切換：

- **流程層**（沒選任何東西）：名稱、代號、目標狀態、啟動條件、退回狀態、備援簽核人；照 a4a 現有的欄位與驗證。
- **簽核節點**：名稱、略過條件（條件編輯器）、簽核人來源（重用 `ApproverSourceEditor`）、會簽或簽、可編輯欄位（只列符合規則的欄位）、逾期時數、找不到人時。與 a4a 的關卡卡片相同，搬進面板。
- **條件節點**：名稱，加上出線清單：每條出線的標籤、條件（條件編輯器）、順序（上移、下移），預設線固定在最後、不能設條件。
- **分支節點**：名稱、分支清單（只讀，提示「要新增分支，請從分支節點再拉一條線」）。
- **匯合節點**：模式（全部到齊、任一到齊），選任一到齊時說明「第一條分支到達後，其他分支自動取消」。
- **通知節點**：名稱、收件人（§12.1）、範本（§12.2，含欄位插入選單與預覽）。
- **線**：標籤；條件節點的出線另有條件與順序（與條件節點面板同步）。
- **進階**：節點代號（預設自動產生 `approval-1`、`cond-1` 這類，可改；已發布過的節點改代號時警告「會被當成新節點」，同 a4a 的關卡代號規則）。

上限與預設值一律從政策生效值 API 取得（簽核設計 a4a 的做法），前端不寫一份。

手機的細節：

- 「能改的屬性」是 §10.4 的全部屬性，包含條件節點出線的條件與順序、匯合模式、通知收件人與範本、流程層屬性；不能改的是圖的結構（新增、刪除節點或線、改連接對象、移動節點）。
- 節點面板、連線把手、「＋」、刪除鈕在手機上不顯示，不只是停用。
- 畫布上方加「節點清單」切換：把節點依從開始的拓撲順序列成清單，點一項開屬性；給難以在小螢幕精準點選的情況使用，也是鍵盤與螢幕閱讀器的替代路徑。
- 工具列只留縮放到全圖、驗證、試算、儲存或發布。
- 後端不分裝置：手機上送出的定義與平板一樣完整驗證。「手機不能改結構」是畫面限制，不是權限（政策設計 §1：畫面呈現方式不屬於規則）。

平板的細節：節點面板收進左側抽屜；屬性抽屜打開時，畫布自動把選中的節點移到可見區域。

### 10.6 試算

沿用 a4a 的試算端點（用編輯中、未儲存的內容，不寫入），結果改為疊在畫布上：預計會走到的節點與線高亮，每個簽核節點旁顯示解析到的簽核人與問題（`noApprover`、`tooManyApprovers`），被略過的節點淡化；並行分支各自標出。手機上同樣疊在唯讀畫布上，另提供清單檢視。

### 10.7 舊流程在設計器中

- 後端 `GET approval-flows/{key}` 對 `sequence` 定義另外回傳轉換後的 `graph`（§7.8 同一個轉換函式），前端只處理 graph，不實作第二份轉換（技術類，主控決定，J14）。
- 設計器打開舊流程時直接顯示直線圖、自動排版，頂端提示「這條流程已轉成流程圖；發布後以流程圖保存，進行中的 N 張單照舊版走完」。
- 不發布就不改資料庫裡的定義（批次轉換見 §13）。
- 原本的 `FlowStagesEditor` 與對話框「關卡」段在流程圖設計器上線的同一段移除（使用者決定：只留一個設計器）。

### 10.8 草稿與發布（U6，使用者裁決 2026-11-13）

「儲存草稿」與「發布」分開：

- **草稿只含定義與版面**：`DraftJson` 存 `DefinitionJson`（含流程層的啟動條件、退回狀態、備援）與 `LayoutJson`。只檢查格式與大小，不跑 §9 的規則；不影響任何送出中或新送出的單。
- **流程列屬性不進草稿**（使用者裁決照建議 2026-11-13）：名稱、目標狀態、優先序、啟停維持在流程列上，存了立即生效，照現行 a4a 的做法（啟停與排序按了就存，簽核設計 §20.4 第 42 條）。被用過的流程不能改目標狀態，照現行在存檔時擋（簽核設計 §5.2）。
- **發布**：跑 §9 全部規則，通過才寫入版本（被用過就開新版本，否則覆寫目前版本，照第一版），並清掉草稿。
- 有草稿時流程卡片標「有未發布的變更」；設計頁打開時載入草稿，可以「捨棄草稿」回到已發布版本。

**只有草稿的新流程**（使用者裁決照建議 2026-11-13）：

- 流程列在第一次儲存草稿時建立（`CurrentVersionId` 為 null），一律**強制停用**。
- 不參與送出與重新比對的流程比對、不進流程快照、不參與入口約束（簽核設計 §5.2 的流程數量規則只算有已發布版本的流程），也不參與試算的流程集合（試算編輯中的這條流程本身照 a4a 的草稿試算端點，不受影響）。
- 發布第一個版本之前不能啟用：流程卡片的啟用開關停用，提示「先發布」；後端對沒有版本的流程設 `Active = true` 回 400。
- 可以調整優先序（佔用 `(ModuleId, ToOptionId, Priority)` 唯一索引的位置），發布後就以那個優先序參與比對。
- 沒有版本、也沒被用過，可以直接刪除。

**程式中假設「流程一定有目前版本」的地方**，要在 fg1（後端）與 fg3（前端）改掉，列為工作項：

- `ApprovalRepositories.ListCurrentByModuleAsync`：以內部 join 連版本表，沒有版本的流程會從清單消失；設計器清單要看得到草稿流程，比對與入口約束則要明確排除它們。（fg1）
- `ApprovalHandlers` 送出時建流程快照、設計器草稿試算組流程集合：`f.Flow.CurrentVersionId!.Value`。（fg1）
- `ApprovalPreviewer` 組流程集合：`f.Flow.CurrentVersionId!.Value`。（fg1）
- `ApprovalFlowHandlers.ResponseAsync`（流程回應）與更新流程時讀目前版本：`flow.CurrentVersionId!.Value`；回應的 `version`、`definition` 要允許為空並加 `draft`。（fg1）
- 啟停端點：沒有版本時拒絕啟用。（fg1）
- 前端 `ApprovalFlow` 型別的 `version`、`definition` 與流程卡片、試算、狀態機分頁「目標狀態已掛 N 個流程」的計數：區分已發布與只有草稿。（fg3）

理由：流程圖一次畫完的成本比卡片高，畫到一半要離開時不能因為「還沒有預設線」就存不了；商用 BPM 也普遍有草稿與發布。替代方案是只在瀏覽器本機暫存（不加資料表欄位），代價是換裝置就看不到、多人編輯互相覆蓋。

草稿只存一份，最後儲存的人為準；兩人同時編輯同一條流程時，後存草稿的人收到 409 並可選擇覆蓋（技術類，主控決定，J15），用流程的修改時間做樂觀鎖。

## 11. 單據頁進度圖

### 11.1 呈現

- 記錄詳情頁的「簽核」區塊（a4b 的 `ApprovalPanel`）在文字時間軸上方加一張**唯讀流程圖**（使用者決定）；文字時間軸與歷程完全保留。
- 顯示實例綁定版本的整張圖，含尚未走到的節點（U8，使用者裁決 2026-11-13）；節點只顯示名稱、型別圖示與狀態，條件出線只顯示設計者寫的 `label`、不顯示條件內容。
- 狀態上色（語意 token，並附圖示，不只靠顏色）：

| 狀態 | 對應節點實例 | 呈現 |
|---|---|---|
| 已通過 | `approved`、`passed` | 正向色、勾 |
| 進行中 | `active`、`waiting` | 主色、時鐘，逾期加警示 |
| 被退回 | `returned`，或退回發起人的那個節點 | 負向色、退回圖示 |
| 已略過 | `skipped` | 灰色虛線框 |
| 已取消 | `closed` 且 `branchCancelled` | 灰色、刪除線 |
| 未走到 | 沒有節點實例 | 淡灰 |

- 走過的線（某個節點實例的 `InEdgeId`）加粗上色；同一節點被重跑多次（退回上一關）時，以最新一次的狀態上色，點節點看全部紀錄。
- 點節點：開出該節點的細節（任務負責人、代理與轉交、動作時間、意見），與時間軸同一份資料。
- 「先前的簽核」（被退回、重來、撤回的舊實例）維持收合；展開時同樣有自己的圖。

### 11.2 寬度

- 桌機、筆電：圖寬度跟區塊一致，高度上限約一個畫面，超出在圖內平移。
- 平板：同上，可雙指縮放。
- 手機：顯示縮放到全圖的縮圖，點了開全螢幕檢視（平移、縮放）；縮圖下方照舊是文字時間軸。

### 11.3 資料

- `GET /records/{id}/approval` 的每個實例加 `graph`：節點（代號、型別、名稱）、線（代號、起訖、`label`）、版面（`LayoutJson`，沒有就 null，前端自動排版）、每個節點的狀態與節點實例清單。條件內容、簽核人來源設定、通知範本不回傳。
- `sequence` 實例（進行中的舊單、已結束的舊單）由後端用 §7.8 轉成直線圖回傳，節點實例以 `StageCode` 對應節點代號；加簽節點實例（`StageCode` 為 null）畫成插在主節點後的小節點。這樣舊單也有進度圖，前端只處理一種格式。
- 臨時讀取權的簽核人、只看歷程的發起人與處理過的人（簽核設計 §20.4 第 25 條）看得到進度圖，範圍同時間軸。
- 記錄回應的簽核摘要（`approval: { status, stage, ... }`）在並行時改列出進行中的節點名稱：「簽核中（財務、法務）」，超過兩個顯示「簽核中（財務等 3 個）」（U9，使用者裁決 2026-11-13）。直線流程維持「簽核中（第 2 關／財務）」。

## 12. 通知節點

### 12.1 收件人

`recipients` 每一項是下列其中一種（使用者決定的四種對象）：

| `kind` | 參數 | 解析 |
|---|---|---|
| `users` | `userIds` | 指定的使用者 |
| `group` | `groupIds` | 群組全部成員（「角色」，§4） |
| `initiator` | — | 申請人（送出的人） |
| `initiatorManager` | `level`（1 到政策 `approval.maxManagerLevel`，預設 1） | 申請人往上第 `level` 層主管，規則同簽核設計 §6.2 |

- 只取啟用中的使用者；解析結果去重。
- 解析在通知節點被走到的當下進行（與簽核人「關卡啟動時才解析」一致）。
- 套件不收具體使用者（簽核設計 §14.2 的規則），所以套件裡的通知節點只能用 `group`、`initiator`、`initiatorManager`。
- 解析後人數超過技術上限（§15）時，只發給前面的人並在歷程記一筆說明；不讓推進失敗（§12.4）。

### 12.2 內容範本

- 範本有標題與內文兩段，都是多語系文字；標題上限 200 字、內文上限 1000 字（技術限制）。
- 佔位符：`{title}`（單據標題）、`{flow}`（流程名稱）、`{initiator}`（申請人姓名）、`{node}`（通知節點名稱）、`{f:<欄位 Id>}`（欄位值）。設計器以「插入欄位」選單產生，不要求設計者手打。
- 欄位佔位符只能引用本模組表頭的啟用中欄位；發布時驗證（§9 G10）。欄位之後被停用或刪除，照第一版「被流程版本引用的欄位不能刪除或停用」的守衛保護（簽核設計 §8.6），範圍擴及通知範本。
- 欄位值以通知寫入當下的記錄值、依欄位型別格式化（選項顯示多語系標籤、使用者顯示姓名、日期依營運時區）。

### 12.3 欄位值的可見性（技術類，主控決定，J16）

通知內容帶欄位值，會碰到「收件人看不到這個欄位」或「收件人根本沒有這張單的讀取權」。規則：

對**每一位收件人**各自判斷，分兩層：

1. **這張單的讀取權**：判斷的是「這位收件人能不能讀這一筆記錄」，含模組讀取權與資料範圍（例如資料範圍「本人」的人，只能讀自己擁有的記錄）；簽核臨時讀取權也算有。沒有這張單的讀取權，收件人**只收標題快照與連結**，不帶任何欄位值：`DataJson` 不存佔位符值，前端顯示範本時所有欄位佔位符都以「（無權限）」呈現。標題快照照簽核設計 §20.4 第 21 條的標題遮蔽規則。
2. **欄位層**：有這張單的讀取權時，逐欄判斷。欄位對他隱藏（欄位權限、限定可見），或欄位是金額、而他沒有該模組的金額權限（`Pricing` 軸，金額遮罩）時，這個佔位符顯示「（無權限）」，不顯示值。簽核臨時讀取權附帶的 `Pricing`（簽核設計 §10.1）只在他是該記錄 `open` 任務的可動作者時成立，判斷時點是通知寫入當下。

欄位有權限但值為空，顯示「—」，與「（無權限）」區分。
- 通知節點**不**給收件人臨時讀取權。收件人點通知連結，照一般權限判斷，沒有權限就是既有的 403 畫面。

這屬於安全規則，列進 §15 可寫死清單。

### 12.4 不擋流程

- 解析不到任何收件人（群組沒人、申請人沒有主管）：不發，歷程記一筆 `notify`（說明「沒有收件人」），照常往下走。
- 範本中的欄位值為空或讀不到：顯示「—」；沒有權限的照 §12.3 顯示「（無權限）」，兩者都不讓推進失敗。
- 通知寫在動作的同一個交易內：動作本身失敗回滾時，通知也不會留下，與第一版的系統通知一致（簽核設計 §12）。
- 每次經過都在歷程記一筆 `notify`（系統身分），附收件人數，不列收件人姓名以外的內容。

### 12.5 儲存與顯示

- 現有 `Dynamic_Notification` 只有種類、標題快照與連結，前端依種類組固定文字（簽核設計 §12：「通知只帶記錄標題快照與連結，不帶欄位值」）。通知節點是這條規則的**例外**（使用者決定第 11 條），所以加 `DataJson`，存範本（各語系）與已依收件人遮蔽、已格式化的佔位符值（技術類，主控決定，J17）。
- 新通知種類 `approvalNotify`；前端依使用者目前的介面語系選範本語系、代入值顯示。後端沒有「使用者偏好語系」可用，所以不在寫入時組好單一語言的文字。
- 選項標籤、使用者姓名這類多語系值，存成各語系版本，前端照同一語系取用。
- 通知保留天數照政策 A14。
- 通知節點**不是**抄送權：收件人看不到簽核歷程、不出現在簽核中心（§12.3）。

## 13. 遷移策略

1. **fg1 的 migration**：只加欄位（§7.6），既有資料不動，既有行為不變。
2. **fg2 起 API 接受 `graph`**：沒有畫面前只能從 API 建立，用於測試；`sequence` 照舊。
3. **fg3 設計器上線**：打開舊流程顯示轉換後的直線圖；發布才寫成 `graph`（被用過就開新版本）。原本的關卡編輯移除。
4. **fg6 批次轉換**：部署後的一次性升級工作，把每條流程**目前版本**是 `sequence` 的轉成 `graph`：
   - 目前版本被用過（被綁定或出現在任何快照，簽核設計 §4.4）就新增一個版本，沒被用過就原地覆寫，與一般存檔規則一致。
   - 只動目前版本；歷史版本、實例快照不動，所以進行中的單照舊版跑完（使用者決定）。
   - 可重複執行：已經是 `graph` 的跳過；每次啟動檢查一次，沒有待轉換的就不做事。
   - 寫系統日誌列出轉換的流程數與新增的版本數。
   - 轉換前後語意等價（§7.8），所以不必通知設計者；版本號會加一，設計器的版本提示照常出現。
5. **套件**：套件格式升一版（簽核流程的格式 8 由 a5 引入，預計流程圖為格式 9，實作時以當時的 `CurrentFormatVersion + 1` 為準）。新格式的 `approvalFlows` 收 `nodes`、`edges`；舊格式的 `stages` 在匯入與開啟時用 §7.8 轉成 graph。匯出一律輸出 graph。驗證層的 V6 擴充為兩種形狀都驗（graph 套 §9 的規則）。
6. **第一版引擎保留**：只服務快照是 `sequence` 的實例。客戶是自架，無法確定各環境都已沒有舊實例，所以不設移除時程；之後若要移除，先提供「列出仍在用舊形狀的實例」的檢查，列 §18。
7. **回退風險**：fg2 之後若已有 `graph` 版本，回退到 fg1 以前的程式會讀不懂這些定義。回退只支援到 fg2 為止；部署回報要寫明。

## 14. 測試策略

**Domain（純函式，`DynamicModules.Domain.Tests`）**

- 結構驗證 G1–G13、警告 W1–W3：以 `poc/shared/approval-graph-cases.json` 的案例驅動；每條規則至少一個通過、一個失敗案例；巢狀並行區、交錯並行區、結束在並行區內、條件節點缺預設線、環。
- sequence → graph 轉換：代號衝突、空條件、開啟套件寫入的對不上單位都原樣保留；轉兩次結果相同。
- 閉包與鎖定欄位：條件節點出線、略過條件、`userField` 都納入；通知範本不納入。
- 路線比較（§8.7）：條件節點改選出線、略過條件變成立、取消分支不參與。

**Application 整合測試（`DynamicModules.Application.Tests`，沿用簽核既有的測試套件與 Demo 組織）**

- **等價性**：第一版既有的簽核情境（請假、費用報支、採購單三份劇本與其他必測，簽核設計 §17）以參數化同時跑 `sequence` 與轉換後的 `graph`，逐筆比對節點實例順序、任務、歷程動作、結果。
- 並行：全部到齊（兩條分支都核准才往下）；任一到齊（第一條到達取消其他、任務關閉、臨時讀取權收回、歷程 `branch-cancelled`）；巢狀並行；分支內有條件節點；送出時就能到達的任一到齊。
- 退回：分支內退回發起人整張退回且其他分支任務關閉；分支內退回上一關只在同一分支段；分支第一個節點不能退回上一關；匯合後第一個節點不能退回上一關。
- 撤回（§8.5）：任何進行中的簽核節點已有人同意或退回就不能撤回；分支內前一關已核准、目前節點還沒人動作，仍可撤回；一條分支已到「全部到齊」匯合等待、另一條分支的進行中節點還沒人動作，仍可撤回；撤回後所有執行線關閉。
- 重新比對：簽核中跨模組彙總讓條件節點改選出線，同意不計入並重來；被取消分支的條件變化不觸發。
- 條件無法判斷：409、整筆回滾、異常通知。
- 併發（§8.13，SQLite 與 PostgreSQL 都跑）：兩條分支同時同意都成功、不回 409（第二個自動重試後處理）；兩條分支同時抵達「全部到齊」匯合，恰好推進一次；同一節點或簽兩人同時同意，後到者 409「已由他人處理」；分支被取消後的同意回 409 並帶「其他分支已完成」；發起人讀取後有分支同意，撤回回 409「請重新整理」；重試用完回 409「單據正忙」。
- 通知節點：四種收件人；沒有收件人不擋；重跑時再發；`DataJson` 內容。
- 通知遮蔽（§12.3，安全測試）：沒有模組讀取權的收件人只收標題快照與連結、`DataJson` 不含欄位值；資料範圍「本人」的收件人，對別人擁有的記錄同樣只收標題與連結，對自己擁有的記錄看得到值；欄位隱藏顯示「（無權限）」；沒有金額權限的收件人，金額欄位顯示「（無權限）」、非金額欄位照常；有 `open` 任務的簽核人依臨時讀取權看得到金額；值為空顯示「—」。
- 批次轉換：被用過的開新版本、沒被用過的覆寫、可重複執行、進行中實例不受影響。
- 套件：舊格式匯入轉 graph；新格式往返（匯出再匯入等價）；V6 對 graph 的檢查。
- 政策：分支數、簽核節點數改嚴只管之後（政策設計 §3.5）。
- 草稿（§10.8）：存草稿不影響送出中與新送出的單；只有草稿的新流程強制停用、不進比對、快照、入口約束與試算的流程集合，啟用回 400，可排優先序；名稱、啟停、優先序存了立即生效；被用過的流程改目標狀態回 400。

**WebAPI**：新增與變更端點的權限、錯誤鍵格式（`nodes.{id}.*`）。

**前端（vitest）**

- 共用案例跑前端的即時驗證，結果與後端一致。
- 自動排版：直線、巢狀並行、互斥會合的座標不重疊。
- 設計器：手機寬度下沒有新增、連線、刪除入口，屬性可改並送出；平板以上可新增、插入、刪除、連線；錯誤標示與定位；草稿與發布流程；只有草稿的流程啟用開關停用並提示「先發布」。

- 被通知範本引用的欄位不能刪除或停用。

## 16. 一條流程套多張單據：方向與介面預留

方向（使用者決定第 2 條）：

- **流程範本**：一份與模組無關的流程圖定義。範本裡引用資料的地方（條件、`userField`、可編輯欄位、通知佔位符）不寫欄位 Id，而寫**槽位**（例如「金額」數字槽、「申請人主管欄」使用者槽），每個槽位有型別。
- **槽位對應**：某模組要套用範本時，設計者把每個槽位對應到該模組的一個欄位（型別相容才可選）。範本加上對應，就得到一份一般的 graph 定義。
- 範本改版時，各模組的流程依各自的對應重新產生定義、走一般的發布與版本規則。

這一版的介面預留（不寫入、不實作）：

- **執行期只吃已展開的定義**：流程版本與快照裡存的永遠是「代入對應之後」的 graph 定義（欄位 Id），執行引擎、鎖定、閉包都不需要知道範本存在。這是最關鍵的介面約束，fg2 的引擎不得引入任何範本概念。
- **欄位參照集中**：graph 定義中所有引用欄位的位置，一律走同一組讀取函式（條件語法的 `field`、`userField.fieldId`、`editableFields`、`{f:<Id>}`），不在各處各自解析。之後槽位只要在這組函式加一種參照形式。
- **流程表預留**：將來在 `Dynamic_ApprovalFlow` 加 `TemplateId`、`TemplateVersion`、`SlotMapJson`；這一版不加欄位，只保證流程與版本的現有欄位語意不變。
- 驗證器拒絕定義中出現 `slot` 這類未知參照。

細節（範本的權限歸屬、套件格式、範本改版時已對應模組的升級方式、範本與「多流程依優先序」的關係）另寫設計，排在 fg 系列之後（使用者決定第 2、3 條）。

## 18. 已知限制

1. **條件節點改選出線就重簽**（§8.7）：簽核中由跨模組彙總、時間條件造成的值變化，若跨過條件節點的門檻，即使新路線比較寬鬆也會從頭重簽。
2. **任一到齊可能立即通過**（§8.3）：分支內沒有簽核節點或都被略過時，送出當下就取消其他分支；只有警告，不擋發布。
3. **進度圖透露路線**：走過的線與被略過的節點，等於透露了條件的結果；條件引用讀者看不到的欄位時，性質同簽核設計 §20.2 第 5 條（預覽的推論管道），只遮蔽條件內容、不消除推論。
4. **第一版引擎無法移除**：自架環境可能長期留有 `sequence` 實例（§13 第 6 點）。
5. **通知節點重跑會重發**（§8.12）：退回上一關多次的單據，收件人會收到多則內容相近的通知。
6. **觸控連線未驗證**（§10.1）：平板的連線操作依賴函式庫的點選連線模式，fg3 開工時先驗證。
7. **沒有退回到分叉之前**（§8.4）：要整個並行區重跑只能退回發起人。

## 19. 主控代為決定的事

### 19.1 使用者行為類（使用者已於 2026-11-13 逐條確認）

- **U11** 流程圖各段排在 a3 之後（§17）。
- **U12** 簽核節點數沿用「關卡數」政策；新增「每個分支的分支數」政策，出廠 5（§15）。

### 19.2 技術類（主控決定）

- **J1** 互斥路徑可以直接在同一節點會合，並行分支才需要匯合節點（§6.2）。
- **J2** 匯合節點明寫 `forkId`（§7.2）。
- **J3** 分路條件放在條件節點的出線上（§7.4）。
- **J4** 版面存 `LayoutJson`，不進定義、不參與版本比對（§7.5）。
- **J5** 每個走到的節點都寫節點實例；簽核節點的 `StageCode` 寫節點代號；`BranchKey` 為分支出線代號路徑（§7.6）。
- **J6** 分支出線依定義順序推進，結果可重現（§8.2）。
- **J7** graph 的路線比較：條件節點改選出線即視為不同（§8.7）。
- **J8** 送出時要求所有自選簽核節點都選好人（§8.9）。
- **J9**（已由 J18 取代）初稿的節點實例層 `RowVersion`。
- **J10** 驗證錯誤鍵以節點、線代號定位；前後端共用判斷案例檔（§9）。
- **J11** 流程圖函式庫用 Vue Flow，動態載入、鎖定版本（§10.1）。

- **J13** 流程圖設計器是全螢幕獨立路由，取代對話框的「關卡」段（§10.2）。
- **J14** sequence → graph 轉換只在後端實作，設計器讀後端轉好的圖（§10.7）。
- **J15** 草稿用樂觀鎖，後存者 409 可選擇覆蓋（§10.8）。

- **J17** 通知加 `DataJson` 存範本與遮蔽後的值，前端依語系組字（§12.5）。
- **J18** 同一張單的動作以實例為單位序列化：實例列條件更新取得處理權、失敗自動重試（上限列 §15）；分支同意不比對畫面的實例版本；匯合判斷在處理權內做；撤回、終止仍比對實例版本，變了回 409；SQLite 與 PostgreSQL 都要有並發測試（§8.13）。
