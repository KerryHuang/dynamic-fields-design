# Demo 資料實作裁決

執行 [`2026-11-05-demo-data.md`](2026-11-05-demo-data.md) 時，對計畫與設計文件的補充與修正。與計畫衝突時以這裡為準；第 1–8 階段的裁決仍然有效。設計文件在[這裡](../specs/2026-11-05-demo-data-design.md)，操作腳本在 [`docs/demo.md`](../../demo.md)。

## 一、寫計畫時的裁決（設計文件 §9）

原設計有幾處做不到，計畫提出建議，使用者全部採納，並已回寫到設計文件。

1. 額外的使用者與群組（`maint01`、`qa01`、`floor02`，群組「保養」「品保」）放進種子資料，不由產生器補。原因：使用者清單在程序啟動時只載入一次，事後補的人會被擋在外面，也沒有新增使用者的指令。
2. 模具是既有實體，沒有反向關聯清單。反向關聯改在三處示範：保養紀錄的「更換零件」、訂單的「品質異常」、報修單的「關聯報修單」。
3. 共用檢視的篩選沒有「目前使用者」與「本月」。檢視改成「未結案報修」與「近 30 天結案」。
4. 公式不能跨模組引用，所以保養紀錄自帶「保養週期（天）」，下次保養日用保養日期加這個週期。
5. 品質異常加「狀態」欄位與「結案後整張唯讀」，「未結案的重大異常」檢視才成立。
6. 品質異常範本以一般參照指向 `order` 模組，單獨套用前庫裡要先有訂單模組，寫進手冊。
7. 產生器切換身分、模擬時間都在同一個 DI scope 內進行，才能維持單一交易。
8. 手動產生需要設計器的新增與修改權限，與「從範本建立」相同。

## 二、執行時的裁決

依任務分組。格式：裁決 — 理由 — 錯了的代價。

### 開工前檢查

- 沒有任務之間的衝突需要裁決。

### 任務 2：種子資料

- 既有客戶 C-002、C-003 也改成虛構名稱（恆川機械、曜陽電子）。理由：repo 已公開，不能出現真實公司資訊。種子資料不覆寫既有的列，所以只影響新建的資料庫，舊的本機資料庫仍顯示舊名稱。

### 任務 7：背景產生與端點

- 站台關閉而中斷產生時，記 Warning，不記 Error。判斷條件是丟出 `OperationCanceledException`，且站台的停止 token 已取消。理由：這是無害、可預期的情況，不該在 log 裡看起來像故障。代價：只是 log 等級。這項排入最終修正波，任務 7 完成時尚未改。

### 任務 8：前端頁面

- 沒有權限（缺設計器的新增或修改）時，「產生 Demo 資料」按鈕顯示但停用，不隱藏。理由：讓使用者知道有這個功能，只是需要權限。任務說明裡「不顯示」的測試項目作廢。代價：改一行。
