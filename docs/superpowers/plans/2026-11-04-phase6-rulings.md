# 第 6 階段實作裁決（R1–R23）

執行 [`2026-11-04-phase6-details-rollup.md`](2026-11-04-phase6-details-rollup.md) 時，對計畫原文的補充與修正。格式：裁決 — 理由 — 錯了的代價。與計畫衝突時以這裡為準；第 1–5 階段的裁決（[`2026-11-03-phase1-rulings.md`](2026-11-03-phase1-rulings.md)、[`2026-11-03-phase2-rulings.md`](2026-11-03-phase2-rulings.md)、[`2026-11-03-phase3-rulings.md`](2026-11-03-phase3-rulings.md)、[`2026-11-03-phase4-rulings.md`](2026-11-03-phase4-rulings.md)、[`2026-11-03-phase5-rulings.md`](2026-11-03-phase5-rulings.md)）仍然有效。

- Ruling R1: Task 4 不呼叫 `RollupRecalc`；Task 5 在 Create／Update／Delete handler 與明細存檔流程加上 `AfterWriteAsync` — Task 4 時這個方法還不存在，計畫寫的「留呼叫點」做不到 — 錯了的代價：無，Task 5 負責。
- Ruling R2: 隱藏「結果是金額的彙總欄位」（以及引用它的公式）由 Task 3 在 `PermissionResolver` 做 — Task 3 的 `Schema_NoPricing` 測試需要它 — 錯了的代價：之後另一個 task 改 `PermissionResolver`。
- Ruling R3: `RecordIndexer` 對彙總欄位套用與公式相同的索引規則（可篩選、可排序）— 計畫沒有任何 task 點名 `RecordIndexer` — 錯了的代價：在 task 之間搬一小段程式。
- Ruling R4: `Phase6Details` migration 的 Up／Down 是空的 — SQLite 改欄位長度不產生 DDL，snapshot 與 model 已帶 MaxLength 20；換成 SQL Server 時依 spec §14 重新產生 — 錯了的代價：上線時多一個 ALTER COLUMN。
- Ruling R5: 彙總條件引用彙總欄位（或依賴彙總的公式）時，訊息是 `彙總設定不正確：條件不正確：不能使用彙總欄位或引用它的公式` — 套進計畫的 `條件不正確：{原因}` 格式，不重用「彙總對象」的訊息 — 錯了的代價：一個字串。
- Ruling R6: 對整數欄位做彙總，推導出的小數位數是 0，不是 2 — 決策 7 的「沒有設定時用 2」指的是小數類型別 — 錯了的代價：只影響顯示精度。
- Ruling R7: `RollupCalculator.Compute` 接收真實的使用者清單（呼叫端傳 `ListUserIdsAsync`）；重新啟用彙總欄位時再跑一次彙總設定檢查 — 條件可能引用使用者欄位，停用期間條件欄位也可能被停用 — 錯了的代價：重新啟用時多一次檢查。
- Ruling R8: 公式被啟用中的彙總引用時，若修改後會依賴彙總欄位，回 400，鍵 `Config.Formula`，訊息 `公式不正確：被彙總欄位引用的公式不能引用彙總欄位` — 守住決策 8「彙總只算一層」 — 錯了的代價：多一個訊息字串。
- Ruling R9: 明細模組的檢視端點（`/modules/{key}/views`）同樣回 404 `模組不存在或未啟用`；以檢視 id 操作的端點（R9b）回這些 handler 原本對「檢視不存在」的 404 — 決策 2「以模組鍵操作的端點看不到明細模組」涵蓋它們 — 錯了的代價：明細模組無法使用檢視（目前沒有地方用到）。
- Ruling R10: 反向關聯分頁排除所有「來源模組是明細模組」的參照欄位，不只排除明細欄位本身 — 明細列不能單獨打開 — 錯了的代價：從明細列指向其他模組的一般參照，在目標那邊沒有反向分頁。
- Ruling R11: 明細列帶 `_delete: true` 但沒有 `id` 時直接忽略 — 那是使用者新增後又刪掉的列，前端本來就不送 — 錯了的代價：格式錯誤的請求會被靜默略過一列無作用的資料。
- Ruling R12: 使用者追加需求「下拉選單都要有 autocomplete」，排成新的 Task 9b：每個 `q-select` 透過共用的 `useSelectFilter` 打字篩選，依選項名稱包含輸入字串、不分大小寫，沒有符合時顯示「沒有符合的選項」；參照欄位的搜尋視窗本來就能搜，不在範圍內 — 放在 Task 9 之後，Task 7 新增的選單也一併涵蓋 — 錯了的代價：多一個前端 task。
- Ruling R13: 新建立的記錄在建立當下就有彙總的空集合值（計數、加總為 0，最小、最大為空），一般參照與明細的彙總都一樣 — 決策 7 規定空集合為 0；原實作「第一筆子記錄出現前是空值、刪光後是 0」前後不一致 — 錯了的代價：每次新增多算一次。
- Ruling R14: 表頭存檔時一律略過表頭本身；若明細模組另有一個一般參照也指向同一個表頭模組，靠這個參照做的彙總在表頭存檔時不重算 — 罕見情況，接受 — 錯了的代價：那個彙總要等下次全量重算才更新。
- Ruling R15: 前端送彙總欄位時帶 `required: false`（與公式相同，型別上 `required` 不能省），不是計畫寫的「不送」— 伺服器只拒絕計算型欄位的 `required: true` — 錯了的代價：無（已確認後端接受）。
- Ruling R16: 以 `block:N` 為目標的明細規則不在前端套用 — 明細表格沒有區塊，`SchemaDetail` 只有攤平的欄位；伺服器照樣判斷 — 錯了的代價：被區塊規則隱藏的明細欄位在表格上仍然看得到。
- Ruling R17: 前端不擋每個明細模組 200 列的上限，超過時顯示伺服器的 `details.{模組鍵}` 錯誤通知 — 上限很少碰到 — 錯了的代價：使用者到存檔時才知道超過上限。
- Ruling R18: 「沒有符合的選項」走 i18n（四個語系都有，zh-TW 照 brief 原文），不寫死 — brief 固定的是文字，不是做法 — 錯了的代價：一個 i18n 鍵。
- Ruling R19: 百分比欄位在公式裡是小數（第 3 階段起 `FormulaEvaluator` 就把 5% 當 0.05），所以計畫寫的稅額公式 `ROUND({未稅合計} * {稅率} / 100, 0)` 是計畫錯誤；驗收與文件一律用 `ROUND({未稅合計} * {稅率}, 0)` — 依既有、已寫進手冊的行為 — 錯了的代價：無。
- Ruling R20: 彙總條件在執行期失效時（例如條件欄位的小數位數被改小），計算時忽略條件、計入所有子記錄，比照規則引擎把無法解析的規則當作不存在；同時修改被彙總條件引用的欄位時，若會讓條件失效就回 400 — 避免表頭寫入回 500 — 錯了的代價：失效期間彙總偏高（只有直接改資料庫才會發生），改成「視為不符合」只要一行。
- Ruling R21: 「在表頭內編號」建立後鎖定，修改時回 `Config.Scope`「在表頭內編號建立後不能更改」；設計器在編輯模式停用這個開關，不另加說明文字 — 比照明細關聯的鎖定 — 錯了的代價：之後補一行提示。
- Ruling R22: 重新啟用彙總欄位時，把重新推導的結果型別與小數位數寫回設定再重算 — 否則停用期間彙總對象改成金額，重新啟用後仍是數字，沒有金額權限的人看得到 — 錯了的代價：無。
- Ruling R23: 明細彙總的彙總對象若對使用者隱藏（例如宣告為數字、但引用金額欄位的公式），彙總欄位與引用它的公式也對他隱藏 — 擋住金額外漏；一般參照的彙總不在此列，見 spec §15 第 37 條 — 錯了的代價：某個其實不是金額的彙總被隱藏。
