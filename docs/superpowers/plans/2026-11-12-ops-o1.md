# 維運地基 O1（o1a、o1b、o1c）Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 讓 Formwright 有 request id 與結構化 log、health live／ready、版本端點、前端錯誤收集，以及背景排程器；任務提醒與通知清理改由排程跑，「即將到期」改成到期前 N 天內補一次、同一任務只補一次。

**Architecture:** 後端沿用 MediatR＋`ServiceResult`＋`ITransactionalRequest`／`WriteGate`；指紋與訊息正規化是 Domain 純函式；排程器是 WebAPI 的一個 `BackgroundService` 加 Application 的 `JobRunner`，同一工作靠 `Dynamic_ScheduledJob` 一列的條件式 `ExecuteUpdate` 租約保證只跑一份（SQLite 與 PostgreSQL 同一份 EF 寫法）。提醒去重從「先讀再寫」改成條件式更新。前端加一個錯誤回報模組（boot），`http.ts` 讀 `X-Request-Id` 顯示錯誤代碼。

**Tech Stack:** .NET 8、EF Core 8.0.11（SQLite 研發／PostgreSQL 正式）、MediatR 12、xUnit＋FluentAssertions、`System.Diagnostics.Metrics.Meter`（.NET 內建，自訂指標用；O1 不裝 OpenTelemetry 套件，見 J30）、`Microsoft.Extensions.Diagnostics.HealthChecks.EntityFrameworkCore`（新增）；Vue 3、Quasar 2（app-vite）、vue-i18n、vitest、bun。

**Spec:** `docs/superpowers/specs/2026-11-11-ops-observability-design.md`（origin/main `cef82aa0` 版：§9、§10、§10.8、§11、§12、§16）；相關：`2026-11-11-policy-settings-design.md`（A6、A7、A13、A14）、`2026-11-10-task-management-design.md` §6.2、`2026-11-12-postgres-provider-design.md`（pg0；§5.6、§7 對 O1 排程器的要求，T5 的 `…Utc` 命名）。repo 規範：`AGENTS.md`、`.claude/rules/{backend,frontend,docs}.md`、`docs/ai/testing.md`。

**修訂紀錄：** 2026-11-12 依 `plan-review.md`（M1–M4、S1–S15、N1–N12）與使用者裁決 D1、D2、B1、B2、B3 修訂；逐條處理見 result.md。

## 計畫判斷（技術類，可推翻）

每條：判斷／理由／選錯代價。〔行為〕＝會讓使用者看到不同的東西但設計已定方向，只是細節由計畫定。

- **J1** 合併順序 o1a → o1b → o1c，不平行。理由：三段都改四語 i18n，檔案是單行 JSON，平行合併幾乎必衝突；client-errors 端點與 `X-Request-Id` 在 o1a，o1c 要用。代價：o1c 晚一段上線。
- **J2** 前端錯誤收件的**後端**端點放 o1a（設計 §10.1 的表沒把它分到任何一段）。理由：它需要 o1a 的指紋與 `ops.clientErrorCollection`；o1c 只剩前端。代價：o1a 上線後端點存在但還沒有前端在送。
- **J3** ready 只檢查資料庫，回應 `{status:"notReady", checks:{database:"fail"}}`，不含 `startup`。理由：`Program.cs:108` 在 `app.Run()` 之前就跑完 migration、種子與索引回填，伺服器還沒聽埠，`startup` 永遠是 ok，寫了是死碼。代價：日後把初始化改背景時要加回 `startup` 一項。
- **J4** 資料庫檢查用 `AddDbContextCheck<DynamicDbContext>`（預設 `CanConnectAsync`），不寫 `SELECT 1` raw SQL。理由：不必經 `ISqlDialect`，兩種資料庫同一份。代價：`CanConnectAsync` 對 SQLite 只證明檔案打得開；O2 要更細的檢查時再補。
- **J5** 請求 log 分兩個 middleware：`RequestContextMiddleware` 在最前面（在 `UseExceptionHandler` 之前；定 request id、加標頭、開 `requestId` scope、**呼叫 `next` 之前**就取路由樣板與 `moduleKey` 存進 `RequestOpsFeature`、請求結束記一行）；`RequestScopeMiddleware` 在 `UseAuthentication` 之後（開 `userId`、`route`、`moduleKey` scope，`route`、`moduleKey` 讀同一份 `RequestOpsFeature`）。理由：`userId` 要等認證後才有，而標頭與 `traceId` 要在例外處理之前就定好；`ExceptionHandlerMiddleware` 在呼叫 handler 前會清掉 endpoint 與 route values，內層 scope 在 `finally` 時也已 Dispose，所以結束行與例外 log 都不能靠 `GetEndpoint()` 或內層 scope。代價：結束行的 `UserId`、`ModuleKey`、`Route` 寫成 template 欄位（`UserId` 在 `finally` 從 `HttpContext.User` 讀，`Route`、`ModuleKey` 讀 `RequestOpsFeature`），不是 scope；只有 handler 內記的 log 才帶 `userId`、`moduleKey` scope。
- **J6** 框架自帶的 `RequestId` log 欄位（`HostingLogScope`，連線序號格式）會和我們的 `requestId` 並存；以 `requestId`（＝框架的 `TraceId`）為準，不去關框架欄位。理由：`HostingLogScope` 在 middleware 之前就建立，改不到。代價：log 裡兩個名字很像的欄位，手冊與部署說明寫明用哪個。
- **J7** 所有 ProblemDetails（含 `[ApiController]` 自動 400）的 `traceId` 改成 `HttpContext.TraceIdentifier`：`AddProblemDetails(o => o.CustomizeProblemDetails = …)`。理由：框架預設用 `Activity.Current.Id`（`00-…-…-01` 格式），和 `X-Request-Id`、既有三個 handler 的 `traceId` 對不上；設計 §10.8 要求「錯誤回應的 `traceId` 與標頭相同」。`SessionMiddleware`（401、403）與 `IdempotencyKeyMiddleware`（400）自己寫的 `{message}` 主體也補 `traceId = ctx.TraceIdentifier`，與既有三個 handler、`ServiceResultExtensions` 同格式。代價：無（`toApiError` 不讀 `traceId`）。
- **J8** 最後一道例外處理回 ProblemDetails（`application/problem+json`，`status` 500、`traceId`），另加 `message` 擴充欄位放四語「系統發生錯誤，請稍後再試」。理由：設計寫 ProblemDetails；前端 `toApiError` 讀 `data.message ?? data.title`，有 `message` 才不會顯示英文 title。代價：無。
- **J9** 規則歸屬用**例外標記**，不用 log scope：三個入口（事件、檢查、任務規則）在每條規則的執行外面加 `catch (Exception e) when (RuleFailureTag.Mark(e, kind, ruleId))`（永遠回 false，不吞例外），把 `ruleKind`、`ruleId` 寫進 `e.Data`（最內層先寫者為準），最後一道例外處理讀出來記進 log。`Mark` **只寫標記、不計數**；`formwright.rule.failures` 只在 `UnhandledExceptionHandler` 真的處理到未處理例外、且讀得到標記時才 +1。理由（計數位置）：穿過規則迴圈的例外有很多是正常流程（`DbUpdateConcurrencyException`、`FrozenFieldException` 的 409、`DatabaseBusyException` 的 503、使用者中止的 `OperationCanceledException`，以及被外層 catch 掉的例外），在 `Mark` 計數會把它們算成規則失敗，O2 若拿這個 metric 做規則自動暫停就會誤停。理由（標記）：`using` scope 在例外往外傳時已經 Dispose，最後一道 handler 記 log 時看不到規則 scope，設計 §10.2.1 的做法達不到 §5.1 的歸屬目的。代價：規則執行**中**記的 log 不帶規則識別（目前這三個入口內沒有自己記 log）。
- **J10** 版本資訊三個值都走 `AssemblyMetadata`（`AppVersion`、`GitCommit`、`BuildTime`），不碰 `InformationalVersion`。理由：沒注入時 `InformationalVersion` 預設是 `1.0.0`，分不出「沒注入」；`.claude` 規則也不准手改 csproj 版本。沒注入時三個欄位都回 `dev`。代價：無。
- **J11** Render 上的 commit 取 `RENDER_GIT_COMMIT` build arg（Dockerfile 以 `GIT_COMMIT` 優先、退回 `RENDER_GIT_COMMIT`）；`APP_VERSION` 目前沒有發版流程，Demo 會是 `dev`。⚠️ 未驗證 Render 是否把 `RENDER_GIT_COMMIT` 當 build arg 傳入；o1a 上線後在 Demo 看 `/api/version` 的 `commit`，是 `dev` 就在交付說明記下，不擋上線。
- **J12** 政策 `ops.slowRequestMs`、`ops.clientErrorCollection` 由 `CachedSystemPolicy`（singleton、60 秒、用 `TimeProvider`）讀；讀不到資料庫時回程式出廠值並記 Warning，不讓請求失敗；**失敗結果快取 10 秒**（`FailureTtl`，期間回出廠值、Warning 每個快取週期最多一則），讀值用自己的 2 秒 token（`ReadTimeout`），不用 `RequestAborted`。`RequestContextMiddleware` 只在耗時 ≥ `PolicyCatalog.OpsSlowRequestMs.Min`（200ms）時才讀慢請求門檻（低於下限一定不慢）。理由：失敗不快取時，資料庫出問題會讓每個請求結束都再連一次資料庫（PostgreSQL 連線逾時預設 15 秒）並各記一則 Warning，把故障放大。代價：資料庫恢復後最多 10 秒才讀回設定值；`FailureTtl`、`ReadTimeout` 兩個新寫死值列進寫死清單。「最多 60 秒生效」寫在這兩項的說明文字（help），不另做畫面元件。
- **J13** 前端錯誤收件：body 超過 8KB 回 413；欄位超長在伺服器**截斷**（訊息 500、stack 4000），不回 413；`kind` 不在 `vue`、`window`、`promise`、`chunk` 內回 400。其他欄位也截斷與驗格式：`name`、`moduleKey` 100 字，`route`、`browser` 200 字，`version` 50 字，`locale` 20 字；`route` 去掉 `?`、`#` 之後的部分，不是 `/` 開頭就丟掉（記成 null）；`lastRequestId` 不符 `^[0-9a-f]{32}$` 就丟掉。理由：前端本來就截斷，伺服器截斷比較寬容；body 上限才是防護；`route` 會進指紋，不設限時匿名就能灌爆 O2 的同指紋聚合。代價：六個欄位上限是新寫死值，列進寫死清單。
- **J14** `SessionMiddleware` 對 client-errors 加「可選登入」分支：帶 cookie 時照常比對資料庫，失效就**降成匿名**繼續（不回 401、不登出），有效才把 userId 交給 handler。理由：設計 B1 要「已登入時照常經過帳號檢查」，但既有 `IsAnonymous` 白名單會整段略過；回 401 又會讓 session 過期時的錯誤收不到。代價：多一個分支與兩個測試。
- **J15** 來源 IP 判斷從 `AuthController.ClientIp()`（private）抽成 `WebAPI/Security/ClientIpResolver.cs`（singleton），登入與 client-errors 共用；行為不變。
- **J16** 排程器的租約、續租、結束、補列都是 `ITransactionalRequest`，經 `TransactionBehavior`／`WriteGate`。理由：設計 §10.2.8 要求工作走 pipeline；SQLite 上租約的 `ExecuteUpdate` 若不經 `WriteGate`，和使用者寫入搶鎖會拿到 `SQLITE_BUSY`。PostgreSQL 上 `WriteGate` 保留程序內排隊（pg0 T18），同一條路徑照用，但正確性只靠條件式更新。**每個 Ensure、Acquire、Renew、Finish 各開一個短 DI scope**，不共用 DbContext：撞鍵失敗的 Added 實體不會留在下一個 Ensure 的 change tracker，續租迴圈與 `Finish` 也不會同時用同一個 context。續租在自己的 scope 與工作的交易並行，不巢狀在工作的交易裡，PostgreSQL 上不會自己等自己（pg0 §15 第 10 條）。代價：每次 tick 多幾次短交易（只有到期時才搶）；長交易（匯入、開應用程式）會讓續租等滿逾時，處理見 J19。
- **J17** 補列（B7）撞唯一鍵時 handler 回 `ServiceResult.Conflict(null)`，讓 `TransactionBehavior` 回滾，排程器把 Conflict 當「別的實例已補」。理由：PostgreSQL 的交易在 INSERT 失敗後整個不能用，不能在同一交易吞掉例外再 commit。撞鍵判斷集中在新的 `IDbErrorClassifier`（Application 介面、Persistence 實作；SQLite 用 extended error code 2067／1555），pg0 只補 Npgsql 分支（23505）。`IsTransient` 包現有 `DatabaseBusy.Is`，pg0 補 40001／40P01。
- **J18** 排程器核心（`JobRunner`、`IScheduledJob`、requests）放 Application；`BackgroundService` 放 WebAPI（Application 沒有參考 Hosting）。技術上限放在 `SchedulerLimits`（`Tick` 30 秒、`Lease` 5 分、`Renew` 1 分、`MaxRun` 10 分），`JobRunner` 建構時可傳入，只有測試會傳別的值。
- **J19** 結果判定：`PartiallyFailed` 也累加 `ConsecutiveFailures`；程式關閉造成的 `Cancelled` 不累加，`NextDueUtc`＝結束時間（下一個 tick 任何實例都可接）；逾時算 `Failed`（`LastError` 寫 `timeout`）。取消原因分三種，log 與 metric `result` 照實記：關閉（`Cancelled`）、逾時（`Failed`／`timeout`）、租約遺失（`leaseLost`，不寫 `Finish`：別人已接手，`Finish` 的 WHERE 本來就會 no-op）。續租：`Renew` 回 false（不是持有者）立刻取消工作、記 Warning；續租丟 transient 例外（`IDbErrorClassifier.IsTransient`，例如 `WriteGate` 等滿逾時的 `DatabaseBusyException`）只記 Warning、下一個 Renew 週期再試，**不把工作判成失敗或取消**（pg0 §7 要求）；只有連續失敗到「上次成功續租的到期時間 − 現在 < 一個 Renew 週期」才主動取消並記成租約遺失，避免租約過期後被別的實例接手而重跑。`Finish` 之前先停掉並 await 續租迴圈，避免續租讀到 false 記一則假的「租約遺失」。新列的 `NextDueUtc`＝補列當下；`SchedulerHostedService` 啟動後先等一個 `Tick`（30 秒）才跑第一次 `TickAsync`，不和冷啟動的第一位訪客搶 CPU 與 `WriteGate`。
- **J20** 排程與租約的測試寫在 WebAPITests（`TestApp(fileDatabase: true)`，每個 scope 一個真的 `DbContext`、真的 Acting 裝飾器），不寫在 ApplicationTests。理由：ApplicationTests 的 `DesignerTestBase` 共用單一 `DbContext`、沒有 Acting 裝飾器，模擬不出「每位使用者一個 scope」與兩個實例。代價：測試較慢；pg0 改 provider 時要讓 `TestApp` 能切 PostgreSQL。
- **J21** `TestApp` 預設 `Ops:Scheduler:Enabled=false`，排程測試自己 new `JobRunner` 呼叫 `TickAsync`。理由：否則每個 WebAPI 測試主機啟動就跑通知維護，改到既有測試的通知筆數。
- **J22** `NotificationUpkeepJob` 每位使用者一個新的 DI scope＋`ActingScope.Begin(userId)`，先用唯讀的 `NotificationUpkeepProbe.NeedsUpkeepAsync` 判斷，成立才送 `EnsureNotificationUpkeepRequest`。理由：共用 scope 時，一位使用者的 `SaveChanges` 失敗會把 Added 的通知留在 change tracker，被下一位的 commit 一起寫出去；先唯讀判斷可避免每小時替每個人搶一次寫入鎖。`NeedsUpkeepAsync` 從 `GetNotificationsHandler` 搬出來，兩條路徑共用。
- **J23** 前端錯誤代碼接在訊息尾巴：`…（錯誤代碼：ab12cd34）`，在 `toApiError` 一處組好。理由：錯誤提示散在 19 處以上的 `$q.notify`／`Notify.create`，各自顯示 `err.message`；改一處就全部生效。設計 U10 寫「多一行」，Quasar notify 預設不換行。使用者已裁決照此做（B2，2026-11-12），設計 U10 在 Task 18 寫回。代價：不是獨立一行；要改成換行得逐處加 `multiLine`；390 寬時要確認尾端代碼沒被截掉（Task 18）。5xx 回應沒有 `message`（例如 Render 代理的 502 HTML）時，先退回四語 `common.serverError`「系統發生錯誤，請稍後再試」再接代碼，不顯示 `undefined`。
- **J24** 前端未處理的 promise rejection 與 Vue `errorHandler` 收到的錯誤，若是 `ApiError`（有數字 `status`）就不回報（Vue 會把 `@click="async () => …"` 沒接住的 rejection 送進 `errorHandler`）；判斷集中在 `shouldReport(kind, error)`，另有瀏覽器雜訊忽略清單 `IGNORED_MESSAGES`（目前只有 `ResizeObserver loop`，技術限制）。理由：那是 API 失敗，後端已有 log；否則每個沒接 `onError` 的查詢都會被當成前端錯誤。Vite 的 `vite:preloadError` 事件與 `router.onError` 都接，走同一個去重，更新提示只顯示一次。
- **J25** 版本注入用 Quasar `build.env`（程式讀 `process.env.APP_VERSION`），不是設計寫的 `import.meta.env`。理由：Quasar app-vite 文件化的做法；兩者效果相同。
