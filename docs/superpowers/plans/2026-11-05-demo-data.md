# 動態模組 POC：Demo 資料 實作計畫

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 系統管理員（或站台啟動時）一鍵產生四個情境（訂單、故障報修、模具保養＋客戶擴充、品質異常）的模組與「像真的」業務資料；全部走既有指令、以各記錄建立者的身分與模擬日期送出，整批單一交易，同一個「今天」產生兩次結果相同。

**Architecture:**
- **範圍化身分與時間**：Application 層的 `ActingScope`（`AsyncLocal`）在一段非同步流程內覆寫 `ICurrentUser.UserId` 與 `IBusinessTime.Now`；`ICurrentUser`、`IBusinessTime` 的註冊被包一層裝飾器，有覆寫時回覆寫值，否則回原本的實作。全部指令在同一個 DI scope（同一個 DbContext、同一個交易）裡送出（待裁決 2）。
- **產生器＝重播既有指令**：`GenerateDemoDataRequest`（`ITransactionalRequest`，唯一的外層交易）依序：交易內衝突檢查 → 以 admin 身分 `InstantiateTemplateRequest` 套用 `order`、`repair`、`mold-care`、`quality` 四個內建範本 → 補跨範本的彙總欄位 → 啟用模組 → 用既有權限指令補欄位層權限與選項範圍 → 把四個情境的記錄步驟依模擬時間排序，逐步以「該步驟的使用者＋模擬時間」送 `CreateRecordRequest`／`UpdateRecordRequest`。任何一步失敗就停下回傳，外層回滾。
- **背景執行**：WebAPI 的 `DemoDataRunner`（singleton）在新的 DI scope 裡跑產生器，同時只允許一個；啟動時（`Demo:SeedOnStartup`）與手動按鈕都走它。狀態用 `GET /demo-data` 查。
- **資料內容用 C# 描述**（spec §8 留給實作者）：四個情境各一個類別，從「今天」與固定亂數種子純函式地算出步驟清單。

**Tech Stack:** 沿用第 1–8 階段，不加套件。

**Spec:** `docs/superpowers/specs/2026-11-05-demo-data-design.md`（權威）；上位文件 `docs/superpowers/specs/2026-11-03-dynamic-modules-design.md`。介面沿用第 8 階段計畫 `docs/superpowers/plans/2026-11-05-phase8-templates.md`（範本格式、`TemplateInstantiator`、`TemplateCatalog`、`TemplateValidator`）。

**前置文件**：第 1–8 階段裁決全部仍然有效。執行時的裁決寫進 `docs/superpowers/plans/2026-11-05-demo-data-rulings.md`。

## 待裁決（2026-11-05 已裁決：全部採下列建議，見 spec §9）

以下是 spec 做不到或互相矛盾之處。計畫**照「建議裁決」撰寫**；裁決不同時，只有標出的 task 要改。

1. **額外使用者與群組由誰補**（spec §4.5 寫「Demo 產生器補上」）。
   - 問題：一是 `DbKnownUsers` 在程序存活期間只載入一次使用者清單。產生器在第一個請求之後才補人的話，`X-User: maint01` 會一直回 401，要等重啟才恢復。二是沒有新增使用者或群組的指令，產生器只能直接寫資料表，違反 spec §7「不直接碰 DbContext」。
   - **建議裁決**：`maint01`、`qa01`、`floor02` 與群組 `maint`、`qa` 放進 `SeedData`（不存在才加），和模具、客戶的處理方式一致。影響 Task 2。
2. **「每個身分開一個 DI scope」和「單一交易」互斥**（spec §6）。
   - 問題：不同 DI scope 會拿到不同的 DbContext 與連線，不可能共用同一個交易。
   - **建議裁決**：在同一個 scope 內用 `AsyncLocal` 切換身分與時間（`ActingScope`）。影響 Task 1。
3. **「模具明細頁看得到反向關聯清單」做不到**（spec §4.3）。
   - 問題：反向關聯只支援指向動態模組的參照（`ListIncomingReferenceFieldsAsync`）。模具是既有實體，參照欄位也不能指向擴充模組（`IsValidRefTargetAsync` 只收 Standalone）。
   - **建議裁決**：改在三處示範反向關聯：保養紀錄明細頁的「更換零件」、訂單明細頁的「品質異常」、報修單明細頁的「關聯報修單」。Demo 腳本照這三處寫。影響 Task 3、Task 9。
4. **共用檢視「我的待處理」「本月結案」寫不出來**（spec §4.2）。
   - 問題：篩選條件沒有「目前使用者」變數，也沒有「本月」運算子，只有 `withinLastDays`。
   - **建議裁決**：改成「未結案報修」（狀態是待處理、處理中、待驗收）與「近 30 天結案」（狀態結案且完成日期 `withinLastDays 30`）。影響 Task 3。
5. **品質異常範本無法完全獨立套用**（spec §4.4 要參照「訂單」模組；指派要求三個新範本都能單獨「從範本建立」）。
   - 問題：`quality.order` 參照的是範本外的模組鍵 `order`，庫裡沒有 `order` 模組時，`AddField` 會回 400「參照目標不正確」。
   - **建議裁決**：接受。「能單獨從範本建立」對品質異常的意思是「庫裡已有 `order` 模組時」，手冊寫明；測試兩種情況都斷言。影響 Task 3。
6. **「下次保養日＝保養日期＋週期」**（spec §4.3）。
   - 問題：公式只能引用同模組的欄位，「保養週期」卻在模具擴充模組上。
   - **建議裁決**：保養紀錄自帶整數欄位「保養週期（天）」（產生器填入該模具的週期），公式寫 `DATEADD({careDate}, {cycleDays})`。影響 Task 3。
7. **品質異常沒有「狀態」欄位**，但檢視「未結案的重大異常」需要它（spec §4.4）。
   - **建議裁決**：加 `status` 下拉（開立、處置中、結案），再加一條「結案後整張唯讀」規則。影響 Task 3。
8. **手動產生需要的權限**：spec §6 寫「設計器的新增與修改權限（和『從範本建立』相同）」，但「從範本建立」只需要 `Add`。
   - **建議裁決**：照派工指示，`Add` 與 `Edit` 都要有。影響 Task 7。

## 已定決策（spec 沒說死、計畫代為決定的部分）

1. **衝突項目**：四個範本裡全部模組的 `Key`，以及有 `HostEntityKey` 的模組（`design.mold`、`sales.customer`）是否已有擴充模組。清單從 `TemplateCatalog` 讀，不另外寫死。訊息格式：`模組代碼 {key} 已存在`、`既有實體 {hostEntityKey} 已有擴充模組`。
2. **狀態判斷**：沒有另存標記。
   - 執行器正在跑：`running`。
   - 這個程序內最後一次成功：`generated`；最後一次失敗：`failed`（附訊息）。
   - 否則看衝突檢查：沒有衝突是 `notGenerated`；四個範本的模組代碼**全部**存在是 `generated`；其他情況是 `conflict`（附清單）。
3. **模擬時間**：所有步驟發生在「今天 −180 天」到「昨天」之間。時刻由種子決定，落在 08:00–17:59。「今天」的步驟一律不做，所以稽核時間永遠在過去，同一天產生兩次連時間戳都相同。記錄**欄位值**裡的日期可以落在未來（交期、下次保養日），範圍照 spec 是「近 3 個月到未來 1 個月」。
4. **確定性**：每個情境各用一個 `new Random(種子)`，種子分別是 `order` 20261101、`repair` 20261102、`mold-care` 20261103、`quality` 20261104。改一個情境不會牽動其他情境的亂數。步驟依（模擬時間、情境順序、加入順序）穩定排序後執行。
5. **身分分配**：
   - 結構與權限一律以 `admin` 建立。
   - 訂單：`sales01`、`sales02` 交替建立，`manager01` 推進狀態。
   - 客戶擴充：`manager01`。模具擴充、保養紀錄、更換零件：`maint01`。
   - 報修：`floor01`、`floor02` 提報，`maint01` 處理；另有 5 筆由 `maint01` 自己提報（預防性檢修），用來示範現場人員的「同群組」範圍看不到它們。
   - 品質異常：20 筆由 `qa01` 建立（含全部「重大」），10 筆由 `floor01`、`floor02` 建立（不填不良率、不選重大），之後由 `qa01` 處置。
6. **權限補充**：範本帶不了、由產生器用既有指令補的部分。做法一律是先 `GetModulePermissionsRequest`，在回傳的完整設定上加東西，再整份 `SaveModulePermissionsRequest`；這個指令是整份取代，不能只送差異。
   - `order`：群組 `qa` 讀取，資料範圍全部，沒有金額軸。品保要能參照訂單（`ReferenceValidator` 會檢查目標模組的 Read）。
   - `quality`：欄位「責任單位」對 `sales` 唯讀；「不良率」對 `floor` 隱藏；選項「重大」的範圍只給 `qa`。
7. **進度**：產生器每完成一個步驟回報一次（完成數、總數），狀態頁顯示「產生中（n／N）」。執行器記錄總耗時，寫進 log：`Demo 資料產生完成：{n} 個步驟，耗時 {秒} 秒`。

## Review Focus

1. **在已有自建資料的庫按「產生」**（例如本機 `poc.db` 已有自建的 `order` 模組，或「客戶」已有擴充）：預期回 409 並列出衝突，任何模組、記錄、編號序號、權限都不變。對應 Task 4 的 `Generate_ExistingOrderModule_Conflict_NothingChanged` 與 Task 2 的 `Seed_DoesNotOverwriteExistingNames`。
2. **兩個觸發同時發生**（啟動時的背景產生還在跑，管理員又按了按鈕；或連按兩下）：預期第二個回 409「Demo 資料產生中，請稍候」，最後只有一份資料。對應 Task 7 的 `Generate_WhileRunning_409`。
3. **跨月、跨年的「今天」**（今天是 12/1 或 1/1）：自動編號期別跟著模擬日期走，「逾期」「本週到期」的資料照樣存在，不會因為日期換算出錯而整批失敗。對應 Task 6 的 `Generate_OnNewYearsDay_SucceedsWithDistributions`。

5. **補上的使用者能不能切換**：在全新的庫啟動後，`X-User: maint01`、`qa01`、`floor02` 不會回 401，而且是第一個請求就能用。對應 Task 2 的 `SeededDemoUsers_AcceptedAsXUser`（WebAPI 測試）。
