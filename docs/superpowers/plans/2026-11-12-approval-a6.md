# 簽核 a6：CRM 設計案與簽核 Demo、文件 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 內建 CRM 多一個「設計案」模組，跑通簽核設計 §17.7 的故事。故事是：業務主管建案並指派業務，業務和設計人員依狀態來回派工，設計上傳圖，業務記下客戶意見再交回設計；兩輪後送簽，由負責業務的直屬主管同意，最後結案。Demo 資料預置三筆停在不同階段的設計案，手冊附一份可以照著操作的 Demo 劇本。

**Architecture:** 程式裡不寫任何 CRM 專用邏輯，設計案是套件資料。模組、狀態機、三條任務規則、權限都放在 `crm-sales.app.json`，套件升到 1.2.0，格式仍是 7。簽核流程目前進不了套件，因為格式 8 屬於 a5。a5 之前，Demo 產生器在 `DemoStructure` 以 admin 身分走既有 API 建流程，順序是先建流程，再把轉移標成需簽核；a5 上線後改由套件內建，產生器拿掉這一步（見「交給 a5」）。Demo 站預設停用上傳，所以平台加一個通用的「伺服器端信任上傳」範圍 `ServerUploadScope`，只有 Demo 產生器會開；HTTP 路徑仍照環境開關回 409。設計圖用程式產生的虛構 PNG，不放二進位檔進 repo。

**Tech Stack:** .NET 8、EF Core（SQLite；PostgreSQL 等 pg0 合併後補驗）、MediatR、xUnit＋FluentAssertions；前端 Vue 3、Quasar 2。a6 預計不改前端程式，只做實機走查。不新增相依套件，沒有 migration。

## 計畫判斷（技術類，直接決定，可推翻）

每條寫判斷、理由與選錯的代價。

- **J1 模組代號與鍵**：表頭 `design-case`／`crm-design-case`「設計案」，明細 `design-drawing`／`crm-design-drawing`「設計圖」；選單分區「銷售」。理由：沿用 `crm-` 前綴與既有分區。代價：無。
- **J2 表頭欄位**：
  - `no`：自動編號「案號」，格式 `DC-{yyyyMM}-{000}`，列表顯示。
  - `name`：文字「案名」，必填，標題欄位。
  - `customer`：參照「客戶」，指向往來對象，`refGuard` 角色限客戶或兩者，同報價單。
  - `owner`：人員「負責業務」，必填。
  - `designOwner`：人員「設計負責人」，必填。
  - `requirement`：多行文字「需求說明」，必填。
  - `status`：選項「狀態」，預設需求確認。
  - `drawings`：附件「設計圖檔」。
  
  §17.7 沒寫案號與案名，但模組需要標題，簽核中心與通知也要顯示可讀的名稱。代價：多兩個欄位。
- **J3 明細欄位**：
  - `case`：參照，`relation: detail`。
  - `version`：整數「版本」，必填。
  - `fileName`：文字「圖檔名稱」，說明寫「對應表頭『設計圖檔』裡的檔名」。
  - `uploader`：人員「上傳人」。
  - `feedback`：多行文字「客戶意見」。
  
  標題欄位是 `fileName`。理由見 U1。代價：檔名靠人工對應，不能點列直接下載。
- **J4 狀態選項代號**依序是 `requirement`（需求確認，灰）、`designing`（設計中，藍）、`customerReview`（客戶確認中，橘）、`managerReview`（待主管確認，紫）、`closed`（結案，綠）、`cancelled`（取消，紅）。`closed`、`cancelled` 標 `readOnly`。理由：一般安裝在 a5 前沒有簽核，結案靠唯讀狀態保護；Demo 加了簽核後，結案另外也是鎖定狀態，兩者不衝突。代價：無。
- **J5 轉移與群組**（空陣列表示有編輯權的人都可以，同既有套件）：

  | 轉移 | 群組 |
  |---|---|
  | 需求確認 → 設計中 | `sales`、`manager` |
  | 設計中 → 客戶確認中 | `designer`、`sales` |
  | 客戶確認中 → 設計中 | `sales` |
  | 客戶確認中 → 待主管確認 | `sales`（Demo 另標需簽核，見 J7） |
  | 待主管確認 → 結案 | `manager` |
  | 需求確認、設計中、客戶確認中 → 取消 | `manager` |

  取消不從待主管確認出發，免得取消落進鎖定狀態的後續範圍。理由：符合 §20.4 第 4 項「送簽轉移限業務群組」。設計中 → 客戶確認中加 `sales`，是為了在一般安裝沒有對應設計群組時仍走得下去。代價：群組設定是套件預設值，客戶可以改。
- **J6 簽核流程內容**（Demo 產生器建立，a5 後改由套件帶）：
  - 代號 `crm-design-case-review`，名稱「設計案主管確認」，掛在待主管確認，優先序 1，啟用。
  - `when` 空、`rejectTo` 設計中、`fallbackApprovers` 省略（省略時由系統管理員頂替，§6.5）。
  - 一關：代號 `owner-manager`，名稱「負責業務主管」，來源 `manager level 1`，`mode any`，`onEmpty fallback`，`dueHours` 不設（逾期屬 a3），沒有可編輯欄位。
  - 轉移 `customerReview → managerReview` 標 `approval { required: true, noMatch: "block" }`。
  
  理由：§17.7 與 §20.4 第 4 項。代價：無。
- **J7 a5 之前的簽核流程由 Demo 產生器建**：新檔 `DemoService/DemoApprovals.cs`，`DemoStructure.BuildAsync` 開完 CRM 之後呼叫。做法照 `ApprovalApiTests.Arrange` 的順序：
  1. 套件裝好的狀態機已經存在。
  2. `CreateApprovalFlowRequest` 建流程。
  3. `SaveWorkflowRequest` 把那條轉移標成需簽核。狀態機從 `IModuleRepository` 讀出後只改那一條。
  
  理由：只用既有 API，不碰套件格式；Demo 本來就在 `DemoStructure` 建套件帶不了的結構（報表、儀表板）。不改成「開 CRM 時自動建流程」，因為那是替特定應用程式寫特例，違反鐵則 1。代價：a5 之前，一般安裝的 CRM 沒有這個流程（U2）。
- **J8 伺服器端信任上傳**：新檔 `Application/Common/Uploads/ServerUploadScope.cs`。它用 `AsyncLocal<bool>` 加 `Begin()` 回傳 `IDisposable`，靜態屬性 `Active` 表示目前在範圍內。兩個讀環境開關的地方改成「`settings.UploadEnabled || ServerUploadScope.Active`」：
  - `AttachmentUploadGate`（a2d2 合併後的位置，以當時程式為準）。
  - `AddTaskCommentHandler`（`TaskCommentHandlers.cs:68`）。
  
  只有 `GenerateDemoDataHandler` 在整批產生期間開這個範圍。它不是政策，只是讓伺服器內部程式跳過「訪客不能寫檔」的環境開關；權限、副檔名白名單、大小上限照常檢查。理由：§20.4 第 7 項要求產生器在伺服器端寫入；Dockerfile.demo 產生資料時已經設了 `Demo__LoginEnabled=true`，上傳是關的（`Dockerfile.demo` 的 `ENV` 在 `RUN --generate-demo-data` 之前），手動按「產生 Demo 資料」時也一樣。只在 Dockerfile 加 `Attachments__UploadEnabled=true`，在 Demo 站上手動產生仍會整批失敗。代價：多一個環境開關的例外，列進交付說明的「可寫死清單」（安全邊界類）。

- **開啟 CRM 時由平台自動建流程**：一般安裝也有。但這是替特定應用程式寫特例，違反鐵則 1，不建議。

**U3 採購單金額門檻的 Demo 要不要在 a6 做**

功能清單的 a6 寫「以設計案與採購單金額門檻情境驗收」，§17.6 也要求 Demo 站示範採購單。但採購單預設流程屬 §14.3，會隨 a5 進套件。選錯的代價：在 a6 做會有一份 a5 就要刪掉的產生器程式。

- **移到 a5 驗收（推薦）**：a5 本來就要讓進銷存套件帶採購單的預設流程，Demo 直接用套件的流程，不寫要丟掉的程式。a6 只示範設計案（一關簽核），大額兩關、小額直接確認要等 a5 才看得到。
- **a6 也用產生器建採購單的兩個流程**：Demo 更早看得到金額門檻與多流程優先序。代價是約 150 行產生器程式加測試，a5 上線時再刪掉。

**U4 建案時要不要派任務給負責業務**

§17.7 只列兩條任務規則（設計中、客戶確認中），但故事寫「業務主管指派給業務；業務收到產品需求」。選錯的代價：不加的話，主管建案後業務沒有任何提醒，Demo 的第一步要靠口頭說明。

- **加一條建立時觸發的規則「確認需求並交設計」給負責業務（推薦）**：主管建案，業務的鈴鐺馬上有「指派給你的任務」；之後主管若換負責業務，未完成的任務會跟著換人（任務設計 §5.5）。例子：`manager01` 建「展示架結構設計」，`sales01` 立刻收到通知。代價是每個案子多一個任務，業務要記得把它標完成。
- **照設計只有兩條**：任務最少。但業務要自己去看設計案列表，才知道有新案子。

**U5 Demo 預置哪些設計案**

Demo 站不能上傳，現場只能從已有圖的階段開始操作。選錯的代價：只放結案那筆的話，現場沒有可以送簽的案子；Demo 站重新部署前，現場的操作會留著。

- **三筆：結案（看歷程）、第二輪客戶確認中（現場送簽、同意或退回）、設計中（看設計人員的待辦）（推薦）**：涵蓋故事的三個階段，現場示範簽核只要 10 分鐘。例子：簡報時先開「感測器外殼改版」講完整歷程，再用「控制箱面板改版」現場送簽、換 `manager01` 同意。
- **只放一筆走完的結案**：最接近設計 §17.7 的驗收句，但現場沒辦法示範送簽與同意。
- **再加一筆「待主管確認」**：主管可以直接示範結案。但會多一筆簽核中心待辦，和現場送簽那筆容易混淆。
