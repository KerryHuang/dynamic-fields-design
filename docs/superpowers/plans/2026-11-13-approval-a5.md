# 簽核 a5：套件格式 8（簽核流程）Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 簽核流程跟著應用程式套件走：套件格式升到 8，轉移可帶 `approval`、狀態可帶 `editable`，頂層新增 `approvalFlows[]`；開啟時流程一律保留（群組被略過就記成對不上的來源、由備援頂替並逐條列出），匯出寫出流程目前版本，關閉、重新開啟、刪除照應用程式生命週期。內建 CRM 的設計案流程改由套件提供，刪除 `DemoApprovals`；進銷存採購單帶預設金額門檻流程，Demo 用它示範「小額直接確認、中額一關、大額兩關」。

**Architecture:** 照格式 7（任務規則，t4b）的分層：`Data/AppPackageData.cs` 加 record → `AppPackageValidator.V8.cs`（結構層、引用層、狀態一致性）→ `AppApprovalFlowCodec.cs`（代號 ⇄ Id、群組對應與頂替清單，純函式）→ `AppFlowInstaller`（開啟時安裝，兩趟存狀態機）、`AppOpenPlanner`（預覽與前置檢查）、`AppExporter`（匯出）。安裝一律走既有的 `SaveWorkflowRequest`、`CreateApprovalFlowRequest`，設計器的全部驗證照跑，失敗整批回滾。**沒有 migration**：流程掛在模組上，模組刪除時 `DeletionRepository.PurgeModuleAsync` 已清流程、版本、實例；模組關閉時簽核動作已回 409。前端只動設計器的簽核人來源編輯器（顯示開啟套件時略過的群組）。

**Tech Stack:** .NET 8、EF Core（只驗 SQLite）、MediatR、xUnit＋FluentAssertions；Vue 3、Quasar 2、TanStack Query、vue-i18n、vitest、bun 1.4.0。不新增相依套件。

## Global Constraints

- **業務政策不寫死**（鐵則 2）：
  - 套件結構層的數量檢查只用**技術上限**，從 `PolicyCatalog` 的 `Max` 取（關卡 `ApprovalMaxStages.Max`＝20、人數 `ApprovalMaxApprovers.Max`＝50、逾期 `ApprovalMaxDueHours.Max`、主管層數 `ApprovalMaxManagerLevel.Max`＝10），程式不寫數字。
  - 政策生效值在兩處把關：預覽與開啟時用**系統層**生效值檢查一次（`AppPackageValidator.ApprovalLimitErrors`，同格式 7 的 `TaskRuleLimitErrors`）；建立流程時 `CreateApprovalFlowRequest` 依**模組**生效值再驗一次（模組在開啟前不存在，覆寫值只會在這一步出現）。

- **fail-closed**：格式 7 以下出現 `approvalFlows`、轉移的 `approval`、狀態的 `editable` 整份拒絕；格式 9 以上「需要較新版本」；任何會讓單據少簽的情況（略過群組、匯出缺資料）一律擋下或改派備援，不靜默略過。

## 計畫判斷（技術類，主控決定，可推翻）

每條：判斷／理由／選錯代價。

- **J1 沒有 migration，流程不記 `AppId`。** 任務規則記 `AppId` 是因為規則可以掛在主檔模組上、要分清是哪個應用程式裝的；簽核流程只能掛在本套件的模組（§14.4 跨應用程式一點），模組刪除時 `PurgeModuleAsync` 已清乾淨，模組關閉時動作已 409。代價：日後若允許流程掛在主檔模組，要補欄位與 migration。
- **J2 `approvalFlows[]` 每一項與 `DefinitionJson` 同形。** 流程層 `code`、`name`、`active`、`module`、`to`、`priority` 之外，`shape`（**必填**）、`when`、`rejectTo`、`fallbackApprovers`、`stages[]` 與定義同名；關卡屬性 `code`、`name`、`when`、`approvers`、`mode`、`editableFields`、`dueHours`、`onEmpty` 與定義同名。差別只在引用寫代號：欄位用限定欄位名、狀態用選項代號、群組用 `groups[].code`，簽核人來源的 `groupIds`／`fieldId`／`candidateGroupIds` 在套件裡叫 `groups`／`field`／`candidateGroups`（§14.2 範例的寫法）。理由：fg6 加 `graph` 時只要在同一個 record 加 `Nodes`、`Edges`，簽核節點直接沿用關卡的 record 與轉換函式；`shape` 是分派鍵（流程圖設計 §7.7），必填讓舊檔與新檔不必猜。代價：手寫套件多一個屬性（§14.2 範例沒寫 `shape`，見「與設計矛盾」第 3 點）。
- **J3 開啟時兩趟存狀態機。** 第一趟照舊存狀態（含 `editable`）與轉移（不帶 `approval`）；接著分錄 → 事件 → 檢查 → **建流程**；最後只對有需簽核轉移的模組再存一次狀態機，這次帶 `approval`。理由：`SaveWorkflowRequest` 要求需簽核轉移的目標狀態已有流程，流程又要求狀態機存在（`DemoApprovals` 的順序就是這樣）；第二趟存檔讓入口約束、事件交叉檢查、鎖定規則全部照設計器規則跑，不另寫一套。代價：開啟多一次存檔。
- **J4 V8 只做「看套件就判斷得出」的檢查，狀態一致性重用 `ApprovalConstraints.Validate`。** 每個有流程或需簽核轉移的模組，用選項代號配發暫時 Id（1、2、3…），在記憶體組出 `Workflow`、只含狀態欄位與選項的 `Module`、`FlowState` 清單，呼叫 `ApprovalConstraints.Validate`，錯誤鍵換回代號（`transitions[draft>confirmed]`、`states[confirmed]`、`flows[inv-po-large]`）。可編輯欄位的公式閉包（§9.2）與事件交叉檢查（§5.3）需要公式與事件的 Id 解析，留給開啟時的設計器指令（失敗整批回滾）。理由：規則只有一份；套件設計 §4.8 本來就把要看資料庫的檢查交給開啟時。代價：閉包與事件的錯誤要到預覽或開啟才出現，不在匯入時（見「與設計矛盾」第 2 點）。Task 0 確認 `ApprovalConstraints.Validate` 只讀 `module.Blocks` 的狀態欄位標籤，不讀其他欄位；讀了就改成傳入標籤函式（小重構，不改行為）。
- **J5 數量上限兩層。** 結構層用技術上限（純函式，啟動時 `AppCatalogChecks` 也跑）；`ApprovalLimitErrors(p, limits)` 用系統層生效值，預覽、開啟、匯入各呼叫一次（同 `TaskRuleLimitErrors`）；模組層覆寫由 `CreateApprovalFlowRequest` 負責。
- **J6 頂替清單由一個純函式產生。** `AppApprovalFlowCodec.Substitutions(flow, mappedGroupCodes)` 給預覽（`groupMap` 裡 map 或 create 的代號）與開啟（實際對應到 Id 的代號）共用，保證預覽說的就是開啟做的。

## 主控裁決（待使用者確認）

影響使用者行為、照最合理的建議先決定，實作照此進行；使用者推翻時改套件內容或對應 Task。
