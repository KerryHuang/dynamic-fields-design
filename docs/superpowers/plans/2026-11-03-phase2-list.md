# 動態模組 POC 第 2 階段：列表實作計畫

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 使用者在通用列表可以依型別篩選、多欄排序、選欄位、用關鍵字搜尋標題，並把這組設定存成個人或共用的清單檢視；查詢全部在伺服器端完成，靠型別化索引表 `RecordIndex`。

**Architecture:**
- 存檔時，依欄位設定把可查詢的值寫進 `Dynamic_RecordIndex`，和 `Record` 在同一個交易內。
- 列表查詢改走 Dapper：`DynamicQueryBuilder` 依 metadata 白名單組出參數化 SQL，每個篩選條件是一個 `EXISTS`，每個排序欄位是一次 `LEFT JOIN`。分頁語法由 `ISqlDialect` 提供，本階段只實作 `SqliteDialect`。
- 篩選條件用規格 §8 的條件語法，由 Domain 的 `ConditionParser` 驗證並轉成型別化的 AST；第 4 階段的規則引擎沿用同一套語法與 AST。
- 前端的 `fieldTypeRegistry` 每個型別加上運算子清單與篩選輸入元件。列表頁加上篩選面板、排序編輯器、欄位選擇與清單檢視選單。

**Tech Stack:** 沿用第 1 階段（見 `docs/superpowers/plans/2026-11-03-phase1-foundation.md` 的 Tech Stack），另加 `Dapper` 2.1.35（Persistence 專案）。

**Spec:** `docs/superpowers/specs/2026-11-03-dynamic-modules-design.md`。本階段對應 §13.2 第 2 項，以及 §3 目標 7、§6.2 的 `RecordIndex` 與 `ListView`、§7 的索引欄、§8 的條件語法與運算子、§11.3 的分頁與篩選參數、§11.5、§12.3 的列表。

**前置文件**：第 1 階段計畫，以及第 1 階段裁決 `docs/superpowers/plans/2026-11-03-phase1-rulings.md`。裁決 R1–R31 對本階段一樣有效。

## 本階段範圍

**做：**
- `RecordIndex`：存檔時寫入。欄位的可篩選或可排序設定被打開時，回填既有記錄；設定被關掉時，刪除那個欄位的索引列。
- 欄位設定加上 `IsFilterable`、`IsSortable`，設計器可以勾選。
- 列表 API：
  - 篩選用 §8 條件語法，可以巢狀 `all`／`any`。
  - 最多 3 欄排序。
  - 關鍵字搜尋記錄標題（`q`）。
  - 伺服器分頁。
- 清單檢視（`ListView`）：
  - 新增、修改、刪除、列出。
  - 分個人與共用，可設預設檢視。
  - 檢視存的內容有欄位、篩選、排序。
- 前端：篩選面板、排序編輯器、欄位選擇、檢視選單、表頭點擊排序。
- 效能基準：1 萬筆記錄、30 個可查詢欄位時的寫入與查詢時間（§15 風險 9）。

**不做（留給後續階段）：**
- 權限：誰能建共用檢視、隱藏欄位不能篩選，都留到第 3 階段。本階段任何使用者都能建共用檢視。
- 條件裡的 `fieldRef`（拿另一個欄位當比較對象）：只在第 4 階段的規則引擎使用，列表篩選回 400。
- `reference`、`formula`、`autonumber`、`rollup` 的索引與篩選，各自在引入該型別的階段處理。
- `SqlServer2008Dialect`：上線前補（§13）。
- 篩選與排序寫進網址：本階段不做，重新整理後回到預設檢視（我的判斷）。

## Global Constraints

第 1 階段計畫的 Global Constraints 全部沿用，另加以下幾條：

- **新表名**：`Dynamic_RecordIndex`、`Dynamic_ListView`。用兩個 EF migration 建立：Task 3 的 `Phase2RecordIndex`、Task 7 的 `Phase2ListView`，一律用 `dotnet ef migrations add` 產生，不手寫。
- **`RecordIndex` 欄位**：
  - 主鍵 `(RecordId, FieldId, Seq)`。
  - 值欄位：`TextValue` 是 `nvarchar(450)`，`NumberValue` 是 `double?`，`DateValue` 是 `DateTime?`，`RefKey` 是 `nvarchar(100)`。
  - 索引建在 `(FieldId, TextValue)`、`(FieldId, NumberValue)`、`(FieldId, DateValue)`、`(FieldId, RefKey)`。
- **`NumberValue` 用 `double`**（我的判斷）：EF Core 的 SQLite provider 會把 `decimal` 存成 TEXT，比大小會變成字串比較。換成 SQL Server 時改成 `decimal(28,10)`，寫進 spec §15。
- **各型別寫進哪一個索引欄**，以這張表為準：

  | 型別 | 索引欄 | 寫入的值 |
  |---|---|---|
  | `text`、`email`、`phone`、`url` | `TextValue` | 原字串，超過 450 字元截取前段 |
  | `time` | `TextValue` | `HH:mm` |
  | `integer`、`decimal`、`currency`、`percent` | `NumberValue` | 數值 |
  | `boolean` | `NumberValue` | `1` 或 `0` |
  | `date` | `DateValue` | 當天 00:00 |
  | `datetime` | `DateValue` | 台北時間的本地時刻，不帶時區 |
  | `enum` | `TextValue`、`NumberValue` | `TextValue` 放 `opt_<id>`，`NumberValue` 放選項 id，排序時 JOIN 選項取 `Sequence` |
  | `multienum` | 同 `enum`，每個選項一列 | `Seq` 從 0 起算 |
  | `user` | `RefKey` | 使用者 id |
  | `textarea` | 不索引 | — |

- **哪些欄位要寫索引**：`IsFilterable` 或 `IsSortable` 為 true 的欄位，以及所有 `multienum` 欄位（照 spec §6.2）。值為 null 的欄位不寫索引列。
- **哪些型別可以設篩選、排序**：
  - `textarea` 兩個都不能設。
  - `multienum` 可以篩選、不能排序。
  - 違反時回 400，鍵是 `Config.IsFilterable` 或 `Config.IsSortable`，訊息是 `此欄位型別不支援篩選` 或 `此欄位型別不支援排序`。
- **篩選參數** `filter` 是 URL 編碼後的 JSON 字串，格式照 §8：

  ```json
  { "all": [ { "field": 12, "op": "eq", "value": "opt_3" },
             { "any": [ { "field": 15, "op": "gt", "value": 1000 }, { "field": 16, "op": "isEmpty" } ] } ] }
  ```

  - `field` 是 `Field.Id`（數字）。
  - 最外層可以是單一條件，也可以是 `all`／`any` 群組。
  - 最多 20 個條件，巢狀最多 3 層。
- **各型別可用的運算子**，以這張表為準。前後端各自實作，但都要拿 `poc/shared/filter-operators.json` 做測試比對，避免兩邊各寫各的：

  | 型別 | 運算子 |
  |---|---|
  | `text`、`email`、`phone`、`url` | `eq`、`ne`、`in`、`notIn`、`contains`、`startsWith`、`isEmpty`、`isNotEmpty` |
  | `integer`、`decimal`、`currency`、`percent`、`time` | `eq`、`ne`、`gt`、`gte`、`lt`、`lte`、`between`、`isEmpty`、`isNotEmpty` |
  | `date` | `eq`、`ne`、`gt`、`gte`、`lt`、`lte`、`between`、`withinNextDays`、`withinLastDays`、`isEmpty`、`isNotEmpty` |
  | `datetime` | `gt`、`gte`、`lt`、`lte`、`between`、`withinNextDays`、`withinLastDays`、`isEmpty`、`isNotEmpty` |
  | `boolean` | `eq`、`isEmpty`、`isNotEmpty` |
  | `enum`、`user` | `eq`、`ne`、`in`、`notIn`、`isEmpty`、`isNotEmpty` |
  | `multienum` | `in`（含任一）、`notIn`（都不含）、`isEmpty`、`isNotEmpty` |

- **運算子語意**（我的判斷）：
  - **值的形狀**：
    - `in`、`notIn` 的值是 1 到 50 個元素的陣列。
    - `between` 的值是 `[下限, 上限]`，兩端都包含。
    - `withinNextDays`、`withinLastDays` 的值是 0 到 3650 的整數 N，範圍是今天到今天加或減 N 天，含頭尾，`datetime` 以整天計。
    - `isEmpty`、`isNotEmpty` 不帶值。
  - **值的正規化**：除了 `contains`、`startsWith`，條件值都先經該型別處理器的 `Normalize`。例如 `date` 必須是 `yyyy-MM-dd`。選項值用「全部選項」檢查，所以停用的選項也能篩選。
  - **`contains`、`startsWith`**：值是 1 到 450 字元的字串，不正規化；`%`、`_`、`\` 會跳脫。大小寫是否區分依資料庫定序，SQLite 對 ASCII 不區分大小寫。
  - **`ne`、`notIn` 的空值**：結果**包含空值的記錄**，例如「狀態不等於取消」也會列出沒填狀態的記錄。
  - **「今天」**：取自 `IBusinessTime`。
- **排序參數**：`sortBy`、`sortOrder` 是兩個等長的重複參數。`sortBy` 是 `Field.Key`，`sortOrder` 是 `asc` 或 `desc`，最多 3 組。
  - 排序欄位必須是啟用中、`IsSortable` 的欄位。
  - 空值一律排最後，不論升冪或降冪。
  - 最後一律補 `Id DESC` 當作次序，確保分頁穩定。
  - `enum` 依選項的 `Sequence` 排序，不依 id 或標籤。
- **關鍵字** `q`：1 到 100 字元，對 `Record.Title` 做 `contains`，跳脫規則同上。
- **查詢錯誤**：一律回 400。
  - 錯誤鍵只有三種：`filter`、`sortBy`、`q`。
  - 訊息要指出是哪個條件、為什麼錯，例如 `欄位 12 不支援運算子 gt`、`欄位 12 不存在或未啟用`、`欄位 12 未開放篩選`。
- **SQL 安全**：SQL 字串只能由程式內的常數和白名單片段組成。欄位 id、值、模組 id 一律走 Dapper 參數。`DynamicQueryBuilder` 的單元測試要斷言：產生的 SQL 字串裡不出現任何使用者輸入的值。
- **`QueryAsync<dynamic>` 例外**：只有 `DynamicQueryBuilder` 的執行端可以用。用到的地方要寫註解，說明理由是「動態 schema 例外（spec §11.5）」。
- **清單檢視**：
  - 端點：
    - `GET /modules/{key}/views`
    - `POST /modules/{key}/views`
    - `PUT /views/{id}`
    - `DELETE /views/{id}`（硬刪除）
  - 欄位格式：`Columns` 是 `Field.Id` 陣列，`Filter` 是 §8 JSON，`Sort` 是 `[{ "field": <Field.Id>, "order": "asc"|"desc" }]`。
  - `OwnerUserId` 為 null 是共用檢視，否則是個人檢視。
  - `IsDefault` 在同一個模組、同一個範圍（共用，或同一個擁有者的個人）內最多一個。設定新的預設時，同範圍舊的預設改成 false。
- **建議的前端預設檢視**：先用自己的個人預設；沒有的話用共用預設；都沒有就用 `ShowInList` 欄位、不篩選、依 `Id` 遞減。
- **`ListView` 變更不遞增 `Module.Version`**：檢視不是 schema 的一部分。

## Review Focus

1. **`ne`／`notIn` 與空值**：篩「故障類別不等於外包」時，沒填故障類別的記錄也要出現。→ Task 5 的 `Query_NeAndNotIn_IncludeEmpty`。
2. **欄位設定在已有記錄之後才打開**：既有 30 筆記錄的欄位，事後勾選「可篩選」，篩選結果要立刻包含這 30 筆。關掉後再篩那個欄位要回 400。→ Task 3 的 `UpdateField_EnableFilterable_BackfillsExistingRecords`，以及 Task 6 的 `Paged_FilterOnNonFilterableField_Returns400`。
3. **排序與分頁的穩定性**：排序欄位大量同值或空值時，翻頁不可以重複或漏掉記錄；空值排最後。→ Task 5 的 `Query_SortWithTiesAndNulls_IsStableAcrossPages`。
4. **清單檢視引用的欄位後來被停用，或被關掉篩選**：套用這個檢視不可以讓列表變成 400。讀檢視時要剔除失效的部分，回應帶 `staleFieldIds` 提示。→ Task 7 的 `GetViews_StripsInactiveAndNonFilterableFields`。
5. **篩選值裡有 `%`、`_`、`'`、`;--`**：只能當字面值比對，不可以影響 SQL。→ Task 5 的 `Query_ContainsWithWildcardsAndQuotes_MatchesLiterally`。
