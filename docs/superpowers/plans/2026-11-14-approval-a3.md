# 簽核 a3：轉交、加簽、代理、逾期提醒 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 補齊簽核的進階動作：簽核人可以轉交、同意並加簽；使用者可以設定代理人；簽核管理員可以終止實例、改派任務；逾期的待簽會在鈴鐺補提醒；沒有模組讀取權、靠臨時讀取的簽核人可以列印預覽那一筆。全部沿用 a2 的動作管線（交易、冪等、實例 `rowVersion`、寫入後盾），資料結構不改，讓 fg1–fg6 的流程圖直接沿用。

**Architecture:** 後端在 `Application/Dynamic/ApprovalService/` 加 MediatR request 與 handler，回 `ServiceResult`，控制器只轉接（`ApprovalsController`）。轉交與改派共用一個「交接」服務；加簽重用同意的核心流程，關卡位置改由一個純函式 `ApprovalPath` 計算（取代 `PreviousRun` 與 `ActivateNextAsync` 的起點推算）；代理在 `ApprovalTaskFactory` 建任務時套用；逾期提醒是新的 `INotificationReminderSource`（讀通知時補寫，與任務提醒同一機制）；臨時讀取的列印照 schema 的 `?recordId=` 做法。**沒有 migration**：代理表、任務的 `Reason`／`OriginalUserId`／`DueTime`／`LastRemindedTime`、關卡實例的 `AddedByUserId`／`AddSignUserIds`／`queued`、歷程的 `OnBehalfOfUserId`／`TargetUserIds` 都在 a2 的 `ApprovalWorkflow` migration 裡。新增三個政策（加簽人數、加簽關卡數、逾期提醒間隔）。前端在既有動作列加四個對話框、簽核中心加代理設定、詳情頁開放臨時讀取的列印。

**Tech Stack:** .NET 8、EF Core（SQLite；新 WebAPI 測試標 `Postgres` trait，不寫 SQLite 專屬語法）、MediatR、xUnit＋FluentAssertions；Vue 3、Quasar 2、TanStack Query、vue-i18n、vitest、bun。不新增相依套件。

## 待確認的行為決定

以下是設計沒寫死、會改變使用者看到的行為的決定。實作照「推薦」進行；使用者推翻時改對應 Task。

**U1 代理只套用在系統解析出的任務，不套用在轉交、改派、加簽指定的人。**
- 推薦：關卡來源與備援解析出的任務（`Reason` 為 `resolved`、`fallback`）才看代理設定；轉交、改派、加簽是動作者明確點名的人，任務就給那個人。
- 理由：點名的人是動作者判斷後的選擇，系統再轉一手會讓動作者以為交給甲、實際到了乙；§7.5 也規定轉交的新任務 `OriginalUserId` 保留最初的人，和代理的 `OriginalUserId = 本人` 衝突。被點名的人如果在休假，他回來可以再轉交，或由管理員改派。
- 選錯代價：選「也套代理」，轉交出去的單會跑到動作者沒選的人手上，歷程要另外說明；選「不套」，點名的人休假時單據停在他那裡，要靠管理員改派。
- 例子：`ops01` 設了代理人 `sales01`（今天到後天）。新送簽的採購單第 1 關解析到 `ops01` → 任務給 `sales01`（代理）。`manager01` 把自己的一張待簽轉交給 `ops01` → 任務給 `ops01` 本人，不給 `sales01`。

**U2 個人代理設定放在簽核中心頂端，不另做個人設定頁。**
- 推薦：簽核中心標題列加「代理設定」按鈕，開對話框設定代理人與起訖日、清除；有代理時頁面頂端顯示「你的簽核目前由某某代理（起訖日）」，已設定但還沒開始時顯示「某日起由某某代理」。
- 理由：系統目前沒有個人設定頁（頁首只有外觀與改密碼），§13.5 的「個人設定」沒有落點；代理只跟簽核有關，放在簽核中心最容易找到，也不用為一個區塊新開頁面與選單。
- 選錯代價：之後若做個人設定頁，要把對話框搬過去（元件可直接重用）；若現在就做個人設定頁，多一個路由、選單與四寬度走查，只放一個區塊。
- 例子：`manager01` 下週休假，開「簽核」→ 右上「代理設定」→ 代理人選「業務一」、起訖 11-17 到 11-21 → 儲存；簽核中心頂端出現「11-17 起由 業務一 代理（至 11-21）」。

**U3 轉交、改派後的期限沿用關卡原本的期限，不重新起算。**
- 推薦：新任務的 `DueTime` 等於舊任務的 `DueTime`（關卡啟動時間＋逾期時數）。
- 理由：設計 §12 把期限定義在關卡上（`DueTime = 關卡啟動時間 + dueHours`），轉交不改變單據等了多久；重新起算會讓「轉一手就重置期限」變成拖延的方法。
- 選錯代價：沿用時，接手的人可能一收到就是逾期，鈴鐺馬上有逾期提醒；重新起算時，發起人看到的期限會因轉交而延後。
- 例子：第 1 關 24 小時、10 日 09:00 啟動，`ops01` 在 11 日 08:00 轉交給 `manager01` → `manager01` 的期限仍是 11 日 09:00，一小時後就逾期。

**U4 管理員終止的意見必填；改派的意見選填。**
- 推薦：終止不填意見回 400（同退回）；改派選填。
- 理由：終止讓整張單作廢、發起人要重送，發起人與簽核人都需要知道原因；§7.1 只規定退回必填，是因為當時終止還沒有畫面。改派不影響單據結果，只換人。
- 選錯代價：選填時，發起人只收到「已終止」通知、不知道為什麼；必填時，管理員多打一句話。
- 例子：系統管理員終止一張採購單，意見「供應商報價已過期，請重新詢價後再送」；`buyer01` 的通知點開後，時間軸上看得到這句。

**U5 「同意並加簽」可以一併修改這一關的可編輯欄位。**
- 推薦：「同意並加簽」用同一個同意對話框，多出「加簽對象」與「會簽／或簽」兩欄；可編輯欄位照常顯示、只送改過的值。
- 理由：§7.6 定義加簽「視同同意」，同意能改的欄位，加簽時也該能改；否則財務要先改金額又要加簽主管時，沒有任何一個按鈕做得到。
- 選錯代價：不允許時，需要「改值＋加簽」的人只能先請下一關退回或改走轉交，流程變長；允許時，加簽關卡的人看到的是改過的值（歷程有記錄），這正是加簽的目的。
- 例子：第 2 關財務 `fin1` 把核定金額改成 18000，同時加簽 `gm`（或簽）→ 記錄的核定金額是 18000、歷程一筆 `add-sign`，`gm` 收到「加簽給你」。

**U6 逾期提醒每隔 24 小時補一次（政策可改），只通知任務的負責人。**
- 推薦：新政策 `approval.overdueReminderHours`（模組可覆寫，出廠 24、範圍 1–720 小時）；負責人打開鈴鐺時，對每個已逾期、上次提醒超過間隔的待簽補一則「簽核逾期」。代理任務只通知代理人（負責人），本人不另收。
- 理由：§12 的 24 小時是業務政策，不能寫死；代理期間本人通常在休假，再收提醒沒有意義，而他的「待我簽核」本來就列著這張。
- 選錯代價：間隔太短鈴鐺變吵、太長逾期沒人管；本人也收時，休假的人回來會看到一整串提醒。
- 例子：`manager01` 有一張 48 小時已過的待簽；早上 9 點打開系統，鈴鐺多一則「簽核逾期：成品外殼 25 pcs」；下午再開不會多一則；隔天 9 點後再開，再多一則。

**U7 臨時讀取的簽核人可以列印預覽那一筆，不另外要求「列印匯出」權限。**
- 推薦：有這筆單據 `open` 待簽的人，即使沒有模組的讀取或「列印匯出」權，也能用啟用中的列印範本預覽；欄位與金額的可見性照臨時讀取（自己群組的欄位隱藏照套、金額看得到）。一般權限能列印的人照舊走一般路徑。
- 理由：§10.1 把「列印預覽」列在臨時讀取的範圍內，使用者 11-12 裁決排進 a3；簽核人常要印出來對紙本或蓋章。
- 選錯代價：要求列印權時，靠臨時讀取的簽核人大多印不了（他們通常連讀取權都沒有），§10.1 等於沒做；不要求時，簽核人在待簽期間能把這一筆印成 PDF 帶走，範圍限這一筆、限待簽期間。
- 例子：`manager01` 不在任何進銷存群組，待簽一張採購單時，詳情頁出現「列印」→ 選「採購單」範本 → 預覽視窗有單頭、明細與金額；同意之後再開這筆，列印鈕消失、列印端點回 403。

**U8 轉交、改派、加簽、代理的對象能不能是發起人，跟「發起人自簽」政策走。**
- 推薦：政策 `approval.allowSelfApproval`（A12）關閉時（出廠值），發起人不能被轉交、改派、加簽，也不會成為代理人收到任務（400 或不代理）；政策打開時允許，與「發起人在關卡名單內時保留」同一個開關。
- 理由：§7.5、§7.6、§7.7 寫「不能是發起人」時 A12 還不存在；A12 就是公司決定要不要允許自簽的地方，同一件事只該有一個開關。
- 選錯代價：寫死「一律不行」時，打開 A12 的公司會發現關卡可以解析到發起人、卻不能轉交給他，規則前後不一；跟政策走時，打開 A12 的公司要知道轉交也受影響（手冊寫明）。
- 例子：出廠設定下，`ops01` 把 `buyer01` 送的單轉交給 `buyer01` → 400「不能交給發起人」。系統管理員在政策頁把「發起人自簽」對進銷存打開後，同一個動作成功，任務給 `buyer01`。

## Review Focus

測試沒有覆蓋、但最可能咬人的五個情境；每條的測試已加進負責的子段。

1. **轉交、代理、加簽交錯時，一人一票被打破。** 例：會簽關卡 `gm`、`buyer2`；`buyer2` 代理給 `gm`；`gm` 先同意自己的，再用代理身分處理 `buyer2` 的；或 `gm` 把任務轉交給 `buyer2` 的代理人。→ a3a `Transfer_ToHolderOfAnotherSeat_400_EvenIfOnlyDelegatedOriginal`、a3d `Delegate_DelegateAlreadyInStage_NotDelegated_LogsNote`、`Delegate_ApprovedAsOriginal_ThenActAsDelegateOnOtherSeat_409`。
2. **臨時讀取權沒有隨動作收回或沒有給到。** 轉交後舊負責人、改派後舊負責人、終止後所有人都要立刻失去讀取與列印；代理期間本人與代理人都要有。→ a3a `Transfer_OldAssigneeLosesReadAndAct`、a3b `Cancel_RevokesAllGrants`、a3d `Delegate_BothCanRead_BothLoseAfterApprove`、a3f `Print_AfterTransfer_OldAssignee403`。

## 計畫判斷（技術類，主控決定，可推翻）

- **J1 沒有 migration。** 需要的欄位 a2 都已建好（見「已在 main」）。代價：無。
- **J2 關卡位置由純函式 `ApprovalPath` 決定**（`Domain/Approvals/ApprovalPath.cs`）。把關卡實例依 `Seq` 走一遍，維護「目前有效的路徑」：同意或跳過的關卡實例放進路徑；遇到被退回的關卡實例，下一個新建的關卡實例就是退回目標的重來，把路徑截到目標之前（目標以 `StageCode` 對應；加簽關卡以「加簽人、加簽對象、方式」對應）。由它提供 `Previous(runs, current)`（退回上一關的目標：路徑上 current 之前最近一個已同意、不是跳過的關卡實例）與 `NextStageIndex(def, runs)`（路徑上最後一個定義關卡的下一個索引）。取代 `ApprovalActionRules.PreviousRun` 與 `ActivateNextAsync` 用「最後一個有 `StageCode` 的關卡實例」推位置的寫法。理由：加簽關卡不在定義裡、被退回後會重來，舊寫法在「退回到加簽關卡、再同意」時會跳過被退回的定義關卡；也不必加錨點欄位（不加 migration）。fg2 可以對同一個 `BranchKey` 的關卡實例呼叫同一個函式。代價：既有兩個呼叫點要換，靠回歸測試保住行為。
- **J3 加簽關卡用 `users` 來源解析。** 啟動加簽關卡時，以 `ApproverSource(users, AddSignUserIds)` 呼叫 `ApproverResolver.Resolve`（`onEmpty = fallback`、流程的備援），所以移除發起人（依 A12）、停用帳號改備援、人數技術上限全部照既有規則；解析出的席位 `Reason` 改成 `added`（備援席位保持 `fallback`）。
- **J4 加簽關卡數以歷程的 `add-sign` 筆數計。** 退回後重來的加簽關卡實例不再計一次。
- **J5 加簽是同意的一種。** 把 `ApproveTaskHandler.Handle` 的本體抽成 `ApprovalApprover.ApproveAsync(task, rowVersion, comment, values, AddSignPlan? plan, ct)`；`ApproveTaskHandler`、`AddSignTaskHandler` 都只是轉呼叫。加簽寫一筆 `add-sign` 歷程（不另寫 `approve`），`Targets` 是加簽對象、`DataJson` 帶 `{ mode }`。
