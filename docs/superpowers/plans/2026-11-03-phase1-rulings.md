# 第 1 階段實作裁決（R1–R31）

執行 [`2026-11-03-phase1-foundation.md`](2026-11-03-phase1-foundation.md) 時，對計畫原文的補充與修正。格式：裁決 — 理由 — 錯了的代價。與計畫衝突時以這裡為準。

- Ruling R1: 權限目錄實體類別命名 `DynamicProgram`（表名仍為 `Dynamic_Program`，屬性照計畫）— 避免與 WebAPI `Program` 撞名 — 錯了只是改類名。
- Ruling R2: FieldConfig 的 bool 屬性（Required、ReadOnly、ShowInList）不可為 null、預設 false；int?/JsonElement? 可為 null — 計畫內文自相矛盾，取可用的一側 — 錯了改型別即可。
- Ruling R3: `ModuleDetailResponse`、`BlockResponse(long Id, I18nText Label, int Sequence, bool Collapsed, List<FieldResponse> Fields)`、`FieldResponse`（照 T7 定義）、`OptionResponse(long Id, string Value /*opt_<id>*/, I18nText Label, string? Color, int Sequence, bool Active)` 移到 T6 定義，T7 沿用 — 消除順序依賴 — 錯了是 DTO 位置調整。
- Ruling R4: 可能 NotFound 的查詢（GetModule、GetModuleSchema、GetRecord、GetPagedRecords）回 `ServiceResult`（DTO 放 Data）；不會 NotFound 的清單查詢（GetModules、GetMenu）直接回 List — 盡量不包裝查詢結果、又能表達 404 — 錯了是 handler 回傳型別調整。
- Ruling R5: T1 Step 1 已完成（commit 3738b71 在 main，工作在 feature/phase1-foundation），T1 實作者從 Step 2 開始 — 錯了無代價。
- Ruling R6: TransactionBehavior 依賴 Application 層 ITransactionManager（BeginAsync→handle Commit/Rollback），EF 實作在 Task 3/6 — DbContext 尚未存在 — 錯了是換抽象介面。
- Ruling R7: HeaderCurrentUser 經 IKnownUsers 驗證，T2 先註冊含 5 個種子 id 的暫時實作，Task 3 換 DB 版 — 種子使用者在 T3 才建 — 錯了是改註冊。
- Ruling R8: FieldOption 補稽核欄位；DynamicProgram、AppUser 豁免（種子/目錄資料）— spec「每張表都有稽核欄位」vs brief 漏列，取 spec，目錄資料例外 — 錯了是加/移欄位。
- Ruling R9: I18nText JSON 為扁平 locale→文字物件 {"zh-TW":...}，非 {values:{...}} — API/前端與 spec §6.2 格式一致 — 錯了是改 converter。
- Ruling R10: datetime 一律轉固定 +08:00（台北無日光節約）、無時區位移的字串拒收；integer 接受 3.0 視為 3；text trim 後計字元數；Registry 另提供 CreateDefault() — brief 未明定的細節 — 錯了是改單一 handler。
- Ruling R11: IUnitOfWork 只有 CommitAsync（=SaveChangesAsync，同一交易內可多次呼叫），不提供 BeginTransactionAsync — 交易已由 TransactionBehavior＋ITransactionManager（R6）負責，兩套交易入口會打架 — 錯了是補一個方法。
- Ruling R12: 稽核戳記放 Domain `AuditableEntity.StampCreated(string userId, DateTime now)`／`StampModified(...)`，handler 用 ICurrentUser＋IBusinessTime 傳入；Module.TouchVersion 內部呼叫 StampModified — 與 TouchVersion 同層、Domain 不依賴 Application — 錯了是搬位置。
- Ruling R13: Update 的 TitleFieldId 非 null 時必須屬於該模組，否則 400 鍵 TitleFieldId 訊息「記錄標題欄位不存在」；Update/Activate/Deactivate/GetModule 找不到 Key → NotFound；Activate/Deactivate/Update 都呼叫 TouchVersion — brief 未定 — 錯了是改單一 handler。
- Ruling R14: T7 細節 — (a) FieldTypeRegistry 以 singleton `CreateDefault()` 註冊進 DI；DefaultValue 檢查的 FieldTypeContext：AddField 選項集合為空、UpdateField 用該欄位現有選項（Active/All/Sequence），PreviousValue＝原 DefaultValue，UserIds 取 AppUser 全部 id；(b) 錯誤鍵 `Config.MaxLength`「長度上限只適用文字欄位，文字欄位最多 4000」（非 text/textarea 有值、<1、text>4000 皆用此訊息）、`Config.Scale`「小數位數只適用數值欄位，範圍 0 到 6」、`Config.DefaultValue`＝handler 的錯誤訊息；(c) Reorder 鍵 `FieldIds`「欄位清單與區塊內欄位不一致」，清單須恰為區塊內全部欄位（含停用）且不重複；(d) UpdateField 換 BlockId 須同模組，否則 400 鍵 `BlockId`「區塊不屬於此模組」，移入時 Sequence 取目標區塊最大值加一；(e) Field/Option/Block Sequence 皆取同層最大值加一；找不到 ModuleKey/BlockId/FieldId/OptionId → NotFound；(f) 所有寫入用 R12 stamp，Field.Key 照 Task 6 作法先 insert 再 commit 再設 f_<Id> — brief 未定 — 錯了是改訊息或單一 handler。
- Ruling R15: UpdateModule 的非 null TitleFieldId 必須是本模組 Active 的 text 欄位，否則 400 鍵 TitleFieldId「記錄標題欄位必須是啟用中的文字欄位」（不屬本模組仍用 R13 訊息）；Active 模組不可把 TitleFieldId 設為 null，400 同鍵「啟用中的模組必須有記錄標題欄位」— brief「TitleFieldId 只能是 text」適用於所有寫入點 — 錯了是放寬驗證。
- Ruling R16: textarea MaxLength 只要求 >=1、POC 不設上限 — brief 未給上限、DB 欄位是 JSON 無長度限制 — 錯了是加一條上限檢查。
- Ruling R17: T9 細節 — (a) 所有記錄操作（含 GetRecord、GetPagedRecords、Delete）都要求模組 Active，否則 NotFound「模組不存在或未啟用」；記錄不存在／已刪除 → NotFound；GetRecord/GetPaged 回 ServiceResult（R4），分頁 Data 為 PagedResponse；(b) CurrentPage<=0→1、PagesSize<=0→10、>200→200（T2 deferred minor）；(c) RowVersion 在 handler 比對，Update 與 Delete 都檢查、都換新 GUID、都 StampModified；(d) 正規化後為 null 的值不寫進 ValuesJson（等同清除），停用欄位與已不存在欄位的舊值原樣保留；回應 Values 為 ValuesJson 全部內容；(e) FieldTypeContext 逐欄位組：選項取該欄位、PreviousValue=舊值、UserIds 用既有 ListUserIdsAsync；(f) Title 依字元截到 200；(g) Phase 1 後端不強制 Config.ReadOnly，RecordIndex 不在本階段 — brief 未定 — 錯了是改單一 handler。
- Ruling R18: T10 細節 — (a) Controller 用 body DTO 承接、路由參數併入 Request，除 schema 的 ETag 處理外只做 mediator.Send＋ToActionResult；(b) schema 一律回 `ETag` header（SchemaETag.For），If-None-Match 相符回 304 無 body；(c) JSON：camelCase、全域 JsonStringEnumConverter(CamelCase)（FieldType 保留自身 lowercase converter）、DefaultIgnoreCondition=WhenWritingNull；(d) body 形狀：PUT fields/{id}/status `{status}`、PUT blocks/{id}/field-order `{fieldIds}`、PUT records/{id} `{values,rowVersion}`、DELETE records/{id}?rowVersion=；(e) Phase 1 不擋未知或缺 X-User（落 anonymous），權限在後續階段；(f) Step 5 需實際啟動、curl 127.0.0.1:5180/swagger/v1/swagger.json 列出路由，貼輸出（一併結清 T1「5180 監聽」待驗）— brief 未定 — 錯了是改 controller 綁定。
- Ruling R19: 新增時套用的 DefaultValue 若正規化失敗（例如預設選項已被停用），視同沒有預設值、靜默略過，必填檢查照常 — 使用者沒填的欄位不該因設計端的變更而無法存檔；比在 T7 擋停用更不擋設計流程 — 錯了是改成在 UpdateOption 擋停用。
- Ruling R20: T11 細節 — (a) 不用互動式 scaffolding（bun create quasar 會停在提問），手寫 package.json／quasar.config.ts 等檔，dev/build 走 `@quasar/app-vite`（`bunx quasar dev`），vitest 另設 vitest.config.ts（@vitejs/plugin-vue＋jsdom）；(b) ApiError：400 取 body.errors、409/404 取 body.message（若有）、網路錯誤 status=0；(c) 選單區塊標題與「系統管理 > 動態模組設計」走 vue-i18n 四語系 JSON，模組名稱用 resolveI18n（目前語系，退回 zh-TW）；(d) .gitignore 已含 node_modules/、dist/、.quasar/，bun.lock 要提交 — brief 未定 — 錯了是改設定檔。
- Ruling R21: 成功但 Data 為 null 時回 200 空 body（ToActionResult 用 Ok()），不回 204 — 全域約束「成功 200」；前端不必特判 — 錯了是改回 NoContent。格式錯的 body 走 ValidationProblemDetails 400（同樣帶 traceId、errors）視為相容。
- Ruling R22: T12 細節 — (a) 錯誤訊息逐字照 task-5-brief.md 的表（含 {n} 代入）；text/textarea 先 trim、空字串視為 null；(b) identity store 的 users 是 id 字串陣列、無顯示名稱端點，user 的 format 顯示 id；user 欄位元件用 GenericSelect 列 users；(c) datetime 元件輸出 `yyyy-MM-ddTHH:mm:ss+08:00`，format 顯示 `yyyy-MM-dd HH:mm`；date/time 原樣顯示；integer/decimal 不加千分位、currency 千分位＋scale（預設 2）、percent 加 %；(d) multienum 選項標籤依 schema 選項順序以「、」串接，未知值顯示原值；(e) boolean 必填時 null 才算缺，false 合法 — brief 未定 — 錯了是改單一 registry 項。
